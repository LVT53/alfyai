## Owner add-on idea (2026-11-10): the model browses websites
Owner's words: "Another good feature would be if the model could traverse websites and click through them to find info instead of relying on the web_search constantly. This would be an extra feature but, very warranted." Status: noted only, not designed and not ranked; an extra beside file analysis and scheduled tasks. Checked the same day: `fetch_url` is Parallel Extract and its tool text says not to use it to find pages (search finds, fetch reads, `readPages` on `research_web` reads for the model). ADR-0068's per-turn check (`url-provenance/turn.ts`) already counts an address inside an earlier tool result, `fetch_url` and `research_web` included (up to 2,000 per result), as a source, so following a link found on a fetched page needs no new exemption; only an address the model writes itself is refused. Unconfirmed: whether the extractor's `full_content` keeps link URLs (`parallel-search/fetch-url.ts` strips nothing). Cost: a turn allows 20 tool steps (`DEFAULT_MAX_TOOL_STEPS`), a fetched page adds up to ~12k tokens re-sent on every later step, and Flash-Next gets no prefix-cache hits ([[alfyai-ai-todo-list-idea]]). Sketched for the owner: (1) numbered links on fetched pages, the model picks an id and the server resolves the address, so it never writes a URL; (2) a bounded server-side "explore this site for X" loop, run like an Atlas job; (3) a real headless browser with controlled egress, the heavy one, with the page prompt-injection risk the first two avoid. My lean: level 2 built on level 1, after file analysis or scheduled tasks. Asked the owner for a recent case where search kept missing something a few clicks deep. Related: [[alfyai-exfil-channels-fix]].

## Owner add-on idea (2026-11-15): restore, refine and in-paint with LTX IC-LoRAs
Owner's words, after video generation was proven: *"Could we also make it possible to ask AlfyAI to upscale or restore an attached video/image with LTX? … And also what about in-painting (editing)?"* Status: **noted only** — not designed, not ranked, and explicitly left out of the video build (`docs/plans/ltx-video/`) on 2026-11-15.

Three capabilities Lightricks ships as IC-LoRAs on the same 22B transformer, all compatible with the LTX-2.5 NVFP4 base we run:
- **Restore** — reference-conditioned clean-up/colourisation of damaged or low-bitrate footage; 960x544 windows of 97 frames, overlapping tiles fused every denoising step, long clips chained. https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Restore
- **Refine Details** — rebuilds texture, edges and grain on soft, compressed or upscaled footage; 1024x576 tiles fused every step. https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Refine-Details
- **In/Outpainting** — mask-conditioned fill or extension of a clip, two-stage and blended with the original; the 2.3 in-outpainting IC-LoRA, documented as 2.5-compatible. https://docs.ltx.io/open-source-model/feature-guides/editing-effects/in-outpainting

**Why it is plausible on this box:** they are tiled, so VRAM follows the tile rather than the frame — the 26.3 GiB ceiling that constrains generation does not block them. The cost is wall time: a community report has 97 frames at 768x1376→1216x2112 taking 206 s on a 32 GB card, so minutes per clip.

**What has to be true first (none of it is ours to clear alone):**
1. **Gated LoRAs.** Both answer 401 without an account that accepted the licence, and the one "mirror" found has zero downloads — not something to put on the box. The owner accepts on the model page, then a token reaches the box.
2. **Uploaded video.** "Restore an attached clip" needs an attachment path that accepts mp4 at all: intake validation, storage, Range serving, a player for attachments, and the vision rules for what a model may be sent of a clip. That is a slice on its own and comes before restore.
3. **LoRA on a quantised base.** The transformer is NVFP4, so an IC-LoRA applies through ComfyUI's quantised LoRA path. That needs measuring, not assuming.

**Two answers the owner should keep:** for a **still image**, LTX is the wrong tool — it is a video model, a still becomes a one-frame clip with nothing for its temporal conditioning to do, so an image upscaler or H3's own edit path is the right answer. For **picture in-painting we already have it** (H3's edit graph with marks, shipped); video in-painting is new, and its cost is a mask editor over time, not the model. Full reasoning: `docs/plans/ltx-video/implementation-plan.md`, "Beyond generation".
