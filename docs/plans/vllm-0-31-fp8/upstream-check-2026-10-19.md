# Upstream check: what vLLM 0.32.0 changes for our Flash-Next setup (2026-10-19)

Method: primary sources only (GitHub API, files read at tag `v0.32.0`, the v0.32.0 release notes, HF `config.json`). Nothing was booted; the only downloads were two small HF `config.json` files (no weights). "Inferred" marks anything I did not read directly.

**Summary.** None of the workarounds we carry on 0.31.0 became native in 0.32.0, and the reason is timing. v0.32.0 (tag `5df63a7203cdb9328d824a27b682e77c7b9928be`, release 2026-10-18) is the release branch cut from main at `fe341a53dda00472c281a2d1f4bd34a74e7eae6e` (2026-10-12 20:49Z) plus 16 cherry-picks, none of them Qwen4Exp or Engram work. Packed-NVFP4 PLE (#56273) merged to main on 2026-10-14, after the cut. Exact-size PLE pinning (#59848), NVFP4 KV on QSA (#54846), the RecoverSSM PRs (#58863, #59366) and recipes #1055 are all still open; the SM120 skinny-GEMM PR (#59869) was closed by its author. 0.32.0 does add Qwen4Exp speed work (merged QSA projections, fused QSA prepare), but every number in those PRs is from other GPUs. It also carries a new Qwen4Exp regression (#62383; fix #62409 still open; the trigger is a prompt past the native 262,144 window, which we do not serve). No flag we use was removed. My reading: nothing in 0.32.0 is shown to help our four goals on SM120 (no PR measures Qwen4Exp there) and it adds regression risk; the release to wait for contains #56273 and #59848, and even that only helps with a checkpoint whose PLE is stored as NVFP4 (ours is FP8).

## 3. Notes per item

### Item 1a. Packed-NVFP4 PLE (#56273)
- Merged 2026-10-14T00:24:55Z, merge commit `4e0681ed5654c1d8afb3c104d4381afd08529de8`. At v0.32.0, `vllm/models/qwen4_exp/common/ngram_embedding.py` has only `Qwen4ExpPLEUnquantizedEmbeddingMethod` (L252) and `Qwen4ExpPLEFp8EmbeddingMethod` (L288). A grep for `nvfp4|e2m1|fp4` over it, `nvidia/ngram_embedding.py`, `common/ple.py` and `nvidia/{model,mtp,ple_layer,qsa}.py` finds nothing.
- What the merged code supports (read at the merge commit): `Qwen4ExpPLENvFp4EmbeddingMethod` is chosen when `ple_embedding_dtype == "nvfp4"` (or a ModelOpt `quant_algo == "NVFP4"` mapping). Layout: `weight` as uint8 packed E2M1 (`[rows, dim/2]`), `weight_scale` as E4M3 per 16 values (`[rows, dim/16]`), both stored per shard (loader error: "NVFP4 PLE tables must be stored as {shard_prefix}<i>.weight and {shard_prefix}<i>.weight_scale shards"), plus one global FP32 scale, parameter `weight_scale_2`. Dim must divide by 16; dtype mismatches raise instead of casting. Rows stay packed and are decoded per lookup; block scales are pinned too when offloaded.
- Footprint, PR text only: packed table 26.822 GiB vs 47.684 GiB for the FP8 table; tested with pinned-host PLE on an RTX PRO 6000 Blackwell Max-Q (SM120) and with the table resident on GB10. No pinned-RSS figure is given. Our FP8 table is the same size (128 shards of `[2,500,012, 160]` bytes = 47.68 GiB; my arithmetic from the 2026-10-04 tensor headers).

### Item 1b. Pinned size and Engram options
- At the tag, `Qwen4ExpPLEPinnedHostEmbedding.allocate_embedding_weight` is `torch.empty(..., device="cpu", pin_memory=True)` (`common/ngram_embedding.py` L461-467). #59848 says this rounds up to a power of two: "47.7 GiB per-rank table: 65.2 -> 47.8 GiB host memory (GB10)". That matches our 64-66 GiB for a 47.68 GiB table.
- #59848: open since 2026-10-03, `mergeable_state: blocked`, mergify conflict notices on 10-08, 10-12, 10-14 and 10-18, six reviewers requested, only a bot comment. Its fix is anonymous mmap plus `cudaHostRegister`, and it says the packed NVFP4 tables "also go through this path". [#60909](https://github.com/vllm-project/vllm/pull/60909) (generic `empty_pinned()`) is open and leaves this table out on purpose. If both land, a 26.8 GiB packed table would pin about 27 GiB instead of rounding to 32 GiB (inferred from the rounding rule).
- `vllm/config/engram.py` at the tag: `cpu_offload: bool = True`, `embedding_across_dp: bool = False`, `dp_shared_memory: bool | None = None`, `use_thp: bool = False`. Same four fields as 0.31.0; the diff is an import move and #59171 dropping the CUDA-alike platform check. `dp_shared_memory` raises unless `data_parallel_size > 1`. `use_thp` is read only by DeepSeek-V4.1 code (code search on main: `vllm/models/deepseek_v41/...`, nothing under `qwen4_exp`; inferred not used by Qwen4Exp). So there is still no reclaimable or smaller PLE mode. Open, not for us: [#62238](https://github.com/vllm-project/vllm/pull/62238) (DSv4.1 Engram disk offload), [#60390](https://github.com/vllm-project/vllm/pull/60390) (share PLE table across DP replicas).
- Corrections to the brief: #54765 and #55515 are issues, not PRs. #55334 was closed unmerged on 2026-10-02; the FP8-PLE-under-ModelOpt path we already run is [#54882](https://github.com/vllm-project/vllm/pull/54882) (merged 2026-09-03, in 0.31.0 and 0.32.0). #54765 itself is still open. #59868 closed 2026-10-06, fixed by [#60142](https://github.com/vllm-project/vllm/pull/60142) (in 0.32.0; an Ampere compile problem, irrelevant to SM120). #55515 closed 2026-10-15 (PP=1 requirement; we run PP=1).

### Item 2. KV capacity
- #54846 is open with label `needs-rebase`, `mergeable_state: dirty`, last update 2026-10-07, one bot review and no human review. A comment there (2026-10-07) says the e4m3 half landed via #55557, so a rebase is "mostly the nvfp4 path". At the tag, `vllm/models/qwen4_exp/nvidia/qsa.py` L154-159 lists `["auto", "bfloat16", "fp8", "fp8_e4m3"]`. The release-note line "NVFP4 KV cache now runs on SM8x and SM12x (#46963)" is the generic path, not this backend (inferred from that list). Open warning for later: [#61225](https://github.com/vllm-project/vllm/issues/61225) (NVFP4 KV silently corrupt under token-major layout).
- `Qwen4ExpQSABackend.supports_kv_connector()` still returns `False` (`nvidia/qsa.py` L205-206). But upstream exercises the OffloadingConnector on this model: recipes main has `kv_offload_support: offloading_cpu/offloading_fs: verified` ([recipes#987](https://github.com/vllm-project/recipes/pull/987), 4x H200 TP4 eager, FP8 checkpoint) and [#57145](https://github.com/vllm-project/vllm/pull/57145) (in 0.31.0 and 0.32.0) reports 3/3 CPU and filesystem reloads. [#60861](https://github.com/vllm-project/vllm/pull/60861) (open) documents that in `align` mode a request resumed from a connector-delivered prefix hit reads an unwritten PLE conv-state block (NaN or silently wrong); local prefix hits are unaffected per the PR. So the brief's "rejected" does not match what I can read: the flag says no, upstream runs it, and it has a known correctness bug. Whether our launch would accept offloading flags is `unknown`; do not use them.
- Pool-size changes in range: none measured. [#61048](https://github.com/vllm-project/vllm/pull/61048) (shared KV group for the replicated PLE state; computed 1.7-5.6% pool at TP8) was closed unmerged 2026-10-11; [#60967](https://github.com/vllm-project/vllm/pull/60967) (open) targets GLM KDA groups. [#57516](https://github.com/vllm-project/vllm/pull/57516) (in 0.32.0) runs `gc.collect()` and `empty_cache()` after weight load, which may shift profiled free memory slightly; no figure given. [#57298](https://github.com/vllm-project/vllm/pull/57298) applies only to `--load-format ipc_cache`.

### Item 3. MTP
- #55357: open, last activity 2026-09-05. Reported on 2x SM120 TP=2, bf16 KV, nightly `73029d4`, in-checkpoint MTP K=3. The mechanism the thread found (when 2+ prompts prefill in one step with MTP configured, the PLE short-conv kernels read a strided Mamba block table and corrupt state) was fixed by #55375 (merged 2026-09-05, `28e605fb3`), which is in both 0.31.0 and 0.32.0. Whether it explains the hours-long episodes in the original report is not established.
- #58863 (open, needs-rebase, dirty) adds `--use-replayssm` for Qwen4Exp GDN (forces the Triton GDN kernel); #59366 (open, blocked, stacked on it) re-fuses it in the CUDA MTP kernel. Neither is in 0.32.0. Also open: [#52244](https://github.com/vllm-project/vllm/pull/52244), [#61309](https://github.com/vllm-project/vllm/pull/61309), [#61017](https://github.com/vllm-project/vllm/pull/61017).
- In 0.32.0 and related (fixes, no measured effect on #55357): #59536 (GDN prefill checkpoint metadata), #59759 (stale Mamba spec blocks), #60210 (MRV2 Mamba align state copies), #59359 (MRV2 MTP sampling-mask replay), #57053 (dynamic K), #59997 (NIXL P/D PLE page; closes #59642, which is P/D only).
- Quantized head: `Qwen4ExpMTP` takes its quant config from `get_draft_quant_config(vllm_config)` (`nvidia/mtp.py` L135); the file differs from 0.31.0 only by sequence-parallel and config-import edits. `SpeculativeConfig` field declarations are identical between tags. The checkpoint's own head is BF16, so the external NVFP4 drafter via `--speculative-config '{"method":"mtp","model":"<dir>"}'` is still the only quantized route. Official recipe main uses the in-checkpoint head with K=3; unmerged recipes#1055 uses an external drafter with K=2 and says the BF16 head "also runs, with a ~37% smaller KV pool on a 96 GB card" (PR author's claim, not verified by me).

### Item 4. SM120 performance
- #59869 was closed by its author on 2026-10-05: "in the overall e2e it is 0.64%, so less than noise" (LM head alone +4.9%). At the tag, `QWEN4_EXP_GEMM_PLANS_BY_CAPABILITY` (`nvidia/low_latency_gemm.py` L294-300) has keys `(10, 3)`, `(10, 0)`, `(9, 0)`, `(12, 1)` only, so SM120 has no skinny-GEMM plans and falls back to the standard linear path (inferred from `.get(capability, {})`).

SM121-only: #59753, #59632, #60027; SM100-only: #59214; H200: #60776.

## 5. Item 7: new known issues (single-GPU SM120, NVFP4 + FP8 KV + MTP)

- [#62383](https://github.com/vllm-project/vllm/issues/62383), open, 2026-10-19: regression from 0.31.1 to 0.32.0. A prefill crossing the native 262,144 tokens with MTP and CUDA graphs kills the engine (illegal memory access); either factor off avoids it. A second user reproduced it on SM120 RTX PRO 6000, TP=1, `nvidia/Qwen3.8-Flash-Next-NVFP4`, YaRN 2.0 to 524,288 (260,067 tokens fine, 280,069 crash). Cause per [#62409](https://github.com/vllm-project/vllm/pull/62409) (open, not merged; the reporter verified it on H200): #59853 shrank the M-RoPE cache, and with YaRN the served positions pass `original_max_position_embeddings`. The PR says the fix is bit-identical for native-window serving, so `--max-model-len 262144` without YaRN should not hit it (inferred; needs the long-prompt boot test).
- [#60489](https://github.com/vllm-project/vllm/issues/60489) / fix [#60490](https://github.com/vllm-project/vllm/pull/60490), both open: the QSA indexer prefill workspace (512 MiB, the `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` default) is invisible to the memory profiler, so the first long prefill can OOM at high `--gpu-memory-utilization`. Reported on 24 GB cards; present on main. We had 2,312 MiB free after the 0.31.0 burst test, which is our margin at 0.94.
- [#62308](https://github.com/vllm-project/vllm/issues/62308) / fix [#62318](https://github.com/vllm-project/vllm/pull/62318), open: since #59533, checkpoints with quantized q/k/v and an unquantized QSA indexer fail to load ("different quantization schemes for the shards of ... qkv_proj"); reported for a compressed-tensors W4A16 checkpoint. Ours keeps attention in BF16 (2026-10-04 notes), so likely unaffected (inferred).
- [#60861](https://github.com/vllm-project/vllm/pull/60861), open: align-mode PLE conv-state bug for connector-delivered prefix hits (KV offload, P/D). Not hit by local prefix caching, per the PR.
- [#62535](https://github.com/vllm-project/vllm/pull/62535), open, 2026-10-19: under MRV2 with `cudagraph_mode=FULL`, a batch containing prefill tokens can be padded into a decode-shaped FULL graph. Found on DeepSeek-V4.1 DSpark (8x RTX PRO 6000, both v0.32.0 and nightly); the PR says it applies to any model where this dispatch happens. No Qwen4Exp report.
