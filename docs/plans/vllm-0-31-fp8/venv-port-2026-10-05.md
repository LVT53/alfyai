## How the venv was built (to reproduce or upgrade)

The venv replicates the validated Docker image: every non-NVIDIA package was pinned to the version in the image's
`pip freeze` (`/root/v031-migration/docker-v031-freeze.txt`), with the `nvidia-*` pins dropped because torch pins its
own (the image had upgraded NCCL past torch's pin; only `nvidia-nccl-cu13` differs, 2.29.7 vs 2.30.7, unused at TP=1).

```bash
uv venv /home/alfyws/venvs/vllm-0.31 --python 3.12
uv pip install --python /home/alfyws/venvs/vllm-0.31/bin/python \
  "vllm==0.31.0" "flashinfer-cubin==0.7.0.post1" "flashinfer-jit-cache==0.7.0.post1+cu130" \
  -c /home/alfyws/v031-venv-constraints.txt \
  --torch-backend=cu130 --index-strategy unsafe-best-match \
  --extra-index-url https://flashinfer.ai/whl/cu130 --extra-index-url https://flashinfer.ai/whl
```

Gotcha: `flashinfer-cubin` 0.7.x is **not on PyPI**, only on `https://flashinfer.ai/whl`; `flashinfer-jit-cache` (prebuilt
kernels, so no nvcc JIT at runtime) is on `https://flashinfer.ai/whl/cu130`. `import vllm._C` no longer exists in
0.31 (the compiled ops are `_C_stable_libtorch` etc.); check `torch.ops._C` instead.

## Other changes made in the same session

- `tei-rerank` capped at 12 GB and `tei-embed` at 4 GB with the memory limit equal to the memory+swap limit (no swapping).
  **Gotcha found the hard way:** with Docker's systemd cgroup driver the container-level swap limit (`docker update` or
  `memswap_limit`) is written straight into the cgroup file, and systemd silently resets it to unlimited the next time it
  re-realizes the scope (starting or stopping any unrelated unit did it). The durable fix is a slice that carries the
  property: `/etc/systemd/system/alfyai-tei.slice` (`MemoryMax=16G`, `MemorySwapMax=0`) and `cgroup_parent: alfyai-tei.slice`
  plus `mem_limit`/`memswap_limit` (4g / 12g) on both services in `/home/alfyws/opt/alfyai/docker-compose.yml`
  (backups `docker-compose.yml.bak-pre-tei-cap-20261005` and `...bak-pre-tei-slice-20261005`). Verified: the slice's
  `memory.swap.max` stays 0 across an unrelated service start/stop and a `daemon-reload`; both containers recreated
  (about 30 s blip each time), healthy, embed and rerank answer correctly, nothing of theirs in swap. The slice nests as
  `alfyai.slice/alfyai-tei.slice` in the cgroup tree (a dash in a slice name means hierarchy).
