## Chosen interface: deepen the existing finalize event/helper

Extend the existing `NormalChatMessageListEvent` `type: "finalize"` variant with `canonicalMessage?: ChatMessage`, and extend the existing `finalizeStreamingMessageList` params with that same optional input. The page's existing finalize adapter forwards it in its existing store update. Do not add another adapter method, store, wrapper module or page reconciliation loop. The canonical branch takes precedence for assistant-row data; metadata may still carry the separately validated user-ID receipt. Ordinary terminal-stream finalization without `canonicalMessage` retains its current metadata semantics and transport unchanged.

In `settleObservation`, after existing ownership checks and exact-row validation, pass the verified full saved row as `canonicalMessage`. Do not convert it into `StreamMetadata`, enumerate durable fields in the runtime, or hydrate by applying a saved output view followed by a partial metadata reconstruction. Canonical adoption is one message-list update, so thinking, anchors and output cannot momentarily describe different snapshots. Existing output/finalize fallback remains for genuinely unavailable or unsaved/finalization-failed evidence; it must not become the successful canonical path. Do not add a second fetch: use the row from the existing bounded `readChatMessages` call, not a whole-conversation store replacement/reload.

The finalizer constructs the assistant result from the saved row as its base, then adds only these explicit client lifecycle/presentation overrides:

- Preserve the held row's `renderKey` (`held.renderKey ?? held.id`), so persisted-ID adoption does not remount MessageBubble/ThinkingBlock. Ignore any saved render key. Unrelated rows retain their order and object identity; replace exactly the owned target, never append a duplicate or choose the last assistant.
- Set `isStreaming: false`, `isThinkingStreaming: false`, `runtimePhase: undefined`, and clear transient `responseActivity`. These are lifecycle facts, not inferred completion outcomes.
- Evidence polling remains the existing targeted owner. On canonical adoption use `evidencePending: !canonicalMessage.evidenceSummary` while the existing targeted evidence poll is requested; its existing completion/timeout owner clears that affordance. Do not retain an old row's evidence or present a permanent pending state. Keep the existing evidence and cost refresh calls for this assistant only, after current-owner checks; no new accounting calculation or wait.

Do not spread the held row under the saved row: absent optional saved properties would leave stale client data. Do not preserve live `normalChatOutputView`, native text, thinking segments, tool status or intent as ephemeral UI state. Start from the saved row (including its saved `thinkingSegments`, which the current read projection supplies), so native/tool/thought-step/attachment display, warnings, intent, model/provider, usage/cost, follow-ups, evidence, continuation links and future durable fields have the same authority as reload. An absent saved field clears an older value. Unknown usage/cost remains unknown, never zero. Saved failure markers remain failures. Derive structural output through the existing `normalChatOutputView(saved)` contract, never an old live view shadowing saved output. Preserve a validated observation's explicit finalization-failure overlay when it is newer than the row; it may only reduce success, never promote it. Do not synthesize structural completion from local Stop or EOF.

Disclosure/selection state already belongs inside keyed components, not to a second row-state object. Preserve component identity; do not write their expansion, selected-anchor or full-reasoning preferences. Canonical adoption for the same completion key must not revoke a fresh terminal disclosure the reader already made, or opt them into raw reasoning. A genuinely changed turn/segment/outcome still revokes ordinary retained disclosure under the existing eligibility-key guard. A rail expanded while live still requires close/reopen after terminal eligibility. Preserve the paused segment's disclosure while another segment resumes. Do not carry stale selected anchor text across a changed trace: existing anchor resolution must use canonical thinking, and unresolved anchors stay hidden.

### Alternatives and deletion test

1. **Selected: extend finalize/helper.** A single optional canonical fact gives both observation modes authoritative row adoption while keeping the existing terminal metadata path. Identity/lifecycle validation stays in runtime; row replacement stays in one existing helper.
2. **New `reconcileCanonicalMessage` event/wrapper.** Rejected for this slice: it duplicates finalization routing, user receipt handling and lifecycle cleanup. Deleting a pass-through wrapper would remove only indirection, with no behavior lost. Reconsider only with a concrete caller need the existing event cannot express, declared before edits.
3. **Add `saved.thoughtSteps`, then more metadata copies.** Rejected: every new durable field would again need edits across runtime and helper; omission and absence/fallback bugs recur. Deleting the chosen canonical branch would force each observation caller to reconstruct the durable row recipe. That complexity belongs in the existing finalizer, not in callers.

## Exact identity, lifecycle and failure contract

- Validate observation stream ID and conversation ID against captured originating/reconnect params. Check saved assistant ID equals the observation receipt and role is assistant; never content-match or infer identity from a neighboring/latest row. The read adapter is scoped to the captured chat; `ChatMessage` itself has no conversation-ID field. Recheck captured chat after its await.
- Validate saved structural turn ID, segment ID, projected completion and finalization consistency against the terminal observation and any already known target identity. Apply this protection to normal observation as well as Stop (current saved-completion comparison is Stop-only). For structural observations, missing/conflicting row structure is unavailable, not permission to adopt an arbitrary same-ID row. Finalization failures are validated through existing parse/project helpers so raw model outcome and failed durable outcome are not confused. No new independent completion evaluator.
- Check epoch, non-detached lifecycle, current chat, exact target still present, and active placeholder/Stop handoff ownership after every await and immediately before mutation and subsequent effects. If hydration already renamed the target, resolve its current ID through the retained render key exactly as Stop does now. Target lookup and write must agree. A new turn, retry/resume/reconnect, reset/detach/dispose, chat switch, removed target or conflicting replacement invalidates old settlement. Ignore late observer/read callbacks and do not affect new errors, costs, drafts, questions, queue or commands.
- Preserve that same held render key through canonical adoption itself: `stopSettlement.owns()` and `targetId()` must still find the row after its ID changes, so post-adoption `onSettled`, evidence/cost refresh and command-permit checks remain valid. Test those actual post-adoption effects, not just the pre-write guard. Reapplying an identical snapshot is semantically idempotent: no duplicate assistant, new observer/Stop, queue action, component remount or unnecessary disclosure reset.
- Preserve original Stop receipt capture, one upstream Stop, read-only observer behavior, existing ten-second/five-request bounds and cancellation. Stop still releases composer and restores queue immediately; canonical hydration never revives active state, drains a queue or completes a newer turn. Normal observation keeps its existing legitimate queue/question behavior; do not accidentally impose Stop mode on it.
- Missing/unreadable/mismatched saved rows retain partial output and explicit unavailable/missing-finish warnings. Unsaved terminal and known finalization failure use existing honest fallback, without claiming persistence or a successful canonical adoption. Existing command permits must still validate exact authoritative assistant identity; no placeholder retry or stale navigation becomes admissible.
- Paused/resumed rows retain canonical `continuesMessageId` and exact segment ownership. Do not overwrite an asking segment with its continuation. Existing reply folding, per-segment Info, whole-reply answer-only Copy/Open as document and Sources placement stay correct. Ordinary activity must never enter answer/Copy/export, even if it resembles an answer.
