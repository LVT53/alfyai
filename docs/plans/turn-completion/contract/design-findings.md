# Normal Chat completion: bounded architecture findings

Investigated read-only at `24823203b` (includes `40f2d74fc`), 2026-11-10. Recommendations for the controller/judge, not an implementation or a verified patch. Read root, services, chat-turn, vision and URL-provenance AGENTS. No client interim-UI investigation, product edits, checks/build/gates, commits, remote operations or subagents. Consulted the new contract spec/plan at the end to align terminology.

## Judge summary

The contract is feasible, but a response-message-only capture is insufficient. Preserve **the complete prepared system + original outbound messages**, including inline prefetched evidence and images, plus **actual SDK response messages**, actual completed tool outputs not yet covered by a finished step, and provenance/privacy labels for every destination-sensitive part. Carry this canonical state into recovery; never invoke `runPlainNormalChatSendModel` to recover a prepared turn. That entry point prepares context and creates tools again.

Use one opt-in Normal Chat working/closing controller inside `normal-chat-model/`; a shared completion reducer inside `chat-turn/`; versioned private continuation persistence for pause and recoverable interrupted turns; and a content-free durable outcome record independent of assistant-message existence. Do not apply Normal Chat closing automatically to generic tool-free callers such as control models or artifact generators.

Three concrete judge conditions:

1. Full context MUST include prefetch embedded inside `prepared.inputValue`/guidance, not just `prepared.prefetchedToolMessages`. Existing ask capture does not contain this material.
2. Full-state capture MUST precede provider-specific gating/flattening; every destination projects from the canonical original again. Gating only native captured tool results does not protect private data embedded in the original prepared prompt or transient photo labels.
3. Plain failover MUST stop restarting `params.messages` with executable tools once any tool execution started. Step callbacks alone cannot prove safety after an interrupted tool step.

## Observed seams and gaps

- `normal-chat-model/index.ts:91,143,159`: stagnation, ask pause and step limit end the tool loop. They do not guarantee a tool-free answer step. Stop conditions cannot force another step after SDK termination; an explicit closing invocation is needed for reasoning-only, length, abrupt-end and similar exits as well.
- `index.ts:1255–1355`: plain failover rebuilds each attempt from `params.messages`, retains `params.tools`, and continues on retryable error. `runPlainNormalChatModelRunAttempt` at 1380 logs steps but exposes neither response messages nor completed progress to this loop. A later provider failure can therefore rerun completed tools. The unsupported-tools downgrade at roughly 1450 also restarts the request; constrain it to proven pre-execution rejection.
- `index.ts:1516`: stream failover stops after any text/reasoning/tool event, which limits replays but also blocks useful continuation after work. Failover must distinguish a safe fresh attempt from a continuation, rather than just remove this boundary.
- `index.ts:1716`: streaming `onStepFinish` forwards cumulative `response.messages`. Those are actual assistant/tool response messages, not the original input or per-step injected user/image messages. Plain result at 1490 exposes only text, finish reason, usage and model metadata. It also maps `result.usage` (last step), while stream finish maps all-step usage.
- `chat-turn/streaming-normal-chat-model-run.ts:128`: constructs full `outboundMessages`, but returns only completion metadata, `continuationGiven` (prefetched native messages + earlier resume), and a last-finished-step response getter. The full prepared system/history/current user packet is lost to consumers. It flattens resumes once using the primary provider before model-run failover; its own comment documents that later cloud failover is not gated again.
- `plain-normal-chat-model-run.ts:94,144`: same context preparation/tool creation and outbound construction, separately. There is no shared prepared-run handle.
- `stream-fallback.ts:357`: two plain reruns with fresh preparation; synthesizes native history messages from `ToolCallEntry` digests and a compact system appendix. It does not use real response messages. Attempt 1 may force `produce_file` for a file request; attempt 2 does not incorporate real messages/results generated by attempt 1. Recovery therefore may reread prefetch, lose original instructions/evidence/reasoning, or repeat production.
- `ask-capture.ts:51`: v1 capture preserves real response messages and result-gating rows, but only after the original current-user packet. `ask-resume.ts:301` reconstructs stored choices and original turn; orchestrator uses `skipWebPrefetch` and a history cutoff. Inline evidence that originally rode inside the prepared input is neither captured nor refetched, so it disappears. History, instructions, memory, catalogue and clock are rebuilt rather than resumed exactly.
- `vision/step-images.ts`: queue entries are drained into one step's `prepareStep` output. They are not SDK response messages. Local-only flags/nameless labels exist on queue entries, not ordinary `ModelMessage` image parts. Capturing only SDK responses loses these observations; blindly persisting injected user messages loses the original locality annotations.
- `stream-terminal.ts:116`: stop then pause then answer/delivery then completed-tool repair. Reasoning-only/empty terminal runs without completed tools fail directly. Other error/catch paths use different gates. `stream-orchestrator.ts:1675–1795` can finalize partial visible text on errors without entering closing or consistently marking incomplete.
- `stream.ts:~875`: existing final-answer facts distinguish text after the latest non-delivering call and successful delivery; use their policy, not `text.trim()`. The orchestrator also treats *any terminal file call*, failed included, as a completed-file exemption. The broader spec deliberately needs successful delivery, so this legacy exception must be removed or narrowed explicitly.
- `send/+server.ts:~545–670`: normal send normalizes/citation-checks and finalizes directly; no shared completion record/closing decision. Only evidence-ready calls are passed onward, dropping failed-call completion facts. Special file intake is a separate route branch; preserve that boundary deliberately.
- `stream-completion.ts:~298,933`: builds private `TurnCompletionRecord` only for saved stream segments and logs at receipt. `stream-terminal.failStream` closes without durable completion telemetry. Finalization failure logs and emits backend failure (`stream-completion.ts:~982`), also without a durable record. Send errors similarly go through the route catch.
- `finalize.ts:577`: shared persistence owner already exists; stream writes messages best-effort, validates identities before receipt, then schedules projection/analytics. Send projection is eager. It may partially persist a user or assistant before later failure: model outcome and save outcome must be separate facts.
- `retry.ts:101,~252`: current explicit retry deletes old assistant/trailing messages and invokes `cleanupFailedTurn` before a new run. It is regeneration, not continuation. Do not let automatic recovery traverse it; it can delete evidence/jobs/question state a continuation needs.

## Recommended contracts and ownership

Signatures below are proposed, not existing exports. Keep runtime closures, credentials and ToolSets out of serialized types.

```ts
// normal-chat-model/continuation.ts: canonical model-level state
interface NormalChatContinuationV2 {
  v: 2;
  rootTurnId: string;
  segmentId: string;
  system: string;
  originalMessages: ModelMessage[]; // fully prepared original input, unflattened
  responseMessages: ModelMessage[]; // cumulative real responses, not UI rows
  // Ordered inserts omitted from SDK response.messages (e.g. step images).
  stepInputs: StepInputObservation[];
  results: CapturedResultProvenance[]; // stable occurrence identities + gate data
  executions: ToolExecutionCheckpoint[];
  attempts: ModelAttemptFacts[];
  budget: RemainingTurnBudget;
}

// chat-turn/shared-normal-chat-model-run-helpers.ts
async function prepareNormalChatTurnRun(
  params: NormalChatSendModelBaseParams,
): Promise<PreparedNormalChatTurnRun>;
interface PreparedNormalChatTurnRun {
  snapshot(): NormalChatContinuationV2;
  // Private process-only runtime, recorder, tools and stop controller.
  // Same object used by plain/stream; never serialized wholesale.
}

// normal-chat-model: one policy engine, two transport consumers
function runNormalChatCompletion(input: {
  run: PreparedNormalChatTurnRun;
  transport: 'stream' | 'plain';
  mode: 'new' | 'continue';
  stopSignal: AbortSignal;
}): AsyncIterable<NormalChatRunEvent>;

function projectContinuationForAttempt(input: {
  snapshot: NormalChatContinuationV2;
  provider: NormalChatModelRunProvider;
  phase: 'working' | 'closing';
  privacy: CurrentDestinationPolicy;
}): AttemptInput; // system, messages, budget, provider options

// chat-turn/completion.ts: pure reducer shared by stream/send
function decideTurnCompletion(facts: TurnCompletionFacts):
  | { kind: 'stopped' }
  | { kind: 'paused'; questionId: string }
  | { kind: 'answered'; via: 'text' | 'delivery' }
  | { kind: 'close'; reason: ClosingReason }
  | { kind: 'incomplete'; reason: IncompleteReason }
  | { kind: 'failed'; reason: FailureReason };
```

`PreparedNormalChatTurnRun` can instead live wholly at chat-turn with a model-only invocation handle passed down; avoid having model runtime import chat-turn implementation. Shared serializable event/checkpoint types must have one owner and no credential fields. A snapshot needs detached/frozen values, not aliases to SDK arrays or mutable tool entries.

### Capture details that make these seams sufficient

Build canonical original messages once, before flattening, from prepared history + `buildCurrentUserMessage(appendTurnGuidance(...), pictures)` + native prefetch + prior continuation. Capture `system` too. That preserves inline prefetch automatically; additionally retain prefetched `ToolCallEntry`/source provenance for citations even when no native prefetch messages exist.

For each attempt, scope response snapshots by attempt ID. SDK step messages are cumulative within an invocation: **replace that invocation's response portion**, do not append it on every callback. Append a new invocation's response suffix once. Occurrence keys need `(attemptId, step/sequence, toolCallId, toolName)`, since providers reuse call IDs and `buildAskResumeCapture` currently maps current-run records by ID/name without occurrence distinction.

Capture finished-step messages in plain AND streaming callbacks. Also extend the execution envelope/recorder contract to report started/settled execution and the exact **capped/compacted model payload actually returned**, including error outputs. The current recorder stores digest rows and `observeResult` sees only successful payloads for URL provenance. Add a separate checkpoint observer; do not broaden failed-result URL provenance by reusing `observeResult`. This observer closes the hole where a tool finishes but transport dies before `onStepFinish`. Reconcile envelope observations against SDK results by occurrence and never duplicate a result. SDK messages remain authoritative; where step completion is absent, record a clearly marked recovered call/result from observed real input/output, never fabricate success.

Capture queued step-input observations with their privacy flags and position before queue drain. Decide a bounded replay policy for prior transient images explicitly: preserving every image indefinitely changes the existing one-step pixel lifetime. At minimum preserve observations needed by closing and label them for provider gates; do not reconstruct remote URLs or refetch thumbnails. Persist prepared pixels only under an explicitly approved bounded retention policy; never serialize Buffer/Uint8Array/URL as ordinary JSON without a codec/validation and size limit.

### Closing and failover algorithm

1. Maintain a root-turn stop controller separate from each provider timeout. Await/quiesce the failed attempt's tool executions first. Stop wins, then a confirmed captured ask pause, then successful delivery or a clean completed answer. Do not run closing on explicit stop, deleted chat, unresolved ask, content-filter refusal, authorization/attachment failure or unsafe in-flight uncertainty.
2. For a usable unfinished state (step cap, stagnation, reasoning-only, length with missing/incomplete answer, clean premature tool end, recoverable no-finish/error), atomically reserve **one closing phase per automatic recovery chain** before awaiting anything. Its instruction is English, retains the existing reply-language rule, uses all available completed subanswers/evidence, reports limitations honestly, and asks for no more tools. It must not ask the model to invent missing evidence.
3. Closing invocation: `generateText` or `streamText` directly over projected canonical context + captured response suffix; **omit `tools`, `toolChoice`, `firstStepToolChoice`, tool repair and every executable ToolSet**. No fresh preparation or tool pack. A retained historical tool-call/result is data, never an instruction to execute it. Unexpected generated tool calls make closing invalid; do not expose hidden executable callbacks as a fallback.
4. Give closing a finite output reserve and deadline within a documented total-turn budget; suggested starting policy is one invocation with maxRetries 0, deadline <=30s and output cap <=4096, further clamped to provider limits and remaining context. These numbers are recommendations requiring real-model sizing, not measured guarantees. Reserve room for visible output on reasoning models; a small cap can be consumed entirely by reasoning. Resolve thinking/provider options for closing per provider, using existing option builders. Preserve real previous reasoning; do not synthesize empty reasoning fields.
5. Stop conditions do not bound an external closing call by themselves. A shared latch, deadline, output limit and provider-attempt budget do. The cleanest strict policy allows closing on one selected destination; pre-request provider selection can choose a fallback, but an empty/failed closing does not start a second answer generation. If the spec permits pre-output transport retry/failover inside closing, charge it to the same hard call/deadline budget and prohibit retries after any answer delta. State this choice explicitly; the current two fallback attempts plus two provider fallbacks would otherwise multiply.
6. Terminal working-phase events are internal facts until closing resolves; SSE gets one terminal receipt, not an early finish followed by more generation. A closing length/error/empty/no-finish remains incomplete/failed, even if some text arrived. Keep original working finish/steps and closing facts separately. A finish reason `stop` alone is not proof of visible completion.
7. Fix plain fallback at its owner (`index.ts:1255`): fresh restart with tools is permitted only if no tool began and no continuation was produced. After execution, continue captured state with no executable tools; never just `continue` the existing loop with original params. Apply the same rule to unsupported-tools downgrade and streaming fallback. No completed execution reruns on any automatic path.

A resumed ask may need **new** tools to finish the request. Preserve the original execution ledger and wrap enabled tools so an identical completed invocation returns its stored real result without executing again; retain call/result identity separately for the new model request. Fingerprints need canonical validated arguments and operation scope, not call ID alone. For writes, use existing durable job/pending-write identities. Semantically equivalent but differently phrased calls cannot be generically deduplicated perfectly; fail closed on ambiguous repeated side effects, do not promise semantic exactly-once from argument hashes. Closing has no such ambiguity because it has no executable tools.

### Provider gates, context budgets and privacy

`messagesForAttempt` currently strips images then optionally gates captured connector outputs. Generalize it into the projection seam above: canonical selection -> destination privacy/vision gating -> provider compatibility/flattening -> provider-specific context/output budgeting -> provider options/cache key. Never flatten once on primary or reuse a previously cloud-gated snapshot as canonical.

Full evidence is broader than native tool results. Inventory and label private proactive connector blocks in system/input text, inline prefetch evidence, assistant text/reasoning that can quote local evidence, photo labels and prepared pixels. Existing `gateCapturedConnectorResults` strips reasoning and connector results for cloud when local-only is set, but does not by itself prove that every private original prompt block or assistant visible quotation is safe. Preserve its fail-closed behavior and occurrence pairing; extend the context-preparation contract to retain source-boundary metadata or destination-safe alternatives for inline blocks. If a previously flattened/private block cannot be projected safely, refuse that destination rather than export it. This is the primary feasibility prerequisite for “FULL prepared original context” across providers.

Store canonical real reasoning exactly when available; destination compatibility/privacy may require omitting it. MiMo's fetch wrapper has invocation-local reasoning keyed by tool call ID (`mimo-reasoning-replay.ts:17`), recreated with the provider client. A new closing invocation cannot rely on the old wrapper's cache. Verify serialization of captured SDK reasoning to `reasoning_content` at the request-body boundary; carry a provenance-scoped replay state only if SDK messages cannot supply it. Never export primary-specific opaque metadata/signatures or cached private reasoning across arbitrary providers.

Run the context guard for closing even without tools: current `prepareStep` construction is conditional on tools, so simply omitting tools also removes that guard. Recompute against destination max context/output limits; current prepared output limit may exceed a fallback's. Keep full canonical state even if an attempt view must digest/truncate. Report budget reductions; preserve current user/instruction boundaries and provenance. A guard cannot always fit oversized system/image/reasoning content: check fit after bounded reduction and fail explicitly instead of claiming a guarantee.

## Pause, resume, retry and persistence

Version ask capture to include the canonical prepared context and transcript, not just `messages` after the current user. Read v1 captures compatibly, marking their evidence fidelity as legacy/reconstructed; never claim v1 contains lost inline prefetch. Reuse the current atomic message/capture stamp and claim-token release/settle/discard ordering. Substitute the person's answer only in the matching latest ask result. Do not append the original user/prefetch twice or re-prepare the whole prompt. Reauthorize current ownership, attachment access and provider/privacy policy on load without rewriting the stored original prompt. User-selected model/depth/personality changes on resume need an explicit override policy; current resume silently rebuilds these. Snapshot version, scope and override metadata make this reviewable.

The new spec explicitly allows **fresh explicit user retry** as a new run. Keep that distinct from continuation/reconnect. If continuation of failed/unsaved work is required, persist a private recoverable checkpoint before destructive retry cleanup; use a separate `continue` mode and claim it by root turn ID/generation. Do not delete jobs/evidence or replay the original user prompt to tools. If checkpoint is absent or in-flight side effects cannot be reconciled, return an explicit non-resumable/uncertain outcome; do not silently downgrade to automatic regeneration. Legacy Regenerate may retain its current fresh-run behavior under the explicit contract.

Share completion classification, normalization, evidence/delivery facts and audit construction between send and stream under chat-turn. Leave framing and JSON/SSE adapters separate. Route send's output through this service before `finalizeChatTurn`; carry failed tool facts for completion even though evidence persistence still filters evidence-ready calls. Keep finalize's message-first receipt/background projection ordering and ask ownership. Moving all stream completion into send's eager finalizer would regress latency and cost settlement.

## Durable failed/unsaved audit and costs

Existing message metadata cannot record a turn with no message; message_analytics requires a message FK. A narrowly scoped additive `chat_turn_attempts`/turn-outcome table under chat-turn is justified. It is execution observability, not a new memory subsystem or a place for raw continuation data.

Proposed writer:

```ts
async function recordTurnOutcome(input: {
  rootTurnId: string; segmentId: string; attemptId: string;
  phase: 'working' | 'closing' | 'persisting';
  outcome: 'answered' | 'delivered' | 'paused' | 'stopped' |
           'incomplete' | 'failed' | 'unsaved' | 'uncertain';
  cause: SafeStopCause; recoveryCount: number;
  userId: string; conversationId: string | null;
  assistantMessageId: string | null;
  providerId: string | null; modelId: string | null;
  usage: AttemptUsageFacts | null;
}): Promise<void>; // idempotent upsert, no raw error text/prompt/evidence
```

Separate generation outcome from persistence status: answered-but-unsaved is possible. One root/segment terminal outcome plus child attempt records (or uniquely keyed phase rows) prevents reconnect duplication. Write admitted/started state before model work and settle in a centralized terminal/finally path covering plain errors, stream fail, no-output failure, closing failure, stop and persistence failure. On process restart, settle abandoned started records as interrupted/uncertain, never answered. Audit writes are best effort with content-free failure logging; if the DB is unavailable, durable telemetry cannot be guaranteed. Do not represent a logging attempt as a durable success. Account/conversation erasure and incognito rules apply; incognito should not gain person-linked persistent audit/continuation content merely to satisfy telemetry.

Do not conflate completion audit with usage_events or behavioral memory events. Aggregate stability counters can consume content-free outcomes; raw captures never go to telemetry. Full continuation storage belongs to an access-controlled short-lived checkpoint lifecycle, cleared after final completion/discard/deletion, with bounded sizes and schema validation. Sensitive fields should not appear in conversation read models or list queries.

Preserve `40f2d74fc` accounting behavior (`analytics.ts:2748` `getMessageUsageState`, pending/ready/untracked, conversation totals, receipt-before-background analytics). Keep terminal message IDs and delayed settlement. Plain currently maps last-step usage; recovery replaces `latestProviderUsage`; both lose earlier calls. Introduce per-attempt/per-step attribution with stable IDs, and sum each actual model call once. Distinguish total billed input from last-step prompt-size/context-ring input. Do not add aggregate stream usage on top of already recorded step usage, or count reasoning twice inside provider output tokens. A single token sum priced as the final model is wrong after provider failover.

`getMessageUsageState` currently selects `.limit(1)` usage row for the assistant; if the implementation adds multiple main-attempt rows, update the server read model deliberately to aggregate attributable rows and define settlement readiness, or keep a single reconciled message accounting row with an attempt ledger behind it. Otherwise the existing delayed-cost fix will report ready after the first partial row and undercount the rest. No client changes are investigated here.

## Minimum focused validation for the implementation judge

- Plain provider fails after a counted completed tool and before terminal response: fallback uses original system/input + real results; execution counter remains 1.
- Tool settles before SDK step callback, then transport breaks; continuation has its real output once. Tool remains running/timeout side effect unknown: no competing execution or fabricated completion.
- Inline-prefetch evidence + native-prefetch evidence survives closing and ask pause/resume with fetch count unchanged; all sources remain available to citation/provenance checks.
- Snapshot equality for original instructions/history/pictures and real reasoning across primary continuation; local-to-cloud captures prove connector payloads, labels, pixels and quoted reasoning are gated per destination, including flatten primary -> cloud fallback.
- Stop before/during closing, confirmed ask pause, successful delivery followed by later unfinished research, failed/pending/refused delivery, zero-text reasoning-only, length, stagnation, max steps, no finish, closing empty/error/truncation, unknown/dropped tool: bounded truthful terminal outcomes for send and stream.
- Duplicate terminal events/reconnect/finalize retries create one outcome/receipt; assistant save failure still records unsaved outcome when DB is available; deleted conversation stays quietly stopped.
- Working + closing + failover usage attributed once, last-step context size retained, delayed per-message cost includes all attributed calls, incognito untracked. No full gates were run for this investigation.
