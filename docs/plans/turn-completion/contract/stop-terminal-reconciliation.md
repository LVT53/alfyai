## Problem and invariant

Normal active Stop aborts the reader after structural activity (diagnostic sequences 1–7) and receives no terminal completion. The server saves the stopped segment correctly, but the current page never reads it. Reload works. Evidence: `/tmp/alfyai-thinking-stop-diagnostic-summary.json` and `/tmp/alfyai-thinking-stop-wire-diagnostic.log`.

The [thinking display amendment](thinking-display-amendment.md) remains binding: retained ordinary activity requires an explicit projected stopped/paused/incomplete/failed completion and a fresh terminal disclosure. Local Stop intent, `wasStopped`, missing frames and elapsed time establish no completion outcome.

## Exact implementation shape

1. Retain the current `StartStreamParams` beside the current handle inside ClientTurnRuntime, cleared with that handle. For a cut-reply question retain those same params with its dead handle. Identity is the originating/reconnect stream ID, conversation ID and placeholder ID; terminal turn/segment IDs must agree with any already projected completion or pending observation identity. Never match a reply by text or the last assistant row.
2. A successful Stop captures that identity and the **post-Stop** `turnEpoch`, flushes existing partial buffers, and calls the existing upstream stop capability exactly once. Existing immediate composer release and queue-to-draft behavior remains synchronous with its current local end path. Stop reconciliation never sets sending/polling/active back to true and never drains queued work, even if the server won the race with an answered outcome. Repeated Stop must not invalidate a reconciliation when nothing remains stoppable.
3. Launch a private read-only observer through the existing `adapters.streamChat` transport, using only `reconnectToStreamId` with the captured conversation and no retry/question-answer/tool execution options. This is an observation request for that exact prior stream, never a fresh send. It must not call `startStream`, create a placeholder, enter normal retry/reconnect recovery, replay content into the message list, or become `activeStream`. Ignore replay token/tool/activity callbacks; only scoped typed observation metadata can authorize settlement. Detach each observation handle when its read ends or expires; never call its Stop capability. Prove observe-only behavior from the existing transport/backend contract before implementation; if that contract cannot guarantee no generation, stop and report the gap rather than invent a fallback.
4. Bound the entire handoff to 10 seconds (runtime scheduler), including terminal detail read. At most five observation requests, with 250 ms between pending responses; each request is capped at the smaller of 2 seconds and remaining deadline. A scoped pending result permits another read; unavailable, rejection, missing/mismatched metadata or exhausted deadline ends unavailable. No endless health wait, status heuristic or generation fallback. A terminal result ends observation and reads only its exact `assistantMessageId` through `readChatMessages`, within the remaining deadline.
5. Extend the existing private `settleObservation` seam with an explicit Stop settlement mode/ownership predicate, rather than duplicate terminal projection. Normal settlement retains current behavior. Stop settlement can target the retained old placeholder after `completeTurn` clears active state, but must never call `completeTurn`, change current stream/buffers, offer automatic retries, drain queues, or clear another turn's errors. It applies the existing canonical saved-row view and terminal completion/finalization marker through `applyNormalChatOutput` and `finalize`; preserves answer text, activity, model completion and accounting refresh. A terminal finalization failure stays inspectable as that failure, never durable success. An absent named durable row remains unresolved, retaining the partial and explicit unavailable warning; an explicitly terminal observation with no saved row ID can retain its authoritative in-memory outcome without claiming persistence.
6. Every scheduled action and every write after an await checks captured epoch, non-detached lifecycle, current conversation, captured placeholder still present, and observer ownership. New send/retry/resume/reconnect, chat switch, reset/detach/dispose invalidate the handoff. Late promises and callbacks cannot mutate messages, errors, costs, queue, questions or runtime state. Terminate and detach the private observer on invalidation. Keep this lifecycle inside the runtime, with one private current handoff record, not a store or parallel recovery subsystem.
7. Pending-observation Stop cancels its original retry schedule by epoch and hands the same identity to this path; do not fabricate stopped completion. Cut-reply Stop uses its retained dead handle/params, cancels existing cut-reply continuation by epoch, and hands off identically. An unsent update-wait Stop retains its existing behavior and creates no observer. An unaccepted question answer retains its existing quiet card recovery; do not invent a resumed segment. Accepted resumes use their exact segment identity.
8. Unavailable remains explicit (`chat.observationUnavailable` plus existing missing-finish warning), preserves partial answer and structural activity, and never invents stopped/failed/answered completion. A saved stopped completion may precede final known usage: preserve the existing targeted cost refresh, without awaiting accounting as a condition for terminal disclosure.

- Active Stop after activity-only `step_settled`: immediate idle/composer and queue restoration, then scoped observer terminal plus durable read yields explicit stopped completion, empty answer and retained activity. Exactly one upstream Stop, no fresh generation/retry/tool replay.
- Partial answer survives Stop, pending observations and unavailable; canonical saved answer wins only for the exact row. Server already answered race applies answered truth, never relabels stopped and never auto-sends queue.
- Pending observation Stop and cut-reply Stop hand off once; prior observer schedules/cut-reply continuations cannot run recovery afterward. Unsent update-wait and unaccepted-answer branches keep their existing semantics.

- Scoped pending becomes terminal; perpetual pending reaches finite deadline; hung observer/read, unavailable, missing metadata, wrong stream/chat/segment, missing saved row: bounded unavailable with no invented completion and no impossible message polling.
- Persisted stopped completion before late known usage triggers existing accounting refresh and retains completion; finalization-failed/unsaved terminal remains explicit and preserves partial output without claiming saved success.
- Repeated Stop and terminal callback races settle at most once; no timer or late transport callback revives active state.
- Complete retained replay and replay-to-live terminal receipt both settle; missing structural completion/receipt, conflicting row identity, finalization failure and stale replay callbacks preserve uncertainty and ownership.
