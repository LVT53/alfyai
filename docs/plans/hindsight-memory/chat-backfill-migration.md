# Rebuild memory from original chats

Status: feasibility investigation, 2026-11-18. No production migration or product implementation authorized or performed.

## Accepted migration policy — owner approved 2026-11-18

This section is the current decision, superseding earlier proposals where they differ. The owner approved these rules after the capacity/concurrency tests. Approval is for the migration policy and implementation planning, **not execution of a migration or implementation**.

1. **Honor deliberate exclusions across all legacy records.** Inventory deleted/suppressed profile items and saved `do_not_remember` review resolutions, including decisions whose affected items no longer have those statuses. Do not infer user intent from an item's extraction origin. Preserve the recorded action, scope, original source identity and available action time in a migration manifest.
2. **Exclude the identifiable statement, not unrelated chat content.** Map exclusions to their known source revisions/native facts and apply the bounded explicit-action mechanism. Older source delivery, retries, fork copies and re-extraction cannot restore the excluded statement. This is not a permanent topic ban: a genuinely new explicit statement can establish new information under the normal rules. Replay/import time must never masquerade as a new assertion.
3. **Preserve verified user-written statements and edits separately.** Standalone user-authored entries may legitimately lack a chat source. Keep their trustworthy text, scope and ordering; do not seed Hindsight with the old generated profile, portrait or summaries. Endorsement of generated text is not proof of authorship. Existing deliberate accept/use-fact choices belong in the audit as user intent, without reviving the dropped permanent-protection feature.
4. **Do not guess unresolved exclusion mappings.** Use explicit provenance and available resolution/evidence metadata first. Hold affected material out of publication and report the exception. If the affected boundary cannot be established, hold that user's historical backfill for resolution. This does not block new eligible memory from working. Do not omit an entire chat merely because one known statement was excluded, or build a global semantic prohibition/discovery engine to hide missing provenance.
5. **Known privacy boundaries always win.** Exclude incognito material, pre-reset material and known memory-disabled periods. Deleted chats are not recoverable sources. Recheck current permissions, source deletion and reset epoch before processing and publication. Permission to import uncertain history never overrides these boundaries or deliberate removals.
6. **Unknown memory-off history requires one optional per-user decision.** Current-enabled status is insufficient. During replacement introduction, offer inclusion of past chats whose eligibility cannot otherwise be established. Before acceptance, process only verified eligible history and newly eligible messages; do not send uncertain old text to Hindsight merely to prepare inactive banks. Record the decision and a fixed historical cutoff; it is not permission for future disabled periods. Declining/dismissing must not prevent normal use or trigger repeated prompts. A user can later opt in from Profile settings. Approval by the owner applies to their own account only, not to other accounts.
7. **Avoid routine migration review burden.** Most processing stays automatic. The one-time historical-import choice is separate from bounded exceptions; show an honest status/exception summary using existing UI patterns. Never label unresolved or unprocessed history as completely imported. Do not resurrect the old Memory review inbox or add a Manage screen.
8. **Keep learned project memories in the original project after a chat move.** Preparation can hold earlier project history out of the destination while keeping the accepted original project's documents. A move supplies no permission to replay the original project's assertions into personal memory or another project. The existing deletion and consent rules apply to retained sources across all their banks.

The [full replacement implementation plan](../../superpowers/plans/2026-11-18-hindsight-memory-replacement.md) owns the delivery sequence and acceptance tests. A migration manifest, durable source/exclusion records and exception reporting are app responsibilities; native Hindsight retains extraction/consolidation ownership.

## Backfill approach

Prepare fresh Hindsight banks from each user's eligible original chats before switching that user to the replacement. Do not seed them with the legacy model-generated profile, portrait or chat summaries. Preserve the existing data for a bounded rollback period under the normal privacy/deletion policy; do not delete users' memories to start the new system.

Native extraction remains Hindsight's job. AlfyAI needs a resumable delivery job, eligibility checks, stable source identifiers, original assertion times, and a cutover checkpoint. These are migration and privacy responsibilities, not another memory extractor.

## What is verified

- Current AlfyAI schema retains conversation owner, project ID and incognito flag; messages have role, content, sequence, source ID and creation time (`src/lib/server/db/schema.ts`, conversations/messages).
- Native pinned Hindsight `MemoryItem` accepts content, timestamp, document ID and metadata; `RetainRequest` accepts multiple items, asynchronous work and a caller-supplied operation UUID for idempotent retries. Omitting timestamp defaults to now: migration must supply it.
- An actual synthetic three-message batch on the intended local model retained newer Cork/blue bicycle, older Dublin/green bicycle, and a canoe question with an explicit non-ownership statement. Supplied in nonchronological order, admitted recall plus the existing dated-evidence answer prompt selected Cork/blue and no canoe. Repeating the same operation UUID preserved native IDs without duplicates. Evidence: `ui-qualification-run/backfill-results.json`, `backfill-api.jsonl`, `backfill.cjs`.
- This is a native batch/retry feasibility probe, not a production-volume throughput benchmark, proof of all conversation interpretation, or a native current-list solution. The answer uses the existing publication/dated-evidence boundary, not bare native Reflect.

## Preserve deliberate user choices

The old extractor is untrusted; user-authored edits are a different class of evidence. `knowledge-memory-actions.ts` marks corrected facts and summary-edit sentences with `origin: user_authored`. Migrate verified manual statements separately with their original scope and trustworthy action ordering. Do not mistake accepted/protected model output for text actually authored by the user.

Deleted/suppressed facts must not silently return from their old chats. Map existing removal records, saved do-not-remember review resolutions and provenance to eligible sources; preserve only the intended omission, not an entire unrelated conversation. Ambiguous or missing mappings must block publication of the affected material pending resolution. Reconstructing arbitrary semantic deletion rules across all historical chats would be a significant custom-layer expansion: do not silently build it. The [Edit/Remove follow-up](edit-remove-followup-results.md) qualified four bounded cases, while the [current-list follow-up](current-list-followup-results.md) safely withheld an expanded English mixed edit. These are not proof that every historical migration exception is solved.

`clearMemoryAndKnowledgeForUser` retains chats but advances `memory_reset_generations.advanced_at` before clearing memory. Respect that reset boundary; rebuilding pre-reset chats by default would undo Clear Memory. Exclude incognito material and users whose memory is disabled. Current flags alone do not establish historical enabled/disabled intervals; audit available event evidence before using that history. Unknown privacy eligibility is not permission to import.

Deleted chats are not recoverable evidence. A legacy generated fact with no surviving trustworthy source must not be relabelled as verified. Retain it only in the old rollback data if still permitted, not in active new recall. Explicit user-authored standalone memories can survive independently of chat sources.

## Proposed cutover

1. Inventory eligible counts/tokens per user and scope, reset/removal/manual-edit exceptions, missing sources and duplicate/forked/imported messages. Read-only inventory first; do not send real chats to the scratch bench.
2. Create inactive replacement banks per user and project. Take a source snapshot/checkpoint and record subsequent edits/deletes/new messages for catch-up. Use bounded contextual message groups with explicit speaker attribution; assistant guesses and quoted third-party statements are not user facts. Test that context choice before bulk processing.
3. Backfill oldest to newest in bounded asynchronous batches, keeping source assertion dates and a durable operation/checkpoint record. Never use import time as assertion time. If historical message edits lack trustworthy action dates, do not invent ordering from conversation updated time. Preserve latest stored text while flagging unresolved cross-chat precedence.
4. Apply verified user corrections/removal constraints and catch up changes since the snapshot. Recheck permissions, deletions and reset generation before publishing. Live delivery and backfill must share stable source revisions so a late retry cannot restore an obsolete source.
5. Validate recall, omissions, attribution and bank isolation; inspect representative English/Hungarian cases and all known manual interventions. Switch each user atomically only after their banks are ready. Queue new changes during the short final barrier and drain them before activation. Keep the old read path until that user's cutover, rather than expose half-built memory.
6. Keep a bounded rollback path. Privacy erasure must affect old and new stores and queued work alike. Retire old data only after acceptance and the agreed retention period.

## Remaining acceptance work

Native bulk ingestion is feasible; a safe real migration is not yet qualified. [Capacity and aggregate inventory](capacity-backfill-results.md) establish potential per-user volume; [overnight concurrency](capacity-concurrency-results.md) measured about 2.8× serial throughput at six requests, supporting a rough 2–4-hour overnight allowance. These are estimates, not a real migration rehearsal. Test interrupted batches, catch-up during active chat edits, resets/deletions during backfill, historical manual actions, missing source dates, fork deduplication, and full attribution/context selection. Do not promise recovery of every legacy memory: the goal is preserving trustworthy knowledge and user choices without carrying forward extractor mistakes.
