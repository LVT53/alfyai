# Independent lifecycle checkpoint

**Request changes.** Six independent synthetic reproductions reached a forbidden outcome on the combined implementation. A surviving independent assertion was lost, two operations reported success without the promised visible result, a completed Remove was undone on an unchanged edit-resend, an acknowledged Remove sent a new checker request after Memory was disabled, and concurrent resets lost a bound native bank's cleanup handle.

The probes use migrated temporary SQLite databases, the existing job engine, and production service entry points. They replace native HTTP and curation-model responses with controlled fixtures. Claims below describe application behavior for those inputs. Native frequency, semantic quality, release readiness and deployed service behavior remain ungraded.

## Blocking findings

1. **P1 · Source deletion can complete after silently losing a surviving assertion.** In `memory-profile/delivery-runner.ts:208–238`, source cleanup calls the dependency repair helper without its final verification callback. The check at `memory-profile/dependency-repair.ts:524` is optional. The probe removed a root with a submitted dependent, “That one. Separately, I own a bicycle.” The original accepted child fact recorded the bicycle. The native replacement successfully accepted the unchanged assertion but returned zero facts, a possible outcome for a short reply. Cleanup succeeded, the old child became revoked and only an unrelated chess fact remained in Memory. Compare the affected family's original evidence and settled candidate for source cleanup as well as Edit and Remove. Keep an unverified family held with a recoverable cleanup outcome. Verify both loss of an independent fact and restoration of removed context. An unconditional equality or nonempty check cannot distinguish legitimate disappearance of purely dependent information.

2. **P1 · A settled Remove can publish the removed detail in an observation.** `memory-profile/curation-runner.ts:551–622` verifies raw facts. `memory-profile/publication.ts:140–182` checks their fingerprints, then publishes native observation wording. In the probe native invalidated the requested kayak fact, kept the sister's bicycle fact, and returned a stable consolidated observation “green kayak and sister bicycle” supported by the surviving bicycle ID. The normal operation API reported `applied`, exclusion acknowledged and cleanup complete; the actual Memory list displayed that exact wording. Two matching captures and membership of every supporting ID both held. Validate the affected **displayed observation result** against the saved removal and preservation intent before acknowledging success. On failure keep exclusion effective; include replay and repaired descendants in the same contract. This is an observable mismatch even if the extractor and raw-fact checker behave correctly.

3. **P1 · A manual Edit can finish with no visible changed claim.** `memory-profile/curation-runner.ts:613–655` requires a relevant observation for Add only. The probe retained an immutable native “purple kayak” delta, invalidated the old green fact, kept the independent bicycle and returned no observation for the purple fact. The operation API reported `applied` with a null reference; the Memory list contained only the bicycle. Require positive evidence for the requested change in the final accepted observations. An honest split/merge can yield multiple visible rows and no single reference. A surviving unrelated row from the same document is insufficient. Findings 2 and 3 can share a final check over the touched visible observations within the existing bounded curation boundary.

4. **P1 · Overlapping resets can erase the local handle of a new remote bank.** `account-lifecycle/index.ts:75–108,147–152` reactivates by user ID. `memory-profile/delivery-job.ts:126–168` lets a second caller join an existing erasing epoch without assigning exclusive finalization ownership. The probe paused a real Clear Memory request after its fence, completed a second Clear Memory request, admitted a fresh source and drained its real delivery job. The first caller then resumed its broad local deletion. The fresh source remained in the simulated native service, its bank binding disappeared from SQLite and **zero bank cleanup jobs** existed for it. A crash is unnecessary. Give destructive work a durable identity and fence every sweep and completion against it; overlapping requests must coalesce, serialize or safely retain newer-epoch work. Exercise account erasure racing either surviving-account reset as well as two clears and crash resumption. The separate provisioning-before-binding issue is owned by the native operations judge.

5. **P1 · An acknowledged Remove issues a new model request after Memory off.** `memory-profile/curation.ts:164–209` makes separate application and checker calls; `curation-runner.ts:249–278,534` checks the off state at the outer action boundary. The real off transition deliberately exempts acknowledged Remove jobs from cancellation. The probe disabled Memory while the proposal request was outstanding. When its response returned, the worker started a **new** checker invocation containing the old green kayak text while SQLite already reported Memory off. Exclusion and cleanup-pending stayed set. Fence every new model dispatch, including checks and the optional repair attempt, against the live control revision and job authority. A cleanup-only obligation must survive while new semantic work waits for enable. The existing real Remove mid-retain/off test passes for its different barrier.

6. **P1 · An unchanged chat edit-resend can resurrect a prior successful Remove.** `memory-profile/chat-delivery.ts:286–311` assigns a predecessor even when the text is unchanged. `delivery-runner.ts:309–327,364–383` sends the full old assertion in that case and calls replay for the new source ID without predecessor mapping. `curation-runner.ts:858–978` then plans a new before/after edit. The probe first completed a Remove and verified only the bicycle remained. An identical successor retaining the same lineage produced a fresh green kayak fact. All three calls concerned a new no-change edit; **none was supplied the saved removal intent**. The job succeeded and the list contained both green kayak and bicycle again. An unchanged resend carries no newer assertion about the removed detail. Preserve/map the approved prior source family across this path. On a genuine change, distinguish a new deliberate assertion from unchanged wording and apply saved intents in order. Hold/reject ambiguity before publication.
