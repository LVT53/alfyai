# Task 7 independent migration review

**Request changes.** Four synthetic regressions reproduced against migrated SQLite and the existing Memory job runner. The review checked the approved history policy, CLI, migration and privacy fences, authority, and the legacy writer and account-creation entry points.

## Blocking findings

1. **P1 — A later legacy removal can be undone by backfill.** `migration.ts:443–498` generates a new standalone source for every historical review Edit and installs a replay Edit for its original chat. A legacy review Edit already retires the previous row with `metadata.supersededBy` and creates a user-authored replacement with copied provenance (`projection-store.ts:887–944, 1059–1095`). Migration ignores the replacement lineage and its later deletion. The later removal is mapped to the old chat, but has no link to the synthetic standalone review source (`migration.ts:755–773, 776–844`). The probe creates the real legacy replacement through the projection mutation, deletes it through the normal revisioned writer, then prepares and drains the native delivery queue. The deleted correction goes out as a new retain and appears in published rows, while unrelated material survives and the manifest is ready. Resolve the stored replacement lineage and action ordering before generating sources. For a removed replacement, preserve the audit record and the old statement's bounded exclusion, without seeding or replaying the removed replacement. For an active replacement, carry the authored statement once. Hold ambiguities against the affected source boundary.
2. **P1 — An assistant message from a known memory-off period reaches the native retain request.** `migration.ts:657–670` adds assistant context under the preceding eligible user's source. `revisions.ts:379–391, 467–506` rechecks that source and verifies the assistant's identity, parent and text hash, but trusts the parent timestamp for eligibility. The test uses an eligible user message, a delayed assistant message written during a known off interval, and a later eligible user message. The actual retain request for the later message includes the disabled-period text. Check the assistant row's own `createdAt` at packing and dispatch, using the same effective history, disabled-period and reset rules as for any other historical text. Continue checking the parent, scope and text hash. A directly authored Memory Add or Edit is separately verified user intent under the approved policy and does not require consent for uncertain chat history. This counterexample concerns chat text in context.
3. **P1 — Moving a conversation between scopes makes migration preparation non-resumable.** `migration.ts:592–606` compares current text and eligibility without comparing the source scope. The normal conversation move revokes the old source before changing projects. On reprepare, `migration.ts:673–685` correctly declines to reuse the old bank row, then looks up the same user-wide event ID. `revisions.ts:120–146` rejects the old event because its bank differs. The test prepares and drains a personal source, moves the chat to a project through `moveConversationToProject`, confirms the old manifest changed, and receives `memory_event_conflict` on reprepare. Give each authoritative scoped revision a stable identity, retire and clean the old scope, and re-evaluate linked exclusions under the new scope. Test moving back as well, since a revoked identity cannot serve as a new active revision.
4. **P1 — A retired source's terminal failure can permanently block cutover.** `migration.ts:908–948, 1129–1162` counts every failed job in the epoch, including one irrelevant to the current manifest, and `delivery-job.ts:75–97` reuses existing jobs by request ID regardless of status. `jobs/ledger.ts:1033–1057` cancels only queued or running jobs. The probe induces a terminal source failure, deletes the source message, then prepares and drains cleanup and empty-bank provisioning. The source is revoked, but the current manifest reports `changed: false`, `pending: 1`, `ready: false`. Account for jobs needed by the current checkpoint and retain outstanding cleanup as a readiness condition. Preserve failed attempts for audit while letting superseded delivery stop blocking cutover. An unchanged, still-required failure needs a supported same-operation retry or an explicit held outcome rather than a duplicate row.

## Verified cases and boundaries

- The ordinary focused run passed **44 tests in six suites**. In the exercised paths, current-enabled alone did not queue unknown chat history, declining after enqueue prevented native retain, known off/incognito/fork sources were excluded, reset after enqueue fenced old history, and the user could activate with uncertain history held. The new disabled-assistant-context case exposes a separate gap.
- The normal exclusion fixture used an original source timestamp and bounded curation to preserve the unrelated fact. Explicit item/provenance indirection and a review-only unresolved exclusion were inventoried as expected in their fixtures. A verified standalone statement survived separately and a generated endorsement did not become a source. These cases cover representative record shapes.
- Existing tests exercised changed/deleted source detection, rejected another user's manifest, rejected inactive native capability, preserved an existing binding, and rejected a real legacy judge's late write after cutover. The rollback fixture left Memory unavailable after a new revocation and repeated cutover did not renew its rollback baseline. The new project-move and failed-job cases are outside those passing paths.
- `HINDSIGHT_NEW_ACCOUNTS_ENABLED` defaults false. The enabled-path integration test used real managed account creation to verify atomic native authority and interval creation for the new account while leaving the existing account legacy. CLI execution required explicit database/user selection and rejected real-mode mutation without acknowledgement. A positive CLI mutation ran only against a temporary synthetic fixture. Default inspect makes no application row or native/model changes and uses the normal WAL database connection.
- Additional source-read follow-up for the repair review. `prepareMemoryMigration` reads authority, then writes the previously read value back outside the cutover transaction (`migration.ts:535–550`). Concurrent prepare can overwrite a just-committed authority change. Limit its transition to a transactional, conditional `legacy` → `preparing`. Review closure also reuses `do_not_remember` for automatic expiry or obsolete rows (`projection-store.ts:262–270`, `review.ts:291–309`), so inventory must consult persisted action metadata before interpreting those rows as deliberate exclusions. The four executable probes above cover the blocking behavior observed in this pass.

## Reproduction

Run on Node 22 from the repository root. This adds the synthetic probes through a Vitest transform and leaves application source and test files untouched.

```sh
PATH=/opt/homebrew/opt/node@22/bin:$PATH node docs/plans/hindsight-memory/migration-review-fixtures/reproduce.cjs
```

The four probes use temporary migrated SQLite, the existing worker and synthetic native responses. They establish state, fencing and wire behavior. Pinned-native English/Hungarian quality, attribution, and migration acceptance remain separate. The review did not run build, full gates, real account inspection, or deployment.
