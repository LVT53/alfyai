# Per-user Memory replacement migration

Implementation and rehearsal use synthetic data. The owner conditionally authorized the root agent to begin per-user `inspect`, `prepare`, and `verify` for real inactive banks if all implementation, acceptance tests, and final independent review finish before **05:00 Europe/Dublin on 19 November 2026**. If readiness misses the deadline, defer real preparation. Authorization ends at inactive-bank verification. Deployment and authority cutover require separate authorization. Individual workers continue with synthetic data unless the root agent explicitly assigns eligible work.

Keep existing Do Not Remember and history-consent decisions and every exclusion in force. Unknown historical eligibility requires that user's explicit opt-in.

Use Node 22. The single entrypoint is `scripts/memory-backfill.ts`. It requires an explicit database and user, defaults to `inspect`, and prints counts/checkpoint IDs only. The restricted `memory_migration_manifests` rows contain the detailed inventory and original text; do not paste them into logs or reports. Account privacy erasure owns these records alongside other memory state.

## Modes and safeguards

- `inspect`: read-only application inventory; no source/job/account rows created and no model calls. Counts eligible, uncertain, excluded and held sources, authored/endorsed actions and exceptions. The SQLite connection uses normal database WAL settings; inventory does not mutate application records.
- `prepare`: snapshot the original chats/actions/privacy state, create inactive banks, and enqueue the existing Memory delivery jobs. Repeating it resumes stable source/operation IDs and catches changes. It does not activate native reads. The configured existing worker must run to drain jobs; no second scheduler exists.
- `verify --manifest ID`: compare the current source/action/privacy fingerprint with the snapshot and inspect current checkpoint jobs, outstanding cleanup and source acceptance. A failed superseded retain stays in the job ledger. A failed required delivery or cleanup blocks readiness and appears in the failed count. Repeating prepare retries required retryable delivery with the same engine job and native operation identity.
- `cutover --manifest ID`: refuse changed/incomplete snapshots and unconfigured native banks. In one SQLite write transaction, verify the checkpoint and switch the user's reader/writer authority. The legacy projection mutation boundary rejects late old workers after this point. Preparing accounts keep the legacy reader; there is no blended profile.
- `rollback --manifest ID`: restore legacy authority only within the recorded 30-day window and only when the complete privacy/source/action checkpoint still matches. Any post-cutover removal, reset, choice, source change or other nonrepresentable state leaves memory unavailable (`rollback_blocked`) rather than resurrecting old information.

Mutating real-mode commands require `--execute yes --operator-ack approved-per-user-migration`. These are deliberate operator safeguards, not authorization on behalf of the user. `prepare` must respect that particular user's history choice; current-enabled does not grant historical permission. `verify` cannot substitute for the semantic/isolation acceptance report.

Command shape (placeholders, not executed):

```sh
node --import tsx scripts/memory-backfill.ts --database /explicit/database.db --user USER_ID
node --import tsx scripts/memory-backfill.ts --mode prepare --database /explicit/database.db --user USER_ID --execute yes --operator-ack approved-per-user-migration
node --import tsx scripts/memory-backfill.ts --mode verify --database /explicit/database.db --user USER_ID --manifest MANIFEST_ID
```

Use the same explicit acknowledgement for cutover/rollback. Never use an implicit default database or all-user target.

A retain that Hindsight reports failed (it does not retry it) is resubmitted once, automatically, under a new operation ID, provided the failed operation left no fact under the source's document. The delivery holds the job back a minute first (`native_retain_resubmit_due`, a wait, not an attempt), so the refusal that failed it has passed; the next attempt finds the operation failed and commits the new ID and the failed one (`nativeRetainResubmittedFrom`, in the source revision's `context`) before the new call goes out, so a restart never sends a second resubmission. A retain's terminal end is recorded on the revision (`nativeRetainEnded`) and has its own code, not retryable, after which reopening the job asks Hindsight nothing and sends nothing: `native_retain_resubmit_failed` (the resubmission failed too), `native_retain_left_facts` (the failed operation left a fact under the document) and `native_retain_cancelled`. These need the owner; `scripts/memory-resend.ts` is the canonical way to send the chat again under a new operation. `native_operation_failed` on a source delivery is something else: a consolidation or a repair that Hindsight reported failed, and a reopen runs it again. This applies to every account, live chat deliveries included.

## Operator tools for stuck deliveries

Four canonical tools replace the rollout's hand-run scripts (Memory part 4). Each is a dry run unless given `--execute`, asks the permanent tester rule's guard first (the tester account, `users.memory_migration_excluded`, and an unknown account are refused before anything else runs), prints one line per step (`step <name>: ok` or `step <name>: FAILED <code>`, with counts and ids) so a failure names its step, then the whole report as JSON, and exits 1 when it refused or failed. They print counts, ids and status words only, never memory text. Run them from the release's checkout with the app's environment loaded, after a paired backup and with the owner's go-ahead on production.

- `npx tsx scripts/memory-resend.ts --user <id> --job <delivery job id> [--delete-landed]`: a delivery that failed because its retain never landed (Hindsight reports the operation failed, cancelled or unknown, holds no fact under the chat's document, and the bank is quiet). It gives the source a new operation ID, written as not yet sent, keeps the old one as `nativeRetainResentFrom`, clears the retain's recorded end, and reopens the job with its whole attempt limit. The job then sends the chat once more (and, should that fail, holds back a minute and resubmits once, as any delivery does). `--delete-landed` is for a chat whose retain did land but whose facts hold the bank up (the delivery failed after Hindsight completed the retain): a completed operation, an acknowledged retain and facts under the document no longer refuse (a running operation or a busy bank still does), and the dry run counts the facts it would delete. On `--execute` it deletes the chat's document in Hindsight (`delete_document`), waits until the bank has no pending operation, at most `MEMORY_CONSOLIDATION_WAIT_MINUTES` (`bank_settled`, while Hindsight rebuilds what cited the document), refuses `facts_remain` if a fact is still listed under it, and resends with the source written as never sent and never acknowledged, so the job sends the whole chat again.
- `npx tsx scripts/memory-reattach.ts --user <id> --job <delivery job id>`: a delivery that failed although Hindsight holds the chat's facts (a timeout before this release, or a retain that left facts). It marks the source sent and acknowledged and reopens the job with its whole attempt limit, so the job consolidates and publishes without sending the chat again. Read the dry run's fact count first: a failed retain's partial facts become the delivery.
- `npx tsx scripts/memory-recover-consolidation.ts --user <id> --bank <bank id>`: facts Hindsight marked failed in consolidation. On a quiet bank it calls `POST …/consolidation/recover`, runs one consolidation and waits for it (at most `MEMORY_CONSOLIDATION_WAIT_MINUTES`), then counts the failed facts again; a dry run only counts them. Then drain the account.
- `npx tsx scripts/memory-drain.ts --user <id> [--max-minutes 60]`: retries each of the account's retryable failures once (the person's own Retry, under the job's attempt limit), runs the account's jobs and only that account's, waits out holds and waits on Hindsight instead of stopping, and ends with a summary: counts by status and every job it did not finish with its kind, status and code. It first takes back the account's own jobs that a dead process left `running` (`recover_stale`): a drain killed mid-attempt otherwise leaves one holding the box's one Memory slot, for every account. A lease counts as dead two minutes after its last beat, so wait that long after killing a drain before starting the next, and a live job of another process is left alone. A job of the account's own that an attempt put back (waiting on Hindsight, a counted retry) is resumed before the drain gives way to other accounts. `--max-minutes` ends the starting of work, not the finishing of it: past it no job that was never attempted is started, but the jobs put back mid-flight are still resumed (and a running one waited for), so none is left holding its bank, for both of Hindsight's waits (`MEMORY_RETAIN_WAIT_MINUTES` + `MEMORY_CONSOLIDATION_WAIT_MINUTES`) at the most. The `drain` step reports `finishedAfterDeadline` and `leftInFlight` (those left are in the summary). It needs the Memory worker switch on in its environment, and it shares the job caps with the running workers, so on production stop the account's own worker first or let the drain wait its turn.
- `npx tsx scripts/memory-quality-report.ts --user <id> [--baseline] [--judge] [--out <file>]`: not one of the four, and read-only (no `--execute`, no guard): how an account's Memory came out of its deliveries (messages by origin and state, where "imported" is the ChatGPT import alone and the person's own earlier chats, which preparation records under the same event ids without the import's mark, are "history"; facts per message by message length; entries by kind, age, subject, support and duplicates; the imported facts' event dates against the day they were said; the delivery time per job by tenth of the jobs; and the milliseconds the reads took), counted in the process so nobody reads it, and printed as percentages and as JSON with numbers only, no text and no id (`--out` also writes the JSON, mode 0600). It opens no transaction of its own, so it never holds the database's write lock beyond the Memory page's own short read, and its numbers may straddle a delivery that lands meanwhile. `--baseline` adds the same numbers summed over every other native account, the tester left out, without subject counts, and only with at least three such accounts (with fewer it says how many there are and gives no number of theirs). `--judge` adds the model judge's totals. It sends the account's entries to the Memory model, so before every batch and every call it checks that Memory is still on, the account native and active, and the epoch, the control revision and the newest history choice are as the run found them (declining history revokes the entries it would send), and it withdraws the entries no longer published (the totals count them); when consent itself changes it stops at once, prints `memory_quality_consent_changed`, writes no judge totals and exits 1. A delivery landing during a judge run does not stop it: an entry is withdrawn only when a publication drops or replaces the observation behind it.

## Label migration

Memory part 2 labels new facts in extraction; the facts banks held before bank config 2 have no kind or subject, so their entries read as lasting and the account keeps today's Memory page (`memory_accounts.labels_unverified_epoch`). The label migration gives every such fact a kind and a subject through the local-model classifier, then verifies the account and clears its mark, one account at a time. It runs after part 4's admission queue is live (its model calls wait at background priority behind live turns), and after the Earlier gate (an Earlier entry joins a turn only when the message is about it: the TEI reranker's score at or above `MEMORY_EARLIER_RERANK_MIN`, or the words agreeing and the score at or above `MEMORY_EARLIER_RERANK_WORD_MIN`; with no reranker, a timeout or an error the words alone, and the line `[KNOWLEDGE_MEMORY] Earlier rerank unavailable` says why, so `TEI_RERANKER_URL` should answer before the migration runs) is deployed: labels make old temporary entries Earlier.

What it does and never does:

- It asks the permanent tester rule's guard first: the tester account is skipped, counted, and its banks are never read. It also skips accounts not on Hindsight, not active, with Memory off, or already verified.
- It reads each bank's raw facts from Hindsight (`GET …/memories/list`, observations left out) and labels those without a kind, 20 to a model call. A fact the person removed is never sent and never labelled (`removed=`): one a `memory_revocations` row names, and one of a source that is revoked or that a revocation names, unless a source they kept still holds it; Hindsight may list such a fact until its deletion reaches it. A bank the app made but never configured in Hindsight (nothing was ever sent to it) holds no facts yet, whether Hindsight lists none or answers 404 (unverified at the pin which it does); a 404 for any other bank fails the account (`native_not_found`). Every raw fact of every bank of the account's current epoch is labelled, config-1 banks (not yet upgraded by a delivery) and config-2 banks alike, before the account is verified. It never upgrades a bank's config, never calls `reprocess`, and never writes anything to Hindsight.
- Before each batch, and again right before its call leaves the admission queue, the tester rule and the bank's fence are asked (as curation asks them): once the person turns Memory off, clears or erases it, or the account is excluded, no further fact is sent. Three batches failing in a row stop the account (`model_unavailable`) instead of asking for every batch twice.
- Each answered batch is written at once, in a transaction fenced on the bank's epoch and status, to `memory_fact_labels` only. Nothing else changes: an entry's text, support, dates and visibility stay as they were. Part 3's triggers delete the banks' cached Overviews when labels are written; that is intended (the next opening writes a fresh one).
- Verification, per account: every raw fact is labelled or listed as unlabelled with its reason (`no_label`: the model answered twice without a usable label; it reads as lasting), no more than one fact in 20 is left so (`too_many_unlabelled` otherwise: the facts were looked at but not labelled), the kind mix is plausible (`implausible_labels` when under 15% of the labelled facts are lasting once 20 are labelled: a model calling everything temporary; roll that account back and run it again once the model is fixed, because labelled facts are not asked again), every fact it labelled reads the same in Hindsight's second listing (`facts_changed` otherwise: its label was chosen for the old wording), and a fingerprint of the account's published rows (text, native text, support, dates, which rows are visible, the banks' generations, every fact's event date, and the states and dates of the sources those rows rest on) is unchanged. A source no published row rests on does not count: a chat during the run records a pending source, and a revocation or an import its own, and none of them fails an account any more. A publication does (`published_rows_changed`), and a re-run finishes the account. Only then is `markMemoryLabelsVerified` called, and the account gets the new page. A batch that fails twice (`model_unavailable`), a fact left without a label, changed published rows or a moved epoch fail the account, and the run stops there.
- A re-run skips labelled facts and verified accounts, except that it asks again for the facts an earlier run left without a usable label (a verified account keeps its verification; one with nothing left is skipped `already_verified`); an interrupted run (Ctrl-C, a crash) keeps every batch it wrote, and the next run labels only the rest.
- It prints counts, ids and codes only: per account the facts this run labelled per kind and per subject, those left unlabelled by reason, the whole account's labelled facts per kind and subject (a resumed run's too), its entries per kind and subject and how many are Earlier (they leave the current page and recall's basics once labelled), and whether verification passed. Never memory text. Ctrl-C aborts the model calls in flight (the next run labels their batches); every batch already answered is kept.

Production procedure (each step needs the one before it; the owner's go-ahead before step 3):

1. **Dry run**, from the release's checkout with the app's environment loaded: `npx tsx scripts/memory-label-migration.ts`. Counts only: accounts, skipped and why, banks (config-1 banks counted), facts, removed facts, already labelled, to label, estimated model calls, and the entries as they read now. Read it before going on; an account with a `failure=` (for example `bank_repair_blocked`) will stop the run there.
2. **Paired backup**, as `deploy/hindsight/README.md` ("Backup, restore and upgrades") describes: Memory workers paused (the global worker and every scoped worker) and no native operation outstanding, then the AlfyAI SQLite database (online backup, `sqlite3 "$DB" ".backup '<dir>/chat-<UTC>.db'"`) and Hindsight's PostgreSQL database (all tenant schemas, `pg_dump`: plain `.sql`, `.sql.gz`, custom format or a directory dump) into one folder, within two hours of each other, plus the secret bundle as the README requires: the deployment's settings files, taken in the same sitting ("The secret bundle", below). Keep the workers paused for the run: a delivery that publishes during it changes the published rows and fails verification.
3. **The owner's go-ahead**, with the dry run's counts.
4. **One account first**: `npx tsx scripts/memory-label-migration.ts --execute --user <id> --backup <dir>`. The command checks the backup before it writes (both halves present and readable; the SQLite one an app database, not the live database file itself or a link to it, holding every account to label exactly as the live database does: the same epoch, labels mark, banks and generations, and classifier-label count; the PostgreSQL one a dump, a gzipped one inflated to be read; both from the last four hours and within two hours of each other; and the secret bundle, a readable `.tar` or folder of `*.env` files inside the same window, "The secret bundle", below) and names it (`backup: sqlite=… postgres=… bundle=… env=…`); it refuses otherwise. Check its line: `verified`, `verification=passed`, the counts per kind and subject as expected, `unlabelled.no_label` small. Open that person's Memory page only with their permission; the counts are enough otherwise.
5. **The rest**: `npx tsx scripts/memory-label-migration.ts --execute --all --backup <dir>` (add `--concurrency 2` or `3` overnight if the queue is idle). It prints one line per account as each finishes and stops at the first that fails; fix the cause (`model_unavailable`: the model or the queue; `published_rows_changed` or `facts_changed`: a worker published or delivered during the run) and run it again: verified accounts and labelled facts are skipped.
6. **Resume the Memory workers.**
7. **Rollback**, one account at a time: `npx tsx scripts/memory-label-migration.ts --rollback --user <id>` (dry run: how many classifier labels it would undo), then the same with `--execute --backup <dir>`. It returns that account's classifier labels to unlabelled (their event dates kept), takes back its epoch's verification (`revokeMemoryLabelsVerified`: marked unverified and no longer recorded as verified, so today's Memory page, and an in-place upgrade marks it again), and writes nothing else. It works with Memory off, says whether the migration had verified the epoch (`epochVerified=`), and refuses an epoch the migration never ran on (`code=label_migration_not_run`), so a new epoch is never sent to today's page. What it cannot restore, because nothing records it: whether a fact had a label row before (the undone row has no kind or subject, which reads as no row does, and the next publication refreshes it), a subject extraction gave a fact without a kind (the next publication copies it back from Hindsight's tags; today's page shows no subjects meanwhile), and the rows' `updated_at`. The migration is the only writer of classifier labels today; if a fallback classifier for new facts is ever added, it needs its own record, because a rollback undoes every classifier label of the epoch. Restoring the paired backup is the last resort, under the restore hold (`deploy/hindsight/README.md`, "Restore hold"), because it also takes back everything written since.
8. **After a release rollback and a roll forward**, run the label migration again, from step 1. The bank-config restore to config 1 (`deploy/hindsight/README.md`, "Bank config 2" and "Bank config 3") returns every native account but the tester's to today's page, because the first release writes facts without labels and may create config-1 banks (a restore to config 2 does not: config 2 labels every new fact). After a roll forward from either, run the relabel again ("Relabel (bank config 3)", below): it asks about the facts the older release labelled temporary in between, and never about a fact it asked about before. The migration is resumable: facts it labelled before are skipped, and only what the previous release wrote is sent to the model.

### Relabel (bank config 3)

Config 2 labelled a dated purchase or acquisition temporary, so a phone the person bought ages into Earlier. Config 3's words (`deploy/hindsight/README.md`, "Bank config 3") say it is lasting; new facts get that from extraction once their bank is on config 3, and **the relabel** moves the facts labelled temporary today. It is the label migration's second mode (`--relabel`, `memory-profile/label-relabel.ts`): it asks the local-model classifier, with the new words, about every fact whose label is temporary, and writes the answer where a classifier label wins (`recordClassifiedFactLabels`) when the fact is no longer temporary. It runs once, after the config 3 release is deployed and `db:prepare` has created `memory_label_relabels` (migration 146), and does not need the banks to be on config 3 yet (it uses the classifier, not Hindsight's extraction).

What it does and never does (the migration's safety, and a little more, because the account already has its labels):

- The permanent tester rule's guard first (the tester's banks are never read); it skips accounts not on Hindsight, not active, with Memory off, and accounts whose epoch still waits for the label migration (`labels_not_verified`: the migration labels those with the new words anyway). A new account that never needed the migration is relabelled: its facts carry extraction's labels.
- It only lists from Hindsight (never writes there), never sends a fact the person removed, and asks only about facts whose label is temporary and that no earlier run asked about (`temporary=`, `alreadyRelabelled=`, `toRelabel=`; 20 to a model call, background priority behind live turns, fenced before each batch as the migration is).
- **Nothing is written until the account verifies.** The answers are held, then checked: each answer was chosen for the text Hindsight still holds (a second listing); the published rows are as they were; at most one fact in 20 is unanswered, and one is always tolerated (`too_many_unanswered`: it keeps its label and is asked again by the next run); and not almost every fact moved (`implausible_relabel`: over 90% of at least 20 answered, a model that has stopped reading). Only then one fenced write for the account (the banks' epoch and status, the tester rule, and a check inside the write that the published rows are exactly as they were) stores a classifier label for each fact that moved (kind and subject from the answer; the fact's event date kept) and a record of every fact asked (`memory_label_relabels`: the label it held before, and whether it changed). A failed account is left as it was.
- A fact the new words still call temporary keeps its row exactly as it was, and is recorded as asked, so it is not asked again for as long as its label reads as the relabel left it (a record whose label is gone, because the label migration was rolled back or a publication copied extraction's tag back, is stale: the fact is asked again and the record replaced); a fact the model left unanswered is asked again by the next run; a re-run asks nothing it asked before (`skipped nothing_to_relabel`).
- Counts only: per account the facts asked, those moved per kind (`moved.lasting=`), those left temporary, the account's entries and how many are Earlier before (`before.earlierEntries=`) and after (`earlierEntries=`), and whether verification passed.

Production procedure (the owner's go-ahead before step 3), with the Memory workers paused as for the migration:

1. **Dry run**: `npx tsx scripts/memory-label-migration.ts --relabel`. Counts only. An account with a `failure=` will stop the run there.
2. **Paired backup with the secret bundle**, exactly as step 2 of "Label migration" above (workers paused, no native operation outstanding, SQLite and PostgreSQL dumps within two hours of each other, the settings bundle in the same window). The command refuses without it.
3. **The owner's go-ahead**, with the dry run's counts.
4. **One account first**: `npx tsx scripts/memory-label-migration.ts --relabel --execute --user <id> --backup <dir>`. Read its line: `relabelled`, `verification=passed`, `moved.lasting=` and the entries leaving Earlier (`before.earlierEntries=` against `earlierEntries=`).
5. **The rest**: `npx tsx scripts/memory-label-migration.ts --relabel --execute --all --backup <dir>`. It stops at the first account that fails (nothing of it written); fix the cause and run it again.
6. **Resume the Memory workers.**
7. **Rollback**, one account at a time: `npx tsx scripts/memory-label-migration.ts --relabel --rollback --user <id>` (dry run: `changed=`, `toRestore=`, `leftAlone=`, `lookedAt=`), then the same with `--execute --backup <dir>`. It puts back, for each fact the relabel changed, the kind, subject and origin it held before, only where the label still reads as the relabel wrote it and was not written again since (a label changed or rewritten since is left, and counted `leftAlone`), and forgets the account's records, so the next run asks about those facts again. It works with Memory off, never touches the account's label verification or anything else, and refuses an account the relabel never ran on (`code=label_relabel_not_run`). Rolling back the label migration (step 7 above) forgets the account's relabel records with the labels they stood on, so run the relabel again after it, not its rollback.

### The secret bundle

A database pair restores nothing without the worker ID, keys and tenant bindings in the deployment's settings files (`deploy/hindsight/README.md`, "Backup, restore and upgrades"), so the command looks for them in the backup folder before it writes (a rollback's `--execute` too): a plain `.tar` holding at least one `*.env` file, or a sub-folder holding `*.env` files, from the last four hours and within two hours of both halves of the pair (a folder counts by its oldest `*.env` file). It reads only a tar's entry headers (a name, a size and a checksum in 512 bytes each, never what an entry holds; an entry counts only when its header's checksum holds and its data lies inside the file, so an archive cut off inside an entry adds nothing) and opens each file of a folder to prove it can; it never reads, compares or prints a settings value, and a file named `*.tar`, `*.tgz`, `*.tar.gz`, `*.env` or `*.yaml` is never opened to be taken for the SQLite backup or the dump. The `backup:` line gives the bundle's name, size, number of `*.env` files and time, nothing else. It proves the files are there and readable, not that the set is complete: compare `tar -tf` with the deployment's folder before the go-ahead.

Take it as production did, as root, from the deployment's folder, in the same sitting as the two dumps (`BACKUP_DIR` is the folder you pass to `--backup`):

```bash
cd /etc/alfyai-memory/production
tar -cf "$BACKUP_DIR/deployment-files.tar" ./*.env ./*.yaml
```

The migration runs as the app user, who cannot read root's files, so hand the copy to that user and keep everyone else out (the tar holds the database password and the native worker ID). `APP_USER` is the user that runs the command in step 1 (`id -un` there):

```bash
chown APP_USER "$BACKUP_DIR" "$BACKUP_DIR/deployment-files.tar"
chmod 0600 "$BACKUP_DIR/deployment-files.tar"
chmod 0700 "$BACKUP_DIR"
```

Use a plain tar: a `.tar.gz` cannot be listed without inflating the settings in it, so it is not looked at, and a copy that keeps old times (`cp -p`, `cp -a`) reads as stale. When the run is over, move the folder with the rest of the backup. The refusals:

| Code | Meaning |
|---|---|
| `backup_secret_bundle_missing` | no `.tar` with a `*.env` entry and no sub-folder with `*.env` files in the folder |
| `backup_secret_bundle_unreadable` | a `.tar` or a sub-folder in the folder cannot be opened by the app user (the `chown` above), and no readable bundle is there |
| `backup_secret_bundle_stale` | the bundle is older than four hours |
| `backup_secret_bundle_not_paired` | the bundle is more than two hours from either half of the pair |

## Eligibility and live changes

Unknown historical on/off periods remain out of native requests until the user explicitly includes them, with a fixed cutoff/version. Known off intervals, incognito, deleted sources and pre-reset statements remain excluded. The optional choice is available while preparing and after cutover; native functionality can activate with uncertain history still held. Including/declining later resumes the existing manifest. Source permissions are checked again at native dispatch/publication, and withdrawal revokes queued historical sources before acknowledgement.

Known removed statements are mapped using explicit source/item/provenance IDs, including review-only do-not-remember records. A saved bounded action is applied by shared native curation before publication and replayed on retry, preserving unrelated facts. Generated endorsed profile text is audit intent, never native source material. Verified authored standalone statements retain their own scope and action date. A current legacy review replacement supplies that authored statement once. If the person removes it, the correction stays in restricted audit records and the bounded exclusion of the original statement still applies. Automatic review closure preserves its recorded reason. Where the old pre-edit statement or action date is unavailable, the affected source is held explicitly rather than inventing a correction. An unknown exclusion boundary holds historical backfill for that user; new eligible memory remains independent. Under that hold, an older review-only edit with no linked replacement needs an exact active and unexpired item in the same current scope and reset generation before it can carry over. If that support is absent, pre-cutover verification rejects the previous checkpoint and repeating prepare reconciles any previously staged source through the normal cleanup jobs. A later genuinely new assertion is not a permanent topic ban.

Preparation captures a full content/action/control fingerprint. Repeat preparation to catch persisted chat edits/deletes, new chats and legacy choices. Same-ID text changes without a trustworthy original edit event are reported as exceptions; import time is never asserted as the edit date. During final cutover, SQLite's write transaction is the brief ingestion barrier: source/action changes serialized before the switch invalidate verification, and later live turns use native authority. Native late results remain subject to epoch/source/control fences.

## Per-user quality comparison

For each authorized migration, record the legacy Memory baseline before cutover and repeat the benchmark against replacement Memory after cutover. Use the same questions, expected evidence and scoring criteria for that user. Check factual recall, currentness, attribution and correct omission. Blind the scorer to the Memory implementation and report gains, regressions, inconclusive cases and sample size per user. An aggregate can supplement the individual results.

Keep each benchmark within that user's authorized personal and project scopes. Apply their consent and every source exclusion to both runs. Omit any case that becomes ineligible between runs and record the count and reason. Keep raw evidence in restricted, user-scoped storage and use no data from other users. This procedure requires authorization before it is run on real accounts.

## Synthetic rehearsal

Use only an isolated migrated SQLite fixture in the system temporary directory, with a `.alfyai-memory-synthetic` marker containing `alfyai-memory-synthetic-v1` beside it, and only `@test.invalid` accounts. Pass `--synthetic-fixture yes`. Synthetic mode bypasses the production operator acknowledgement, never the source/consent/epoch/cutover checks. Real-mode flag parsing and execution are also tested against a temporary synthetic database, never a real account database.

`migration.integration.test.ts` runs actual SQLite migrations and the existing job engine. Its native HTTP and curation fixtures are deterministic and explicitly do **not** prove native semantic accuracy. Real pinned-native EN/HU acceptance, throughput, backup/restore and independent review remain separate full-replacement gates.

## Rollback retention

Retain permitted legacy data for at most the 30-day rollback window recorded at cutover, subject to normal user erasure/deletion immediately. No automatic purge is implemented or authorized by this tooling. At expiry, an operator must review the retention/acceptance record and explicitly authorize disposal or document a bounded extension; this is not permission for indefinite retention. Do not restore a backup without preserving newer reset/revocation/control records. A blocked rollback requires resolution of the newer privacy state; it must not be bypassed by changing `authority` manually.

## New-account rollout

`HINDSIGHT_NEW_ACCOUNTS_ENABLED` defaults false and is separate from worker pause. With an authorized rollout configuration, only genuine new account creation receives native authority and an opaque tenant/known interval atomically. Existing accounts are unchanged. A missing/offline native service leaves the new account native and unavailable/pending; account creation itself performs no network request and never silently falls back to legacy. Use the normal application environment/configuration when invoking the CLI; it does not choose an implicit database or grant historical permission.

## Owner-approved review of a held cohort

The optional review worker defaults off. It requires the server-side `HINDSIGHT_QUARANTINE_ENABLED` flag and the pinned native dry-run extraction capability. The historical Include decision alone starts no review. A separately authorized operator identifies a fixed prepared manifest and verifies the exact owner identity, consent cutoff and canonical sorted held-source ID digest before granting access. The grant requires `--mode authorize-review --manifest ID --authorization-file FILE` alongside the existing per-user execution acknowledgement. The absolute owner-private file contains `userId`, `email`, `manifestId`, `cutoff`, `cohortHash`, `cohortCount`, the exact serialized `manifestHash`, a reviewed `deniedSourceIds` array and the resulting `allowedCohortHash`. Both cohort hashes are SHA-256 of the JSON-encoded sorted IDs. Prepare the receipt from the named, reviewed cohort. Keep it and any evidence off public logs and out of source control.

The owner can then explicitly start review. Only the exact currently eligible authored source goes through pinned dry-run extraction, with no preceding chat context. Known linked withdrawals, revisions requiring native curation replay, explicit known excluded wording, and changed source, project or consent checks hold the source before dispatch. Native dry-run does not retain facts, create embeddings, or publish Memory. SQLite drafts are accessible only through the owner's review API. Any explicit Keep or Edit and keep is a new owner-authored assertion in its original scope, dated at approval. The original source assertion date remains provenance. During preparation the approved action goes to the inactive native target and becomes available to chats after cutover. Discard stores a content-free decision. Restore holds, rollbacks, Clear Memory, Clear Workspace and account erasure remove the review grant and its drafts. Chat ownership and scope moves scrub affected draft content and detach obsolete approval provenance. The ordinary account archive excludes the grant and pending drafts.

Known text matching is conservative and cannot establish the semantic equivalence of unidentified or paraphrased historical material. Confirm the scope of consent for processing the held cohort before enabling it. Keep all withheld sources whose known exclusion cannot be resolved before inference outside that reviewed grant.

### Recover completed retains in an inactive bank

If several completed retains are present in the same inactive bank, a source job can fail publication because other sources in that snapshot have yet to be admitted. Keep the account in Preparing under legacy authority. Stop its scoped worker between completed attempts, preserve the SQLite and native backup, and verify the target account, current manifest and bank. The global Memory worker and new-account enrollment must be paused. No other operator may write that bank while the recovery runs.

```bash
node --import tsx scripts/memory-backfill.ts --mode recover-retained \
  --database /explicit/database.db --user USER_ID --manifest MANIFEST_ID \
  --bank BANK_ID --execute yes --operator-ack approved-per-user-migration
```

This operation reads the native bank without retaining any source again. It requires settled native operations and an unchanged manifest, and checks the current eligibility, scope and withdrawal state of every recovered source. Any unknown raw or observation support, or any change to the text or support of a previously published observation, blocks publication. Preserve the legacy serving state in that case.

The recovered sources enter one application generation. Failed checkpoint jobs are reopened through the job engine, which verifies their admitted native facts before completing them. Drain only the exact account's jobs. Run normal migration verification and scope recall checks before completing cutover. A successful recovery command alone does not make the account ready.

If an earlier attempt changed a previously approved observation, first establish the exact unpublished contributing source revisions in that bank. Use a protected operator receipt containing the account, manifest, bank, current manifest SHA-256 and exact contributor source IDs. `rewind-unpublished` requires that receipt through `--authorization-file`, in addition to the same explicit account, database, manifest, bank and execution arguments. Pause the account's worker and preserve a paired backup before starting.

The command invalidates only the old, unpublished source revisions. It removes those exact native documents and verifies that all existing published wording, support and dates return, allowing a regenerated native ID only when the full match is unique. All original eligible sources remain in the ordinary migration inventory and may be retained again with new immutable operation IDs. During this operation, the bank's new delivery is fenced by its manifest. If the operation is interrupted, rerun the same scoped command with the same receipt. If a user withdraws a source in the interim, verify the current controls and prioritize the canonical privacy cleanup. The rewind cannot authorize the changed observation or cut the account over.

A protected receipt may specify `holdCorrectionConflict: true` for an older source whose native facts changed the wording of a later authenticated authored observation in the same bank. This requires a strict date order, original scope, and complete raw support proof. A source with an independent native fact or observation cannot be held through this path. The resulting `held_conflict_with_later_correction` disposition is scoped to that original message, body hash, assertion date and scope. It records why the source could not be migrated safely. The original conversation remains available through ordinary authorized chat history, and the hold does not resolve any user review or record successful delivery.

During preparation, older ordinary history may corroborate a generated observation of a plain authored statement without an operator step, but only while the observation's published support is the statement's own facts. The observation must keep its native ID, its shown wording and its facts. Its native text may differ only by Hindsight's dated notes made from the facts the job adds; a note made from any other fact is a rewording and fails closed. Each fact the job adds must come from that job's own default-history chat, which must be older than the statement. The chat's fact may also form an observation of its own, or appear only inside the statement's row; the owner extended the rule to the second case on 21 November 2026, after a chat of Zsombor's merged into a statement that way. Such a note is Hindsight's record of an earlier state, so the older chat may have said something different. The note stays in the native text used for matching and is never shown, and the chat's words then appear only as the row's source quote, not as a memory of their own. Exact pinned edits, their exact-wording companions, explicit edits and statements tied to an edit or removal stay exact. The row is published with its native support, so the Memory page lists the older chat as a second source and shows no single date, and removing the row removes both facts; where the chat also has a row of its own, removing either hides both until Memory rebuilds them. If the statement itself is withdrawn during preparation, Hindsight rebuilds the chat's fact on its own. Where that fact had no row of its own, the source cleanup cannot verify the rebuild: it waits (three attempts, then failed) until another delivery publishes it, so the account may stay on legacy Memory until an operator acts. A row that already carries chat evidence stays exact, so a second corroboration or a dropped link fails closed for an operator. Deleting a document makes Hindsight delete every observation that cites one of its facts and consolidate the surviving facts afresh, so withdrawing a corroborating chat during preparation hides the row and Hindsight rebuilds the statement from its own facts. When no other row presents the statement, the next job publishes that rebuilt row in Hindsight's new wording, which is the owner's accepted "hidden until Memory rebuilds it". When another row still presents it, the source cleanup cannot prove an exact restore and later history fails closed, so the account stays on legacy Memory. No tool settles that state yet, and the same is true for any chat whose evidence shares a row with an authored or edited fact. The owner chose this on 21 November 2026.

A preparation that published an account's authored statements before its older history (for example when the history was held at the first prepare and included later) can be started over with `--mode restart-preparation`. It needs a protected receipt `{userId, manifestId, manifestHash, restartPreparation: true}` naming the current manifest by the SHA-256 of its manifest JSON, plus the usual execution acknowledgement. It refuses unless the account is active and still preparing, the manifest is still preparing or failed (never prepared or cut over), no rewind or cutover is recorded, nothing of the account or its tenant is running, and the epoch holds no quarantine review and no action the new epoch cannot rebuild (anything but the migration's own actions and resent chat edits). In one atomic step it moves the account to a fresh epoch, marks the old manifest `restarted`, carries the old epoch's chat scope moves and its held-history boundary forward, and queues a `restart-erase:<bank>` cleanup job for each old Hindsight bank. The reset generation, legacy Memory and the person's controls stay as they were, and the person's cleanup status leaves those jobs out. It then cancels the old epoch's queued jobs (they stay as a record) and runs one prepare, which queues history before authored statements, and in which correction holds and edit exceptions keep applying. If it stops after the atomic step, rerunning it with the same receipt resumes; once the new epoch has its manifest the receipt is spent. The cleanup jobs belong to the account's tenant, so the scoped workers and the account drain do not run them: before draining, run each `restart-erase:<bank>` job through the job engine and confirm the old bank is gone. Verify is not ready until they have succeeded. A later erasure queues its own `erase:` job for the same bank; whichever runs second succeeds without native calls once the other has. A restart cleanup that can never succeed keeps the account from cutting over, which fails closed. History first is only queue order: drain with an operator drain that claims the account's jobs in queue order and finishes a source in retry backoff before any other (the production rollout tooling's per-account drain does), and stop at the first history failure so that no statement runs ahead of an older chat. Known limits: each restart copies the account's scope moves, so the data archive lists them once per epoch. Take a paired backup first. Owner's decision, 21 November 2026, for Zsombor's account.

An unlocated removal (a dated legacy edit or removal whose provenance names a chat that no longer exists, so its inventory action lists no source and carries a `missing_source` exception) can only be checked by its literal wording, so the boundary refuses every default-history chat that would change a published row. The owner can have it checked by meaning instead (owner's decision for sales, 21 November 2026). `inspect` lists the approvable action IDs as `unlocatedRemovals` and approved ones as `approvedUnlocatedRemovals` (content-free). `--mode approve-unlocated-curation` needs a protected receipt `{userId, manifestId, manifestHash, approveUnlocatedCuration: true, actionIds}` naming the current manifest by the SHA-256 of its manifest JSON, under the same file checks and execution acknowledgement as a restart. It refuses unless the account is active and preparing, the manifest belongs to the current epoch and is preparing, failed or prepared, no rewind or cutover is recorded, and every ID is a current unlocated edit or removal with a date and something to forget. The checkpoint keeps the IDs in `migrationCurateUnlocated`, with the epoch of the last new one in `migrationCurateUnlocatedEpoch`; approvals only accumulate, and a restart carries them. From the next prepare, each eligible default-history chat in the removal's scope (every scope when it has none) gets a `migration_remove` action that lists only that chat, so its delivery runs the curation forget step (plan, apply with its own review, then the final review) on that chat's facts before it publishes. A review that refuses or cannot answer fails the job, and nothing publishes. Before each edit, the step saves on its action the chat's facts as they were and the facts the edit is to leave, and withdraws any earlier pass; a passed final review is recorded for that revision. A transient failure after an edit (Hindsight briefly unavailable, a slow consolidation, capture or repair, the review model not answering) is retried: if the chat's facts are still as they were, the step runs again, and if they are as the saved edit left them, it goes on without editing again, its final review comparing the result with the saved facts. A refused final review fails for good, even when another source's repair replay in the same delivery caused it, and so does an attempt that finds the facts neither as they were nor as the edit left them, a partial edit say (`memory_meaning_check_interrupted`): report it to the owner and do not retry it by hand. A chat that failed for good holds its bank, since its retained facts keep later publications there from being accepted; in preparing, the remedy is a restart. Verify counts accepted chats without a passed check (`meaningCheckMissing`) and is not ready while there are any, a delivery of an accepted chat without one fails with `memory_meaning_check_missing`, and `recover-retained`, `repair-selective-retain` and the recovery at the end of `rewind-unpublished` refuse such chats. An approved removal keeps holding these recovery tools back: it no longer carries its `missing_source` exception, so a plain rewind in its scope takes `matchPlainMigrationRewind`'s strictest branch (a reviewed merge is refused, and every published row must come back exactly or as an exact companion). This fails closed; restart the preparation instead. Such a chat may then change published rows, and so may authored statements and explicitly included chats; a default-history chat whose own delivery did not run that step is still held to exact reconnection, and the removal's literal wording stays refused at every publication and at cutover. Chats published before the approval only ever had the wording check, and a prepare does not deliver them again: verify reports `curationSweepPending` and stays not ready until the account runs in an epoch that began after the approval. So approve, then restart the preparation as above (a prepared manifest needs one prepare first, which returns it to preparing; seal the restart receipt after that prepare), run the restart's cleanup jobs and drain; approving another removal later needs another restart. An approved account is not cut over yet: `cutover` refuses with `memory_migration_cutover_curation_unsupported` while any approval is recorded, though verify still reports whether the account would be ready and whether the sweep is pending. The owner may accept that risk for one account: `cutoverMemoryMigration(userId, id, { acceptApprovedCuration: true })`, or `--mode cutover --accept-approved-curation yes`, skips only that refusal (readiness and every other check stay). The owner chose this for sales on 22 November 2026, after its sweep finished ready. On such a live account a `prepare` (the live take-up of held imported chats, a history choice made by an operator) refuses unless the owner accepts it the same way: a forget step that fails there would hold the bank with no remedy. Nothing yet withdraws and holds a chat whose forget step fails on a live account, and that chat's retained facts would make every later publication in its bank fail (`memory_candidate_unaccepted`), the person's own turns included, with neither a restart nor a recovery available there. The ChatGPT import and maintenance still leave an imported older chat in an approved removal's scope owed, as a safeguard; on a live approved account, `prepare` refuses with `memory_migration_live_curation_prepare_refused` unless the owner passes `--accept-approved-curation yes` for that run. Each covered chat costs four to six more calls to the local model per approved removal, and one more consolidation round. Both follow-ups are still open for a live approved account: withdrawing and holding a chat whose forget step failed for good (the owner's call), and giving the new-assertion check fresh evidence on the live path.
