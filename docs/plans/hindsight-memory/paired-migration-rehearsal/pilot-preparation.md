# Owner-only paired pilot

Production smoke and the owner's authorization for the pilot must both be confirmed before accessing the account. The selector is the exact stored email the owner approved. Keep that selector out of repository evidence. A read-only identity lookup returns only the immutable application user ID for that exact email. Require one match, record the authorized ID privately, and require both values to match again at each later step. Do not search names, roles, email prefixes, or alternate accounts if this fails.

1. Inspect the selected user's migration eligibility before prepare. Keep existing consent, reset, incognito, deletion, Do Not Remember, and project boundaries in force. Unknown sources are outside the benchmark unless the owner's recorded history choice makes them eligible. Never use another account's records as a negative control. An unverified legacy preference or summary can be withheld from evaluation without granting access to its supporting chats.
2. Freeze questions, independently supported expected answers, scope, source references and timestamps, scoring rules, provider/model, answer instruction and sampling parameters. Include visible currentness, ownership, project boundaries and unknown questions. Freeze this material before generating baseline answers. Use only eligible evidence snapshots to grade, and mark an affected pair ineligible if a boundary changes. Retain raw questions, evidence and answers privately on the authorized host. The report contains counts, outcomes and a fixture hash rather than owner details.
3. Run the legacy phase before the first prepare or authority change. The legacy reader performs housekeeping and records prompt-use telemetry. Run the actual reader on an isolated, single-owner mirror where those statements are rolled back. Read the source on a read-only connection in one consistent snapshot with exact owner predicates and a field/table allowlist. Do not copy the production database, password hashes, unrelated accounts, or unneeded conversation content. Minimum legacy inputs are that user's recall controls, scope identity, projection state, current eligible projection items, and matching semantic embeddings when used. Use existing owned IDs for the question scopes; any empty synthetic probe context belongs only in the mirror. Withhold any summary that cannot be tied to eligible facts. If the mirror cannot be made without changing the evidence semantics or bypassing exclusions, stop before preparing the owner.
4. After separately authorized migration and verification, repeat the frozen questions through the replacement reader under unchanged scope. Reverify the cutover generation, source fences and eligibility before using native recall. Use an owner-scoped mirror for any rollback of reader housekeeping. A changed authorization or source exclusion blocks the affected probe. Do not write probes to chats, learning tables, or the production analytics ledger.
5. Keep the identity mapping and raw evidence private. Have a scorer assess randomized answer labels against frozen gold before revealing the implementation key. Compare factual correctness, currentness, attribution and omission, including gained, lost and inconclusive pairs. Report sample size and prove that the probe questions produced no durable application or native changes.

The synthetic rehearsal exercises rollback around the actual reader on a dedicated single-account database. It does not establish that a real pilot mirror exists or that the owner's legacy profile has any eligible facts. A genuinely empty legacy view is a baseline outcome.
