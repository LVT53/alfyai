# Owner-only paired pilot

Production smoke and the owner's authorization for the pilot must both be confirmed before accessing the account. The selector is the exact stored email the owner approved. Keep that selector out of repository evidence. A read-only identity lookup returns only the immutable application user ID for that exact email. Require one match, record the authorized ID privately, and require both values to match again at each later step. Do not search names, roles, email prefixes, or alternate accounts if this fails.

1. Inspect the selected user's migration eligibility before prepare. Keep existing consent, reset, incognito, deletion, Do Not Remember, and project boundaries in force. Unknown sources are outside the benchmark unless the owner's recorded history choice makes them eligible. Never use another account's records as a negative control. An unverified legacy preference or summary can be withheld from evaluation without granting access to its supporting chats.
2. Freeze questions, independently supported expected answers, scope, source references and timestamps, scoring rules, provider/model, answer instruction and sampling parameters. Include visible currentness, ownership, project boundaries and unknown questions. Freeze this material before generating baseline answers. Use only eligible evidence snapshots to grade, and mark an affected pair ineligible if a boundary changes. Retain raw questions, evidence and answers privately on the authorized host. The report contains counts, outcomes and a fixture hash rather than owner details.
3. Run the legacy phase before the first prepare or authority change. The legacy reader performs housekeeping and records prompt-use telemetry. Run the actual reader on an isolated, single-owner mirror where those statements are rolled back. Read the source on a read-only connection in one consistent snapshot with exact owner predicates and a field/table allowlist. Do not copy the production database, password hashes, unrelated accounts, or unneeded conversation content. Minimum legacy inputs are that user's recall controls, scope identity, projection state, current eligible projection items, and matching semantic embeddings when used. Use existing owned IDs for the question scopes; any empty synthetic probe context belongs only in the mirror. Withhold any summary that cannot be tied to eligible facts. If the mirror cannot be made without changing the evidence semantics or bypassing exclusions, stop before preparing the owner.
4. After separately authorized migration and verification, repeat the frozen questions through the replacement reader under unchanged scope. Reverify the cutover generation, source fences and eligibility before using native recall. Use an owner-scoped mirror for any rollback of reader housekeeping. A changed authorization or source exclusion blocks the affected probe. Do not write probes to chats, learning tables, or the production analytics ledger.
5. Keep the identity mapping and raw evidence private. Have a scorer assess randomized answer labels against frozen gold before revealing the implementation key. Compare factual correctness, currentness, attribution and omission, including gained, lost and inconclusive pairs. Report sample size and prove that the probe questions produced no durable application or native changes.

The synthetic rehearsal exercises rollback around the actual reader on a dedicated single-account database. It does not establish that a real pilot mirror exists or that the owner's legacy profile has any eligible facts. A genuinely empty legacy view is a baseline outcome.

## Baseline harness

`owner-baseline-shape.cjs` accepts only an exact email and previously verified immutable ID on stdin. It opens the maintained database read-only in a deferred snapshot, returns a status alone, and reads neither statements nor chats. This probe is separate from the benchmark.

`owner-legacy-mirror.ts` accepts the exact identity and frozen question scopes in a dedicated process with `DATABASE_PATH=:memory:`. It opens the source read-only and closes it before the application reader runs. The source projection and authorization must prove the whole evaluated legacy profile admissible. The mirror admits at most 12 persistent current facts, with exact owner and project scope, original unedited conversation provenance and an exact stored quote and verbatim statement present in the same eligible authored message. It checks the supporting conversations for ineligible, imported, or uncertain authored context and uses the application's historical eligibility policy. A summary, unverified paraphrases, unknown provenance, unresolved edits or withdrawals, or a potential semantic shortlist holds the baseline. The mirror does not guess facts or report blocked projections as empty. It copies admissible statements and the minimal scoped shell to an in-memory database, runs the existing persona reader, and rolls back per-probe housekeeping. Compile or load the module only from the verified release with its migrations. The export returns private data to its in-process caller. Keep it out of stdout and logs. Pass its synchronous checkpoint verifier to the private transport for each dispatch. It repeats eligibility and compares the active authorized projection against the original snapshot. A change holds the run.

`private-answer-transport.cjs` sends only to the exact canonical private IPv4 endpoint recorded in the owner-private frozen run file, after it is independently checked against the selected provider's approved address and model. It uses a direct HTTP agent, no proxies, redirects, DNS or fallback, and the fixed Qwen request settings used in the rehearsal. Keep the API key out of the run file and pass it only in process. The synthetic transport check uses a loopback mock and fake key. Run the mirror check from the release root with `node --import tsx docs/plans/hindsight-memory/paired-migration-rehearsal/verify-owner-legacy-mirror.mts`. It uses a disposable fully migrated database and compares both scopes byte-for-byte against the actual legacy reader on a copy of that synthetic database.

## Freeze and scoring

Before baseline inference, freeze the UTC cutoff and a 90-day window ending at that cutoff. Source eligibility, reset, and consent can shorten that window. The cutoff freezes scoring rather than allowing older or excluded facts to enter by default. Record an as-of timestamp, independently supported gold, and an immutable source reference for every positive question. Select up to 12 short cases, allowing fewer if the eligible pool is small. Include personal current facts, then project-specific facts with an authorized personal-scope contrast where available, precise ownership, and unknowns against similar entities. Freeze language where it reflects actual use. Record uncovered strata rather than manufacturing eligible evidence.

An earlier-only fact is scored separately through explicitly authorized retained-chat search with historical attribution. Record the observed time and original eligible chat, require attribution as of that conversation, and omit those cases from current-persona denominators. An unknown current question about an earlier-only fact stays in the current stratum and must not promote the earlier value. Run unchanged cases after cutover and revalidate their scope and eligibility. Cases affected by a consent, deletion, reset, move or factual change are ineligible in both arms. Blind cross-arm labels and report each stratum's admitted count, blocked count, accuracy, privacy failures, and gained/lost outcomes. The retrospective cohort must be marked unmeasured if a paired authorized historical reader was unavailable.
