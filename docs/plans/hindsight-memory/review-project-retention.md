## Initial findings

## P1 · Project deletion can publish older project chat text as personal Memory

`deleteProject` clears the project assignment on the remaining conversations in its owned write transaction. The ordinary move path records a scope edge there. The delete path omits the edge. Bank retirement protects the old bank, when one exists. With an unlearned source, the historical scope lookup has neither a prior source nor a move to consult and starts and finishes at the new personal scope. This also makes the project data eligible as historical context in that scope. [Project deletion](../../../src/lib/server/services/projects.ts#L399) · [Ordinary scope change](../../../src/lib/server/services/memory-profile/chat-delivery.ts#L439) · [Scope lookup](../../../src/lib/server/services/memory-profile/scope-history.ts#L40) · [Historical candidate selection](../../../src/lib/server/services/memory-profile/migration-progress.ts#L574) · [Source staging](../../../src/lib/server/services/memory-profile/migration.ts#L234)

Reproduced by creating a synthetic chat with an older project message, then calling the owned `deleteProject` service before any Memory account or source exists. Choose Include history, inspect, prepare and drain the actual job engine. The old message is classified `eligible`. The captured retain call sends “My bicycle is blue. My dog is Rex.” to the personal bank. After synthetic cutover, both resulting facts are visible through the application's publication reader. A new personal message created in the same chat after deletion publishes normally through live intake. A second inspect and prepare still classify the older message as eligible and leave both old facts published alongside the new personal one.

Record the project-to-personal scope edge in the owned project deletion transaction for each detached conversation, including accounts without a bank. Verify that the earlier project message stays out of personal retain, context and publication while a new personal turn still learns normally.

## P2 · Repeated Include can revoke an accepted source on return to its original project

Preparation preserves a learned imported source when its old bank differs from the conversation’s current scope and the text remains eligible. Once the conversation returns to that bank, the accepted revision goes through the generic stale-delivery check. An off/on cycle advances the account’s control revision. Even after Memory is back on and historical permission still covers the assertion, the revision mismatch revokes the accepted source and the reuse check selects a new one. [Learned-source exception and revocation](../../../src/lib/server/services/memory-profile/migration.ts#L156) · [Prepared source reuse](../../../src/lib/server/services/memory-profile/migration.ts#L275) · [Control revision](../../../src/lib/server/services/memory-profile/migration-policy.ts#L221)

Reproduced by learning an imported assertion in A and cutting over the synthetic account, moving A → personal → B, switching Memory off and on, and preparing in B. The original accepted revision still exists. Move the chat back to A and save Include with a new request ID. Preparation changes the original revision to `revoked` and its two facts disappear immediately from the application's publication reader. Draining the engine submits the unchanged assertion under a second native document ID. Both retains carry the original 2020-01-01 assertion date. The failure concerns revocation and duplicate learning despite unchanged text and permission.

Preserve and reuse an eligible accepted project source in its own bank through preparation even when the control revision has advanced. Keep the current control fence for unaccepted delivery and enforce actual source deletion, import withdrawal, project erasure and reset.
