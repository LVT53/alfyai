# Preparing inactive Memory banks before deployment

**Blocked while the old app serves the account.** The owner’s conditional authorization for 19 November 2026 at 05:00 Europe/Dublin covered per-user inspection, preparation and verification after implementation, acceptance and independent review. The old app can acknowledge privacy changes that the migration worker cannot reconstruct or enforce. Meeting the time condition would still leave that blocker in place. A compatible application rollout requires separate authorization.

## Synthetic evidence

The probe used Node 22.23.2, a temporary SQLite database with the candidate migrations, `@test.invalid` accounts and a second database connection writing the same persisted fields as the old app. It ran `refreshConfig()` and the actual Memory job engine with only `memoryDeliveryJob` registered. The Node HTTP boundary was replaced in-process with a deterministic Hindsight wire fixture. The probe exercised dispatch and publication with no application listener, socket, native service, production connection or real content.

| Mutation after preparation | Source dispatch and manifest verification |
| --- | --- |
| Turn Memory off, write a chat message, then turn it back on using the old preference update | The open enabled interval created by `prepare` covered the entire gap. Inventory excluded the message while Memory was off and marked it eligible after re-enable. A repeat `prepare` queued it, native `retain` received it in the fixture, and `verify` returned `ready: true`. There was no recorded off interval. |
| Persist a legacy suppression and a `do_not_remember` review resolution after enqueue | The old mutation created no native action or revocation. `verify` returned `changed: true`. The queued source passed its final fence, sent the original statement in `retain`, and the delivery succeeded. The manifest stayed unready. Repeating preparation can reconcile a changed manifest, after the earlier dispatch has already occurred. |
| Switch Memory off and leave it off, advance the legacy reset generation, edit or delete the persisted message, set incognito, or move a pending chat to another project | Each still-current mutation failed the immediate source fence and made `verify` report `changed: true`. Those fences protect future dispatch. The old app does not enqueue cleanup for already-submitted content. |
| Delete the user after a successful retain | Foreign-key cascades removed the account, bank binding, source revisions and manifest. One orphaned delivery row remained, with zero cleanup jobs. The fixture still held the native fact. The old account-deletion path has no tenant erasure handoff. |

The old preferences route updates `users.memory_enabled` and `updated_at`. The next version’s `assertMemorySourceCurrent()` checks the current flag, reset date, message identity and hash, current scope and stored eligibility controls. The checks for chat-derived sources do not read fresh legacy item and review decisions at dispatch. `verifyMemoryMigration()` hashes the current persisted records and guards later activation. It cannot recover an elapsed off period with no record or prevent an earlier send. Stopping the worker and running a fresh `verify` before each batch still leaves the old app able to erase an enrolled account and discard the bank bindings. ## What the replacement changes while accounts retain legacy authority

- The preferences route calls `setMemoryEnabled()`, which transactionally records the interval, advances the control revision and queues cleanup for pending sources. Account erasure, workspace reset and Memory reset establish an epoch fence and a durable cleanup handoff before completing local erasure. Conversation and message deletion and project removal use native revocation paths. [Memory controls](../../../src/lib/server/services/memory-profile/migration-policy.ts) · [Account lifecycle](../../../src/lib/server/services/account-lifecycle/index.ts) · [Source cleanup and scope moves](../../../src/lib/server/services/memory-profile/chat-delivery.ts)
- The current public Memory actions route calls `submitMemoryAction()`. The synthetic probe confirmed that a valid removal request for a preparing account receives `409 memory_not_ready`. The item route is GET-only. The old `applyKnowledgeMemoryAction()` compatibility service has no production route callers in this tree. The replacement temporarily withholds public profile editing and removal until native authority. The legacy chat reader and the legacy `/remember` add path can still run during preparation. The worker should start only after old app instances and in-flight legacy handlers have drained. [Action route](../../../src/routes/api/knowledge/memory/actions/+server.ts) · [Item route](../../../src/routes/api/knowledge/memory/%5BitemId%5D/+server.ts) · [Action authority check](../../../src/lib/server/services/memory-profile/curation-actions.ts)

The smallest path supported by the existing design is a separately authorized compatible rollout, keeping existing accounts on legacy authority and `HINDSIGHT_NEW_ACCOUNTS_ENABLED=false`, followed by per-user preparation with the existing job engine. The deployment needs to account for the temporary curation availability change. Running a standalone worker against the old app does not supply the missing privacy writes. A new queue or periodic comparison would leave the lost-history and account-erasure cases open.

## Counts-only inspection

If the owner authorizes counts while the old app is still live, use the `inspect` CLI on a restricted, integrity-checked SQLite snapshot prepared to the final reviewed schema in isolation. The current CLI queries native control and manifest tables, so it needs that schema to run. The command opens a normal writable WAL connection and its read transactions acquire the SQLite writer reservation. Running it on an isolated snapshot keeps that overhead and schema preparation away from the live app. Use one explicitly approved account and record only counts, with no extraction, source material, credential logging or persistent unapproved copies. This is an inventory of the captured snapshot. It does not establish native readiness.
