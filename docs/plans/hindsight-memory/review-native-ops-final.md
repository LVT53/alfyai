## Private transport

The native client and the curation SDK's production fetch adapter both use the direct transport. The configured base is checked before the native capability request. Curation checks its exact gateway path before sending and still runs its last dispatch fence after address resolution and body preparation. The direct transport supplies explicit HTTP(S) agents, refuses redirect responses and connects approved aliases to a checked literal address. Its original Host header survives alias resolution. The focused DNS test verified that a mixed public/private result stops before dispatch. [Private transport](../../../src/lib/server/services/memory-profile/private-endpoint.ts#L60), [Native call site](../../../src/lib/server/services/memory-profile/hindsight-client.ts#L75), [Curation call site](../../../src/lib/server/services/memory-profile/curation.ts#L121), [Node proxy documentation](https://nodejs.org/learn/http/enterprise-network-configuration)

An added loopback probe used real HTTP and HTTPS listeners under the proxy flag. A stale dispatch fence, an already aborted request, and an abort from inside an asynchronous fence produced zero unintended requests. A 100 ms deadline while reading a partial HTTP body rejected and closed the listener's socket. A trusted certificate for the literal IP completed, while an untrusted certificate and a trusted certificate for the wrong IP failed before an HTTP request. The probe measured zero ambient proxy connections. Alias lookup through the OS can finish after the requested deadline. The transport checks the signal again before selecting an address or dispatching credentials, so the expired lookup cannot send a request. [Node DNS lookup](https://nodejs.org/api/dns.html#dnspromiseslookuphostname-options), [Node TLS identity check](https://nodejs.org/api/tls.html#tlscheckserveridentityhostname-cert)

## Bank configuration and erasure

The attempt persists the endpoint, credential hash and pending marker inside the job and account fences before dispatching its only configuration PATCH. Both first provisioning and first deliberate Add use the same arrangement. Retries of a pending binding do a readback. Reset captures the same binding and the pending marker in its opaque cleanup job inside the reset transaction. Cleanup holds through absence or mismatched configuration, records settlement before deleting, and checks for absence after the bound DELETE. Older bound rows with no version carry a different marker because a committed result cannot account for all their former metadata writes. The focused test observed no native calls for that legacy case. [Configuration checkpoint](../../../src/lib/server/services/memory-profile/bank-configuration.ts#L28), [Reset intent](../../../src/lib/server/services/memory-profile/delivery-job.ts#L215), [Cleanup worker](../../../src/lib/server/services/memory-profile/delivery-runner.ts#L151)

I reran the job-engine cases for a late commit after reset, exhausted retries after a lost submission, and older unversioned bindings. The late-commit case verified one PATCH, one eventual DELETE and zero POSTs capable of retaining user text. The lost-submission case exhausted bounded retries without a second PATCH and carried its pending marker into reset. These cases use the actual job engine and migrated SQLite with a simulated native transport. Separately, a fresh scratch PostgreSQL database running the pinned native commit `9fb28dbd724dc1ce4da7cb4c49008e601db76c5f` started with the synthetic bank absent. The real app client sent one PATCH and a loopback relay withheld the server's HTTP 200 from that client. A fresh authenticated client verified the exact expected configuration, deleted the bank, and confirmed absence. The delay between native creation and config persistence was exercised by the SQLite job test's synthetic transport. [Job integration cases](../../../src/lib/server/services/memory-profile/delivery-job.integration.test.ts#L573), [Native commit pin](../../../deploy/hindsight/engine-commit)

An intent may require operator reconciliation when the client loses the write before native dispatch, the write fails without laying down exact configuration, or an older row has no receipt. After bounded retries it can remain failed and retryable. The runbook requires quiescing and verifying the original bound service before recording completion. A 404 alone cannot settle an ambiguous write. [Pending configuration runbook](../../../deploy/hindsight/README.md#pending-bank-configuration)
