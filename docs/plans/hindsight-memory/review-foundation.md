## Findings

1. **P1 · Every nonempty native recall response takes the failure path.** `src/lib/server/services/memory-profile/hindsight-client.ts:30,193` requires the list field `fact_type` on recall results. The pinned `hindsight-api-slim/hindsight_api/api/http.py:751–752` returns `type`. A concrete probe with `{results:[{id:"o",text:"Kayak",type:"observation"}]}` threw `native_format_unsupported`. The integration catches it and loses native relevance ranking on every successful nonempty query. Decode list and recall separately. Validate observation type, ID and text, preserve the exact published match, and exercise a saved native recall response through the actual client and chat read path.

2. **P1 · A completed operation can publish an incomplete or duplicated bank as ready.** `delivery-runner.ts:149–160`, `hindsight-client.ts:174–184`, `publication.ts:117,164–175`. Native consolidation can enqueue another round at `engine/consolidation/consolidator.py:2486`. Individual permanently failed facts carry `consolidation_failed_at`; list rows expose pending/failed state. Waiting for one ID proves neither a drained bank nor successful consolidation of all relevant facts. Capture ignores the page's total/offset, duplicate IDs and source consolidation markers. Native offset pages can shift while a later round runs. Publishing only validates rows that happen to be present and promotes every staged source in the bank. In a migrated in-memory database, one accepted row became two on a duplicated observation candidate. A subsequent raw-only candidate carrying `consolidation_failed_at` replaced both with zero rows and bank status `ready`. Require bank-wide settlement of relevant native work, reject incomplete/unstable pages, duplicate IDs and relevant pending/failed facts, and scope promotion to the intent that actually passed. Allow legitimate zero-fact extraction with proven completion. Test a follow-on round, deletion/insertion between pages, staged work from another attempt and preservation of the last accepted generation.

3. **P1 · Lost retain acknowledgements can strand a delivery or re-extract it on manual retry.** `delivery-runner.ts:127–146`, `hindsight-client.ts:112–126,140–172`. A process dying after the submitted flag commits but before the POST leaves no remote operation to find. Each automatic retry scans up to 10,000 operations with per-operation payload GETs and eventually fails. Conversely the engine clears a terminal failure's checkpoint at `jobs/ledger.ts:845`; a user retry can send a new native mutation after the first actually succeeded. The pinned native `api/http.py:1465–1472,9864–9879` explicitly accepts an application-supplied UUID `operation_id` for async retain and returns the original operation on replay. Persist that identity with the durable intent outside the disposable attempt checkpoint, resend the same identity, validate the response, and test both sides of the POST, terminal retry and a real restart.

4. **P1 · Source privacy can change before the actual remote write, and cleanup can be permanently suppressed.** `delivery-runner.ts:72–110,123–145,178–195`, `revisions.ts:150–172`. The source is read before asynchronous configuration; the subsequent write fence checks the bank but not the source. Revoking a message while configuration is awaiting a response still permits its stored text to be sent afterward. The later staged-data check only prevents local publication. The same enabled/interval/project checks precede document cleanup. Delete a source with Memory off or after its project disappeared and the worker fails before sending DELETE. The concurrent setting integration also cancels source-cleanup jobs with extraction jobs. A late retain can run after a deletion because a local job leaving running status releases the native bank to another worker. Validate current source, conversation/scope and control authority at the last possible submission boundary. Keep grant revocation immediate. Preserve a separately eligible, idempotent cleanup intent for already-sent data, reconcile outstanding native writes and verify absence after they settle. Test deletion while configuration is blocked, off during an accepted native submission, subsequent bank work, and physical cleanup after the project is gone.

5. **P1 · Reset/erasure has a durable-work gap and can report success against the wrong backend.** `delivery-job.ts:66–101`, `delivery-runner.ts:64–70`, `hindsight-client.ts:82,219–235`. The epoch commits before cancellation, listing banks and enqueuing tombstones. A crash in that gap fences local reads but leaves no recoverable cleanup intent for the old native bank. A bank created in the new epoch during that gap can also be selected for erasure. The tombstone contains no native service binding and uses the current global URL and tenant-key mapping. A URL/key change can send DELETE to a different service or schema and accept a missing bank there as success while the original retains data. Bind cleanup to the provisioned service/tenant identity and retiring epochs. Atomically record the required tombstones and epoch advance with recovery via the job engine, retain in-flight operation identities, and verify cleanup against the bound backend. Exercise partial enqueue/crash, a new post-reset bank, endpoint/credential rotation, native outage and late completion. The existing erasure test's fake DELETE immediately succeeds and does not simulate unavailability.

6. **P1 · Editing one fact renews unrelated old assertions.** `contracts.ts:25–26`, `delivery-runner.ts:138–145`, `publication.ts:140–145`, integration producer `chat-delivery.ts:23–29`. The new payload stamps the entire revised message with the explicit edit time. The configured retain mission omits the source-edit paragraph from the frozen mission actually used by `current-list-followup/common-serial.cjs`. The approved gear fixture changes an orange kayak to green while old decaf wording remains; the later espresso statement must keep its precedence. **Foundation** should persist immutable original text/dates plus a reliable before/after edit-event identity, send the qualified structured native event and use the full frozen mission. **Integration** should supply the real predecessor, original assertion time and explicit edit time, keep still-valid independent evidence admissible, and avoid turning unchanged retries or copied forks into fresh assertions. The tested envelope and native-only changed-claim instructions are at `docs/plans/hindsight-memory/correction-recovery/supersession.cjs:4,10`. Require the frozen EN/HU and project fixtures after forced replay. No application-side fact extractor is needed.

7. **P1 · Stored version and tenant diagnostics do not attest the serving engine.** `delivery-runner.ts:105–122` writes the compile-time pin after a config echo and later compares it only with itself. Restoring a different service, losing its bank, or changing its config after the first delivery bypasses all capability/config checks. `revisions.ts:44–46` creates a random tenant ID and `hindsight-client.ts:214–235` expects its credential in a preexisting environment JSON map. There is no reproducible provisioning/binding path or native isolation/capability test. Supply the pinned deployment definition and a validated provisioning mechanism, check effective config and endpoint/extension identity at startup or binding change, and record observed content-free diagnostics. Verify the actual pinned digest separately from native API version if only the latter is exposed. Exercise two synthetic tenants and projects including wrong-key read, retain, edit, list and delete. A local URL string and an Authorization header assertion do not exercise isolation.

8. **P1 · Local job concurrency does not constrain model concurrency or implement foreground admission.** `delivery-job.ts:15–20` constrains local active jobs per user and globally. `delivery-runner.ts:25–46,149–155` waits inside fixed deadlines after work entered native queues. Native extraction fan-out, follow-on consolidation and abandoned requests outlive those local slots. There is no foreground activity signal, idle-mode switch, downshift or pause. A configured six can remain six during active chats and a limit of one can still produce multiple native inference calls. Implement the durable admission/bounded native request budget measured in `capacity-concurrency-results.md:9,30`, coordinate bank ownership across unresolved remote requests, and measure actual simultaneous model calls, foreground latency, cancellation and recovery using the synthetic fixture service.

9. **P2 · Snapshot storage and work under SQLite's global writer lock scale poorly.** `publication.ts:103–162,185–214`, `presentation.ts:8–17`, `drizzle/1777140000135_hindsight_memory.sql:44–55,138`. Each delivered source copies the entire bank into another generation and retains every earlier copy. A workload accumulating one independent observation per delivery writes 500,500 rows for 1,000 accepted deliveries. Formatting scans every native row again for each observation. This happens inside the synchronous write transaction; the project's database policy acquires the write lock even for the all-source/all-row read transactions. This is a structural count, not measured latency. Prepare indexed suffix lookup and candidate batches outside the activating transaction, preserve a short checked pointer switch, bound retained snapshots with explicit stale-cursor handling, and benchmark representative bank sizes and other SQLite writers. Preserve provenance-backed explicit version history separately.

10. **P2 · Dedupe and control fences lack sufficient identity.** `delivery-job.ts:46–59` always reuses the first job with the same user/request ID, even when bank, epoch, source, or kind differs. `revisions.ts:90–106` accepts a repeated source event with the same text and bank but different lineage, conversation or message. `delivery-runner.ts:75–80` compares second-resolution job and interval times using greater-than-or-equal. An off/on followed by a valid new job within the same second can permanently reject that new delivery. Validate the immutable request/event binding on reuse, track a monotonic control revision at enqueue and require the intended lineage revision at acceptance. Test conflicting reuses, out-of-order completions and same-second control transitions.
