## Retrying an already failed compensation

The withdrawal-aware checker update exposed a different barrier in both saved accounts. The same-request retry and normal enable path reopened the action, but it failed with `memory_dependency_source_missing` before asking the revised checker. The earlier terminal failure had cleared the job checkpoint. The held replacement source still existed in SQLite under the same `dependency:<jobId>:<childId>:restore` event identity and retained its original date. The retry deleted its native document. The rebuild chooses a new row ID for the same event identity after losing the checkpoint. An insert conflict leaves the old held source row in place, so lookup by the newly chosen ID fails. Both app operations remain failed with cleanup pending and unrelated Add returns 409. Neither old schedule appeared in native active facts or admitted recall. ## Reproduce the targeted paths

Use the baseline's synthetic loopback services. Start the Hungarian case under a fresh `ALFYAI_LIFECYCLE_RUN` and run it again with `hu after-replay` for removal and the genuinely new assertion. That phase starts a new app process while the same scratch native API and PostgreSQL stay up. The harness refuses drift between phases by default. The recorded retest allowed only the observed concurrent curation changes and saved the before and after hashes.

A cancellation fixture resumed from its own saved record accepts the invocation `cancel recover`. It resubmits the original action request unchanged and uses the app's enable handler. Use `ALFYAI_LIFECYCLE_CANCEL_OMISSION=true` with a fresh run for the pure-omission draft. The same runner provides native raw and observation records, app publication, list and detail payloads, recovered source times and admitted recall.
