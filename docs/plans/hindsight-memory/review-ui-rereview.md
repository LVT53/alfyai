# Memory UI fixes — independent rereview

**Request changes.** This review checked the revised working tree, including the coordinator, restored visits, real chat navigation, Profile status, introduction, shared guards and tests. An independent Node 22 run of the coordinator, history choice, cleanup, hover and reduced-motion suites passed **96 tests in 5 suites**. The checks below describe remaining observable paths outside those tests. Browser/native acceptance is still outstanding.

## Remaining findings and regression cases

1. **P1 — applied operations repeat navigation on focus.** `KnowledgeMemoryView.svelte:460–478,634` leaves the completed request in `pending` after success. Save an edit, wait for its accepted detail, press Back, then blur and refocus the window. The focus handler polls the completed ID. The list counts as relevant at line 93, so the old completion reopens its detail. Clear the completed request/action before navigation and keep only genuinely outstanding cleanup under observation. Test that focus issues zero further operation GETs and preserves the list. Also cancel an in-flight editor and verify completion refreshes data without reopening a view the user left.
2. **P1 — restored unknown requests can lock all writes indefinitely.** `KnowledgeMemoryView.svelte:480–508,604–615`. Lose a POST that never reached the server, navigate away and restore the visit. The snapshot has only its request identity. Restore sets unknown acknowledgement true and drops the action. A 404 from the owner-only lookup leaves the intent unresolved; both the timer and Check status can only repeat the GET. The global busy check at lines 97–118 disables writes in every scope. Preserve the unresolved identity and safe same-ID recovery, permit ordinary unrelated use, and distinguish an unconfirmed lookup from proof of nonapplication. Test repeated 404s after remount, independent work in another scope, and eventual authoritative acknowledgement with no duplicate mutation.
3. **P1 — a privacy or authorization refusal is shown alongside cached data.** `KnowledgeMemoryView.svelte:240–244,289–306`. Load a project list/detail, revoke access or delete the project elsewhere, then refocus. The list retains prior rows on every HTTP failure; detail retains its previous quotation on 401/403. A detail 404 clears detail but the following failed list request still retains the old rows. Keep last-accepted content on transient processing failures; remove affected cached rows, detail and actionable drafts on authoritative access loss. Exercise both owner denial and a deleted scope after an accepted read.
4. **P1 — optional introduction traps normal use when offline.** `MemoryHistoryImportNotice.svelte:63–80,107`. Open the intro explanation, disconnect, then press Escape or X. Both try to save decline, and only a successful POST closes the dialog. Every available dismissal requires the unreachable server. Close the dialog immediately, retain the unacknowledged decline/its ID and suppress repeat presentation for the visit while reconciling safely. Test a rejected decline POST, keyboard access to the page, no inclusion, and later retry of the same decision. On a cross-tab decision change, a stale open introductory editor should also close once eligibility disappears, rather than overwrite the other tab's decision on dismissal.
5. **P2 — transient chat pagination failure is reported as permanent source loss.** Chat `+page.svelte:3349–3352` swallows page-read failures. `src/lib/client/linked-message-navigation.ts:18` converts a non-advancing page to unavailable. Chat `+page.svelte:2993,3000` tells the user that the message is no longer available and consumes the visit. Also `+page.svelte:3316–3319` shares an in-flight read across chat IDs. Navigate to B's older source before A's slow page returns and B awaits A's promise, then reports B's source unavailable. Keep read identity per chat and distinguish exhausted authorized pagination from a retryable transport failure. Test a first-page failure then successful retry, and links in two conversations with a delayed first response.
6. **P2 — pending and completed privacy cleanup can appear together.** Settings `+page.svelte:1109` writes a permanent pending phrase into the general success strip. `MemoryCleanupStatus.svelte:17–32,62` separately renders pending, then completion; nothing updates the earlier strip. After an online recovery the reader can see both “still pending” and completion. Make one component own the live status and test the full Profile flow through the pending-to-verified transition. A transient GET failure during a pending cleanup also stops its timer unless focus or manual refresh intervenes.
7. **P2 — background refresh stops on one transport failure, and announced retry performs no update.** `KnowledgeMemoryView.svelte:174–183,239–245,661`. While the page reports working, reject the scheduled GET once and leave the tab focused. No later read is scheduled; dismissing the alert leaves “Updating” indefinitely. Also the background failure alert's Retry only fetches the same failed resource again. Continue status reconciliation independently of requests succeeding; if the action merely reads status, label it accordingly or wire the real authorized retry. Exercise recovery without changing focus.
8. **P2 — a restored visit can transiently render the previous scope's page.** `KnowledgeMemoryView.svelte:604–625` changes selected scope and view but never clears `page`. The snapshot restore can target an already-mounted instance (`knowledge/+page.svelte:77–80`). With personal rows already on screen, restore a project and delay its GET. The Personal rows remain under the project label, indefinitely if the load fails. Clear the old page/detail and related feedback on a scope-changing restore before awaiting, and guard post-await scroll/focus against a subsequent navigation.
9. **P3 — focus selector chooses the Back button before the heading.** `KnowledgeMemoryView.svelte:155–158,665`. A CSS selector list returns the first matching node in DOM order. On detail and editor, Back precedes the newly added heading and receives focus instead. Select the explicit heading first with a separate fallback query. Verify activeElement on entry and restoration on Back.
