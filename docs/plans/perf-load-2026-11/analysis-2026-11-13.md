# Why the cold load is slow — chunk and transport analysis

Companion to [report-2026-11-13.md](./report-2026-11-13.md). Written 2026-11-13 against the production
build of `f72474c0d` and the live hosts. Method: read the built client chunks, map the sizes that the
harness measured, and check the live response headers and the host's Apache modules. No app code changed.

## 1. Production serves text assets uncompressed

- `GET https://ai.alfydesign.com/_app/immutable/entry/app.DdsZFkzV.js` → `HTTP/1.1 200`,
  `Content-Length: 233669`, `Content-Type: text/javascript`, **no `Content-Encoding`**, no `Vary`.
- `Server: Apache`. `apache2ctl -M` lists **neither `deflate` nor `brotli`**; no compression conf is enabled
  and no vhost sets an output filter.

So every script, stylesheet and JSON body crosses the wire at raw size. Measured on the built assets:

| asset | raw | gzip −9 |
|---|---|---|
| `chunks/OxTN49w0.js` | 631.3 KB | **162.9 KB** |
| `entry/app.*.js` | 227.8 KB | **74.8 KB** |
| `chunks/Db9P8UnJ.js` | 156.6 KB | **46.6 KB** |

The harness's transfer numbers are therefore *not* inflated by a test-only setting: they are what production
sends. Compressing text at the server is the single largest saving available and needs no app change.

## 2. The biggest landing asset is the i18n catalogue, in both languages

`chunks/OxTN49w0.js` (631 KB raw / 163 KB gzip) is the internationalisation bundle:

- 1,830 keys matching `"<section>.<key>.<part>"`;
- 12 `en:{…}` and 12 `hu:{…}` dictionary blocks;
- zero functions in the file — it is data, not code.

Every reader downloads **both** languages. Splitting by locale would roughly halve the chunk before
compression and halve it again after; loading only the active locale is the second-largest saving. The
chunk is pulled by the landing because the landing renders the composer, whose strings live in it.

## 3. Request count is the waterfall driver

- Landing cold: **76 distinct script chunks**, 101 subresources, last script response ends at 40.8 s.
- Chat cold: **104 script chunks**, 135 subresources, last script response ends at 60.3 s.
- Landing → chat in-app: 46 more subresources, 33 chunks, 18.1 s to a clickable composer.

At 400 ms RTT a chunk costs a round trip whether it is 2 KB or 600 KB. This is why the page paints late
even though the total bytes, once compressed, would be modest.

## 4. The chat route pays on the click

Opening a chat inside the app pulls the chat route's own node chunk (368 KB raw) plus its stylesheet
(107 KB) plus supporting chunks — 845 KB uncompressed, no new document. The landing does not preload it,
so the whole cost lands on the interaction.

## 5. What is already right

- MapLibre (the 1 MB `chunks/Z8JdxaIm.js`, 277 map-library markers) is **not** loaded by the landing or the
  chat: route splitting keeps it out.
- The Document editor closure stays out of the landing too (the gate measures it separately at 70.9 kB gzip).
- Caching is effective: the warm reload moved 14 KB and was usable in 1.4 s — the cost is first visit only.

## Ranked next steps (not done; listed for the owner's decision)

1. **Enable compression at the server** (brotli, gzip fallback) for `text/javascript`, `text/css`,
   `application/json`, `image/svg+xml`. Expected: about 3× fewer bytes on every cold load, no app change,
   no behaviour change.
2. **Ship one language, not two.** Split the i18n catalogue per locale and load the active one; expected to
   roughly halve the biggest asset, and more once combined with (1).
3. **Cut the landing's 76 chunks.** Merge small shared chunks and defer what the first interaction does not
   need; fewer round trips is the lever that matters at high latency.
4. **Preload or prefetch the chat route's chunks on intent** (pointer-down / hover on a conversation), so the
   18-second in-app transition loses its byte cost.

## Caveats

- The local build's asset hashes differ from the deployed ones (`entry/app.Drj7vlvj.js` vs
  `entry/app.DdsZFkzV.js`), so file names do not match the live site one-for-one; sizes and composition do.
- Byte figures from the harness match production's uncompressed behaviour (verified above). Request counts,
  timings and waterfall conclusions are independent of compression.
- The measurement profile is deliberately harsh (400 ms RTT, 50 KB/s, CPU ×4); absolute times are
  worst-case mobile, the relative ranking is the point.
