# Why the cold load is slow — chunk and transport analysis

Companion to [report-2026-11-13.md](./report-2026-11-13.md). Written 2026-11-13 against the production
build of `f72474c0d` and the live hosts. Method: read the built client chunks, map the sizes that the
harness measured, and check the live response headers and the host's Apache modules. No app code changed.

## 1. Production serves text assets uncompressed

- `GET https://ai.alfydesign.com/_app/immutable/entry/app.DdsZFkzV.js` → `HTTP/1.1 200`,
  `Content-Length: 233669`, `Content-Type: text/javascript`, **no `Content-Encoding`**, no `Vary`.
- `Server: Apache`. Correction (2026-11-14): this host is RedHat-style (`/etc/httpd`, `httpd -M`), and both
  `deflate_module` and `brotli_module` **are loaded**. What is missing is configuration: no
  `AddOutputFilterByType`, `SetOutputFilter` or `BrotliCompressionQuality` exists anywhere under
  `/etc/httpd`, so nothing is compressed. (My first check used `apache2ctl`, which does not exist here, and
  printed a false "neither loaded".) The public vhost proxies to node; the streaming paths
  (`/api/chat/stream`, `/api/chat/retry`, `/api/stream/webhook`) are proxied explicitly with
  `flushpackets=on`.

So every script, stylesheet and JSON body crosses the wire at raw size. Measured on the built assets:

| asset | raw | gzip −9 |
|---|---|---|
| `chunks/OxTN49w0.js` | 631.3 KB | **162.9 KB** |
| `entry/app.*.js` | 227.8 KB | **74.8 KB** |
| `chunks/Db9P8UnJ.js` | 156.6 KB | **46.6 KB** |

The harness's transfer numbers are therefore *not* inflated by a test-only setting: they are what production
sends. Compressing text at the server is the single largest saving available and needs no app change.

## 2. The biggest landing asset is the i18n catalogue, in both languages

`chunks/OxTN49w0.js` (631 KB raw / 163 KB gzip) is the internationalisation bundle:

- 1,830 keys matching `"<section>.<key>.<part>"`;
- 12 `en:{…}` and 12 `hu:{…}` dictionary blocks;
- zero functions in the file — it is data, not code.

Every reader downloads **both** languages. Splitting by locale would roughly halve the chunk before
compression and halve it again after; loading only the active locale is the second-largest saving. The
chunk is pulled by the landing because the landing renders the composer, whose strings live in it.

## 3. Request count is the waterfall driver

- Landing cold: **76 distinct script chunks**, 101 subresources, last script response ends at 40.8 s.
- Chat cold: **104 script chunks**, 135 subresources, last script response ends at 60.3 s.
- Landing → chat in-app: 46 more subresources, 33 chunks, 18.1 s to a clickable composer.

At 400 ms RTT a chunk costs a round trip whether it is 2 KB or 600 KB. This is why the page paints late
even though the total bytes, once compressed, would be modest.

## 4. The chat route pays on the click

Opening a chat inside the app pulls the chat route's own node chunk (368 KB raw) plus its stylesheet
(107 KB) plus supporting chunks — 845 KB uncompressed, no new document. The landing does not preload it,
so the whole cost lands on the interaction.

## 5. What is already right

- MapLibre (the 1 MB `chunks/Z8JdxaIm.js`, 277 map-library markers) is **not** loaded by the landing or the
  chat: route splitting keeps it out.
- The Document editor closure stays out of the landing too (the gate measures it separately at 70.9 kB gzip).
- Caching is effective: the warm reload moved 14 KB and was usable in 1.4 s — the cost is first visit only.

## Ranked next steps (not done; listed for the owner's decision)

1. **Enable compression at the server** (brotli, gzip fallback) for `text/javascript`, `text/css`,
   `application/json`, `image/svg+xml`. Expected: about 3× fewer bytes on every cold load, no app change,
   no behaviour change.
2. **Ship one language, not two.** Split the i18n catalogue per locale and load the active one; expected to
   roughly halve the biggest asset, and more once combined with (1).
3. **Cut the landing's 76 chunks.** Merge small shared chunks and defer what the first interaction does not
   need; fewer round trips is the lever that matters at high latency.
4. **Preload or prefetch the chat route's chunks on intent** (pointer-down / hover on a conversation), so the
   18-second in-app transition loses its byte cost.

## Caveats

- The local build's asset hashes differ from the deployed ones (`entry/app.Drj7vlvj.js` vs
  `entry/app.DdsZFkzV.js`), so file names do not match the live site one-for-one; sizes and composition do.
- Byte figures from the harness match production's uncompressed behaviour (verified above). Request counts,
  timings and waterfall conclusions are independent of compression.
- The measurement profile is deliberately harsh (400 ms RTT, 50 KB/s, CPU ×4); absolute times are
  worst-case mobile, the relative ranking is the point.

## Staging trial, 2026-11-14 — verification results

Config applied to the staging vhost only (`ai.dev.alfydesign.com`, the `*:443` block), after a backup at
`/etc/httpd/conf/httpd.conf.bak-perf-20261114`; `httpd -t` passed, then a reload. Types compressed:
`text/html text/plain text/css text/xml application/xml application/json application/javascript
text/javascript image/svg+xml`, with `BrotliCompressionQuality 5` and `Header append Vary
Accept-Encoding`. `text/event-stream` is deliberately absent. Browsers get br where they ask for it, gzip
otherwise.

| Check | Result |
|---|---|
| JS entry (`/_app/immutable/entry/app.*.js`) | `Content-Encoding: br`, 233,254 → **76,908 bytes** |
| CSS | `br` |
| `/api/health` JSON | `br` |
| HTML document | `gzip` (browser context) |
| Font (`/fonts/*.woff2`) | no encoding, 43,588 bytes |
| PNG (`/apple-touch-icon.png`) | no encoding, 4,197 bytes |
| Range request on the font | **206**, `Content-Range: bytes 0-99/43588`, 100 bytes, no encoding |
| Chat stream (`POST /api/chat/stream`) | `text/event-stream`, **no Content-Encoding**, `chunked`, `X-Accel-Buffering: no`, events arrived progressively; 15 output chunks, text-end, finish |
| Browser pass (390×844, signed-in dummy account) | document 200, 180 script responses with br/gzip, **0 console errors, 0 page errors**, message sent and answered |
| Caching | `cache-control: public,max-age=31536000,immutable`; `Vary: Accept-Encoding` |

Known nuance: revalidating a **compressed** asset with its `If-None-Match` `W/"…-br"` tag returns 200 rather
than 304 (the proxy backend does not know the `-br` suffix Apache appended). Hashed assets are served
`immutable` and are never revalidated, so this costs nothing in practice; identity requests still answer
304.

Not exercised: generated-file downloads (PDF/DOCX) and the image-job WebSocket. Both are outside the
compressed types by construction (binary content types are not in the list; WebSocket upgrades are not
response-filtered), and the Range check covers the download mechanism.

## Addendum, 2026-11-14: the three open checks, and one new lever

**Generated-file download.** Asked the staging dummy account for a one-page PDF; it produced
`compression-test.pdf` (591 bytes). `GET /api/chat/files/<id>/download` through compressed Apache:
`200`, `content-type: application/pdf`, `content-disposition: attachment`, **no `Content-Encoding`**,
591 bytes, valid `%PDF-1.4` header. With `Range: bytes=0-99`: **206**, `content-range: bytes 0-99/591`,
exactly 100 bytes. Downloads and byte ranges are untouched.

**WebSocket.** The browser opens none: `new WebSocket` exists only in the server-side ComfyUI client
(`src/lib/server/services/images/comfyui/client.ts`), which talks to ComfyUI directly and never crosses
Apache. The vhost's `Upgrade` rewrite is not used by the app path, so there is nothing for a response
filter to break.

**ETag / 304.** Identity requests revalidate to `304`; a compressed asset answers `200` because Apache
appends `-br` to the proxied ETag and the backend does not match it. Hashed assets are served
`cache-control: public,max-age=31536000,immutable` and are never revalidated, so this costs nothing in
practice. Accepted, not mitigated.

**New lever: the site speaks HTTP/1.1 only.** `http2_module` is loaded, but both app vhosts pin
`Protocols http/1.1` (`/etc/httpd/conf/httpd.conf:2774` and `:3004`), and `curl --http2` negotiates
HTTP/1.1. With 76 script chunks on the landing and 104 on a chat, HTTP/1.1 serialises requests across ~6
connections per origin; HTTP/2 multiplexes them on one. Likely a larger win than any single chunk change,
and the same class of server-only change as compression.

### Candidate levers, ranked by expected effect on a poor connection

1. **Compression** (staging verified: 233 KB → 77 KB on the entry). Pending production.
2. **HTTP/2 on both vhosts** (`Protocols h2 http/1.1`): turns 76–104 queued requests into one multiplexed
   stream. Server-only; needs the same staging verification as compression.
3. **One language, not two**: the i18n catalogue is the biggest single asset (631 KB raw / 163 KB gzip,
   1,830 keys, both dictionaries). Split per locale and load the active one.
4. **Fewer chunks on the landing**: merge small shared chunks, defer what the first interaction cannot use.
5. **Fonts**: 127 KB (6.6 % of the cold landing). Subset, drop unused weights, `font-display: swap`,
   preload the one weight used above the fold.
6. **Hydration vs first click**: the composer is clickable ~10 s before hydration on a cold load; early
   clicks land on inert markup. Either ship less blocking script or show a "still starting" state.
7. **Prefetch the chat route's chunks on intent** (pointer-down on a conversation), so the in-app
   transition stops paying 845 KB at click time.
8. **Polling cost**: the chat detail polls every 2.5 s while pictures/turns are active; confirm it stops
   when idle and consider back-off on poor connections.

## Landing paint stagger (owner, 2026-11-14)

The owner's report: on a slow connection the welcome message and composer appear first, and the project
folders and the rest arrive seconds later. The measurement harness records only whole-page paints (FCP/LCP),
not per-element arrival, so this is not yet quantified. Candidate causes, to be measured before fixing:
the home summary is fetched after hydration rather than server-rendered into the first payload; the
landing has no reserved space for the sections that arrive later, so the page settles in stages; and the
chunks that render those sections are part of the 76-chunk waterfall. A per-element timestamp pass
(`data-*` markers plus a MutationObserver, or Playwright's per-selector visibility timing) belongs in the
harness before any change.

## Why a generated picture reaches the screen late (investigated 2026-11-14)

The chain from ComfyUI finishing to the picture being visible:

1. **ComfyUI finishes.** The runner follows it by polling `/history` every **1 s**
   (`image-runner.ts`, `FOLLOW_RETRY_MS = 1000`; progress is written every 1 s).
2. **Store + thumb.** The PNG is downloaded, stored, and a thumbnail is generated eagerly with sharp
   (`files.ts`, `storeImageFile`) — no lazy-thumb cost on first view.
3. **The card settles** in the database; the client does not know yet.
4. **The client polls.** The chat page re-reads the **whole conversation detail** on a fixed
   **2.5 s** interval while any take is active (`+page.svelte`, the `pollForImageCards` effect), then stops
   when nothing is active (`shouldPollImageCards`). The tick that sees the finished take is the one that
   shows the picture.
5. **The image is fetched and decoded** by the card after that render.

So the avoidable part is mostly step 4: up to 2.5 s of fixed latency, and each tick is a full-detail read
that grows with the conversation, which on a poor connection can itself take seconds. Rough visible lag is
1 s (history poll) + store/thumb + **0–2.5 s** (client poll) + fetch/decode.

Candidate fixes, smallest first:

- **Adaptive poll**: ~750 ms while a take is running, 2.5 s otherwise (one constant plus a derived
  interval), and only re-read what changed.
- **Cards-only read**: a lightweight endpoint for the poll, so a tick is a few KB rather than the whole
  conversation.
- **Push on completion**: an SSE channel from the job engine (the chat already streams SSE for turns; the
  job engine has no event channel today) — near-instant, the largest change.
- **Cache headers on image files**: confirm the thumb and full PNG can be cached per file id so a re-render
  does not refetch.
