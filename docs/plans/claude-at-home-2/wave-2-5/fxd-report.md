- **Toast (fixed)**: `in:flyIn` used `y: -12` — `fly`'s `y` is the *starting offset* for `in:`, so a negative value starts the toast ABOVE its resting spot and animates it down, the opposite of §7.2 #33 ("rises 12px and fades in"). ## Finding 9 — the flaky e2e (pre-existing, found by the orchestrator)

- **Root cause**: `tests/e2e/artifact-chat-card.spec.ts`'s "shows the card during the turn..." test had no `test.setTimeout` of its own, so it inherited `playwright.config.ts`'s global 60,000ms default — while budgeting 30s *each* for three separate slow steps (final assistant text, workspace visible, workspace's own text) on top of login/conversation/provider setup. None of those 30s allowances is meant to be "normal" — they exist for a cold dev-server compiling the Tiptap-heavy Document editor chunk for the first time (an existing comment in the test says so). When the environment is that slow, cumulative elapsed time can cross the 60s ceiling *before any single await reaches its own allowance*, and Playwright fails whatever happened to be in flight at that moment — which explains both disparate failure points the orchestrator saw (`toBeEnabled()` near the start, the workspace text near the end) as *one* shared cause rather than two separate races. `atlas-job-flow.spec.ts` already calls `test.setTimeout(120_000)` for exactly this kind of long live-model flow; this spec simply never did.
- **Fix**: `test.setTimeout(120_000);` as the first line of the test body.
- **Proof**: 5 consecutive green runs (`--repeat-each=5 --workers=1`, matching `playwright.config.ts`'s own `workers: 1`/`fullyParallel: false`), ~2.8s each once warm.
- **A methodology note for the record**: an earlier attempt at the same 5x proof *without* explicitly pinning `--workers=1` produced spurious, identical failures across all 5 repeats (`message-input` staying disabled through `login()`, "2 × locator resolved"). Root-caused this before trusting either result: it reproduces even on repeat 1 (cold), and does not improve by repeat 5 (should be warm by then if it were a cache issue) — ruling out cold-start. It is a concurrency artifact of my own verification command, not a reflection of the fix or a real suite-execution risk: this project's own config already pins `workers: 1`/`fullyParallel: false` for exactly this kind of shared-admin-account e2e test, and pinning it explicitly on the CLI reproduces that intended sequential execution cleanly. The 5x-green result above is the one I'm standing behind.
- **Files**: `tests/e2e/artifact-chat-card.spec.ts`.
