### `document/change-pill-decoration.ts` (new) — the widget decoration
A ProseMirror plugin (`changePillPluginKey`, state = `ChangePillEntry[]`) whose `decorations(state)` builds one `Decoration.widget` per entry, positioned via a **doc-only** mark lookup (`marks.ts`'s new `findAlfyChangeMarkRange`, since a plugin's `decorations(state)` prop has no live `Editor` to call `.schema`/`.view` on — only `state.doc`, which still carries its own schema via `.type.schema`). ### `DocumentBody.svelte` wiring
- Dropped `changePositions` state entirely and its two `changeMarkRectFn`/`localizePoint` build sites — the pill no longer needs screen coordinates.
- `$effect` pushes `pendingChanges` (mapped to `ChangePillEntry[]`) into the editor via `setChangePillsFn` whenever it changes (mirrors the existing comment-anchor effect).
- `handleKeepChange`: status → `"kept"` immediately; the actual `keepChangeFn` (mark-clear) call and `removePendingChange` are **deferred** `KEEP_SETTLE_MS` (1400ms, redesign §7.2 #13) so the widget's live-mark lookup keeps working throughout the "Kept" window instead of the mark vanishing instantly.
- `handleUndoChange`: captures `changeDocRangeFn`'s `.to` as `fallbackPos` and the block's own current (pre-undo) markdown from `blocks` state as `appliedMarkdown` **before** calling `undoChangeFn` (Undo's node-replace destroys the mark immediately, unlike Keep). Schedules the normal autosave, fires the acknowledge call, and starts a `UNDO_SETTLE_MS` (5000ms, §7.2 #14) removal timer.
- `handleRedoChange` (new): cancels that timer, restores `appliedMarkdown` by calling `undoChangeFn` again (reused in reverse — it's generically "set this block's content to X", never direction-specific), re-marks the block under the SAME `changeId` via `remarkChangeFn`, flips status back to `"pending"`.
- `handleKeepAllChanges`/`handleUndoAllChanges`: iterate the (unmutated, captured-once) `pendingChanges` map and call the same per-change handlers.
- New `pendingList` derived + `reviewIndex` state + `handleReviewPrev`/`handleReviewNext` (wrap-around stepper, calls `seeChange` to scroll+flash).
- `<ReviewBar>` mounted in a new `.document-review-bar-slot` — a **direct child of `.document-content`** (the scrolling grid, `position: relative`), not nested inside `.document-content-text`: `position: absolute` on a grid item removes it from grid track placement entirely, so it overlays the scrolling text as a simple `position:absolute` child rather than becoming a third grid column, and being a **direct** child (not nested in the scrolled inner column) is what keeps it visually pinned to the bottom while the text scrolls underneath.

## Ruling 61 — a pending Alfy change survives a reload

Documents only, exactly as ruled. Stored on the artifact's own `metadata_json` (no migration): `metadata.review = { throughVersion: number; keptBlockIds: string[] }` — `throughVersion` is always either `0` ("no marker yet") or an **Alfy-authored** version number (never a user one, so the field's own meaning never drifts), `keptBlockIds` are blocks already acknowledged (Keep or Undo) past that marker.

### `document-ops.ts`
- `computePendingReviewBlocks(throughVersion, keptBlockIds, versions)` — **pure**, no DB. For every version newer than the marker, diffs it against its immediate parent (`versionNumber - 1`; contiguous by ruling 47) block by block, keeping only the MOST RECENT version to change each block id. A block whose last change came from Alfy (not in `keptBlockIds`, still present in the latest version) is pending. This single "most recent change wins" rule elegantly satisfies BOTH of ruling 61's "minus" clauses without tracking them separately: a user's own later edit to the same block becomes that block's own most recent change (author `"user"`), excluded the same way Undo's own resulting version excludes it — Undo's explicit `keptBlockIds` write is belt-and-braces with this, not the only thing excluding it. Each version's body is parsed at most once (memoized) even though it's read as both "current" and "someone else's parent".
- `getDocumentReviewState` — **read-only** (ruling 61: "recomputed on load", never a write); reads the CURRENT stored marker/kept-list and every version fresh, every time.
- `acknowledgeDocumentReviewBlocks` — the one write, shared by Keep and Undo: adds the named block ids to `keptBlockIds`, recomputes; if that empties the pending set, advances `throughVersion` to the latest ALFY version (never a later user one) and clears `keptBlockIds`.
- `applyDocumentPatch` bootstraps the marker on an artifact's first Alfy edit after this shipped (`metadataPatch: { review: { throughVersion: <the version before this edit>, keptBlockIds: [] } }`, only when no marker exists yet) — the one write site, so an artifact that predates ruling 61 never retroactively flags old Alfy edits as pending.

### Route + client
`src/routes/api/artifacts/[id]/review/+server.ts` — GET (pending list) / POST (`{blockIds}` → acknowledge, returns the recomputed list). `requireApiUser`, `?conversationId=` honoured, a foreign/missing/non-Document id all answer the identical `{ok:false, reason:"not_found"}` 404 body (ruling 39/49). `src/lib/client/api/artifacts.ts`: `fetchDocumentReviewState`, `acknowledgeDocumentReviewBlocks`.

### `DocumentBody.svelte`
`restorePendingReview` runs once, right after `loadState = "ready"` — **never blocks the editor becoming interactive** (fire-and-forget, its own try/catch; a failed fetch reads the same as "no marker yet"). For each server-reported pending block, calls `remarkChangeFn(editor, blockId, blockId)` (the block id itself IS the synthetic `changeId` — there's no live per-character opId left from a past session, and ruling 61's own pending set is block-granular) and inserts a `PendingAlfyChange` into the SAME `pendingChanges` map a live change would use, `isNewBlock` carried through from the server. From that point on Keep/Undo/Redo/the review bar treat it identically to a live-session change — no special-casing anywhere else. `myToken` guards against a document switched away from before the fetch resolves. Every Keep/Undo also calls `acknowledgeDocumentReviewBlocks` (best-effort, fire-and-forget — matches this file's own established "auxiliary services degrade gracefully" pattern for `refreshAfterCommentChange` etc.).

## Deviations from spec, with reasons

1. **Redo of a live-session change with `insertedBlockIds` loses the extra inserted blocks.** `handleRedoChange` only has the PRIMARY block's own captured `appliedMarkdown` (from `blocks` state) to restore — the multi-block case (an op whose text read as MORE than one block, e.g. Alfy split a paragraph in two) has no equivalently cheap capture point for the EXTRA blocks' own content once Undo has already deleted them. A deliberate, narrow, documented simplification (see `handleRedoChange`'s own comment) rather than a second, heavier redo-snapshot mechanism; Keep/Undo themselves are fully correct for this case, only a Redo-after-Undo of a multi-block change is affected, and only for the extra blocks (the primary block's own text redoes correctly).
2. **The comment thread's own change chip (`changeIdByCommentId`/`changeChipByCommentId`, flagged by rd3a's hand-off) does NOT survive a reload.** The comment-reply-to-change linkage was never itself a persisted concept (pre-ruling-61 either) — ruling 61's own metadata is block-scoped, not comment-scoped, and there is no server-side record of "which comment thread produced this specific pending block". This is a real, bounded gap: after a reload, a restored pending block's own pill/mark/review-bar-entry all work correctly, but the ORIGINAL `@Alfy` reply's own chip (in the margin) shows no "pending"/"kept" badge next to it. Judged small enough (a cosmetic badge on an already-visible reply, not a loss of reviewability) not to warrant inventing a second persisted linkage table for this step.
3. **The chat header's artifact-count-button pending dot is NOT wired to the durable state.** rd2's own hand-off flagged this as agent 4's job ("feed `hasUnreviewedArtifactChange` from real persisted state"), and my own brief names it. I investigated the wiring (`+page.svelte`'s `hasUnreviewedArtifactChange`/`liveDocumentAlfyActivity`) and found there is no existing precedent for a callback reaching all the way from `DocumentBody.svelte` through `DocumentWorkspace.svelte` to `+page.svelte` (the existing `onCommentCountChange` callback only goes DocumentBody→DocumentWorkspace, for the Comments button's own badge) — and the FULLY correct fix (working even when the panel was never opened this session at all) needs a server-computed aggregate through `conversation-detail/read-model.ts`, touching shared, sensitive read-model code late in an already-large diff. Deferred and reported as a follow-up task rather than risking a late, under-tested change to `+page.svelte` (3393 lines, central to every other redesign agent's own work too). The review bar's own count (the part of this sentence that's unambiguously mine) DOES correctly count the reloaded pending changes — confirmed live in the Playwright run above.
4. **The review bar's prev/next buttons use the standard `.btn-icon` (40×40px)**, not a bespoke 44px button — matching the app's own existing shared icon-button size rather than introducing a one-off variant or touching the global class for this one spot. Keep all/Undo all (the OTHER §4.4 44px requirement) do get the full 44px on phones.
5. **Found, but did not fix** (reported as a separate follow-up task): `undoAlfyChange`, given a legitimately empty `previousMarkdown` for an EXISTING (not new) block, collapses the document by one block instead of restoring an empty one — a pre-existing bug in the markdown round-trip (likely `blocks.ts`'s segmentation), unrelated to this session's own changes, discovered while designing the `isNewBlock` flag and deliberately not touched (out of scope, and the existing test suite never exercised this path either way).

## Hand-off — reuse these

- **`mount()`/`unmount()` from `"svelte"` to embed a real component inside a ProseMirror widget decoration** (`change-pill-decoration.ts`): the first use of this pattern in the codebase. Reuse this directly for any future interactive decoration (Canvas/Slides' own "floats at the node's corner" pill, per redesign §8) rather than hand-rolling vanilla DOM the way the non-interactive `alfy-writing-decoration.ts` tag widget does.
- **`findAlfyChangeRangeInDoc`/`findAlfyChangeMarkRange` (`marks.ts`)**: the doc-only-core-plus-Editor-wrapper pattern for anything a ProseMirror PLUGIN's own `decorations(state)` prop needs to read that was previously only reachable via a live `Editor` — a `Node` always carries its own schema via `.type.schema`, so the Editor was never actually required.
