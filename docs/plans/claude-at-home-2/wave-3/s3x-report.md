Six things a reader of this report should know first:
1. **The editor's budget is NOT met on the honest measure**: 66.3 KiB gzip (67,872 B = 67.9 kB SI), 1.3 KiB over the spec's 65 in the guard's own unit (KiB) and 2.9 kB over it in SI. It IS met on the spec's literal reading (the chunk that contains `CanvasEditor`: 59.4 KiB = 60.8 kB SI). Details and the levers left are in "The budget".
2. **A poster of an App is a card, not a picture of the App.** The App runs in a sandboxed frame with no pixel access from outside; the poster is the card that says so (`Az élő alkalmazás nem része a képnek.`). A real snapshot needs a bridge inside the frame (Slice 2's sandbox, ruling 58) — an owner decision, see open questions.
3. **The canonical `/api/chat/files/[id]/preview` refused every poster** (its rule: a file that hangs from no reply is served only if a job made it). The spec's "no new store" holds, but serving needed a 3-line exception by file name.
4. **An App block reloaded whenever its data object was replaced** (any poster, resize-free data write): S3-R1's load effect read `data.artifactId` through the whole prop. Fixed (a derived id); without it a poster capture reset a running App.
5. **The export hangs from the chat's newest reply**: a produced file is shown, listed and remembered through a reply, and the file-production read model lists only files that hang from one.
6. The other lazy loads I tried and reverted (the flow library's own resize corners, selection toolbar and minimap) saved nothing: the library is one module, so what they use stays in the shared chunk and the split only added chunk overhead. Recorded so nobody retries them.

## What I built, per step

### Step 0 · the dependency
`npm ci` in the worktree (replacing the symlink), `npm install --save-exact html-to-image@1.11.11`, committed alone. `vite.config.js`: `html-to-image` in `optimizeDeps.include` — it is imported only by code the editor loads with `import()` from a `.svelte` file, which the dev optimizer's scan never sees (it would re-optimize and reload the page under a test).

### Step 1 · posters
- `_lib/poster.ts`: `POSTER_WIDTH/HEIGHT` (640 x 400, the box a poster is drawn to fit; scale 0.5–2), `posterPlaceholder`, `blockName`, `keepInPicture` (`html-to-image`'s filter: what a picture leaves out — `[data-export-skip]`, comment pins and the catcher, Alfy's layer, the drawing pad and its selection chrome, the library's handles/resize corners/selection), `stillify` (see below), `renderPoster`, `capturePoster` (draw + upload, returns the `PosterRef`), `withTimeout` (20 s), `boardFonts` (font CSS read once).
- **A poster is taken from a detached COPY of the block's content**, made by `stillify`: iframes/canvases/videos/scripts out, thumbnails loaded eagerly, an App replaced by a card with its name and "the live App is not part of this image", a map reduced to the card's own inline route drawing (the live map container and its markers removed) plus a "Nem élő alaptérkép / Basemap not live" badge. The block on the board is never touched, never flickers, and an App is never reloaded. (I first designed a board-wide "still mode" that the content modules would read; a copy is simpler and has none of the flicker or state risks, and leaves the chat's `MapRouteCard` and S3-R1/R2's nodes untouched.)
- Timing per the spec: once 800 ms after a block first shows with its data; again 800 ms after its data or size changes; once more at the start of an export for any block without one. Content is waited for (its chunk, the map's inline route) up to 5 s; images up to 3 s.
- **Where it lives and what it does to the board**: `_lib/pictures-controller.svelte.ts` (`CanvasPicturesController`), loaded with the rest of the picture parts (`export-parts.ts`) only when a board has an App/map/photos/live web whose poster is due, or Download is pressed. A poster goes on the block's data through `CanvasBoard.setBlockPoster` — **not a step of the reader's and not a save of its own**: it rides with the reader's next step. Reason: a poster-only save would be a user version, and ruling 63's review makes any user version after Alfy's change disable its Undo. What was pending is settled first, so nothing the reader did is swallowed; a block being dragged makes the board refuse and the controller offers it again (1.5 s, four times).
- A failed capture never blocks anything: `PosterError`, the block keeps drawing live, its meta line says `Nem sikerült állóképet készíteni erről a blokkról.` once (and not in a picture of the board, and with a tooltip when cut short), it is not retried for the same data, and the export draws it as a card and names it.
- Server: `services/artifacts/canvas-export.ts` `storeCanvasImage` (facade), for both `source: "canvas-export"` and `"canvas-poster"`, through `storeGeneratedFile`. A poster is a chat file named `canvas-poster-<board>-<block>.png` that hangs from no reply and has **no artifact**, so nothing lists it; a new one replaces the last of its block. `shared/artifacts/poster-file.ts` owns the name, and `generated-file-serving.ts` serves a file of that name although it has no reply (the exception, with 2 tests: it does serve a poster, and still refuses an unattached `.txt` that only looks like one).

### Step 2 · PNG export and Download
- `_lib/export-png.ts` `exportBoardPng` in the spec's order: bounds of blocks (as the panel measured them) and marks → clamp 800x600…2400x1800 → camera remembered, moved, one frame → posters mounted (a placeholder card for a block with none) → `toPng` on the viewport element with its transform overridden (60 s timeout) → **unmount and camera restore in a `finally`** (a restore that throws synchronously, or a canvas that is gone, does not mask the error or skip the unmount) → upload. Empty board: `ExportError("empty")` before anything is touched. `unionRects/exportSize/cameraForBounds` are the library's own `getViewportForBounds` maths, written out so the lazy chunk imports nothing from `@xyflow`.
- `POST /api/artifacts/[id]/exports/png` (`requireApiUser`, `?conversationId=`, thin over `storeCanvasImage`): JSON `{ source, dataUrl, nodeId? }` → `{ ok: true, fileId, width, height, filename }` (`filename` is an addition so the browser saves it under its name; without it SvelteKit's router took the synthetic anchor for a navigation). 401 unauthenticated, 404 a stranger's/missing/non-board id **byte for byte alike, before the picture is looked at**, an incognito chat's board only with its `?conversationId=`, 415 not a PNG (judged by the bytes: signature, IHDR, IEND — not by what the request says), 413 over the byte cap (10 MiB export / 1.5 MiB poster, checked on the declared length, the read length, the base64 length and the decoded length) or larger than a browser could draw, 409 a board that belongs to no chat, 400 a body that is not a request.
- The export is a produced file (ruling 18): `chat_generated_files` on the chat's newest reply (`getLatestAssistantMessageId`, new in `messages.ts`), `syncGeneratedFilesToMemory` makes its `generated_output` artifact (and the OCR readback every produced image gets), and a `used_in_output` link ties it to the board. It shows as a File card under that reply and as a row in the panel list; the board itself gets no version. A chat with no reply still gets the file to download, just not listed.
- Header Download for a Canvas: `registerPanelActions({ openDownload })` → `CanvasDownload.svelte` on `AnchoredPopover` (popover on desktop, sheet on phones, `canvas-download-popover` / `canvas-download-png`): one option "PNG image / PNG-kép", a status while drawing, then "the picture is saved with this chat's files" with a "Download again" link, and the download starts by itself (`startAuthenticatedDownload`, the canonical `/api/chat/files/[id]/download`). While it draws, the editor puts an opaque veil over the board so the camera's trip is not watched. Blocks drawn as cards are named in **one** notice (in the popover; the panel shows the same notice when the popover is closed, never both).
- Empty board: the option is disabled and says so. Failures are words (`too large`, `no chat`, `could not export`) with Try again.

## The budget

**The one honest measure**: what opening the editor downloads *because* it opened — the gzip size of the editor's chunk and every chunk it imports statically, CSS included (a stylesheet is render-blocking, part of what first paint waits for), with a chunk it shares only with its own lazy parts (everything under `artifacts/canvas/`) counted as its own, and one the chat route already loads not counted. This is the guard's `exclusiveGzipBytes`, the "loads N chunk(s) of its own" figure. **Why not the bare size of the chunk that contains `CanvasEditor`** (the spec's literal reading, and S3-C's/S3-A's "default reading"): it falls whenever a module moves into a chunk a lazy part also imports, though the same bytes load — in this slice it fell from 68.0 to 59.4 while the closure moved from 74.1 to 66.3 — so it can be moved by a refactor that saves nothing. Both are now held (`--max-target-gzip 65000`, spec-literal, currently 59.4 KiB = 60.8 kB; `--max-gzip 69000`, the honest one), and a third number is printed, not held: what the editor also loads that only OTHER lazy entries share (3 chunks, 17.0 KiB: the d3 modules mermaid shares, …).

| | before (`5e74823d`, measured here) | after (`3b61dd82`) |
|---|---|---|
| **closure, what the editor loads on its own** | 74.1 KiB gzip (243.6 kB raw), 7 chunks | **66.3 KiB gzip = 67,872 B (215.1 KiB raw), 11 chunks** |
| the chunk that contains `CanvasEditor` alone | 68.0 KiB | 59.4 KiB (60,776 B) |
| chat route's first load (`/(app)/chat/[conversationId]`, 75 chunks) | 535,771 B gzip | 536,931 B (+1,160 B; budget +2,048) |
| Chart.js / MapLibre in the editor's static closure | not checked | none (`--forbid`) |

The closure fell 7.8 KiB. **It is 1.3 KiB (KiB unit of the guard's own reports) over the spec's 65**; in SI, 67.9 kB against 65 kB. What came out and what it cost (KiB, measured on the closure, not estimated): the drawing layer with its geometry, the freehand library and the tray (−7.1), the Insert menu made independent of the registry so it could load on demand (−0.7 net), placement (−0.4), the Versions sheet (real load −4.4; not in the number, another lazy entry shares it), the checklist (−0.9) and chart, the states and saving notices (−0.3). What put back: the picture's plumbing that must be in the editor (the board's picture API, the overlay, the glue: +1.7 before any of it was made lazy).

**What is left, and why I stopped**: the flow library is 36.9 KiB of the 66.3 (one module, `@xyflow/system/dist/esm/index.js`, so nothing that uses a piece of it can leave: I tried the resize corners, the selection toolbar and the minimap on demand, three ways, and the closure did not fall — the library just split into more chunks), its stylesheet 2.5 KiB, and ~27 KiB of ours that a board needs to draw at all (the board, the editor's save machinery, the schemas that validate a stored board, the shell, the note kinds). What would still cut it, each with a cost I did not want to take without you: frames, stickies and text as lazy kinds (≈ 1.5 KiB; every board's first paint waits for one more request), our own dot background instead of the library's `Background` (≈ 0.4; a visual change), a pruned copy of the library's `base.css` (≈ 0.4; a copy to keep in step with a pinned version), dropping the minimap (≈ 1.4; a feature). **Recommendation: a ruling that sets the honest budget at 67 KiB (about 68.6 kB), or a decision on one of those four.** The guard enforces 69,000 B now, so a regression is caught, not the spec's number.

The guard (`scripts/check-artifact-chunks.mjs`), what changed:
- `--allow-entry artifacts/canvas/` replaces the four specific flags: every lazy entry under the Canvas folder is a part of the editor (it may share chunks with it, does not count as a leak, and a confined library may live in its closure). This was necessary, not tidy: Rolldown moves whatever a lazy part imports into a chunk both share, and the four-flag list missed every new part.
- `--max-gzip` (closure), `--max-target-gzip` (the chunk alone), `--forbid PACKAGE` (Chart.js, MapLibre: fingerprints `chartjs-`+`_adapters`, `maplibregl-canvas`+`maplibregl-map`), `--chat-route ID --chat-baseline BYTES [--chat-tolerance]` (the route's first load: root layout, layouts and page from SvelteKit's generated route table, every chunk they import statically once; growth only; baseline 535,771 B measured on the base tree), and the informational "shared only with other lazy entries" line.
- **The `html-to-image` fingerprint S3-B wrote (`Failed to clone iframe`) is not in 1.11.11**: the guard reported the package "not in this build" and would have said so for ever. It now finds it by its own error strings.

## Deviations from the spec / brief, and why
- **A poster is served by the canonical routes only because `generated-file-serving.ts` now allows it by name** (the spec assumed the routes would serve any chat file). See item 3 above.
- **A poster of an App is a card**, not a picture of the App (item 2).
- **Posters are not saved on their own.** Spec: "referenced from the node's data". They are, and are saved with the reader's next step; a session with no later step re-takes them next time (bounded: a new one replaces the old file). Reason: versions and ruling 63's Undo.
- **The spec's `mountPosters(missing)` is state-driven** (`board.showPictures` → an overlay in `NodeShell`), not DOM surgery; the live block stays mounted underneath (`visibility: hidden`), so an App keeps its state through an export.
- **`--allow-entry` is now the family flag**, and `--max-gzip` is enforced above the spec's 65 (item 1).
- The export's response carries a `filename` (spec: `{ fileId, width, height }`).
- `posterFailed` shows in the block's meta line as the spec says, but not inside a picture of the board.
- `artifact-canvas-draw.spec.ts`'s frame test and `artifact-canvas.spec.ts`'s menu count changed (above).
- The draw tray and toolbar CSS: the toolbar's button rules are now `.canvas-toolbar :global(.tool…)` so the tray, drawn inside the bar but loaded apart, wears them.
- `InsertMenu` takes `rows`/`entryFor` props; `CanvasToolbar` warms the menu itself and asks the board (`onwarm`) for the drawing layer and the placement when a reader reaches for Draw or Insert, so they are there when pressed; the board keeps the loaded placement, so an insert on a warm board is as immediate as before the placement went lazy.
- `ChecklistNode`/`ChartNode` are content modules now (`checklistShell`/`chartShell`); a lazy block reaches the flow through a new `board.updateData` (the board's own `flow.updateNodeData`), because a lazy content module may not import the library (S3-R1's rule, which its test now enforces for both).

## Open questions
1. **An in-frame snapshot bridge for Apps?** It would let an export show the App's own pixels, at the price of shipping a renderer inside every App frame and a new message the sandbox accepts (ruling 58, Slice 2). I did not touch the sandbox.
2. **The budget** (item 1): a ruling, or one of the four cuts.
3. **The new File does not appear in the panel list/chat until the conversation is read again** (the chat page has no channel that says "a file was made outside a turn"; a Document's PDF export has the same limit). A small event on `subscribeArtifactChanges` would do; I did not widen it.
4. **A poster outlives its block** (deleted from the board: one small file until the conversation goes; a re-take replaces by block, a deletion does not sweep). A sweep must not delete a poster of a block the saved board does not have YET (posters are taken before the autosave lands), so it needs the board's unsaved state; skipped.
5. **The model's `read_generated_file` tool can see a poster by name** (`canvas-poster-…png` in the conversation's file list): harmless today, but the tool could skip that prefix (`isPosterFileName`).
6. **Every exported PNG is queued for the OCR readback** all produced images get (MinerU). Useful (the text on a board becomes searchable) or a cost per export: `syncGeneratedFilesToMemory` has no switch to skip it.
7. `pixelRatio` is 1 for the export (800–2400 wide): a 2x for sharper text on a dense display would double the bytes; ruled by the byte cap, not chosen.

### A paragraph for `AGENTS.md`'s Artifacts section (I did not touch it)
> **Pictures of a board (Wave 3).** A board leaves the panel as a PNG. Only the browser has it drawn, so the browser makes the picture and `POST /api/artifacts/[id]/exports/png` (a thin route over `services/artifacts/canvas-export.ts`, facade `storeCanvasImage`) keeps it through the one generated-file path after judging whose board it is (a stranger's and a missing one answer alike, an incognito chat's only with `?conversationId=`), that the bytes are a whole PNG by their own signature and ends, and that they are no larger than a browser could draw (415, 413). An export is a produced file (ruling 18): a chat file on the chat's newest reply, its `generated_output` artifact and a `used_in_output` link to the board. A block a clone of the DOM cannot carry (an App's sandboxed frame, the map's WebGL canvas) has a POSTER: a chat file that hangs from no reply and has no artifact (`shared/artifacts/poster-file.ts` names it; `generated-file-serving.ts` serves it by that name), referenced from the block's data as `PosterRef`. A poster is taken from a detached copy of the block's content (`_lib/poster.ts` `stillify`: nothing live in it, what a picture cannot show said in words), never from the block on the board, and goes on the block's data without being a step of the reader's or a save of its own (`CanvasBoard.setBlockPoster`). Everything a picture is made of — the controller, `html-to-image`, the Download popover — is ONE lazy entry, `canvas/export-parts.ts`; `_lib/export-png.ts` moves the camera, mounts posters or a placeholder card (`board.showPictures`, drawn by `NodeShell`) and puts both back in a `finally`. **The chunk guard holds the editor's initial closure** (`--max-gzip`, its own chunk and what it statically imports, CSS included), keeps Chart.js and MapLibre out of it and the chat route within 2 KiB of its baseline (`npm run check:artifact-chunks`, part of `npm run build`): a lazy part of the editor is an entry under `artifacts/canvas/`, imports no `@xyflow/*`, and imports as little of the editor as it can (whatever it imports is split into a chunk the editor must load too).
