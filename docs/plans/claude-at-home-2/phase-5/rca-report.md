# RC-A — re-check of the friction build (report only, nothing fixed)

Model: Claude Sonnet 5.5 (`claude-sonnet-5-5`). Tree: worktree `rc-a`, detached at `03882bd00` (= `feat/artifacts` head, the whole friction build merged).

**How it was walked.** Production build (`npm run build`: 32 `Unused CSS selector`, baseline) served with `node build` on 5500 against a scratch DB, `PLAYWRIGHT_TEST` unset, chat/control/title models through the tunnel on 30410 (`qwen3-6-27b`). A fresh Hungarian user (a second fresh one for the phone tours, an English one for the string scan). Real input only (mouse, keyboard, touch with `hasTouch`/`isMobile`); the in-page code only *observed* (layout-shift observer, a per-frame box/opacity tracer, CDP screencast frames with wall-clock times, 1-min load 2–3 in every log line). Widths 1440, 1366, 1280, 1180, 1100 docked, 390 and 360 (phone, touch); light, dark, reduced motion. The audit's own kit was copied (`p5/rca-kit/`, walks `r2…r29` next to the old `w*`), each finding walked with the audit's steps and measured the way the audit measured it.
**Real-model use:** 16 chat turns / panel model calls in the walk proper, one at a time (first message, Document request, Alfy edit, App + change, board + note, PDF request, @Alfy comment, read-only question, phone PDF request, App Módosítás, Regenerate, board @Alfy, one-line first message), plus 2–3 in an early batch I started by mistake with a loose file filter (then I wiped the DB and restarted).
**Environment caveats (not product findings).** (1) The tunnel is one slot: title generation, the control model and the chat share it, so the title and App-verifier timings below are this Mac's. (2) Web research (Parallel) is not configured here, so every App that states a real-world fact ends with "Alfy nem tudta ellenőrizni az alkalmazás adatait." (`verify.ts`: unsettled claim + no research = `unavailable`); the audit's Apps had no such claim. (3) No Docker: the App `.html` and XLSX jobs cannot run. (4) My browser is en-US, so Knowledge dates (Oct 12, 2026…) are not judged.
Evidence: logs `p5/rca-kit/r*-log.txt` (and `w1-log.txt`), screenshots `p5/rca-shots/` (20, each looked at).

## Verdict in one paragraph

Of the 30 findings, **22 are fixed, 8 are better but not finished (F3, F4, F6, F12, F15, F18, F22, F24), none is unchanged, none is worse**; the owner's three later finds are fixed. ### The two calls the owner should hear about

1. **Cards after the text (FB-7).** In a short or medium reply it reads well: text, the closing sentence, then "✓ Létrehozva …" and the card, like an attachment (`OwnerCall1-short-reply-app-card-after-text.png`, `F16-F17-F22-canvas-reply-card-after-text.png`). In a long reply (the Document turn, ~2,200 px) the card is the very last thing and during streaming it is below the fold for the last 30 s of the turn (card at 15 s of 48 s); at the end the view follows to the bottom, so it is found. Two things make it feel heavier: a turn with create + edit calls (this model does it every time) stacks **one card per call** (three identical 221 px "Bécsi hétvégi útiterv" cards in a row), and a failed call's raw block sits between text and cards (new #2). My call: keep it, but show one card per item per reply.
2. **"Alfy dolgozik a dokumentumon…" on a read-only turn (FB-6).** It does mislead slightly: the strip stood 7 s on a question that ended with "Nem módosítottam semmit". It never sticks (gone at the end of the turn) and it is quiet, so I would keep it but word the read phase differently ("Alfy átnézi a dokumentumot…") or show it only once the edit call exists.
