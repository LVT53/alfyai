# Model Output Never Picks an Address That Is Fetched Without a Click

Status: Accepted (2026-10-12). Amended 2026-10-13 (FX-W): decisions 9 and 10, the summary mark in decision 5, and the WebRTC entry of the open list.

Alfy reads pages, emails and files a stranger may have written, and the local model is uncensored, so a prompt injection in them can make it write an address with private data hidden in the path, the query or a subdomain. As a link that address is harmless: following it is the reader's choice. As a request nobody clicked (an `<img>`, a favicon, a page the server reads for the model, a picture a report embeds) it hands the data to whoever owns the address. So **an address the browser or the server requests on its own must come from the user's own messages or from a tool's result, never from the model's words.** Model-written markup also stays inert: no forms, no overlays.

The owner approved this on 2026-10-12 as the prerequisite for [ADR-0067](0067-alfy-works-on-your-computers-through-an-outbound-agent.md), which puts file contents and command output in the model's context. The brief is [`docs/plans/exfil-channels/design.md`](../plans/exfil-channels/design.md).

## Decisions

**1. One shared vocabulary.** `src/lib/shared/url-provenance.ts` is where both sides compare addresses: the comparison key (host without `www.`, path and query exact, scheme and fragment ignored), the addresses in a text or a tool payload, and what a message's own tool calls returned (`toolImages`, `toolSourceHosts`, read from the calls' candidates, which the server writes from the tool's results; a call's input never counts).

**2. One gate for HTML.** `sanitizeHtml` removes every attribute that makes the browser fetch unless its caller allows that exact address. So file previews, the Document history preview and Mermaid get nothing remote by default. Model markdown also loses forms, popovers, positioning CSS and class names the renderer did not write itself (the app's global utility classes could otherwise draw a fake login screen over the chat).

**3. A chat reply shows only pictures its own tools returned.** An image_search result is shown as Brave's 500 px thumbnail through the same-origin `/api/image-search/thumbnail` route, and the Immich photo proxy stays as it is. Any other image becomes a visibly external link chip and is never fetched. The CSP's `img-src` drops `https:`.
Rejected:
- **Originals straight from their hosts:** the renderer would be the only defence, and every host sees the reader.
- **A full proxy of originals:** a DNS-pinning SSRF guard, a cache and, in a sample of Wikipedia lead images, a 2.3 MB median per picture through the home server. A 500 px copy averaged 68 KB.

**4. The server keeps, per user and in memory only, the hosts and thumbnails tools returned.** The favicon proxy, the thumbnail route and report favicons fetch nothing else. It is filled when a tool returns and when stored messages are read, so old chats keep their icons. It never touches the database, because an incognito chat promises no writes.
Rejected:
- **A table:** a migration, a backfill, and incognito tool results written to disk.
- **Signed URLs:** a signature at every place a source reaches the browser.
- **A message id on every favicon request:** five components to thread it through, and no answer while a reply streams.

**5. fetch_url and produce_file check provenance in code, per turn.** An address must appear in this conversation's user messages, or in a tool result: this turn's full payloads, including links on pages already read, plus earlier turns' stored sources. A tool whose output is the model's own words (`run_python`, `produce_file`, the artifact tools) is not a source, or `print("https://…")` would launder an address. Nor is the text of a connector result that a local model summarised for a cloud chat model: that model read the user's mail, events or files, a stranger's email among them, so an address in its summary may carry what it read. Such a call counts only through its candidates, which the server writes from the provider's own answer (an event's or a file's link). Every summary is asked for in one place, `decideLocalDistill`, which marks the tool call it runs in; the tool envelope stores the mark on the call (`localDistilled`), so later turns read it too. The mark fails closed: asked outside a tool call, `decideLocalDistill` refuses before the local model reads anything, and `markCallLocallyDistilled` throws, because a summary nobody marked would count as a tool's own words (it used to do nothing there, so a connector path added outside the envelope would have passed every test). The one summary that is not a tool's result, the proactive connector block spliced into the prompt, asks with `decideLocalDistillForPrompt`: no mark, no call, and an address in the prompt never counts for fetch_url or produce_file anyway; a test holds the list of who may ask. A refused address never reaches Parallel, and the model is told why. A produce_file picture that fails the check is left out of the document with a warning.

**6. The server's own fetchers resolve before they connect.** They refuse if any resolved address is not public, and they connect to the address they checked. Before, they checked IP literals only.

**7. SvelteKit's CSRF origin check is back.** `trustedOrigins: ['*']` was a patch for an internal OCR route that has since been deleted. Nothing posts forms across origins.

**8. `frame-src` is enforced on every page even when `CSP_MODE` is report-only.** This is a deliberate exception to the CSP rollout in [`docs/security-headers.md`](../security-headers.md), because model-written App code can otherwise navigate its own frame to any address. Measured in Chromium: eight ways of navigating the frame (`location`, `window["loc"+"ation"]`, `assign`, `replace`, a meta refresh, an anchor click and two more) reached an outside host without it, and none did with it. `off` still removes all CSP, as the escape hatch.
Rejected, measured to do nothing:
- **A Navigation API guard in the App's bootstrap:** the `navigate` event never fires in a sandboxed, opaque-origin frame.
- **`X-DNS-Prefetch-Control: off`:** it changed nothing in any probe.

**9. An App's WebRTC and frames are held in the browser.** Chromium's CSP does not govern WebRTC: a peer connection sends STUN and TURN requests (UDP, and TCP for TURN over TCP) to a server of the App's choosing as soon as it gathers candidates, with no click and nothing a policy asks about, and the App audit can only look for words. The CSP's own `webrtc 'block'` is not honoured (Chromium 147 reports "Unrecognized Content-Security-Policy directive 'webrtc'" and the datagrams still arrive), so the brake is in the App's document.

Measured in Chromium 147 (Playwright 1.59) against a fake STUN/TURN endpoint the test owns, counting UDP datagrams and TCP connections (`tests/e2e/app-webrtc-guard.spec.ts`; controls show a page outside the frames and the App under the product's exact sandbox and CSP both reach it). Before this decision: 13 routes to the constructor in the App's own realm (the plain name, the prefixed name, a name joined or decoded at run time, `globalThis`, `self`, `with (window)`, `Reflect.get`…), and 23 ways of making a document of the App's own that ran its script with a fresh constructor (`srcdoc` through six spellings, `innerHTML` and its relatives, `document.write` whole and in pieces, a `javascript:` source, XSLT). After it: none, and mutating the fix in two places (no write-prefix rule; XSLT left in) each fails the spec.
- **The bootstrap is the first thing in the served document.** It used to go in after the first `<head` anywhere in the text, so a script before it, or the word in a comment or a string, ran first; and the reader that looked for the end of a doctype's comments looked for `-->`, so `<!-->` hid a script from it. The bootstrap now stands at offset 0, with a copy of the leading doctype ahead of it so the page stays out of quirks mode (a comment's end is read the way the tokenizer reads it). Before anything else it makes `RTCPeerConnection`, `webkitRTCPeerConnection`, `mozRTCPeerConnection`, `RTCDataChannel`, `XSLTProcessor` and `documentPictureInPicture` `undefined` and unconfigurable.
- **A frame the App makes itself is kept from existing.** It has a window of its own with its own constructors; the parent cannot reach into it (it is cross-origin: `contentWindow` and `window[0]` throw), `frame-src` is not asked about `about:srcdoc`, and the frame runs the script it is given. The document is served with `require-trusted-types-for 'script'; trusted-types default`, and the bootstrap's default policy refuses `iframe.srcdoc` always, any string with a frame tag (`iframe`, `frame`, `frameset`, `fencedframe`, `portal`, `object`, `embed`) in any HTML sink, and a `document.write` that ends where such a tag could be going: a parser puts a write in front of the rest of the document, so a tag can be finished by the next write or by the document's own text. Scripts and script URLs pass through (the CSP decides those), so an app's own string handling is unchanged. XSLT is removed because it builds elements and attributes with no string passing a sink: it was the one route Trusted Types did not cover. A blank frame still works and is inert (cross-origin, and a `javascript:` source is refused as a script sink), and the CSP still refuses `blob:`, `data:` and same-origin frames.
- **A document whose own markup carries a frame tag is not served.** A parser makes a document of it with no script running, and nothing in the browser stops that. The App route answers a 422 notice in the App's frame, with the App's own strict headers and in both languages; the code stays in the Code tab, and a saved version is refused the same way (`not_runnable`). The scan is text and over-approximates on purpose (a tag in a comment or a string is refused too): a scan that understood where a tag really was would be a second HTML parser, and every place it disagreed with the browser's would be a way round it.
- **The audit's second layer** reads the obvious spellings (joined, escaped, `fromCharCode`, `atob`, a joined list; `stun:` and `turn:` addresses) and adds `no-nested-frames`, so the generator's retry names what it wrote and the writers refuse a body that has it. It is not the guard: a name can be built from anything the code computes.

Measured and left alone, because they were already closed: `contentWindow` of a blank frame, `blob:` and `data:` frames and `object`/`embed` with a `data:` address (the CSP), pop-ups (the sandbox), workers and dynamic `import()` of a data address (the CSP), `fetch`, XHR, `WebSocket`, `EventSource`, `sendBeacon`, `WebTransport`, an image, `preconnect`, `prefetch`, `preload`, a stylesheet, a ping, a CSS url or import or font, audio and video (all reach nothing, by the same measure), and Document Picture-in-Picture from a frame ("only allowed from a top-level browsing context"; removed anyway for an App opened on its own).
Rejected:
- **`webrtc 'block'` in the CSP:** ignored today, and it makes every App log a console error. The control in the spec fails the day Chromium honours it; add the directive then.
- **Reaching into the nested frame from the parent** (`contentWindow`, `window[0]`, wrapped DOM methods, a `MutationObserver`): the child is cross-origin, and a frame's script runs in a task the parent cannot be sure to beat.
- **A nonce or hashes for the App's own scripts:** the App can read its nonce, and a script that behaves differently in a child quotes any hashed script into a frame; an allowlist of the App's code does not separate it from its child.
- **Trusted Types with no default policy:** every string sink refused, and every `innerHTML` in every App with it.
- **Refusing every audit violation when the App is served:** the browser brakes (decision 8, this one) are tested by seeding such bodies past the audit; only the frame tag, the one thing no browser feature stops, is asked at serve time.

**10. A generated HTML report's preview is held to `img-src data:` too, and its pictures are in the file.** The report is the one script-capable page the app previews, and both its header and the preview's srcdoc meta tag allowed `img-src https: http:`: under report-only (the production default) the renderer's escaping was the only gate on what a report fetched, and a report opened outside the app called every host it showed a picture from. A report's https pictures are now fetched when it is rendered, through the loader the PDF already uses (the outbound guard, public addresses only; at most 12 pictures, 3 MB each, 12 MB together), and inlined as `data:` URIs; one that cannot be had is the placeholder with its alt text, and the renderer writes a remote address nowhere a browser would load it. The header, the meta tag and the client's recogniser of the report profile (directive by directive and exactly) agree on the policy, and a browser spec adds a remote canary picture after rendering and shows the policy refuses it.

## Consequences

- Pictures in chats from before this change have no stored thumbnail, so they show as links.
- The ledger assumes one server process. After a restart it refills when a chat is read, but a stored Canvas live-web block shows globes until it is refreshed.
- An address the user wrote only in their instructions, an attached document or a skill's text is refused by fetch_url until they type it or a tool reads it.
- With local summarising on and a cloud chat model, a link inside a summarised email or event (a newsletter's article, say) is refused by fetch_url; the event's or file's own link is not.
- A generated HTML report previewed in the app is held to `img-src data:` whatever `CSP_MODE` says (the policy is the report's own, not the page's) and carries its pictures as bytes. A report rendered before decision 10 still names a remote picture, which the preview now refuses: it shows the picture's alt text until the report is made again.
- An App that makes a frame, or uses `RTCPeerConnection`, XSLT or Document Picture-in-Picture, no longer works, and one whose own markup has an `<iframe>`, `<frame>`, `<object>` or `<embed>` tag is not served at all (the notice and the Code tab remain; an App stored before this change meets the same refusal). `iframe.srcdoc` is refused, and so is a `document.write` that ends in `<` or in the beginning of one of those tag names. A blank frame is fine.
- Some leaks remain, and this ADR names them so nobody mistakes them for closed:
  - **Which address:** a model can still leak a little through *which* tool-returned address it embeds or fetches, for example an attacker page with one link per letter. That is low bandwidth and comes with any provenance rule.
  - **DNS inside an App:** Chromium opens a connection to a blocked navigation's target before CSP refuses the request, so a hostname that carries data can still reach its owner's DNS.
  - **Memory excerpts:** `memory_context` results count as tool results, and they can quote the model's earlier prose.
  - **Connector summaries stored before the mark:** a summary stored on a call before calls were marked carries no mark, so in its own conversation the addresses in it still count as a tool's.
  - **WebRTC inside an App, what decision 9 does not close:**
    - *Engines other than Chromium 147.* Removing the constructors is plain script and holds anywhere; the nested-frame brake is Trusted Types, measured in Chromium only. In an engine that does not enforce it, a script-made frame still runs its script with constructors of its own (the route's refusal of a frame tag and the removal of XSLT still apply). Firefox and Safari were not measured.
    - *A way of making a document that nobody has thought of.* The brake is a list of the platform's ways to make one: a string through a sink (Trusted Types covers them all), markup in the App's own text (the route refuses it), XSLT and Document Picture-in-Picture (removed). XSLT was found by this work, outside Trusted Types, so the list is not closed by construction: a platform feature that makes a document without a string passing a sink reopens the route until it is added. `app-webrtc-guard.spec.ts` is the tripwire, and the `webrtc 'block'` control tells the day a better mechanism exists. Re-run it on every Chromium upgrade.
  - **Files opened outside the app:** a file the model produced can reference remote content when the user opens it elsewhere, and an App downloaded as an `.html` file runs there without the bootstrap or the CSP.
