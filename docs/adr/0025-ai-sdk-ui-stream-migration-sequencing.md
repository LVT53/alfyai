# AI SDK UI streams and messages ship before the next remote deployment

Accepted. The staged migration retired Langflow before replacing the Browser SSE Protocol with AI SDK UI stream framing. Normal Chat retains app-owned durable messages; the 2026-11-11 amendment records the structural envelope decision. The options and migration rationale below describe the original sequencing decision, not an outstanding prerequisite to repeat the migration before deployment.

**Considered Options**

- Replace Langflow and the browser stream protocol in one migration.
- Keep the Browser SSE Protocol permanently and treat AI SDK UI streams as irrelevant.
- Retain AlfyAI's existing durable chat message schema and translate AI SDK UI streams at the runtime boundary.
- Retire Langflow locally first, then migrate to AI SDK UI streams and UI messages as a separate browser/runtime pass before remote deployment.

We chose the staged local migration because AI SDK UI streams and UI messages reduce long-term custom protocol and translation ownership and align better with Vercel's UI tooling, but switching stream/message contracts while replacing Langflow would combine two high-risk changes: model runtime behavior and browser chat runtime behavior. During the first local pass, AI SDK stream and tool parts were adapted into the existing runtime to complete Langflow removal. During the stream pass, AI SDK UI streams intentionally superseded ADR-0016 for the browser-facing contract while preserving app-owned active-stream lifecycle and durable message persistence. Normal Chat persistence may still move to an AI SDK UI message-compatible shape in a later pass. This private deployment may reset the database instead of carrying a legacy conversation migration if that produces a cleaner runtime before the next remote deployment; only configuration needed to bring the new runtime online, such as admin access, model/provider configuration, prompts, defaults, and still-relevant system skills, should be preserved or re-seeded. The stream pass needs tests for reconnect, stop/detach, generated files, context sources, message evidence, queueing, and durable completion metadata before deployment; the message-persistence pass needs equivalent persistence and reload coverage.

**Amendment (E1, 2026-08-15) — stable error codes ride the existing `data-stream-error` framing; no new part names.** The architecture-deepening programme's error-seam slice (E1, server half) consolidated four scattered substring/prose error classifiers (`chat-turn/stream.ts`'s `classifyStreamError`, `chat-turn/stream-fallback-policy.ts`, `normal-chat-model/failover.ts`, `normal-chat-model/provider-compatibility.ts`) into one cause-classification seam, `src/lib/server/services/error-cause.ts`, plus a `classifyStreamErrorCause` wrapper in `stream.ts` that maps a structured cause onto the existing `StreamErrorCode` type. This amendment records that the fix stays entirely inside the payload `data` a stream part already carries — it does not add, rename, or repurpose any AI SDK UI stream part `type`:

- Turn-level failures continue to use the existing `data-stream-error` part (`streamErrorEvent`/`streamRequestErrorEvent`); only the `code` value populating it is now derived from structured signals (HTTP status, `.name`, AI SDK error classes) instead of matching arbitrary substrings like `"prompt"` or `"abort"` against `error.message`, which could coincide with unrelated or user-authored text.
- Tool-call failures continue to use the existing `data-tool-call` part. A failed call now reports a genuine `status: "failed"` (added to the existing `"running" | "done"` union — a new enum member inside an existing part's payload, not a new part name) instead of a `"done"` status that only hinted at failure through `metadata.ok === false`. `metadata.errorCode` on that same payload is a `StreamErrorCode` value from the same `classifyStreamErrorCause` seam, so tool-call failures and turn-level failures share one code vocabulary.
- Truncation/content-filter/file-production-failure notices, which used to be English sentences concatenated into the persisted assistant message body, now ride as a `completionWarningCodes: ChatTurnCompletionWarningCode[]` array on the existing `data-stream-metadata` part instead — again an added field on an existing part, not a new part.
- The `/api/chat/send` non-streaming JSON error response gained a `code` field (an `errorKey`) drawn from the same `classifyStreamErrorCause` seam, so send and stream failures share one code space; this is a JSON body field, not a stream part at all.

E1 defines the codes; localizing them into user-facing copy is E2 (client), which still owns `src/lib/services/streaming.ts` and `src/routes/(app)/chat/[conversationId]/_helpers.ts`'s rendering of `data-stream-error`, `data-tool-call`, and `data-stream-metadata` payloads.

## Amendment (2026-11-11) — structural output and bounded read-only replay

Normal Chat retains its app-owned durable message envelope with additive versioned structural output/completion metadata; this change does not migrate storage to raw SDK UI messages or reset legacy conversations. Existing legacy content remains readable without heuristic rewriting.

- `data-normal-chat-output` carries scoped block/step role settlement and completion; `data-stream-metadata.observation` carries scoped pending/terminal/unavailable truth. These are additive app data on AI SDK UI framing, not a second transport protocol.
- [Shared codec](../../src/lib/services/ai-sdk-ui-stream-contract.ts) owns frame grammar, terminal detection and metadata extraction; server stream helpers own application payloads. Browser transport decodes; ModelRun owns role settlement.
- One [wire journal](../../src/lib/server/services/chat-turn/stream-replay-journal.ts) retains complete replay within 200,000 encoded bytes/10,000 retained frames. It combines deltas by scoped block, preserving their first sequence and all structural settlement events; incremental SSE input is framed before retention. The reviewed 3,157-token turn fits below 40,000 bytes and 30 retained frames. Live subscribers still receive original deltas immediately. Reconnect creates a fresh transport accumulator and atomically replaces the retained partial view after replay; a compact snapshot must never be appended to an old accumulator. Crossing either bound invalidates replay and releases retained frames; a truncated suffix must not masquerade as a complete answer. Saved-state observation resolves through the existing reconnect owner.

We choose bounded all-or-unavailable replay over parallel token/timeline authorities or partial-prefix repair. This limits retention and preserves structural order, at the cost of saved-state recovery once replay is unavailable. Reconnect never gains authority to generate ([ADR-0041](0041-stream-admission-before-turn-preparation.md)).

Evidence: [journal tests](../../src/lib/server/services/chat-turn/stream-journal.test.ts), [reconnect tests](../../src/lib/server/services/chat-turn/stream-reconnect.test.ts), [browser transport tests](../../src/lib/services/streaming.test.ts), [output reducer tests](../../src/lib/shared/normal-chat-output.test.ts).

## 2026-11-11 — negotiated compact output deltas

Clients explicitly request `compact-v1` output before the server emits `data-normal-chat-delta`. Its `{ref, sequence, text}` payload references the full scoped `block_start` sequence on that connection. The shared decoder reconstructs canonical scoped events and rejects unknown, ended or conflicting references. First progress is immediate; following same-block deltas flush within25ms or4KB, and every structural boundary flushes before role withdrawal/settlement. Persisted events and replay remain canonical. Legacy clients receive full events; reconnect broadcasts expand compact deltas before fan-out, so an older observer remains compatible. Legacy text/reasoning frames are suppressed only once structural completion output is active; internal content capture remains available for persistence. This is an explicit addition to the exact data-part allow-list, not an error-code payload change.
