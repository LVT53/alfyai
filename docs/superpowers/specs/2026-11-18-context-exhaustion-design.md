# Context exhaustion: bounded new reads and lossless closing

Status: both slices independently SPEC PASS on 2026-11-18; implementation is authorized by the controller under the user-requested SDD workflow. Inspected base `codex/context-exhaustion` at `3b78f02e24011584fc40dabdc54184817321b6ab` (2026-11-18).

## Decision

Prevent NEW research/fetch results from consuming their aggregate remaining allowance by selecting bounded model-facing views before recorder observation/capture. Recover remaining working capacity pressure through the existing single tools-disabled closing, with output allocation from remaining room on the original destination only. Captured context is immutable. No replay, post-capture shortening, raw-result store, new pipeline or destination escape hatch.

The reported incident (about 98 seconds of research/fetch, empty answer, capacity exit) lacks exact sizes. Neither catalogue-only pressure nor true aggregate overflow is established as its measured cause. Acceptance therefore includes oversized NEW reads, sequential accumulation and parallel reads, as well as lossless closing. Passing Task 1 alone does not complete the fix or prove incident repair.

## Findings and owning seams

- `normal-chat-model/completion.ts:556–578`: `assertFits` charges messages, system, catalogue, the frozen prepared output cap and 4,096-token margin; unknown limits fail closed. Both initial preflight and SDK `prepareStep` use it.
- `completion.ts:1053–1091`: each next step projects the full canonical retained transcript. A result can fit its tool's per-call limit yet exhaust the aggregate prompt. Pending step images enter in `prepareStep`, after initial preflight; closing allocation must include them too.
- `completion.ts:1424–1559`: stop, pause, uncertainty and filtering take precedence. Working `context_capacity` then unconditionally breaks at 1546, so catalogue-free closing is never considered. A step-budget exit already reaches closing, which still rejects when the frozen output cap cannot fit.
- Earlier tool-step prose has settled to activity. Returning `projectNormalChatOutput(...).answer` can therefore correctly return an empty string; `prepared-normal-chat-turn.ts` and `finalize.ts:573+` carry the structural outcome/events into persistence. Promoting activity or inserting a canned answer would conceal the engine failure.
- `prepared-normal-chat-turn.ts` resolves a finite output cap before initial preparation, budgets the catalogue through `requestRoom`, and owns attempt registration, tools and destination privacy. Keep this preparation fix. It leaves initial headroom, not an aggregate bound on subsequent tool results.
- `context-guard.ts` contains the older digest/truncation guard, composed in `normal-chat-model/index.ts` for legacy callers. Completion-policy callers enter the exact engine instead. Importing that guard into completion would violate its newer retained-context contract.
- `docs/plans/context-budget-guards-spec.md` slices 2/3 already describe per-call ceiling and shrinking guard. `normal-chat-tools/shared.ts:505` already calls `capModelPayload(compactModelPayload(...))` before recorder observation/return. Do not duplicate it. Its 32,000-token ceiling is shallow: primitive strings bypass it; nested non-array values can remain oversized. It is not a mathematical context bound.
- Fetch content is capped at 20k–48k characters (`resolveFetchContentCharCap`); research `readPages` splits that shared cap across up to two pages. The brief, source/evidence metadata, prior results and parallel calls still accumulate. Character limits are not token limits.
- Here “exact result” means the existing model-facing result after tool-owned shaping/envelope processing, retained with its execution fact; it does not mean the original unbounded external response.

## Proposed binding amendment

Amend only the unconditional capacity exit in completion contract `docs/plans/turn-completion/contract/spec.md` (“Bounds and escape conditions”), its frozen closing-output allocation in `implementation-plan.md:84,112`, and ADR-0026's oversized-continuation wording:

1. A working capacity rejection after current-segment upstream output or a tool occurrence may request the existing one closing. Do not turn an initial oversized catalogue/request with no progress into a tools-off answer. An explicit human resume also counts retained prior progress as eligible context; automatic terminal observation remains read-only.
2. Preserve stop/pause/uncertain-effect/filter/deadline precedence, existing delivery checks and the one-closing-per-segment allowance. Capacity pressure never selects a fallback. Retain `workingStopCause=context_capacity` when that caused the transition; a successful closing ends `answered/natural_stop`.
3. Measure Q from the actual tools-off, policy/vision/provenance-projected closing request: system + exact messages + closing instruction + pending inserts, with no catalogue. Preserve M=4,096. Let R=floor(W−Q−M).
4. Preserve O when it fits. If it does not, only when provider ID, base URL and model name equal `snapshot.original` may closing use C=min(O,R), provided C≥min(O,1,024). The 1,024-token floor is a proposed application policy, not a provider fact or answer-quality guarantee. Below it, fail `context_capacity`. Never reduce working output, reasoning effort, margin or retained evidence.
5. For every changed destination, including one chosen by human resume, retain the frozen O and existing whole-context privacy gate. No adaptive cap to make a smaller/different destination admissible. A compatible destination already selected by existing transport-failure policy may close only if its complete projected request fits with O.
6. Keep `snapshot.prepared.maxOutputTokens=O`; C is invocation-local. Use C in both SDK request and capacity assertion. No second closing, SDK generation retry or closing failover. A length/empty/error closing remains incomplete/failed under current structural rules; never promote activity.

The closing amendment relaxes output reservation and phase eligibility only. The separate bounded-new-view amendment below changes the fidelity boundary explicitly. Unknown limits remain fail-closed. All shipped refusal/read-only/deadline settlement, output-role, stop reconciliation, finalization-window, resume, accounting and observation fixes remain binding.

## Impacted cases and accounting

- A single huge result, many individually bounded results, large working text/reasoning, prefetched evidence and step inserts can all consume the window. Working and closing use the same serializer/count, including nonempty system prompts and tool wrapper output.
- Same-step parallel execution is intentionally permitted by `completion-tools.ts`; a next-step check sees the aggregate after settlement. Do not close as soon as the first result settles, cancel siblings to recover space, serialize calls, or classify pending writes as safe failures. Unsettled/provider-executed/preliminary effects retain existing uncertainty rules.
- A successful ask pauses even if a sibling result causes capacity pressure. Stop during asynchronous projection/counting/binding prevents dispatch; expired parent deadline, content filter and uncertain effects still prohibit closing. Read-only failures and engine working-deadline settlement keep their shipped certainty behavior.
- After transport failure, existing failover may select one policy-gated closing destination; capacity failure there is terminal. Exact v2 resume replaces only the answered ask result. V1 remains reconstructed legacy. Old captures receive no refetch, shortened evidence, extra allowance or rewritten execution identity.
- Capacity preflight rejection occurs after attempt registration. Current usage entries start null/`complete:false`, and a `prepareStep` exception can leave already reported working-step totals non-final. Preserve known charges once. Where rejection proves no request dispatched, record known zero usage; where every earlier dispatched step has final known usage and the next dispatch was prevented by capacity, finalize only those known totals. Unknown/missing provider usage must remain unknown. Do not infer zeros from a generic exception or closing success; preserve actual provider/model attribution and idempotent ledger linkage.
- The `maxToolSteps:1` “reports capacity failure without shrinking completed evidence” fixture already takes the closing path and proves genuine overflow, not the newly eligible working-capacity transition. Keep that counterexample. Existing initial-schema/exact-boundary tests must still reject with no closing.

## Bounded NEW web views: explicit fidelity amendment

Amend the completion contract and ADR-0026: exact retention begins at the **final bounded model-facing view** returned for a NEW opted-in research/fetch execution. Its payload, omission/coverage metadata, selected evidence and execution fact are retained unchanged through capture, closing, failover and resume. This is a deliberate change to what new reads expose, not a claim that older exact-fidelity wording already allowed shortening. Already captured results, original context, operation identities and old captures are never reshaped. No raw snapshot/store is added; existing ephemeral cache semantics remain.

### One budget owner and concrete interfaces

`completion.ts` remains the sole effective-request budget owner. Factor a local `measureRequest(input: {system?: string; messages: ModelMessage[]}, tools: ToolSet | undefined): Promise<{inputTokens: number; catalogueTokens: number; imageTokens: number; capacity: number; preparedOutput: number}>`, using the same counters and image-budget information as fit/closing. Task 2 consumes Task 1's exact projected step input; it must not independently reconstruct prompts or duplicate destination/output math.

Before each provider step, once, freeze a read pool B from that actual projected input. Reserve: current exact input/system/prior results; pending image costs/inserts; the maximum working output O; the closing instruction/framing; minimum closing output min(O,1024) on the original destination, otherwise O; M=4096; and one assistant/tool-message framing reserve plus one terminal capacity-refusal record. Measure known framing/refusal records with the existing estimator instead of assuming zero. Clamp B to zero for missing/invalid limits. Never use a full-window default when remaining room is unknown. Model reasoning/image estimates retain the limitations below.

`completion-tools.ts` owns the invocation-local pool state (attempt+step scope). Let U be unallocated tokens AFTER the fixed reservations above, excluding the separately held terminal-refusal reserve. For proposal i, h_i is conservative call/result framing and wrapper cost NOT included in the JSON payload estimate; f_i is the measured maximum compact JSON size of the fixed truthful failure view. Admit only if U≥h_i+f_i; choose p_i=f_i+floor((U−h_i−f_i)/2), debit U by h_i+p_i, and expose maxPayloadTokens=p_i, maxFailurePayloadTokens=f_i. Failure replaces success within p_i; it is NOT another payload or another f_i debit. Never charge already counted input/framing twice. The sum of debits cannot exceed the initial U; grants never refund/redistribute within the step, including cached/tiny/failed results. Prior-execution reuse remains before NEW lease admission.

On denial, maxPayloadTokens=0 does NOT limit the refusal: measure the fixed capacity-refusal payload f_d and actual wrapper h_d against the SEPARATE terminal-refusal reserve, debit h_d+f_d there, and expose maxFailurePayloadTokens=f_d. The envelope throws `ToolCallRefusedError` before `params.run`/cache/network and commits that nonempty bounded refusal through existing proven non-execution facts. After that reserve is consumed, further denials cannot borrow outstanding leases; if no independent refusal allowance fits, commit no unbounded payload, terminate explicitly as capacity, and keep the existing exact proposal/execution facts. Arbitrary further proposals may themselves force capacity failure; unlimited refusals are not guaranteed.

Ordinals come from scoped proposal order before awaiting the tool, never network/result completion order. Preserve concurrent execution; do not serialize or cancel dispatched siblings. Reserve the terminal refusal before leases so the first exhaustion can be reported. A pathological number/size of additional proposals or unrestricted other tools may still consume the reserve: final fit must fail explicitly, never promise universal closure. After settled work, read-exhausted ends the working loop into the existing closing; do not invite another model read attempt with no room. Stop/ask/uncertainty/filter/deadline/delivery precedence still applies.

Extend existing leaf `normal-chat-tools/model-payload-budget.ts` with these typed, opaque call-option helpers (private WeakMaps/WeakSet; no payloads or persistent store):

```ts
type ReadResultGrantSpec = Readonly<{ // engine supplies this to the binder
  turnId: string; segmentId: string; attemptId: string; stepId: string;
  executionId: string; proposalOrdinal: number; maxFailurePayloadTokens: number;
} & ({kind: "admitted"; maxPayloadTokens: number}
   | {kind: "denied"; maxPayloadTokens: 0})>;
type ReadResultGrant = ReadResultGrantSpec & {readonly [privateBrand]: true};
markBudgetedReadTool<T extends Tool>(tool: T): T;
supportsReadResultBudget(tool: Tool): boolean;
bindReadResultGrant(options: ToolExecutionOptions, grant: ReadResultGrantSpec): ToolExecutionOptions;
getReadResultGrant(options: object): ReadResultGrant | undefined;
```

Opt-in is registered against the tool's execute function so ordinary tool-object spreads retain it; research/fetch factories mark only their own returned tools. Only the engine calls the binder; the leaf brands/freezes its grant and adapters consume it read-only. Binding returns a fresh options object preserving every existing field and `experimental_context` by identity; a WeakMap keys that exact object to its grant. The wrapper passes it unchanged to the original execute function and the adapter passes the same object to `executeToolWithEnvelope` (its existing Pick type is structurally compatible). A denied grant reaches the envelope pre-run check, which throws `ToolCallRefusedError` inside its existing catch/recorder path BEFORE `params.run`; no upstream/cache access happens. An admitted grant supplies the shaping limit and alternative failure allowance; a denied grant supplies only its separately reserved failure allowance. No ambient SDK context property, sole-tool-name key or new global service. No grant means unchanged behavior only for callers without the completion budget capability, including the App verifier's `createResearchWebTool` caller. An active completion capability with unknown room must issue a denied grant/refusal, never silently omit the grant and fall back to legacy full-window sizing. Denied reads use a pre-dispatch capacity refusal, recorded as definitely-not-executed through existing facts; never label a completed read as not executed.

`web-grounding.ts` owns a pure `boundGroundedWebView(input: {result: GroundedWebResult; pages: GroundedWebPage[]; name: "research_web" | "fetch_url"; cached: boolean; maxPayloadTokens: number}): {modelPayload: GroundedWebModelPayload & WebViewCoverage; candidates: ToolEvidenceCandidate[]; metadata: Record<string, string | number | boolean | null>}`. Extend existing types there rather than introduce a parallel result protocol. Research/fetch adapters read the grant and call this before returning their envelope result, including on cache hits; filter/update the existing entry's candidates, summary and metadata together. Preserve entry identity and its execution fact.

### Selection and recording contract

- Preserve full existing view when it fits. Otherwise select source+evidence/page bundles in existing stable source order, keeping IDs and source links. Oversized page text may expose only a deterministic explicit prefix range: start=0, end exclusive in UTF-16 code units without splitting a surrogate pair, totalChars and hash of the already fetched normalized content. Keep exact returned prefix bytes; never substitute a digest. No new offset input, next-page promise, automatic paging or refetch; guidance says narrow the requested topic/URL to request more, which may require a new read.
- `WebViewCoverage` is `{bounded: true, coverage: "full" | "partial" | "none", omitted: {sources: number; evidence: number; pages: number}, pageRanges: Array<{sourceId: string; contentHash: string; start: number; end: number; totalChars: number}>, hint: string}`. Counts describe the already fetched/cached candidate set, not the whole website; range totals make partial pages explicit. Stable hash/offsets describe that content version only, with no guaranteed retained backing content. Fixed scaffolding/hints are English.
- Drop the unscoped answer brief on ANY partial source/evidence/page selection, including an omitted quote or shortened page body even when all source IDs remain. Keep it only for a full-fitting candidate view preserving all available supporting content; coverage:full refers to that fetched/cached candidate view, not merely source IDs. No claim parser/model call is added. Do not truncate JSON blobs or whole source IDs/URLs. Select quotes only with their returned source; prefix-page claims must be supported by the exposed range or a separately returned quote. Omitted source/quote/body facts have no factual citation eligibility. Selected source metadata alone can identify a source but cannot support unseen content.
- ALL candidate/chip/citation/provenance observation metadata uses only the selected view, including `createGroundedWebMetadata`, recorder `observeResult`, page candidates, counts, source lists and digest input; filtering the payload sources array alone is insufficient. Retain unrelated previously admitted provenance; do not revoke prior valid URLs. Apply existing URL admission and locality/distillation policy before view observation. A private fetched/cache result is not permission to forward raw content to cloud. Selection cannot retrieve omitted content to satisfy later failover/resume.
- The envelope owns ONE final commit boundary for capability-granted reads on ALL paths: success, returned failure and catch/onError. Measure the final compact JSON including coverage/notice/cache flags under maxPayloadTokens and 32,000 for success, or maxFailurePayloadTokens for refusal/error; framing/wrapper h is charged separately above, never spendable payload. Compaction/cap must preserve the selected semantics. Before digest/observe/record/return, validate the final view and selected-only candidates/metadata. No arbitrary onError text or stale success metadata may bypass this boundary.
- After a read, a malformed/oversized attempted view or onError output is replaced BEFORE commitment with the fixed truthful failure view within the admitted f_i allowance: success:false, coverage:none, no evidence candidates/citation support, bounded summary/hint/metadata. Do not reselect, truncate that attempted view or claim ToolCallRefusedError/definitely_not_executed after fetching/billing. If no useful unit fits, use this same returned-failure path. Pre-run denial alone is proven non-execution; post-read failure is known failed subject to existing abort precedence. No reserved failure allowance means explicit capacity without an unchecked payload commit.
- Exact equality assertions compare the same semantic final model-output view, including its SDK result wrapper, across recorder observation, capture and parsed wire output; they do not equate a JSON object to HTTP bytes. Test arithmetic at U=h_i+f_i and one below, a denied grant's nonempty refusal, and post-read selection-validation/onError failures through this boundary. Test all source IDs retained but a quote/page tail and its brief-only fact omitted: the committed brief, candidate and citation support must exclude that fact; exposed ranges/quotes remain usable evidence.

## Accounting and finite limits

Accounting changes remain conditional on a regression proving a capacity exit prevented dispatch: zero only for an attempt with no dispatched request; finalize earlier known totals only if all dispatched usage is final. Generic errors, missing usage and unknown transport tails remain unknown. Existing pricing/ledger owners and idempotent linkage stay unchanged.

NEW bounded single/sequential/parallel web reads must now demonstrate a bounded truthful admitted view and one structural closing when reserved input fits. Old oversized captures and unrestricted other tools remain exact and may fail explicitly. Lossless-closing-only success is not acceptance of the entire objective. Synthetic counts above are not production incident reproduction; record that uncertainty in the final report.

The estimator does not fully count reasoning/images; reuse available image costs and reserve maximum working output plus measured framing, but keep the final fit guard and actual provider rejection behavior. Arbitrary model output, mixed non-opted-in tools, old captures, unsupported projections or exhausted deadlines can still prevent a nonempty answer. No universal growth, tokenizer or semantic-quality guarantee is made. No extra approval cycle is required for the user-authorized bounded-result objective; the controller incorporates the explicit amendment after judge acceptance.
