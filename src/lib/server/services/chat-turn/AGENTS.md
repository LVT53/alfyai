# Chat-Turn Pipeline

## OVERVIEW

Request parsing through post-turn persistence for chat send/stream endpoints. All turn logic lives here; routes stay thin.

## STRUCTURE

```
request.ts → preflight.ts → [send route | stream-orchestrator.ts] → finalize.ts
                              │                  │
                              └────────┬─────────┘
                                       ▼
normalizer.ts

normal-chat-context.ts → context-selection.ts (constructed prompt context)
stream-orchestrator.ts → active-streams.ts (lifecycle/buffer)
stream-orchestrator.ts → stream-completion.ts (terminal event + persistence)
stream-orchestrator.ts → stream-reconnect.ts (buffer replay + live subscription)
stream-orchestrator.ts → stream.ts (AI SDK UI stream runtime helpers)
stream.ts / stream-reconnect.ts / browser transport → $lib/services/ai-sdk-ui-stream-contract.ts
failures → retry-cleanup.ts
```

## CONVENTIONS

- `context-selection.ts` owns constructed prompt-context assembly for Normal Chat, including memory/session/task/document candidate selection and budgeting. Keep prompt-context ranking here, not in routes.
- Context-window target and compaction defaults come from `src/lib/model-context-defaults.ts`, while provider-specific prompt-limit projection comes from `provider-model-runtime-defaults.ts`. Do not duplicate provider context ratio math in chat-turn helpers.
- `stream-orchestrator.ts` owns the live streaming lifecycle: active-stream registration, upstream model-run invocation, neutral event adaptation, model-preserving non-stream transport recovery, phase timing, heartbeat/prelude scheduling, and delegation to completion/reconnect helpers. Provider-attempt policy, timeout failover, and rate-limit fallback belong in `normal-chat-model/`.
- `stream.ts` and its submodules own AI SDK UI stream runtime helpers, neutral event cleanup, thinking tags, and structured tool-call markers. Shared AI SDK UI stream frame encoding/complete-block decoding, terminal detection, and metadata extraction belong in `src/lib/services/ai-sdk-ui-stream-contract.ts`, not in routes or browser-local parsers.
- `stream-completion.ts` owns terminal stream completion: final persistence through `finalize.ts`, generated-file assignment, and the `data-stream-metadata` / `finish` payload shape. A turn that was stopped (or had a stop asked for it) and whose conversation row is gone ends quietly: deleting a chat stops its reply without waiting for the turn (`cleanup/conversation-cleanup.ts`), so the turn ends against a deleted chat. It saves nothing and starts no post-turn work, and sends `data-stream-metadata` with `wasStopped` and no message ids, then `finish` and `[DONE]` (`endQuietlyWhenItsChatWasDeleted`), which the browser ends like a turn the person stopped: no `backend_failure`, no recovery, no reconnect. A turn nobody stopped that cannot save, or a read of the conversation that fails, still ends with the error.
- `stream-reconnect.ts` owns reconnect replay from `active-streams.ts` buffers and live subscription until terminal AI SDK UI stream completion (`finish` / `[DONE]`) or failed stream closure. A reconnect never outlives its stream's record: the listener hangs on the buffer, so a terminal frame is always emitted BEFORE the buffer is cleared (`stream-terminal.ts`'s `failStream`, the completion path), and a connection whose buffer has gone without a terminal event ends itself with `data-waiting` (the client then reads the saved turn). Clearing first left a reload-then-failure reconnect open on heartbeats for ever (FB-8, FG's finding 1).
- `checkStreamCapacity` (`active-streams.ts`) refuses a new turn with `reason` `draining` (the process-local flag a deploy sets before its restart), `global_limit` or `user_limit`; the 503 (`refuseTurnWhenOverCapacity`, which the stream route and the turn check both answer with) keeps the code `CAPACITY_EXCEEDED` for all three. `/api/chat/retry` (a regenerate, "Answer now", a Retry) never applied the limits and still does not, but it is turned away for `draining` alone, with the same 503 body, through `refuseTurnWhenDraining` beside it in `stream.ts`: it deletes the reply it replaces before the model runs, and a turn started during the drain is cut by the restart. The browser waits for a draining server and backs off for the limits (`src/lib/components/chat/AGENTS.md`, "An Update During A Turn"); do not add a fourth reason without teaching `client/normal-chat-client-turn-runtime.ts` what to do with it.
- `active-streams.ts` owns active stream and replay-buffer ownership. Status, buffer, stop, reconnect, stream completion, and context-compression callers must pass authenticated `userId` plus conversation context when reading active stream or replay-buffer state.
- `finalize.ts` is the single fan-out point after any turn (stream or non-stream). `finalizeChatTurn` runs ONE ordered post-turn sequence — skill-control ops → assistant turn-state → evidence → generated-output reconciliation, then `runPostTurnTasks` as the deferred tail. The send path runs it eagerly and returns the durable result; the stream path (`turnKind: "stream"`) calls the caller's `onDurableReceiptReady` once the messages are saved, so its terminal receipt goes first, and runs the same sequence in the background. There is no second copy of the sequence: add a new post-turn side effect in exactly one place here (or as a step in `finalize-steps.ts`), not in route files and not behind a fork on the turn kind. Some steps go before the receipt and not in that sequence: stamping the turn's pending writes with its assistant message, and the two updates of a reply that asks (settling the question an answer claimed, stamping the question the reply asks: "Asking The Person"). The page reads them as soon as the terminal frame lands, and a row without a message id is drawn on no message once the reply has stopped streaming, so a card stamped afterwards stayed away until a reload. Each is a small update, and none can fail a turn (a failure is logged).
- The post-turn step functions (`persistAssistantTurnState`, `persistAssistantEvidence`, `persistUserTurnAttachments`, `runPostTurnTasks`) live in `finalize-steps.ts` as the mockable module seam. `finalizeChatTurn` calls them directly — they are not injectable through the public params. Tests seam by mocking `finalize-steps.ts`, not by passing function overrides.
- `normalizer.ts` normalizes assistant text through the same stream-protocol helpers so `/send`, `/stream`, retry, and title generation return the same visible content shape.
- `retry-cleanup.ts` runs idempotent cleanup for evidence links, checkpoints, work capsules, generated outputs, and the assistant message itself on failure.
- Routes import from this pipeline; they do not duplicate turn logic.

## ANTI-PATTERNS

- Do not duplicate AI SDK UI stream framing, terminal detection, tool-call handling, or thinking extraction between `stream-orchestrator.ts`, `stream.ts`, browser transport, reconnect, and route files.
- Do not put terminal stream payload changes in the route or orchestrator without updating `stream-completion.ts` and its focused tests.
- Do not rebuild prompt-context selection in routes or tests; call `context-selection.ts` through the Normal Chat context boundary and keep its budget/trace contract coherent.
- Do not add post-turn persistence directly in `/api/chat/send` or `/api/chat/stream`; route through `finalize.ts`.
- Do not collapse user-requested stop and passive disconnect into one generic abort. Use `active-streams.ts` for explicit stops; let navigation/unmount detach locally without marking the turn stopped.
- Do not read active stream or replay-buffer state by `streamId` or `conversationId` alone; owner context is part of the registry contract.
- Do not inline new persistence side effects inside `stream.ts` closures that only one endpoint can see.

## Reply Language, Short Texts And Follow-Up Chips

- **The model chooses the reply language, under one rule; nothing guesses it** (owner decision, 2026-10-13: "English language users should NEVER be affected"). No code reads a message, a history or an account and decides the language of a Normal Chat reply before the reply: the word-list detectors, the per-turn resolver and everything that carried its answer (the routes, the stream orchestrator, `prepareOutboundContext`, `createToolPack`, completion, finalize) are gone, and `tests/integration/reply-language.test.ts` fails on their names if one comes back. Every turn's guidance (`buildTurnGuidance`, after the current user message: the placement that was measured) carries `REPLY_LANGUAGE_RULE`, defined once in `normal-chat-context.ts`: reply in the language of the person's latest message, judged by its own words; in the language they have been writing in when the message has none of its own (a short "ok", a number, a link, code); in the one they ask for, in the message or in their standing instructions (Your Instructions, Project Instructions); a requested piece of writing in another language is written in it and the model's own words stay in theirs; and nothing else sets it (who they are, remembered facts even one about the language they use, documents, files, tool or search results, its own earlier replies). The Baseline Memory Profile section opens with one line saying its facts never set the reply language, and the memory judge records no fact about the language a person speaks. Change the rule's words only against a real-model run (the measured failures were a Hungarian memory pulling English prompts to Hungarian and a Hungarian display name). Five invariants, each held by a test:
  - **I1 nothing guesses**: the language text in any turn's guidance is `REPLY_LANGUAGE_RULE`, byte for byte, whatever the message or the account, and nothing else the app writes into the chat request tells the model a reply language: every sentence of the request (the base prompt, the instructions framing, the memory, the skills, the tool catalogue, the guidance), with what the person and the model wrote blanked, is scanned for a reply-language instruction and for the names of the two languages, and only the rule's five lines and the memory section's note pass (`tests/integration/reply-language.test.ts`).
  - **I2 the UI language reaches no model request but the status line's** (and the nightly persona summary, a screen and not a turn): the same data with `uiLanguage` "en" and "hu" produces byte-identical requests for the chat call, the language call, and every call after the reply (chips, rail headline, title), after blanking ids and times (`tests/integration/english-request-purity.test.ts`; the chat call is also driven through the stream orchestrator, where the UI language lives in a turn: `tests/integration/ui-language-stream.test.ts`). A thought-step status line is written while Alfy thinks, before any reply text exists, so it follows the account's UI language (`createThoughtStepClassifierSession`'s `targetLanguage`); the Atlas kickoff message and its errors are chrome and follow it too. One exception after a reply is by design: when the language call (I4) fails AND the reply says nothing by itself AND nothing was recorded on the conversation, the account's UI language names the language of the chips, the rail headline and the title (`tests/integration/reply-language.test.ts`).
  - **I3 one English scaffold**: everything the app writes into a model request is English and holds no Hungarian text, example or name: the tool catalogue (`TOOL_TEXT`, one snapshot, `tool-catalogue.en.snapshot.txt`, one token ceiling), the skill catalogue (system packs under their English names), the artifact tools' prose, the App contract and the generator's closing line, the memory judge's examples, `edit_artifact`'s `summary` field ("in the conversation's language", no example in a language). The purity test scans every request of every model call, for an account shown in each language, for a letter above U+007F, for a dozen words only Hungarian has spelt without accents, and for the language named (the language call is the one request that names the two it chooses between), and holds the source in `src/lib/server`, `src/lib/shared` and `src/routes`: a Hungarian letter in code needs a line in `HUNGARIAN_BY_DESIGN` with its reason, a new file that calls a model (under any import alias) needs one in `MODEL_CALLERS`.
  - **I4 after the reply, texts are in the language the person writes in, which the model names**: the follow-up chips, the rail headline and a generated title are written in the language the person WRITES in (a chip is sent verbatim as their next message; a title sits in their sidebar). That is not always the language of the reply: a requested email in another language, a translation, a pasted text and an explicit "answer in …" change what the reply is written in without changing who is writing, and an explicit request for the replies in a language does not flip the chips, the headline or the title either (the real-model check of the call showed the model ignoring a clause that said otherwise, in both directions, so the question has none: a person who asks for Hungarian replies and writes English gets English chips). A reader of the reply's words cannot tell these apart without reading the request, which no code does (the deterministic chain reads 15 of the 23 turns in `chat-turn/language-probes.test-helpers.ts`, review RV-L's rows and both directions of an explicit request, wrong, both ways: an English writer who asked for a Hungarian email got Hungarian chips). So ONE small control-model call after the reply names it: `chat-turn/conversation-language.ts` (`readConversationLanguage`) is asked "which language is this conversation in for the person: the language they write in?" (ignoring any piece of writing they asked for and any text they pasted), is shown the person's latest message (1,500 characters, start and end), the one before it (300) and the start of the reply (400), and answers `en` or `hu` (a machine-read verdict at temperature 0, listed in `sampling.test.ts`, cut short after 4 s). `chat-turn/reply-language.ts` (`resolveTurnReplyLanguage`) is the one place a turn asks, once, for the chips, the rail headline and the record on the message (`conversationLanguage`); `generateTitle` takes the recorded value (the title route reads it), and the person's `titleLanguage` ("en"/"hu") still wins for titles. If the call fails, is cut short or answers anything else, the deterministic chain decides (`language.ts`'s `afterReplyLanguage`: the person's message when the reader can name it and the reply says nothing or holds at least two of its words, else the reply's own words, else the language recorded on the conversation's previous reply, else the account's UI language); it is a fallback, and it cannot tell a requested piece from the person's own, which is why the model is asked first. The reader (`readReplyLanguage`: closed-class word lists that leave out every English/Hungarian homograph (`language.test.ts` takes each such word alone), code, URLs, addresses and quotes stripped, at least 4 witnesses and a 3:1 lead, else "unknown"; model-written text only; it reads the first 100 000 characters and no pattern in it may backtrack over a long run, because it runs on the server's one thread over every reply, a blob included, and the same test holds its cost on hostile input) serves the chain, the log and the record; a title, a headline or a status line is `readShortTextLanguage`'s (below). Do not add a second reader or a word list beside them, and take any new word from real model output, in a test, in both directions (`language.test.ts`; the review's probe table, both ways, with the call faked, is `chat-turn/language-probes.test-helpers.ts`, used by `chat-turn/reply-language.test.ts` and `tests/integration/reply-language.test.ts`).
  - **I5 observability**: one content-free line per turn, `[LANGUAGE] ui=<en|hu> conversation=<en|hu> reply=<en|hu|unknown>` (`conversation` is the language the turn named, `reply` what the reply's own words read as), a warning line when the model answered a person writing English with a reply that reads as Hungarian (`conversation=en`, `reply=hu`, whatever the account is shown in: the owner's own case is an account shown in Hungarian), both stored on the assistant message (`conversationLanguage`, read back by `getLastConversationLanguage` as the fallback of a later turn whose call fails and whose reply says nothing; `replyLanguage`, the record), and counters in `normal-chat-stability-snapshot.ts` (`replyLanguage`: turns, replies that said nothing, turns the chain had to decide, and the warning case as `englishWriterHungarianReplyCount`) (`chat-turn/reply-language.test.ts`).
  - Content the server has the model write on its own follows the person's words, not a language it guessed: an App's labels are written in the language of the person's message (`buildAppRequestMessage` shows the generator those words, `requestText`; a change keeps the App's language unless it asks for another; the panel's and the chat card's regenerate send no language); an Atlas report is in the language of the question, which the model reads once at job start (`atlas-v3/question-language.ts`, kept on the ask checkpoint; the account's UI language then English if it cannot).
- `src/lib/server/services/chat-turn/short-local-text.ts` is the one place that cleans a short text a person reads (a title, a thought-step status line, a rail headline): a stray think block (`stripLeakedThinking`; one extra request for an unclosed one through `askWithThinkingRetry`), leaked reasoning and request restatements in English and Hungarian (`isReasoningLeak`, `isRequestRestatement`), and JSON-wrapped answers. Do not add a second cleanup beside it, and take any new phrase it should catch from real model output, in a test, in both directions. Few-shot examples for such a call travel as text in the one user message, never as earlier assistant turns (the chat template renders each with an empty think block and the model then re-opens one: 19% of titles). The status line is written in the account's UI language (it is written before any reply text exists); the rail headline and the follow-up chips are written in the language the turn named for the conversation after its reply (`resolveTurnReplyLanguage`, carried by `completeStreamTurn` and `finalizeChatTurn`), never in a fresh read of the latest message. The parity check that drops a line in the other language than asked for is `readShortTextLanguage` (a title is content words, so it counts a word spelt the Hungarian way, two accented letters or one in a word of seven letters or more and not on a short list English borrows, as well as the closed-class words: Hungarian needs two witnesses and a 3:1 lead, English one closed-class word and nothing Hungarian) and drops a line only when it is plain about it: a single name ("Zürich", "Béla Bartók"), the homographs ("Van Gogh Biography", "Chevy Volt Review") and a line of English content words pass.
- `src/lib/server/services/chat-turn/follow-up-chip.ts` says what a follow-up chip is and is the one check for it: a chip is the person's NEXT MESSAGE to Alfy (a tap sends its text, verbatim, as the user's own message through `handleSendFollowUp`), so it is an instruction or the person's own question about something the reply names, one short plain sentence in the language of the conversation for the person. It is never Alfy offering (`Szeretnéd, ha…?`, `Would you like me to…?`, `Írjam le…?`), a question put to the person (`Mennyi a kereted?`), a statement about the person (an invented fact in their mouth), or a generic push (`Tell me more`). `follow-up-suggestions.ts` owns the prompt that asks for it, and the prompt's examples must pass the same check. Take any new phrase the check should catch from real model output, in a test, in both directions. The chips' language is the conversation's for the person (the invariant above: the model's answer to one question after the reply), never the reply's by default and never a flip made by code reading the message for a request: `Hogy mondják angolul, hogy alma?` and `Írj egy e-mailt angolul a kollégámnak` leave the conversation in Hungarian (the person writes Hungarian; the email is the piece), `Write an email to my colleague in Hungarian` leaves it in English, and `Válaszolj angolul` or `Answer in Hungarian` leave it where it is: the person still writes the language they write, and a chip is their next message. A chip is also held to the language by the chip check itself (`isInLanguage`): besides the words only the other language has, it asks the reader of short texts (`readShortTextLanguage`) and, for an English turn, drops a sentence of four words or more that has no English word in it and a word spelt the Hungarian way (`Fejtsd ki részletesebben a két szakaszt` was kept under an "in English" request on the real model), while English chips that carry a Hungarian name, `Van Gogh` or `volt` stay.

## Asking The Person

`ask_user` lets Alfy stop a reply to ask 1 to 3 questions, and the same reply carries on from the answer ("Ask me first": the spec is `docs/plans/ask-me-first/design.md`, the numbered calls are in `plan.md` beside it). The reply that stops is saved as a segment, the question is a row, and the answer is a turn of its own that saves the next segment. The browser's half is `src/lib/components/chat/AGENTS.md`, "Questions In A Reply".

### The Tool

- `ask_user` (`normal-chat-tools/ask-user.ts`) takes 1 to 3 questions of 2 to 3 options. `ASK_LIMITS` (`src/lib/shared/ask-user.ts`) holds every cap once: the tool's zod schema applies them, and `checkAskQuestions` runs again in `execute` for what a schema cannot say (one Recommended option on a one-pick question, a text that is only space). It is the catalogue's last tool, so the cached prompt prefix moves only at its end. (`ask-user.test.ts`; `normal-chat-tools/index.test.ts`, "ask_user is the catalogue's last tool".)
- A run takes one ask. A second call is refused `already_asked`, so every question of a pause is on one card (`ask-user.test.ts`, "refuses a second ask in the same turn"). A call the tool refuses asked nobody: it is a finished call marked `ok: false`, nothing waits, and the model goes on.
- Only the streaming run can pause (`canPause`, set in `streaming-normal-chat-model-run.ts`). The plain send route and the non-stream fallback answer the same tool `not_available`, so the catalogue never varies between runs.
- The tool records and returns; it never waits. It writes the question row (`recordAskQuestion`: `waiting`, no message id yet) and returns `{ status: "waiting_for_user" }` (`ASK_PAUSE_STATUS`).
- Everything the app writes into the request is ASCII English (ruling 79, above): the description, the results and notes (`buildAskAnswerRecord`) and the flatten lines. The questions, labels, notes and the person's own words are data. The description says "Phrase questions and options in the conversation's language" because "write ... language" reads as a reply-language instruction to invariant I1's scan. `tests/integration/english-request-purity.test.ts` runs a resume for an account in each language.
- `shared/ask-user.ts` is a leaf with no imports. The model run, the tool, the store, the routes and the browser all read it, and anything it imported would travel to all of them or close an import cycle.

### The Pause

- The stop is a custom condition on the pause result, not `hasToolCall`. `askedTheUser` (`normal-chat-model/index.ts`, in `buildToolStopWhen`) ends the run after the step whose `ask_user` result is the pause marker (`isAskPauseOutput`). `hasToolCall("ask_user")`, which the design (5.3) names, would also stop on a call the schema refused or the tool declined, and the model must get its turn after those to fix the card or go on. (`normal-chat-model/index.test.ts`: "stops right after the step whose ask_user result is the pause", "goes on after an ask_user call that was refused".)
- The capture is read after `finish`, never at `finish-step`. `onStepMessages` hands the turn the attempt's cumulative `response.messages` (tool results whole) after each step. The SDK finishes the last step's callback before `finish`, so a run that ends with a `finish` holds the ask's result and one that closes without it may not (`holdsAskResult`): such a turn is not paused. A failover starts its next attempt's messages afresh. `buildAskResumeCapture` (`ask-capture.ts`) makes `{ v: 1, messages, results }`: what follows the person's message, and one row per tool result (call id, tool, `localDistilled`, digest) so a resume can gate each whole result per attempt. An `ask_user` result has no row. (`ask-capture.test.ts`.)
- The pause is decided before the fallback. `stream-terminal.ts` decides it after the stop check and before the visible-answer check (`isPaused`: the run asked, and what it said and read holds the ask's result, which a resume answers). A reply that asked before saying a word has no visible answer and a completed tool call, which the check after it would answer with a whole second generation. A stop asked before this branch wins: the segment is saved stopped and its question discarded. (`stream-terminal.test.ts`: "completes a paused run as paused, before the whole-generation fallback", "lets a stop asked before the pause win".)
- A paused segment is saved complete as it is, gets no follow-up chips, and its terminal frame names the question (`waitingQuestionId`) only when the stamp landed (`stream-completion.test.ts`, "gives a paused segment no follow-up chips and names its question in the terminal metadata").
- A reply saved without the pause (stopped, failed, recovered by the fallback) has its question discarded, and `stream-completion.ts` saves its ask call as `The user stopped the reply before answering.` or `The reply ended before the user answered.`, so a later turn never reads a question that is not open. The fallback is handed no ask call.

### The Question Row

- A question has five statuses (the diagram at the head of `ask-questions.ts` shows every move): `waiting`; `answering` (an answer claimed it); `answered`, or `closed` (the X); `discarded` (the reply never saved it, or it can never be resumed). An `answering` question returns to `waiting` when the resume does not land, the answer kept on the row. The table (`ask_questions`) goes with the asking row, the chat and the person.
- Stamping ties a question to its row. `stampAskQuestion` (called by `finalize.ts` before the receipt) writes the message id and the capture (`resume_json`) in one UPDATE, and only a stamped question can be claimed. The capture is cleared when the question settles or is discarded.
- An unstamped question shows only while its chat's stream runs. The orchestrator discards the turn's own in `finally` when the turn ends unsaved (`discardAskQuestion`) and clears the chat's leftovers when a turn that holds the chat's stream starts (`discardStaleAskQuestions`; a crash leaves them).
- One claim wins, in one synchronous step. `claimAskQuestion` reads, checks the in-process map of live resumes (`liveResumes`), releases a stale `answering` row, updates and adds the map entry with no `await` between them, and hands the winner a claim token. `releaseAskQuestion` and `settleAskQuestion` act only for the live claim's token and then always clear it, so a second release or a stale settle never undoes another device's claim. (`ask-questions.test.ts`: "never lets a second claim undo a first whose stream has not started", "lets one of two claims win on a question a restart left answering".)
- The map tells an answer on its way from the `answering` row a restart leaves (the stream registry cannot: it says nothing between the claim and the stream, while the route prepares the turn). That row reads as `waiting` with the answer that did not go through, so the card comes back with it, and the next claim releases the row first. Every path after a won claim ends in one release or one settle, or the chat refuses new messages, with no card to answer, until a restart.
- The lists and the counts read the same rows. A row nobody can read (`readRow`) never fails a person's list, never marks a chat in the sidebar and never refuses a message (`listConversationAskQuestions`, `listWaitingAskConversationIds`, `hasWaitingAskQuestion`). The list is read after every turn, hydrate, poll and write confirm, so it selects only the columns a card is made of (`AskQuestionListRow`), never the capture, which can run to about a megabyte (`ask-questions.test.ts`, "reads only the columns a card needs, never the capture").
- A question that waits closes the chat to new turns (`findWaitingQuestionRefusal`, `ask-resume.ts`; a question that answers counts too). `/api/chat/stream` (a fresh send; a reconnect and an edit's resend pass), both branches of `/api/chat/send` and `/api/chat/retry` answer 409 `QUESTION_WAITING`. Retry is refused too because it deletes the old rows while it prepares, before the stream arbiter, which would then only reconnect it to a running resume and leave an orphan segment. The page reads the questions and the chat again and puts the words back in the draft. (`stream.test.ts`, "refuses a new message with 409 QUESTION_WAITING while a question waits, and lets a reconnect and an edit's resend through"; `send.test.ts`; `retry.test.ts`.)

### The Resume

- A reply that paused is consecutive assistant rows (segments). Each continuation names the row it continues in `metadata_json.continuesMessageId` (no column; `ChatMessage.continuesMessageId`). A row id belongs to one conversation, so anything that copies messages into another conversation remaps the link to the copy of the row it names, or drops it (`copyMetadata`, `conversation-forks.ts`; `conversation-forks.test.ts`: "points a copied continuation at the copied row it continues", "drops the link when the continued row was not copied"). The same fork copies the `answered` and `closed` question rows of the rows it copies (`copyAnsweredAskQuestions`: new ids, the copied asking row, the fork's chat, no capture; never a question that waits or answers), so a forked reply draws the folded line between its segments (Ruling 48; "the questions it asked").
- History says what happened, in order. `renderHistoryTurn` (`conversation-history.ts`) renders a segment that asked as its other calls and results, then its words with the ask call, then the answer as the call's result; the next segment follows as any reply, and flatten mode says `[asked the user: ...]` and `[the user's answer: ...]` (`flattenedAskLines`). A segment really asked when `askCallPausedTheReply` (`shared/ask-user.ts`) says so, the one test that history and `stream-completion.ts` share: a refused or unfinished `ask_user` call asked nobody and renders as any call. `updateAssistantToolCallResult` (`messages.ts`) writes the answer into the asking row, naming the call by id, tool and question, since a provider may reuse an id for another tool's call, or for a card the tool refused, in the same row. (`conversation-history.test.ts`.)
- The resume (`ask-resume.ts`) is a turn on the person's own message that carries the reply on. Its origin is `ask_resume` (not a retry origin, so finalize does not count it as a regenerate); it runs with `skipPersistUserMessage`, no regeneration appendix and no instant acknowledgment, and it deletes nothing. `prepareAskResumeTurn` takes the question the answer route has just claimed, finds the reply by the rows' own `continuesMessageId` links (`findReply`, over `walkReplySegments` in `messages.ts`, which "Open as document" reads a reply with too: the person's message is the user row right before its first segment), rebuilds that message as a regenerate does (`resolveStoredTurnChoices` and `preflightStoredTurn` in `retry.ts`: the skill and forced web search come from the first segment's record, the model, depth, personality, connections and open item from the answer's body) and hands the orchestrator `resume` (`AskResumeInput`, defined in `ask-capture.ts` so the orchestrator, completion and finalize need not import the entry). A reply that can never be resumed (a capture that cannot be read or holds no result of the ask, segments that no longer lead back to the person's message, no user row before the first) is refused 409 `QUESTION_NOT_WAITING` after its question is closed for good (the Answer Route, step 6): that claim was won, unlike the answer route's `QUESTION_ALREADY_ANSWERED`, where it was lost. (`ask-resume.test.ts`.)
- The input is the history before the person's message, the message and its guidance, then the reply so far with the answer as the ask's result. The run gets `continuationMessages` (`buildAskResumeContinuation`: the capture's messages with the answer in place of the pause) after the person's message and any prefetched page, `historyBeforeMessageId` (the history ends before that message: `loadSessionPromptContext`, carried by `constructedContextParams` so the rebuild after automatic compression ends at the same row; the rows automatic compression itself summarizes end there too, `rowsBefore`, or it would compress the person's message and the paused segments that the continuation sends again, and a compression marker would be drawn between two segments of one reply: `normal-chat-context.test.ts`, "ends the compression source before the person's message") and `skipWebPrefetch` (no page is read again). The prompt estimate counts the continuation, and the non-stream fallback carries the same params, the continuation before its own replay. (`context-selection.test.ts`; `streaming-normal-chat-model-run.test.ts`; `stream-fallback.test.ts`.)
- The answer reaches the model as a fixed English record (`buildAskAnswerRecord`: `answered`, `left_to_you` or `closed`, each with a note), and the same record's summary and digest replace the pause in the asking row's call.
- Every attempt, failover included, is built from those original messages through `gateMessagesForAttempt` (`gateCapturedConnectorResults`, `ask-capture.ts`). Off the person's box, when they keep connector data local (`hasLocalDistillEnabled`), it reads each result by its own tool name: a connector result that is not already a digest or a local summary becomes its row's digest, or a fixed note when no row has its call id and tool, so what it cannot place fails closed. The same attempts lose the segment's thinking: the reasoning parts of its assistant messages (the SDK keeps them in `response.messages` and the provider sends them back as `reasoning_content`; a stored reply's history never replays any) and thinking left in a text part (`normalizeVisibleAssistantText`, the stripper the stored text goes through), because a local model's thinking can quote the mail or the photo it read; a local attempt keeps them. A provider may reuse a call id across responses, so rows pair with results by id, tool and order, and the capture makes a row for every result of the run. A provider in flatten mode gets the continuation as text (`renderAskContinuationAsText`), gated first, but that fold is made once, with the provider the run starts on: a flatten primary's failover to a cloud attempt is not gated again (no provider uses flatten mode today). `continuationGiven` keeps the messages as they were. (`ask-capture.test.ts`, "decides again for each attempt it is asked for" and "the thinking of a paused segment".)
- The segment speaks as the reply's next part. It names the row it continues, its citation gate reads the earlier segments' stored tool calls (`priorSegmentToolCalls`) and the words the person typed into their answers (`userTexts`: typed words only, never an option's label, which the model wrote), and URL provenance is seeded from the captured results (`url-provenance/AGENTS.md`). The ask's own result is found by call id and tool name together (`holdsAskResult`, `buildAskResumeContinuation`), since a provider may reuse an id for a connector's result. (`stream-completion.test.ts`, "names the row a resume segment continues and lets it cite what the reply found earlier".)
- A resume releases nothing itself. `prepareAskResumeTurn` passes the won claim's token on unchanged. A refusal from it is the route's to release (but for a reply that can never be resumed, which the preparation closes for good itself: the Answer Route, step 6); from then on the release is the orchestrator's outermost step: `startHoldingTheClaim` wraps the whole of the stream's `start`, so the arbiter's early returns and a throw in the setup or in the turn's own ending release it too (a no-op once the question settled). Finalize settles the question, writes the answer into the asking row's ask call and only then stamps a question the segment asks again, all before the receipt, so a card never comes back for an answered question. (`stream-orchestrator.test.ts`, "runs a resume with its continuation and no instant acknowledgment, and gives its question back when it ends unsaved"; `finalize.test.ts`, "settles the answered question first and stamps the new one after it, when the reply asks again".)

### The Answer Route

`src/routes/api/conversations/[id]/questions/[questionId]/answer/+server.ts` (`answer.test.ts`). The order is the contract:

1. `isAskQuestionTaken`, the store's read-only check: a question already answered or closed, or answering under a live resume of this process, is answered 409 `QUESTION_ALREADY_ANSWERED` before anything else, a draining server included. The winner's resume holds the person's one stream (`PER_USER_STREAM_LIMIT` is 1 by default), so a loser that met the capacity gate first would be told to wait for room to lose a claim it can never win. An `answering` row a restart left has no live resume: it is not taken, and goes on to the gate and the claim.
2. The capacity gate (`refuseTurnWhenOverCapacity`: 503, the send's body).
3. The body: 400 `INVALID_BODY`, and 400 `STREAM_ID_REQUIRED` (without a stream id the orchestrator skips the arbiter, the stream's registration and the stale-question sweep, and the resume could run beside another turn).
4. The question read (404 `QUESTION_NOT_FOUND`; a row whose words cannot be read is 409 `QUESTION_ALREADY_ANSWERED`, as the list shows no card for it) and `checkAskAnswer` (400 `INVALID_ANSWER`).
5. `claimAskQuestion`, the one arbiter: a lost claim is 409 `QUESTION_ALREADY_ANSWERED`.
6. `prepareAskResumeTurn` refuses in two ways, and the route answers both as the retry route answers its own. A refusal that can pass on a later try (the retry preflight's: an attachment not ready, a picture that cannot be read) leaves the claim for the route to give back, and the answer stays on the row. A reply that can never be resumed (the resume's own 409 `QUESTION_NOT_WAITING`: a capture that cannot be read or holds no result of the ask, segments that no longer lead back to the person's message) is closed for good by the preparation itself, never by the route (Ruling 46): `closeForGood` (`ask-resume.ts`) discards the question with the won claim's token (`discardClaimedAskQuestion`, capture cleared) and rewrites the ask call in the row that asked to `The reply ended before the user answered.`, the sentence a reply saved without its pause gets. The card is gone, the chat takes messages again, and a later turn reads no open question; before this a permanent refusal gave the claim back, and the card, whose answer and X failed the same way, kept the chat closed to messages, Retry and edits. The route's give-back after a close is a no-op, the claim being spent. The page reads the questions after the refusal (`answerNotSent`), finds nothing waiting and opens the box. (`ask-resume.test.ts`, "closes the question for good when it can never be carried on"; `answer.test.ts`, "a question whose reply can never be carried on"; `page-runtime.test.ts`, "drops the card and opens the box when the server closed the question for good".)
7. `runChatStreamOrchestrator` with the resume.

From the claim until the orchestrator returns its stream, every way out gives the claim back with its token (`releaseAskQuestion`): the preparation's refusal (a no-op after a close for good), and a throw from the preparation or the orchestrator, which answers 500 `ANSWER_FAILED`. From then on the orchestrator holds it. Refusals carry a `code` and no `errorKey`: the page localizes by code.

- put shared request parsing, attachment preflight, model normalization, stream framing, and finalization in `chat-turn/`
- let `src/lib/server/services/chat-turn/stream-orchestrator.ts` and the stream submodules own shared upstream event parsing, tool-call marker handling, downstream token/thinking framing, and leading-output cleanup
- let `src/lib/server/services/chat-turn/normalizer.ts` normalize assistant text through the shared stream-protocol helpers so `/send`, `/stream`, retries, and title generation use the same visible content shape

- keep route files thin and transport-oriented
- preserve AI SDK UI stream part names and payload expectations unless the parser/UI/tests are intentionally updated together

Do not:

- duplicate turn logic between `send` and `stream`
- add new AI SDK UI stream part shapes casually; this touches browser parsing and tests
- hide persistence side effects inside route-local closures that only one endpoint can see
- couple provider transport details directly into page components
- duplicate stream-tag parsing or inline-thinking extraction between the browser stream consumer and `api/chat/stream/+server.ts`
- scatter freshness-sensitive search guards outside `normal-chat-context.ts`
