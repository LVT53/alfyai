# Native replacement boundary (ADR-0071)

The authorized Hindsight replacement supersedes the local-only architecture below **for accounts whose authority is Hindsight**. Keep extraction/consolidation native. New implementation belongs in this folder: `hindsight-client.ts` owns private tenant-bound transport and observed pin/config checks; `revisions.ts` owns source/epoch fences; `delivery-job.ts` uses the existing job engine; curation modules own deliberate user actions; `publication.ts` owns coherent published generations; `native-read.ts` owns the UI read contract. No new scheduler or semantic extraction pipeline. Tenant/admission extensions live under `deploy/hindsight/`; runtime config remains in config-store. Personal recall may accompany any scope; project recall must never escape that project.

Recall (`memory-context/native.ts`, `recallMemory`) only reads, and has two callers. Every turn's section (`chat-turn/context-selection.ts`) searches each eligible bank twice through one client: with the person's message and with the fixed core query (`CORE_MEMORY_QUERY`). `messageRecallQuery` folds whitespace, adds the chat's title to a message of four words or fewer ("and the second one?"), and cuts a long message to its first 300 and last 200 characters (Hindsight parses dates in a query on one CPU worker). The `memory_context` tool searches once, with the model's query. `allocateRecall` (`memory-context/recall-allocation.ts`) shares the budget in lanes: a project chat's own entries up to `MEMORY_RECALL_PROJECT_PERCENT` (default 50), the person's basics up to `MEMORY_RECALL_CORE_PERCENT` (default 25, the per-turn section only), then both banks' message matches in turn, then what is left over. A failed search leaves the bank's other search in charge; only a bank whose searches all fail gives its accepted rows in stored order. Every row counts as its whole line (`recallLineTokens`), because the memory section always goes into the prompt whole. Rows reach the model through `formatRecalledMemory` (`memory-context/recall-format.ts`): the person's entries, then the project's under their own line, each with when it was last said (its newest source date, on the turn's one clock). When any row has a time, one line opens the rows and says what the times mean (`RECALL_TIMES_NOTE`): when the person last mentioned the entry, not when it happened, so a lasting fact stays true however long ago it was said, and the times only choose between entries that disagree. Its tokens are reserved like the heading's, and the `memory_context` tool's result carries it too. Each call logs one content-free `[KNOWLEDGE_MEMORY] Recall` line per bank. Recall writes nothing: being recalled never keeps an entry current. The person's words now reach Hindsight as recall queries, so its logger stays at warning (`deploy/hindsight/compose.yaml`, `HINDSIGHT_API_LOG_LEVEL`).

Labels and age (part 2). Every bank runs config 2 (`contracts.ts`, `nativeBankConfig(kind)`): config 1's missions plus part 2's sentences (requests, reactions and brainstorm steps are not memories; a settled choice keeps its outcome; a real change keeps the old value only as earlier history, no invented dates; corrections unchanged), and `entity_labels` with `kind` (lasting, ongoing, temporary; leans to lasting) and the bank kind's `subject` list, both `tag: true`, so Hindsight's own extraction writes `kind:`/`subject:` into each new fact's tags at no extra call. A bank the previous release configured (stored version `HINDSIGHT_ENGINE_COMMIT`) already holds the person's data, so its next delivery or curation upgrades it with a plain PATCH that a retry may send again; it keeps its version until a readback proves config 2 (then `NATIVE_BANK_CONFIG_VERSION`), so a lost PATCH never holds deliveries, edits, Clear Memory or erasure. Only a new bank's creating PATCH keeps the single-submission fence (`NATIVE_BANK_CONFIG_PENDING`). Version writes are compare-and-set, a config 2 bank is verified against its own kind's config, `verifyConfig` compares by value (labels are arrays of objects, JSONB reorders keys), and paths that only verify accept config 1 too. The release is one-way for upgraded banks: rolling back needs `scripts/memory-bank-config-restore.ts` first (`bank-config-restore.ts`; `deploy/hindsight/README.md`, "Bank config 2"). Never change a fact's entities or tags in Hindsight to label it: at the pin that regenerates its observations. Labels live app-side in `memory_fact_labels` (`fact-labels.ts`), keyed by bank and Hindsight fact id, read through `readFactLabels` and nowhere else: `publishNativeSnapshot` copies each raw fact's extraction labels and event date (`occurred_end ?? occurred_start`) there, and the classifier writes there through `recordClassifiedFactLabels`, whose labels win from then on. An entry takes kind and subject from its newest labelled fact (`entryLabels`); unlabelled reads as lasting. `entry-time.ts`'s `memoryEntryTimeState` decides at read time, on the caller's one clock, with config-store's `getMemoryAgingThresholds` (`MEMORY_TEMPORARY_EARLIER_DAYS` 21, `MEMORY_ONGOING_QUIET_DAYS` 21, `MEMORY_ONGOING_EARLIER_DAYS` 90): a temporary entry is Earlier that long after the later of its last mention and its event, an ongoing one quiet and then Earlier after its last mention; lasting, unlabelled, undated and person-written entries (`isAuthoredMemorySource`: a `manual:` event or a migrated authored item) never age. Recall never moves an entry's date. In recall an Earlier entry never enters the core, reaches a turn only from the top three places of its bank's message ranking, only when the message mentions it (`memory-context/earlier-mention.ts`: a shared significant word, folded as Workspace Search folds, stop words in both languages left out, an inflected word matched by its stem; Hindsight gives no relevance score at the pin) and at most three per turn, and the `memory_context` tool returns Earlier entries and their earlier states (`parseEarlierStates` over the published `nativeText`); a labelled row shows its kind (`temporary, said 3 weeks ago`), and `RECALL_EARLIER_NOTE` opens the rows when one is Earlier. Each row is budgeted at its exact formatted cost (`recallLineTokens(item, now)`). The classifier (`fact-classifier.ts`, `classifyMemoryFacts`) labels up to 20 facts per call through `createCurationModel` (the admission-gated memory model path, temperature 0, thinking off) with the bank config's own label words; its only callers are the label migration and the fallback, never a person's turn. The label migration is `label-migration.ts` (`runLabelMigration`, `rollbackLabelMigration`; command `scripts/memory-label-migration.ts`, runbook "Label migration"): the tester guard first, every raw fact of every bank of the current epoch (config 1 and 2 alike) labelled in fenced batches, then verification (every fact labelled or listed with its reason, at most one in 20 left without a usable label, at least 15% of the labelled facts lasting once 20 are labelled, the published rows' fingerprint unchanged) before `markMemoryLabelsVerified`; a later run asks again for facts left without a label, a verified account's included; it only lists from Hindsight and stops at the first account that fails.

Waiting and admission (part 4). A Memory job waits for Hindsight's own operation state, never a fixed time: `delivery-runner.ts` polls an operation in five-minute slices (`NATIVE_WAIT_SLICE_MS`), and a slice that ends while Hindsight still works hands the job back under `native_retain_waiting` or `native_consolidation_waiting`. The kind's failure policy (`delivery-policy.ts`, `decideMemoryDeliveryFailure`) requeues a wait without counting it, for as long as config-store's `getMemoryNativeWaits` allows from when the streak began (`MEMORY_RETAIN_WAIT_MINUTES` 30, `MEMORY_CONSOLIDATION_WAIT_MINUTES` 60; capture's quiet wait is a consolidation wait), then ends the job `native_operation_timeout`, retryable; real failures keep three tries with the waits left out, and anything that compares an attempt with the limit uses `countedDeliveryAttempt`. A retain an earlier attempt saw finish is never sent or asked about again (Hindsight forgets receipts, and a POST of a forgotten ID re-extracts the chat). A sent retain's first look acts on Hindsight's answer: completed is accepted, failed resubmits, cancelled ends, unknown sends its own ID, running is waited for. A retain this attempt saw fail is held back a minute (`native_retain_resubmit_due`, a wait) before its one resubmission; its terminal ends are recorded on the revision (`nativeRetainEnded`) with their own codes (`native_retain_resubmit_failed`, `native_retain_left_facts`, `native_retain_cancelled`), after which a reopen asks Hindsight nothing. The retain bookkeeping keys live in `revisions.ts` and `withoutRetainBookkeeping` keeps them out of a repair's replacement. Every memory model call declares its place in the gateway's queue through `createCurationModel`'s `admission` (`admission.ts`: `interactive` for what a person waits for, the Overview; `background` for curation jobs, the classifier and the label migration; a lane per tenant, never the tenant id itself); its timeout is its declared wait plus the model's run. The permanent tester rule is `users.memory_migration_excluded` read through `memoryMigrationGuard` (`migration-guard.ts`) and nothing else: every migration of existing Memory data asks it (preparation and its restart, the operator tools, the label migration), ordinary operation never does. The canonical operator tools are `operator-tools.ts` with their command lines in `scripts/memory-*.ts` (resend, reattach, recover-consolidation, drain; `docs/plans/hindsight-memory/migration-runbook.md`): dry runs unless executed, the guard first, one reported step each, counts and ids only.

The Memory page and the Overview (part 3). `entry-view.ts`'s `memoryEntryView` is the one definition of an entry (its supporting facts from the row's `sourceIdsJson` among `admittedNativeFacts`, labels by `entryLabels`, last mention by `entryLastSaidAt`, time state on the caller's clock): recall and the page both build entries there. `subject-read.ts` is the page's subject index (`readMemorySubjectIndex`: one summary per subject with a current entry, in the bank kind's list order, the Projects row's `active`, the Earlier fold's count and previews) and a subject's entries (`listMemorySubject`, 100 a page, a cursor pinned to its generation; `all` is every Earlier entry); current means current or quiet, an unlabelled entry or one labelled for the other bank kind sits under `other`, and the only earlier states shown are Hindsight's dated notes (`parseEarlierStates`), never Hindsight's `GET /memories/{id}/history` (its rows carry the consolidation's time and keep corrected and edited wording). Which page an account gets is `labels-verified.ts`: `memory_accounts.labels_unverified_epoch` names the epoch whose banks may hold facts from before config 2 (migration 143 marked every account with a bank in its current epoch, except the accounts the tester flag names; `ensureConfiguredBank` marks the epoch again when it upgrades a config-1 bank in place); a new account or a new epoch reads verified, and the label migration clears the mark with `markMemoryLabelsVerified(tx, userId, epoch)`, which also records the epoch in `labels_verified_epoch`. A verified epoch sticks: an in-place upgrade does not mark it again (every fact in that bank predates the upgrade), while a bank the previous release created (`created_by_previous_release`: a rollback followed by a roll forward) marks it again and forgets the verification. `revokeMemoryLabelsVerified` takes a verification back outright (marked again, no longer recorded as verified): the label migration's rollback calls it, and so does `bank-config-restore.ts`, for an account as soon as one of its banks is restored and for every native account but the tester's once a run leaves no bank on config 2 (the previous release writes facts without labels); after a rollback and a roll forward the label migration runs again. `overview.ts` writes the Overview: one call through `createCurationModel` (person-read, so the family's sampling; the account's UI language named once, like the persona summary) over the current entries, the most recently mentioned that fit `OVERVIEW_INPUT_TOKEN_BUDGET`; it is stored one row per bank in `memory_overviews`, only this module reads the table, migration 144's triggers delete it whenever the bank's entries can change, a read whose entries no longer match deletes it, and a write stores nothing when the entries changed while the model wrote.

The job registration and recovery interface lives in `delivery-job.ts`. Its handler uses `dependency-plan.ts` for bounded discovery and holds, and `dependency-repair.ts` for native execution under the existing attempt. Use `curation-intent.ts` to read persisted action intent. The worker reads history eligibility and settles manifest progress through `history-eligibility.ts` and `migration-progress.ts`. Preparation and authority transitions live in `migration.ts`.

Legacy tables and code below remain only for per-user authority-gated migration/rollback; do not remove user data or revive legacy extraction for migrated accounts. No nightly persona rewrite or legacy portrait is introduced into native Memory. See ADR-0071 and the approved replacement plan for explicit supersessions.

## Legacy boundary (only while legacy authority is active)

# Profile Memory

Task/document continuity and profile memory are separate subsystems. Continuity lives on `task-state.ts`; durable profile memory (facts about the user) is owned by the local Memory Profile Projection plus the LLM intake judge and nightly consolidation. There is no external memory service.

- Continuity boundary:
  - [`src/lib/server/services/task-state.ts`](../task-state.ts) plus its internal modules under `task-state/` (control-model, continuity, artifacts, chunk-sync, mappers)
- Profile memory judge (intake):
  - [`src/lib/server/services/memory-judge/`](../memory-judge/) — `index.ts` (per-segment run), `runner.ts` (idle/dirty sweep), `segment.ts` (watermarks), `prompt.ts`, `schema.ts`
- Consolidation (nightly rework):
  - [`src/lib/server/services/memory-consolidation/`](../memory-consolidation/) — `index.ts` (runner + scheduler), `steps.ts` (expire/renew, reconcile/merge), `summary.ts` (persona summary)
- Recuration (one-time cleanup):
  - [`src/lib/server/services/memory-recuration.ts`](../memory-recuration.ts)
- Fact store authority:
  - [`src/lib/server/services/memory-profile/`](./) — see its narrow seams (`projection-store.ts`, `read-model.ts`, `active-context.ts`, `telemetry.ts`, `review.ts`, `dirty-ledger.ts`, `types.ts`)
- Recall into prompts:
  - [`src/lib/server/services/memory-context/`](../memory-context/)
- Public read facade + maintenance/orchestration:
  - [`src/lib/server/services/memory.ts`](../memory.ts), [`src/lib/server/services/memory-maintenance.ts`](../memory-maintenance.ts)
- Event log:
  - [`src/lib/server/services/memory-behavior-log.ts`](../memory-behavior-log.ts)


Rules:

- `memory-judge/` is the only intake path from conversation into profile memory. It runs on three tiers of triggers — idle (deferred after a turn), explicit (user asks to remember), and marathon/sweep (long or backlogged conversations) — over the unjudged segment tracked by per-conversation watermarks in `segment.ts`. Advance the watermark only after a real run; never re-judge already-judged messages.
- The judge admits candidates through five gates in `schema.ts` (hedge, evidence-trail, third-person, missing-expiry for time_bound, missing-target for update/strengthen). Keep the gate order and reasons stable; post-filter rejects must stay measurable via the `judge_candidate_rejected` intake telemetry rather than being dropped silently.
- Honour the dry-run switch (`MEMORY_JUDGE_DRY_RUN`): in dry-run the judge records `judge_dry_run_decision` telemetry and advances the watermark but writes no profile items. Do not add a second dry-run flag or bypass it in routes.
- `memory-consolidation/` is revision-based and per-user isolated: expire/renew then reconcile/merge steps run against the current projection revision, write a report row per non-skipped run, and refresh the persona summary. Change detection may skip a user with nothing new. Never let one user's consolidation read or write another user's items.
- `memory-recuration.ts` is a one-time, admin-triggered rewrite/cleanup of the existing fact store; it is not part of the per-turn path. Do not wire it into chat routes or the scheduler.
- `memory-profile/` is the authority on fact state: item `status` (including `retired`), provenance, and projection revisions. User-protected items — `user_authored` items and facts the user accepted in Guided Memory Review (true `origin` kept, `endorsement: "user_accepted"` added) — must never be rewritten, retired, merged, superseded, or deleted by the judge, consolidation, or recuration; the user can still edit or remove them. The one exception is consolidation's renew step: an accepted (not `user_authored`) time-bound fact is renewed on the same recent-evidence rule as any other time-bound fact, and only its `expiresAt`/`updatedAt` change, because its expiry was inferred; a `user_authored` fact's end date is the user's own and is never auto-extended. Automated writers gate on the single predicate `isUserProtectedMemoryMetadata` (or `readMemoryItemUserProtection` when the reason matters, as renew does) in `memory-profile/types.ts`; read item metadata through `parseMemoryItemMetadata`. Do not re-implement origin or endorsement checks locally.
- Recall belongs to `memory-context/`: the prompt gets the persona summary plus active facts, each fact carrying its own evidence. Do not build a second lexical/semantic persona search surface beside this boundary, and do not invent "today/now" timing for undated facts.
- `memory.ts` is the public read facade for the Knowledge Base Memory Profile and keeps `/api/knowledge/memory/overview` as a projection-backed wrapper. It must not depend on a live external overview service, raw markdown cleanup, or task-memory tables.
- `memory-behavior-log.ts` owns the persisted normalized event log (recorded via `recordMemoryBehaviorEvent`, backed by the `memory_events` table) for important state changes (deadlines, preference updates, fact replacement, project continuity transitions, document supersession). Add new event types there; do not create ad hoc side logs or route-local event tables.
- `memory-maintenance.ts` owns per-user maintenance scheduling and lazy semantic-embedding backfill. Chat-triggered maintenance stays serialized/debounced there; generated-output duplicate repair and dormant-family (`historical`) downgrades reuse `evidence-family.ts` from there rather than a separate sweep. Historical families are soft-deprioritized, not hidden.

Do not:

- create a new top-level continuity service when `task-state.ts` can own the behavior
- add a second intake path, regex persona pipeline, or temporal-truth/salience/supersession subsystem outside `memory-judge`/`memory-consolidation`/`memory-profile`
- copy the `user_authored`/metadata parse helpers, `clip`, token estimation, or prompt-compaction helpers into another service
- create or restore `project-memory.ts`, `persona-memory.ts`, or any external memory adapter (memory is local-only, see ADR-0045)
