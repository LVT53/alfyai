# Images

Making and changing pictures: the ComfyUI client and its fake, graphs, pixel guards, picture files, cards and takes, the image job. Parent rules: `src/lib/server/services/AGENTS.md`.

## ComfyUI (`comfyui/`)

- **Addresses.** `COMFYUI_URL` for Qwen and `COMFYUI_H3_URL` for H3 (`RuntimeConfig.comfyuiUrl` / `comfyuiH3Url`, selected by `IMAGE_MODEL`), both read through `config-store.ts`, reached with plain `fetch` (injectable `fetchImpl`, as `mineru/client.ts` does), never `$lib/server/outbound`. Nothing a model writes becomes an address (ADR-0068).
- **Routes.** Only `POST /upload/image`, `POST /prompt`, `GET /queue`, `POST /queue` (delete), `GET /history/{id}`, `GET /view`, `POST /interrupt`, `POST /free`, `GET /system_stats` (Tool Health) and the `/ws` socket. Add no other route without a ruling.
- **Interrupt rule.** `POST /interrupt` only when `GET /queue` shows our own prompt running. `cancel(promptId, { interrupt })` deletes a pending prompt either way; for a running one it interrupts only with `interrupt: true` (the card's Stop) and otherwise answers `"running"` and leaves it. The turn-abort path passes `false`: a take ComfyUI has started finishes onto its card.
- **One writer.** Nothing outside `services/jobs/` writes `image_jobs` lifecycle columns; this folder never touches job state.
- **No facade cycle.** `services/artifacts/` imports only these two stores' file helpers (`images/files.ts` for pictures, `images/video-files.ts` for clips: list an item's file ids, delete them). Neither store may import the artifacts facade (`cards.ts` may: nothing the facade imports leads back to it).
- **Storage.** Picture files live under `data/image-files/<conversationId>/` with a relative `storage_path`; `data/image-files` is in `storageRoots()` and every unlink goes through `resolveDeletablePath`. Beside `<id>.png` and `<id>.thumb.png`, a picture whose long edge is past `IMAGE_DISPLAY_LONG_EDGE` (1600) gets `<id>.display.webp` at store time: a **lossless** WebP fit inside 1600 (no enlargement), alpha kept, so the chat card's `srcset` can download it instead of the original PNG. A picture whose long edge is past `IMAGE_LARGE_LONG_EDGE` (2560) gets `<id>.large.webp` on the first `?variant=large` request: the panel's copy, a **lossless** WebP fit inside 2560 (no enlargement), alpha kept, made lazily (only the panel asks for it, and a candidate take that is never picked never pays for it) with the display copy's own machinery — atomic write, one in-process generation per file and kind, a copy that is not a whole WebP removed and made again once, a failure falling back to the original. A picture within 2560 has no large copy (its original is served). Nothing new is stored in the DB: both paths are derived from `storage_path` like the thumb. `?variant=display` serves the display copy; for a picture stored before display copies existed, the first request makes it from the full PNG, persists it atomically, and serves it. Both copies are removed with the picture. `?download=1` is always the full PNG, whatever variant is named. `readImageFileBytes`' `full` is still what miners and edits receive.
- **Result pictures.** Graphs end in `PreviewImage`, so results are `type: "temp"` (cleared on a ComfyUI restart); `ComfyImageRef.type` also allows `input` and `output`. Uploaded inputs persist on the GPU box until a cleanup is set up (plan 2c).
- **Socket.** One WebSocket per client, opened on the first `submit`. It only adds progress events; polling `/queue` and `/history` decides every outcome, so a client with no socket still finishes.

## Picture models (`templates.ts`, `canvas.ts`)

- **Two services, one selected model.** `IMAGE_MODEL` (`qwen` | `h3`, `getImageModel()`) selects the model for NEW takes. Qwen keeps `COMFYUI_URL`, its 1 MP canvas, its 4 MP print and its transparent generate; H3 uses `COMFYUI_H3_URL` at 12 MP. `isImageMakingConfigured` asks only the selected model's URL.
- **The take keeps its model.** `TakeRequest.model` is written when the take is enqueued. The runner builds `graphFor(request.model, mode, transparent)`, makes `createConfiguredComfyClient(request.model)` and stores `mayBeSeeThrough` from that model, so an admin switch only affects new takes (a retry keeps the request's model). The card's Stop cancels on the take's stored model's server (never the other server when that URL is missing), and "another take" gates on and reuses the card's stored model. Old v1 rows without `model` read as `qwen`; an unknown value makes the row unreadable.
- **H3 renders at 12 MP.** `canvasForNewPicture(..., "h3")` is 4224x2816, 2816x4224, 3456x3456, 4608x2592, 2592x4608; H3 `print` is a no-op. `canvasForEdit(..., "h3")` keeps the base's shape at 12 MP (`H3_AREA`), in multiples of 32, so an odd upload gets an odd canvas; a shape past the side limit loses area. 4 MP was the first tier and starved full-body people (wax skin, no hair); the model card's effective range is about 4-20 MP with the best results near 16 MP, and 12 MP is what the card and GPU hold. `MAX_SIDE_BY_MODEL.h3` is 6272 (Qwen stays 2752).
- **No H3 transparency.** H3 has no transparent graph: `graphFor("h3", mode, true)` is null and never falls back to Qwen. `make_image` refuses a transparent request under H3 before a card or take (`transparent_unavailable`), telling the person to switch the Admin "Picture model" to Qwen; there is no automatic Qwen route. H3 results are stored opaque (`mayBeSeeThrough` false even over an alpha base). Qwen's transparent generate is unchanged.
- **H3 prompts and slots.** H3's edit graph has the same ten `images.image_1`..`image_10` slots and `image_1` is the base. Its `wrapPrompt` prefixes `<Picture 1> `; Qwen's transparent wrap is untouched. H3's node set is `MiniMaxH3ImageConditioning` + `ConditioningZeroOut` + a 6-step euler/simple `KSampler` at CFG 1, ending in `PreviewImage`.
- **Steps and CFG come from the template.** `GraphTemplate.steps`/`cfg` are Qwen 30/1 and H3 6/1; `buildPromptGraph` writes them instead of a global.
- **GPU memory ordering.** H3 12 MP peaks at the card's edge (48.4 of 48.9 GB, because ComfyUI evicts the text encoder while sampling), so BEFORE a take submits, `freeOtherPictureModel(request.model)` sends `/free` (`unload_models` + `free_memory`) to EVERY OTHER configured engine: Qwen and LTX for an H3 take, H3 and LTX for a Qwen take, both picture servers for a video take (`freeOtherPictureModels("ltx")`). `otherPictureModels(engine)` returns the list; there is no "the other one" any more, because a third engine would make a pair free the take's own server. It never frees the take's own service, and a missing, unreachable or same-address service is ignored so the take goes on. This must happen before the `/prompt` POST, so the selected service loads into memory the others no longer hold. **Never free a busy engine:** `freeOtherPictureModels` skips any engine with a queued/running take (unloading under a live render is `Fault failed: 2`, the H3 log's corruption). **The cross-engine gate:** after its own claim and before uploading, freeing or POSTing, every take waits for an EARLIER claimed take on any other engine (`waitForOtherEnginesIdle`, one ledger read about a second apart, capped by the take's own render deadline — `image_render_timeout` / `video_render_timeout`; a Stop aborts the wait and settles as cancelled). A take already on the GPU (a prompt, or a phase past `submitted`) blocks whatever its age; a take still inside its own gate blocks only if its `phase_at` (milliseconds, id as the same-millisecond tie-break) is earlier. A merely QUEUED take on another engine does not block: it is not on the GPU, and when it claims it sees this take running and waits itself. That claim order is what stops two takes starting together from waiting on each other until both deadlines. While it waits the take stays in its first phase: nothing fails before the deadline, the video ETA baseline keeps ticking, and the picture card shows its waiting state. The idle timer frees every configured engine after `IMAGE_IDLE_FREE_MS`, and `anyLiveTake` counts video takes too, so a video render is never freed mid-take.

## The fake (`comfyui/testing/fake-comfyui.ts`)

A real loopback HTTP and WebSocket server for unit and Playwright tests. It imports Node built-ins and sharp only, so specs may import it by relative path. Options: `steps`, `stepDelayMs`, `startDelayMs` (delays `execution_start` and the first step, not the queue: the prompt is listed as running from the moment it is posted, which `normal-chat-tools/make-image.test.ts` relies on; `holdQueue` is what keeps one pending), `fail` (`reject` | `execution`), `ignorePromptId` (answers with an id of its own, like a ComfyUI from before caller-supplied ids), `render` (override per call or through `setOptions`); for video, `videoBytes` (the mp4 a `SaveVideo` graph answers with; defaults to `FAKE_VIDEO_BYTES`, a real 5 s 64x64 clip), `videoOutputKey` (`images` | `videos` | `gifs`, where its saved clip lands in `/history`) `failAfterPromptCount` (execution fails after the first N, for a chain's second segment) and `progressPlan` (an exact progress series, so an ETA test can drop `max` mid-take like a node reset); controls: `holdQueue`, `holdRequests(path, held)` (parks `/upload/image`, `/prompt`, `/free` or `/view` requests after recording them), `restart` (forgets prompts and history, keeps uploads). It takes a caller's `prompt_id` on `POST /prompt`, as ComfyUI does. Tests that run the real client over the fake start with `// @vitest-environment node` (jsdom's `Event` and `FormData` do not mix with Node's WebSocket and fetch).

## Takes on the job engine

A take is one render of a card: a job of the `image` kind (`image-job.ts`, tables `image_jobs` and `image_job_attempts`; the card is `image_cards`). The engine owns every lifecycle transition; this folder writes only the take's own columns (`queue_ahead`, `progress_percent`, `eta_seconds`, `phase_at`, `result_file_id`, `measures_json`, `cancel_interrupt`…). `held_until` and `phase_at` are milliseconds; every `mode: "timestamp"` column is unix seconds.

| `image-job.ts` | the kind's definition (six at once install-wide, four per person, so prompts reach ComfyUI together and its queue orders them), `enqueueTake`, `cancelTake`, `retryTake`, `cancelImageTakesForUser` (quiesce, Clear Workspace), `cancelImageTakesForConversation` (chat delete, before any picture file is removed) |
| `image-runner.ts` | the handler, loaded on the first claim: upload inputs, build the graph, name the prompt (a uuid) and checkpoint its id, submit it as `prompt_id`, follow, guard an edit, store the PNG, succeed |
| `cards.ts` | cards and picks (below): `createCard`, `settleCard`, `releaseHold`, `hideTake`, `useTake`, `replacePick`, `settleHeldCards`, `versionBodyForTake`, `versionBodyForPhoto` |

- **Phases.** `image-job.ts` lists `submitted`, `starting`, `rendering`, `finishing`. The engine's claim writes the first (`phases[0]`) before the runner starts; the runner's `enterPhase(ctx, "submitted")` after the POST repeats it only to stamp `phase_at`. `starting` is written when ComfyUI lists the prompt as running (or says `execution_start`), `rendering` on the first progress step, `finishing` when the follow is done. `submitted` is therefore over about 20 ms after the claim on a quiet machine (the socket, the POST, the first queue read), so a 20 ms poll sees it only by chance: a test reads the phases from the database itself (`recordPhases` in `image-runner.test.ts`, a trigger on `image_jobs`) and never polls for one.
- **Cards and picks (`cards.ts`).** A card's pick is the take in use as of that card. A held take (`held_until` in the future) is never promoted; `releaseHold` clears it and settles, and a take that lands later is settled by the runner right after `ctx.succeed` (`settleCard` itself skips held takes). The winner is `preferTakeId` if eligible (succeeded, not hidden, not held, with a file), else the oldest eligible take. The claim is one `UPDATE image_cards SET picked_take_id = ? WHERE picked_take_id IS NULL`: only the caller whose update changed a row writes the version, so "show me four" gives one version and three takes to pick. A failed artifact write undoes the claim. An item that no longer exists leaves the card with no item and no pick (a `change` card whose `artifact_id` is null is never settled, so a deleted item is not made again) and the take's picture is discarded. `useTake` on a settled card appends a version authored by the person (`pickedTake`); `replacePick` (the model's retry of the take in use) appends one authored by Alfy with the old take's summary and hides the old take; `hideTake` refuses the pick. `clearTakeHolds` runs synchronously in `hooks.server.ts` `init`, before the process serves a request and before the job engine starts (no tool call survives a restart); a deferred clear would wipe the hold of a request already being served. It assumes ONE app process: a second process booting would clear the first one's live holds. `settleCardsAfterRestart` stays deferred (after the engine starts), only settles, and never touches holds.
- **A photo item's version 1 is the canvas-sized copy.** The upload itself is never modified and stays the chat attachment; version 1 of a photo item is the normalized PNG the first change was made from (the take's base input), authored by the person (`userPhoto`), its own anchor with chain 0. Download or History of "the original" therefore gives the downscaled copy.
- **No import cycle.** `image-job.ts` loads `image-runner.ts` dynamically; the runner never imports `image-job.ts` (the deadline lives in `take-request.ts`). `cards.ts` (imported by the runner for `settleCard`) must not import `image-job.ts`: card code that does (`card-actions.ts`, "another take") must not be imported by the runner.
- **Two Stops.** `cancelTake(userId, takeId, { interrupt })`: the card's Stop (`true`, the default) may interrupt our own running prompt; the composer's Stop (`false`) cancels a take that has not reached ComfyUI (queued, or running with no prompt id: still preparing its inputs, since the runner writes the id it will submit under BEFORE the `POST /prompt`; the check and the cancel are one transaction), only deletes a prompt still waiting in ComfyUI's queue, and leaves a started render, or a prompt whose POST is in flight, alone (the call answers false and the take is not cancelled). When ComfyUI answers with another id than the one sent (a version that ignores `prompt_id`), the runner logs it and rewrites the checkpoint with ComfyUI's. The kind of Stop is written on the take (`cancel_interrupt`) before the engine cancels it, so the run that gets the abort, in this process or another, acts on the right one. Bulk cancels (erasure, chat delete) always interrupt.
- **The tool inside the turn (`normal-chat-tools/make-image.ts`, `result-look.ts`).** The call waits up to `IMAGE_TOOL_WAIT_MS` (100 s). `wait.ts` supports a one-second `onTick` callback; Normal Chat connects meaningful tool activity to its idle watchdog. The model engine's remaining working deadline can end this wait. Only the composer's Stop (`UserStopReason`) cancels, with `interrupt: false`; every other abort only releases holds. A landed take whose guard measured a clear miss (`nothing_changed`, `outside_marks`) gets ONE retry in the same call when at least 25 s of the wait is left and it is not itself a retry: same request, a seed avoiding both, origin `auto_retry` (the model's own `retryOf` keeps origin `retry`, so the card can fold only the automatic one), held. `pickBetterTake` keeps the retry unless it failed or only it missed; when both missed, the one with more change inside the marks. The loser is hidden (`hideTake`), the winner released, `retried` is set on the shown take and in the payload and metadata. A miss only eyes can see is the model's `retryOf`: the new take replaces the old through `replacePick` when the old is in use, unless `pickBetterTake` prefers the old, which then stays and the model is told so. A take that ends the call with a miss is told as a failed edit over every other note, and it still lands on its card. A picture that lands after the wait gets no look and no retry. Model execution reserves closing time inside `REQUEST_TIMEOUT_MS` (default 300 s total, 240 s working). Normal Chat applies a 150 s meaningful-activity idle limit and the configured total deadline from admission through preparation and finalization. An already-started database commit retains receipt ownership after transport detaches until its actual result settles. These model deadlines do not bound the detached image job itself.
- **End to end.** `tests/e2e/images-pipeline.spec.ts` runs a whole turn against the fake ComfyUI (`createFakeComfyUi`, started in the spec's process and set as `COMFYUI_URL` through the admin config route by `tests/e2e/images-helpers.ts`); the fake model calls `make_image` on `AI_SMOKE_MAKE_IMAGE_MARKER`.
- **Failure codes.** unreachable `image_server_unreachable` (retryable), rejected graph or `GraphBuildError` `image_graph_rejected` (not), failed render `image_render_failed`, timeout `image_render_timeout`, missing result `image_result_missing` (all retryable), missing input file `image_input_missing` (not), no address `image_server_not_configured` (not), unreadable request `image_request_invalid` (not), the explicit-picture filter's `image_blocked` (not; `retryTake` refuses it) and `image_unchecked` (retryable on the card; the model is never offered a retry of either). Only `image_worker_lost` is requeued by the policy (three attempts, 2 s apart); everything else waits for the person's Retry.
- **Resume.** A later attempt that finds `{ promptId }` in the checkpoint follows that prompt. Once the checkpoint is written, `unreachable` and `bad_response` while following are transient: the follow is retried for `FOLLOW_GRACE_MS` (60 s, longer than a ~26 s reload, capped by `IMAGE_RENDER_DEADLINE_MS`). Before the submit, `unreachable` fails the take at once. When ComfyUI is back and no longer knows the prompt (or its temp picture is gone), the take is submitted once more, once per run; a second miss fails `image_result_missing`. The fake's `outage(ms)` is the faithful reload (refuses connections, then forgets); `restart()` is zero-downtime.
- **A stopped take stores nothing.** After `storeImageFile` the runner checks the signal, and if `ctx.succeed` is refused it removes the picture by path (`discardStoredImageFile`), row or no row, because a chat's cleanup may already have run.
- **Marked edits (`guards/guard-edit.ts`, `guards/marks-clamp.ts`).** The picture model never sees boxes: it gets the clean picture and the place in words (`promptWithMarks`), because shown a boxed copy it drew the boxes into its results. A take queued before that still holds a `marked` input; `take-request.ts` still parses the role and the runner leaves it out. The boxes bound the paste: each is grown by half its short side, between 2% and 10% of the picture's short side, feathered inward, for every path, and a result over `globalChangeShare` is NOT kept whole (`global: true` is reported). Whether a box changed is `boxChangedShare`, at work resolution, because at full size the model's noise reads as change. Every box must change; one that did not is a miss (`nothing_changed`, or `outside_marks` when something else changed), and when at least one did, what the model made inside the clamp is kept whole except on see-through pixels. The fourth-change re-anchor deliberately rebuilds the pixels outside the marks from the anchor wherever the base had not left it (the drift reset); earlier changes the base already carries are kept.
- **Which picture a marked call changes (`requests.ts`).** Naming the marked copy is naming the picture it was painted from. The boxes join a call whose first picture is the marked one (any version of its item, then the version marked is the base), `startNew` included, and a call naming no picture unless it is `startNew`. A call whose first picture is another goes without them. A chosen older version is the base, except that a later change of the same card in the turn builds on the take just made.
- **See-through is the request's to decide (Task 17).** The runner stores a take with `storeImageFile({ mayBeSeeThrough })`: true only when its graph was the transparent one (`graphFor(...).transparentApplied`) or the base it changes is stored see-through; otherwise the alpha is dropped whatever the pixels say (ai.dev: a plain generate came back with 5 pixels at alpha 244-249). `alpha.ts`'s 250 threshold is the second guard, for a request that may be see-through; an input (a photo, a card picture) is measured by its own pixels.
- **Exposed edges take the base (`guards/composite.ts` `overBase`).** `guardEdit` measures the aligned result as it is (an edge alignment exposed is alpha 0 and is not an edit), and every PASTE goes through `overBase(base, aligned)`: where the result is see-through the base shows, so an opaque base always gives an opaque picture. Where the base itself is transparent nothing is filled.
- **A whole repaint is not aligned.** An unmarked result over `globalChangeShare` is kept as the model drew it (`overBase(base, resizeRaw(result, …))`: only its own see-through pixels show the base). Nothing is pasted, and undoing its reframe left a strip of the base along an edge: production, 31 Oct, five of twenty single-picture edits, shifts up to 42 x 57 px and scales from 0.94 to 1.055 on 1184 x 896, a strip of 1.6% to 6% of the frame. Its `dx`, `dy` and `scale` measures still say where it sat against the base; they were not undone.
- **Input copies stay.** Every input is copied (only the changed item's own file is reused), so the input copies of a card that never settles stay until the chat is deleted. Accepted cost.
- **Seeds.** `enqueueTake` redraws a seed that is on `request.avoidSeeds` (never the seed that made an input). `retryTake` re-renders a failed or cancelled take with its own seed, which is not an input's.

## The video take (`video/`, docs/plans/ltx-video slice 4)

- **A third engine, its own kind.** `COMFYUI_LTX_URL` (`getComfyuiLtxUrl`, `isVideoMakingConfigured`) is the LTX server; `videoJob` is the kind (one global, one per person) with its own tables (`video_jobs`, `video_job_attempts`) and its own `VIDEO_RENDER_DEADLINE_MS` / `VIDEO_TOOL_WAIT_MS` in `video/request.ts` — never the picture's numbers. `hooks.server.ts` starts it beside the image kind.
- **The graph.** `comfyui/ltx-templates.ts` builds `graphs/ltx-image-to-video.api.json`, hand-written from the shipped `video_ltx2_5_i2v` template's API export with the enhancer branch removed, the NVFP4 transformer the feasibility numbers were measured on (`ltx-2.5-22b-distilled-transformer-nvfp4`; the template's int8 file is larger, unmeasured and absent from the LTX worktree) and the conv VAE (`ltx-2.5-video-vae-conv-bf16`) in place of the diffusion one. The audio VAE is a checkpoint read by `LTXVAudioVAELoader`'s `ckpt_name` (`models/checkpoints`), not the plain `VAELoader`. The names, the sigmas and the frame constants live in `ltx-spec.ts`, which imports no JSON: the video request module needs the frame constants, and a bare JSON import on an e2e spec's import path stops Playwright loading it (the graph module keeps the JSON import for the Vite build). Two passes, the template's own sigmas, 121 frames at 24 fps. The runner hands it the output size (`videoSizeForSource`: long edge 1280, short side floored to a multiple of 32 — 1280x704 for a 16:9 still, 704x1280 portrait) and the graph halves it for the first pass, flooring each half to a multiple of 32 (a raw 176 would silently become 160 inside the latent).
- **The chain.** A 5 s take is one segment. A 10 s take is two: segment 2's guide is the LAST DECODED FRAME of segment 1 (`ffmpeg -sseof -0.1`, not a re-render), and the two mp4s are concatenated (stream copy, re-encode fallback when the codec parameters differ). If segment 2 fails, the take FAILS: one segment is never stored and served as ten seconds.
- **Resume.** The checkpoint is `{ promptId, segment, segments }`: the current segment's prompt id (which `promptIdOf` reads, so a Stop finds it) and every finished segment's saved clip. A restart follows the prompt instead of rendering it again; a finished segment's clip is fetched from ComfyUI; a prompt ComfyUI forgot (it restarted) is re-rendered once for that segment. ComfyUI returning another prompt id than the one sent rewrites the checkpoint, as the picture path does.
- **Store and settle.** Nothing is stored until the whole clip is checked, and the check covers **every frame** (the owner ruled a sampled video filter weaker than the picture path is not acceptable). One ffmpeg pass writes the model's input as raw rgb24 at 224x224 (no PNG decode or resize in Node) and the full-size frame 0 as the poster together; the classifier runs the frames in batches of `PICTURE_CHECK_BATCH_SIZE` (16) on ONE session, 8 inference runs for 121 frames and 16 for 242. Measured on the app host with the pinned fp32 model on a 5 s 1280x704 clip: an **exempt** take decodes only the poster (≈40 ms; no check stream, no frame files, no classifier), while a **filtered** take decodes the raw check stream (≈50 ms) and then pays **≈3.7–4.2 s of batched inference** (8 runs, ≈0.47 s a batch), so the filter costs about 4 s on top of a take; a 10 s clip's 16 runs are ≈7.0 s. The old per-picture path was 34–37 ms a picture here, and the 18 s serial estimate came from a slower box. `blocked` fails `video_blocked`, a check that cannot run `video_unchecked` (fail closed); neither stores anything. `storeVideoFile` writes the mp4 with its derived poster and thumbnail and the product length (5000/10000 ms); its container metadata is stripped first (`-map_metadata -1`), because ComfyUI writes the prompt and node graph into the mp4's tags. The clip is attached to its item, and a new `video` artifact is created (its id recorded on the take in the fenced write, so a retry appends) or a version appended to `request.artifactId`. A failed artifact write discards the stored clip; a Stop after the store discards it and takes back the just-appended version (or deletes the item the take made).
- **The media phase has its own deadline.** Every ffmpeg/ffprobe call takes the take's signal and `MEDIA_TIMEOUT_MS` (120 s, capped by the attempt's remaining render deadline), so a wedged child fails the take `video_media_failed` instead of holding the kind's one slot forever; a caller's Stop kills the child and settles as a stop. The attempt deadline is re-checked at every media phase boundary and before each classifier batch.
- **GPU-side leftovers are an accepted cost.** `SaveVideo` writes into ComfyUI's persistent `output/video/` (under the graph's `video/alfyai` prefix), and the uploaded guide stills stay in its input folder, so an abandoned take leaves an mp4 and its stills on the box. Nothing sweeps them. The fix, if it is worth it, is a per-take prefix plus a sweep on the GPU host; recording it here keeps it a known cost rather than an unmentioned one.
- **Failure codes.** `video_server_unreachable` (retryable), `video_graph_rejected` (not), `video_render_failed` / `video_render_timeout` / `video_result_missing` (retryable), `video_input_missing` (not), `video_server_not_configured` (not), `video_request_invalid` (not), `video_item_deleted` (not), `video_media_unavailable` (ffmpeg missing; not), `video_media_failed` (retryable), `video_artifact_failed` (the item could not be saved; retryable), `video_blocked` (not; `retryVideoTake` refuses it), `video_unchecked` (retryable). Only `video_worker_lost` is requeued (three attempts, 2 s apart).
- **Stop.** `cancelVideoTake` mirrors `cancelTake`: the card's Stop (`interrupt: true`) may interrupt the running segment; the composer's Stop (`interrupt: false`) cancels before the first POST and otherwise only deletes a prompt still waiting in ComfyUI's queue. Chat delete and Clear Workspace cancel the chat's or person's takes before the files go.
- **Tests.** `video/runner.test.ts` is the pipeline over the fake (5 s, the chain, resume, every phase stopped, the filter) and `tests/e2e/images-video.spec.ts` proves the whole server path against the fake with the real ffmpeg. Nothing measures the GPU.

## The explicit-picture filter (`picture-check/`, plan 2b Task 18)

- **Who.** `policy.ts` `isExplicitFilterOnFor(userId)`: on unless `IMAGE_EXPLICIT_FILTER_ENABLED` is off (config-store) or an admin exempted the person (`users.explicit_picture_filter_exempt`, Users pane, `user-admin.ts`). A person it cannot read is filtered. Incognito chats follow the same rule.
- **Before rendering.** While the filter applies, make_image's description carries one line telling the model to decline (`createToolPack` threads `explicitPictureFilter`), and `make-image.ts` refuses, before any card or take, a `prompt` or `title` that `request-terms.ts` matches (`explicit_request`). The list is small, whole-word, English and Hungarian, with innocent uses let through ("nude-coloured", "the naked eye", "no nudity"); anatomy and swimwear words are left to the picture check. Its tests hold innocent prompts.
- **After rendering.** `image-runner.ts` calls `checkFinishedPicture` (`index.ts`) on the PNG exactly as it would be stored, so a generate, an edit's pasted result, Another and every retry pass through it. `blocked` fails the take `image_blocked`, a check that cannot run fails it `image_unchecked` (fail closed); neither is stored, so nothing can be served, thumbnailed or downloaded. Uploaded photos themselves are not checked.
- **The classifier (`classifier.ts`, `model.ts`).** Falconsai/nsfw_image_detection, fp32 ONNX export (the owner's choice), pinned by revision and SHA-256 (`model.ts`), run in-process on the CPU with onnxruntime-node (2 threads, one check at a time, about 150 ms a picture). It also has a batch entry (`classifyRawFrames`): raw rgb24 frames at the model's 224x224, `PICTURE_CHECK_BATCH_SIZE` (16) per `run` on one session, which is what the video filter uses (121 frames measured at ≈3.7–4.2 s in the video section). `npm run models:fetch` (`scripts/fetch-picture-check-model.ts`, run by both deploy scripts) puts it in `data/models/picture-check/`. Life cycle: only a real check loads the model; the file is read once per load and that buffer is both hashed and handed to the session; a failed load is not retried until the file changes; every check (load included) has a 15 s deadline (`CHECK_TIMEOUT_MS`), after which it is unavailable and the engine it ran on is dropped, so a hung run never wedges the queue; the session is released after `IMAGE_IDLE_FREE_MS` with no check. A missing or different file is `PictureCheckUnavailable`. Tool Health: `make_image:picture_check` checks the file's presence and hash only (cached until it changes), never loading the model.
- **Tests never use an explicit picture.** `IMAGE_CHECK_CLASSIFIER=stub` (honoured only under vitest or `PLAYWRIGHT_TEST`; vitest-setup and the e2e servers set it) flags only `STUB_EXPLICIT_COLOUR` and cannot check `STUB_UNAVAILABLE_COLOUR`. The real model has a smoke test on safe pictures, skipped without the file. `tests/e2e/images-picture-filter.spec.ts` holds the blocked card, the exempt person and the switch.
- **Logs** are content-free: take id, verdict, milliseconds.

## The turn's numbered pictures (`turn-pictures.ts`, `marks.ts`)

- **One numbering authority.** `resolveTurnPictures` numbers a message's uploads, the card pictures attached (`pictureRefs`), the picture open in the panel and the marked copy; `vision/turn-images.ts` takes every number from the index. Its `TurnPictureSource` is `upload` or `image_file` (role `attached` / `open` / `marked`); the picture server's `PictureSourceRef` (T12) is the same shape under `kind`. A picture reaching the turn twice has one number.
- **Access is scoped.** `validatePictureRequest` (called by `chat-turn/preflight.ts`) refuses a ref to a file the person does not own, or to an incognito chat's file outside that chat, as `404 picture_not_found` through `getImageFile`'s scope, and marks on a file that is neither a ref nor the open picture as `400 invalid_image_marks` (the request is refused loudly, never sent with its marks silently dropped; a client that drew marks on a picture which is no longer open attaches that picture as a ref, plan 2b Task 6, so the marks stay valid). Only a regenerated turn and the resend of an edit (`keepReadableRecordedPictures`) drop what they can no longer read, quietly. Marks may instead name an uploaded photo (`uploadArtifactId`, in `ImageMarksRequest` and the recorded `marks`): it must be one of the message's `attachmentIds`, whose ownership the attachment gate checks, and a photo of an earlier message rides again as an attachment. The marked copy is painted from it through `loadPicture`; the photo stays an upload, so its item still starts with it as version 1. It never counts pictures. The open picture is read only when `activeDocumentArtifactId` is an Image item of this person whose file they may read.
- **Marks.** `marks.ts` paints each box as a stroke of `max(4, 0.006 x long side)` in its colour (`MARK_COLOURS`, the shared constant) with a filled tag of `max(28, 0.035 x long side)` at the top left holding the letter as white strokes on a 5x7 grid (`LETTER_STROKES`, no font), composited with sharp from one SVG; the copy is stored as a `marked` picture file of the chat, for the chat model's eyes only. A copy that cannot be made is logged and the turn goes on without it.
