# Images

Making and changing pictures: the ComfyUI client and its fake, graphs, pixel guards, picture files, cards and takes, the image job. Parent rules: `src/lib/server/services/AGENTS.md`.

## ComfyUI (`comfyui/`)

- **Address.** `COMFYUI_URL` only (`RuntimeConfig.comfyuiUrl` in `config-store.ts`), reached with plain `fetch` (injectable `fetchImpl`, as `mineru/client.ts` does), never `$lib/server/outbound`. Nothing a model writes becomes an address (ADR-0068).
- **Routes.** Only `POST /upload/image`, `POST /prompt`, `GET /queue`, `POST /queue` (delete), `GET /history/{id}`, `GET /view`, `POST /interrupt`, `POST /free`, `GET /system_stats` (Tool Health) and the `/ws` socket. Add no other route without a ruling.
- **Interrupt rule.** `POST /interrupt` only when `GET /queue` shows our own prompt running. `cancel(promptId, { interrupt })` deletes a pending prompt either way; for a running one it interrupts only with `interrupt: true` (the card's Stop) and otherwise answers `"running"` and leaves it. The turn-abort path passes `false`: a take ComfyUI has started finishes onto its card.
- **One writer.** Nothing outside `services/jobs/` writes `image_jobs` lifecycle columns; this folder never touches job state.
- **No facade cycle.** `services/artifacts/` imports `images/files.ts` only. `images/files.ts` must not import the artifacts facade (`cards.ts` may: nothing the facade imports leads back to it).
- **Storage.** Picture files live under `data/image-files/<conversationId>/` with a relative `storage_path`; `data/image-files` is in `storageRoots()` and every unlink goes through `resolveDeletablePath`.
- **Result pictures.** Graphs end in `PreviewImage`, so results are `type: "temp"` (cleared on a ComfyUI restart); `ComfyImageRef.type` also allows `input` and `output`. Uploaded inputs persist on the GPU box until a cleanup is set up (plan 2c).
- **Socket.** One WebSocket per client, opened on the first `submit`. It only adds progress events; polling `/queue` and `/history` decides every outcome, so a client with no socket still finishes.

## The fake (`comfyui/testing/fake-comfyui.ts`)

A real loopback HTTP and WebSocket server for unit and Playwright tests. It imports Node built-ins and sharp only, so specs may import it by relative path. Options: `steps`, `stepDelayMs`, `startDelayMs`, `fail` (`reject` | `execution`), `ignorePromptId` (answers with an id of its own, like a ComfyUI from before caller-supplied ids), `render` (override per call or through `setOptions`); controls: `holdQueue`, `holdRequests(path, held)` (parks `/upload/image` or `/prompt` requests after recording them), `restart` (forgets prompts and history, keeps uploads). It takes a caller's `prompt_id` on `POST /prompt`, as ComfyUI does. Tests that run the real client over the fake start with `// @vitest-environment node` (jsdom's `Event` and `FormData` do not mix with Node's WebSocket and fetch).

## Takes on the job engine

A take is one render of a card: a job of the `image` kind (`image-job.ts`, tables `image_jobs` and `image_job_attempts`; the card is `image_cards`). The engine owns every lifecycle transition; this folder writes only the take's own columns (`queue_ahead`, `progress_percent`, `eta_seconds`, `phase_at`, `result_file_id`, `measures_json`, `cancel_interrupt`…). `held_until` and `phase_at` are milliseconds; every `mode: "timestamp"` column is unix seconds.

| File | Owns |
|---|---|
| `take-request.ts` | `TakeRequest` (what `request_json` holds), `parseTakeRequest` (null for anything unreadable), `StoredTakeMeasures`, `IMAGE_RENDER_DEADLINE_MS` (shared by the kind and the handler so neither imports the other) |
| `image-job.ts` | the kind's definition (six at once install-wide, four per person, so prompts reach ComfyUI together and its queue orders them), `enqueueTake`, `cancelTake`, `retryTake`, `cancelImageTakesForUser` (quiesce, Clear Workspace), `cancelImageTakesForConversation` (chat delete, before any picture file is removed) |
| `image-runner.ts` | the handler, loaded on the first claim: upload inputs, build the graph, name the prompt (a uuid) and checkpoint its id, submit it as `prompt_id`, follow, guard an edit, store the PNG, succeed |
| `cards.ts` | cards and picks (below): `createCard`, `settleCard`, `releaseHold`, `hideTake`, `useTake`, `replacePick`, `settleHeldCards`, `versionBodyForTake`, `versionBodyForPhoto` |
| `idle-free.ts` | `scheduleIdleFree` (one unref'd timer on `globalThis`, re-armed after every take, `IMAGE_IDLE_FREE_MS` 15 min measured in plan 2c) and `freeIfIdle(client)` |
| `comfy-client.ts` | the only place a client is made from `getConfig().comfyuiUrl` |
| `testing/` | `fixture.ts` (migrated database), `run-takes.ts` (`drainImageTakes`, a thin wrapper over the engine's `drain`) |

- **Cards and picks (`cards.ts`).** A card's pick is the take in use as of that card. A held take (`held_until` in the future) is never promoted; `releaseHold` clears it and settles, and a take that lands later is settled by the runner right after `ctx.succeed` (`settleCard` itself skips held takes). The winner is `preferTakeId` if eligible (succeeded, not hidden, not held, with a file), else the oldest eligible take. The claim is one `UPDATE image_cards SET picked_take_id = ? WHERE picked_take_id IS NULL`: only the caller whose update changed a row writes the version, so "show me four" gives one version and three takes to pick. A failed artifact write undoes the claim. An item that no longer exists leaves the card with no item and no pick (a `change` card whose `artifact_id` is null is never settled, so a deleted item is not made again) and the take's picture is discarded. `useTake` on a settled card appends a version authored by the person (`pickedTake`); `replacePick` (the model's retry of the take in use) appends one authored by Alfy with the old take's summary and hides the old take; `hideTake` refuses the pick. `clearTakeHolds` runs synchronously in `hooks.server.ts` `init`, before the process serves a request and before the job engine starts (no tool call survives a restart); a deferred clear would wipe the hold of a request already being served. It assumes ONE app process: a second process booting would clear the first one's live holds. `settleCardsAfterRestart` stays deferred (after the engine starts), only settles, and never touches holds.
- **A photo item's version 1 is the canvas-sized copy.** The upload itself is never modified and stays the chat attachment; version 1 of a photo item is the normalized PNG the first change was made from (the take's base input), authored by the person (`userPhoto`), its own anchor with chain 0. Download or History of "the original" therefore gives the downscaled copy.
- **No import cycle.** `image-job.ts` loads `image-runner.ts` dynamically; the runner never imports `image-job.ts` (the deadline lives in `take-request.ts`). `cards.ts` (imported by the runner for `settleCard`) must not import `image-job.ts`: card code that does (`card-actions.ts`, "another take") must not be imported by the runner.
- **Two Stops.** `cancelTake(userId, takeId, { interrupt })`: the card's Stop (`true`, the default) may interrupt our own running prompt; the composer's Stop (`false`) cancels a take that has not reached ComfyUI (queued, or running with no prompt id: still preparing its inputs, since the runner writes the id it will submit under BEFORE the `POST /prompt`; the check and the cancel are one transaction), only deletes a prompt still waiting in ComfyUI's queue, and leaves a started render, or a prompt whose POST is in flight, alone (the call answers false and the take is not cancelled). When ComfyUI answers with another id than the one sent (a version that ignores `prompt_id`), the runner logs it and rewrites the checkpoint with ComfyUI's. The kind of Stop is written on the take (`cancel_interrupt`) before the engine cancels it, so the run that gets the abort, in this process or another, acts on the right one. Bulk cancels (erasure, chat delete) always interrupt.
- **The tool inside the turn (`normal-chat-tools/make-image.ts`, `result-look.ts`).** The call waits up to `IMAGE_TOOL_WAIT_MS` (100 s) and ticks `onToolActivity` once a second (`wait.ts`), which the orchestrator wires to `UpstreamIdleTimeout.touch`, so a picture's wait never trips the stream's idle watchdog. Only the composer's Stop (`UserStopReason`) cancels, with `interrupt: false`; every other abort only releases holds. A landed take whose guard measured a clear miss (`nothing_changed`, `outside_marks`) gets ONE retry in the same call when at least 25 s of the wait is left and it is not itself a retry: same request, a seed avoiding both, origin `auto_retry` (the model's own `retryOf` keeps origin `retry`, so the card can fold only the automatic one), held. `pickBetterTake` keeps the retry unless it failed or only it missed; when both missed, the one with more change inside the marks. The loser is hidden (`hideTake`), the winner released, `retried` is set on the shown take and in the payload and metadata. A miss only eyes can see is the model's `retryOf`: the new take replaces the old through `replacePick` when the old is in use. A picture that lands after the wait gets no look and no retry. The turn's stream-wide cap is `max(60 s, REQUEST_TIMEOUT_MS)` (default 300 s), so an admin `REQUEST_TIMEOUT_MS` under about 130 s can end the 100 s wait; README and `.env.example` say so beside `COMFYUI_URL`.
- **End to end.** `tests/e2e/images-pipeline.spec.ts` runs a whole turn against the fake ComfyUI (`createFakeComfyUi`, started in the spec's process and set as `COMFYUI_URL` through the admin config route by `tests/e2e/images-helpers.ts`); the fake model calls `make_image` on `AI_SMOKE_MAKE_IMAGE_MARKER`.
- **Failure codes.** unreachable `image_server_unreachable` (retryable), rejected graph or `GraphBuildError` `image_graph_rejected` (not), failed render `image_render_failed`, timeout `image_render_timeout`, missing result `image_result_missing` (all retryable), missing input file `image_input_missing` (not), no address `image_server_not_configured` (not), unreadable request `image_request_invalid` (not), the explicit-picture filter's `image_blocked` (not; `retryTake` refuses it) and `image_unchecked` (retryable on the card; the model is never offered a retry of either). Only `image_worker_lost` is requeued by the policy (three attempts, 2 s apart); everything else waits for the person's Retry.
- **Resume.** A later attempt that finds `{ promptId }` in the checkpoint follows that prompt. Once the checkpoint is written, `unreachable` and `bad_response` while following are transient: the follow is retried for `FOLLOW_GRACE_MS` (60 s, longer than a ~26 s reload, capped by `IMAGE_RENDER_DEADLINE_MS`). Before the submit, `unreachable` fails the take at once. When ComfyUI is back and no longer knows the prompt (or its temp picture is gone), the take is submitted once more, once per run; a second miss fails `image_result_missing`. The fake's `outage(ms)` is the faithful reload (refuses connections, then forgets); `restart()` is zero-downtime.
- **A stopped take stores nothing.** After `storeImageFile` the runner checks the signal, and if `ctx.succeed` is refused it removes the picture by path (`discardStoredImageFile`), row or no row, because a chat's cleanup may already have run.
- **Marked edits (`guards/marks-clamp.ts`).** A marked edit pastes back only inside the marks grown by 10% of the short side, feathered inward, for every path: a result over `globalChangeShare` is NOT kept whole (it is measured, flagged `outside_marks` when most of the change is outside the marks, and pasted limited, with `global: true` reported). The fourth-change re-anchor deliberately rebuilds the pixels outside the marks from the anchor wherever the base had not left it (the drift reset); earlier changes the base already carries are kept.
- **See-through is the request's to decide (Task 17).** The runner stores a take with `storeImageFile({ mayBeSeeThrough })`: true only when its graph was the transparent one (`graphFor(...).transparentApplied`) or the base it changes is stored see-through; otherwise the alpha is dropped whatever the pixels say (ai.dev: a plain generate came back with 5 pixels at alpha 244-249). `alpha.ts`'s 250 threshold is the second guard, for a request that may be see-through; an input (a photo, a card picture) is measured by its own pixels.
- **Exposed edges take the base (`guards/composite.ts` `overBase`).** `guardEdit` measures the aligned result as it is (an edge alignment exposed is alpha 0 and is not an edit), but every path pastes or keeps `overBase(base, aligned)`: where the result is see-through the base shows, so an opaque base always gives an opaque picture, including the whole repaint, which once stored the exposed strip transparent. Where the base itself is transparent nothing is filled.
- **Input copies stay.** Every input is copied (only the changed item's own file is reused), so the input copies of a card that never settles stay until the chat is deleted. Accepted cost.
- **Seeds.** `enqueueTake` redraws a seed that is on `request.avoidSeeds` (never the seed that made an input). `retryTake` re-renders a failed or cancelled take with its own seed, which is not an input's.

## The explicit-picture filter (`picture-check/`, plan 2b Task 18)

- **Who.** `policy.ts` `isExplicitFilterOnFor(userId)`: on unless `IMAGE_EXPLICIT_FILTER_ENABLED` is off (config-store) or an admin exempted the person (`users.explicit_picture_filter_exempt`, Users pane, `user-admin.ts`). A person it cannot read is filtered. Incognito chats follow the same rule.
- **Before rendering.** While the filter applies, make_image's description carries one line telling the model to decline (`createToolPack` threads `explicitPictureFilter`), and `make-image.ts` refuses, before any card or take, a `prompt` or `title` that `request-terms.ts` matches (`explicit_request`). The list is small, whole-word, English and Hungarian, with innocent uses let through ("nude-coloured", "the naked eye", "no nudity"); anatomy and swimwear words are left to the picture check. Its tests hold innocent prompts.
- **After rendering.** `image-runner.ts` calls `checkFinishedPicture` (`index.ts`) on the PNG exactly as it would be stored, so a generate, an edit's pasted result, Another and every retry pass through it. `blocked` fails the take `image_blocked`, a check that cannot run fails it `image_unchecked` (fail closed); neither is stored, so nothing can be served, thumbnailed or downloaded. Uploaded photos themselves are not checked.
- **The classifier (`classifier.ts`, `model.ts`).** Falconsai/nsfw_image_detection, fp32 ONNX export (the owner's choice), pinned by revision and SHA-256 (`model.ts`), run in-process on the CPU with onnxruntime-node (2 threads, one check at a time, about 150 ms a picture). `npm run models:fetch` (`scripts/fetch-picture-check-model.ts`, run by both deploy scripts) puts it in `data/models/picture-check/`. Life cycle: only a real check loads the model; the file is read once per load and that buffer is both hashed and handed to the session; a failed load is not retried until the file changes; every check (load included) has a 15 s deadline (`CHECK_TIMEOUT_MS`), after which it is unavailable and the engine it ran on is dropped, so a hung run never wedges the queue; the session is released after `IMAGE_IDLE_FREE_MS` with no check. A missing or different file is `PictureCheckUnavailable`. Tool Health: `make_image:picture_check` checks the file's presence and hash only (cached until it changes), never loading the model.
- **Tests never use an explicit picture.** `IMAGE_CHECK_CLASSIFIER=stub` (honoured only under vitest or `PLAYWRIGHT_TEST`; vitest-setup and the e2e servers set it) flags only `STUB_EXPLICIT_COLOUR` and cannot check `STUB_UNAVAILABLE_COLOUR`. The real model has a smoke test on safe pictures, skipped without the file. `tests/e2e/images-picture-filter.spec.ts` holds the blocked card, the exempt person and the switch.
- **Logs** are content-free: take id, verdict, milliseconds.

## The turn's numbered pictures (`turn-pictures.ts`, `marks.ts`)

- **One numbering authority.** `resolveTurnPictures` numbers a message's uploads, the card pictures attached (`pictureRefs`), the picture open in the panel and the marked copy; `vision/turn-images.ts` takes every number from the index. Its `TurnPictureSource` is `upload` or `image_file` (role `attached` / `open` / `marked`); the picture server's `PictureSourceRef` (T12) is the same shape under `kind`. A picture reaching the turn twice has one number.
- **Access is scoped.** `validatePictureRequest` (called by `chat-turn/preflight.ts`) refuses a ref to a file the person does not own, or to an incognito chat's file outside that chat, as `404 picture_not_found` through `getImageFile`'s scope, and marks on a file that is neither a ref nor the open picture as `400 invalid_image_marks` (the request is refused loudly, never sent with its marks silently dropped; a client that drew marks on a picture which is no longer open attaches that picture as a ref, plan 2b Task 6, so the marks stay valid). Only a regenerated turn (`keepReadableRecordedPictures`) drops what it can no longer read, quietly. It never counts pictures. The open picture is read only when `activeDocumentArtifactId` is an Image item of this person whose file they may read.
- **Marks.** `marks.ts` paints each box as a stroke of `max(4, 0.006 x long side)` in its colour (`MARK_COLOURS`, the shared constant) with a filled tag of `max(28, 0.035 x long side)` at the top left holding the letter as white strokes on a 5x7 grid (`LETTER_STROKES`, no font), composited with sharp from one SVG; the copy is stored as a `marked` picture file of the chat. A copy that cannot be made is logged and the turn goes on without it.
