# Vision

What the chat model sees of an image. The chat turn's own wiring lives in `chat-turn/`; read its AGENTS.md before adding a model call.

- **Pixels belong to one turn.** They ride in the messages of the turn that needs them (there is no look-at-image tool); afterwards history carries a short description of the image.
- **Every image a model is sent comes out of `prepareImageForModel`** (`prepare-image.ts`: upright, flat, first frame, JPEG), never the stored original, so the budgets hold.
- **Budgets.** An attachment goes at most 1600 px on its long side (about 1,600 tokens), an Immich thumbnail at most 512 px (about 250). Tokens are `ceil(w/32) * ceil(h/32)` (`estimateImageTokens`). A turn carries at most 8 attachment images and 8 thumbnails as pixels. A prepared picture is charged by its own `estimatedTokens` (a square one at the limit is about 2,500, not 1,600) wherever the current message is counted: the history budget, the packet's room, the compression check, the output reserve and the full-prompt estimate.
- **Who receives pixels.** Only a model whose `imageMessageParts` capability is explicitly `true` (the admin's "Can see images" tick). A cloud model gets images only when that model is ticked, and Immich pixels follow `connections/locality.ts` (local summarising and the cloud warning). `providerCanSeeImages` is the one question and the one reading: `normal-chat-model/index.ts` builds the provider's `imageMessageParts` entry from the stored JSON with `parseCapabilitySupportMap`, the reader behind `modelCanSeeImages`, so the admin form and a chat turn never disagree.
- **The current message.** `turn-images.ts` builds it (`buildCurrentUserMessage`: the text, then each picture as an image part holding a base64 string) and both model runs, send and stream, call it; nothing else puts pixels into a request. It prepares the attachments in the order given, two at a time (a HEIC photo decodes on the calling thread), and a picture that cannot be read or decoded is logged and left out, never a failed turn. A BMP is never sent (`isSeeableImage`: sharp has no BMP decoder), and the ones past the limit are named to the model.
- **Words to the model.** A model that cannot see is told `CANNOT_SEE_IMAGES_GUIDANCE` when the message attaches an image, and one that can is told which pictures the limit left out. Both ride the turn guidance (after the message, never the cached system prompt) and are English whatever the person writes.
- **Failover.** An attempt on a model that cannot see gets no image parts.
- **Profile memory** receives descriptions, never pixels.
