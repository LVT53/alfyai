# Vision

What the chat model sees of an image. The chat turn's own wiring lives in `chat-turn/`; read its AGENTS.md before adding a model call.

- **Pixels belong to one turn.** They ride in the messages of the turn that needs them (there is no look-at-image tool); afterwards history carries a short description of the image.
- **Every image a model is sent comes out of `prepareImageForModel`** (`prepare-image.ts`: upright, flat, first frame, JPEG), never the stored original, so the budgets hold.
- **Budgets.** An attachment goes at most 1600 px on its long side (about 1,600 tokens), an Immich thumbnail at most 512 px (about 250). Tokens are `ceil(w/32) * ceil(h/32)` (`estimateImageTokens`). A turn carries at most 8 pictures as pixels in all (`MAX_TURN_IMAGES`, counted across the uploads, the card pictures, the open picture and the marked copy, in number order; a message may hold any number of pictures and nothing refuses it for their number) and, apart from them, at most 8 Immich thumbnails for the whole turn (`STEP_IMAGE_TURN_BUDGET`, held by the turn's `StepImageQueue`: a look takes what is left of it, so ten looks do not send eighty pictures). A prepared picture is charged by its own `estimatedTokens` (a square one at the limit is about 2,500, not 1,600) wherever the current message is counted: the history budget, the packet's room, the compression check, the output reserve and the full-prompt estimate.
- **Who receives pixels.** Only a model whose `imageMessageParts` capability is explicitly `true` (the admin's "Can see images" tick). A cloud model gets images only when that model is ticked, and Immich pixels follow `connections/locality.ts` (local summarising and the cloud warning). `providerCanSeeImages` is the one question and `readModelImageInput` (`src/lib/model-image-input.ts`) the one reading of the stored JSON: `normal-chat-model/index.ts` builds the provider's `imageMessageParts` entry from it (a yes, an explicit no or nothing said) and `modelCanSeeImages` takes only its yes, so the admin form and a chat turn never disagree. `providerCanSeeImages` lives in `provider-vision.ts` (`model-vision.ts` re-exports it) because the model run asks it before every attempt and `model-vision.ts` imports the run: the run must never import `model-vision.ts`, since a fifth circular dependency fails the Fallow gate.
- **The current message.** `turn-images.ts` builds it (`buildCurrentUserMessage`: the text, then each picture as an image part holding a base64 string) and both model runs, send and stream, call it; nothing else puts pixels into a request. It prepares the attachments in the order given, two at a time (a HEIC photo decodes on the calling thread), and a picture that cannot be read or decoded is logged and left out, never a failed turn. Only a picture `isSeeableImage` accepts is sent (below); the ones past the limit, and the ones that were attached and not shown, are named to the model.
- **Pictures are numbered, once, by the turn's picture index.** A message carries its uploads, the card pictures the person attached (Attach), the picture open in the panel and the marked copy of the person's marks. `images/turn-pictures.ts` (`resolveTurnPictures`) is the ONE numbering authority: refs keep the numbers the person saw, the image uploads (`attachedImagesOf` order: attachment order, once each) fill the free ones, a ref with a repeated or out-of-range number comes after them, then the open picture, then the marked copy. A picture reaching the turn twice (Attach'ed and also open, the same upload twice) has one number and is sent once. `collectTurnImages` computes no number of its own when it is given the index (`numberOf` from `uploadNumberOf(index)`, the other pictures as `extras`, keyed `image-file:<fileId>` as photo-look's are `immich:<id>`); without an index it numbers the uploads by their place, the uploads-only case. The person's "picture 2" and the model's `Picture 2: <name>` are the same picture whether or not it can be seen or is sent. `buildCurrentUserMessage` puts that label (`pictureLabel`, which cleans the name itself through `oneLineName`, the one cleaning rule) in a text part right before each image part; the held-back and not-shown sentences use the same labels (a name that cleans to nothing falls back to the picture's id). Thumbnails from a tool are not numbered (`buildStepImagesMessage`: their entry label, then the pictures).
- **Two lists, two jobs.** `TurnImages.pictureImages` (`PreparedModelContext.turnPictureImages`) is every picture sent, labelled and in number order: the only input `buildCurrentUserMessage` reads, what `viewing_images` counts and what the token budget counts. `TurnImages.images` (`currentImages`) stays the UPLOADED pictures alone and feeds `scheduleImageDescriptions` alone: an image file (a card picture, the open picture, the marked copy) is never described into `image_descriptions` (R15). `TurnImages.pictures` names every picture of the message, sent or not.
- **Words to the model.** A model that cannot see is told `CANNOT_SEE_IMAGES_GUIDANCE` when the message attaches an image, and then the pictures by number so it can still hand them to `make_image` (`Pictures in this message: Picture 1: rug.jpg; Picture 2: Cosy living room (open in the panel).`). When the message holds more pictures than one `make_image` call takes (`getImageReferenceCap()`, only while `isImageMakingConfigured`), either model is also told `make_image takes at most N pictures per call: pass the ones the picture needs.`; four or fewer add nothing. One that can is told which pictures the limit left out and, one line each, `Picture <n>: <name> was attached, but it could not be shown to you.` for every image attachment not sent for any other reason (`TurnImages.notShown`: a BMP, a type the app does not know, a file that would not read or prepare); a model that cannot see gets the first and none of these, except that a message holding the marked copy of the person's boxes gets `MARKED_PICTURE_GUIDANCE` in the first one's place while picture making is on (a marked photo passes the send gate with no text, so "answer from that text" would leave it nothing). All of it rides the turn guidance (after the message, never the cached system prompt) and is English whatever the person writes.
- **The line while it looks.** A streamed turn that sends pictures says so while the model reads them, on the response-activity channel and nowhere else:
  - Server: `runStreamingNormalChatSendModel` emits one entry after the context is prepared and before the model call (`RESPONSE_ACTIVITY_IDS.VIEWING_IMAGES`, `kind: "viewing_images"`, `status: "running"`, `count` = the pictures sent, `prepared.turnPictureImages.length`). A turn with none (a model that cannot see has none) emits nothing. The entry carries the count and nothing else: no name, no description.
  - Browser: `isResponseActivityKind` (`services/streaming.ts`) must list the kind or the parser drops it. `MessageBubble.svelte` shows `chat.responseActivity.viewingImage` / `viewingImages` ("Looking at the image…", "Looking at 2 images…": two keys, since `$t` has no `#` and no braces in a plural branch) in its status line, below the text, only while the reply streams and before any word or thought arrives, so nothing is inserted above prose (F16). It is looked for before the other labels: the server sends `context-ready` and `drafting-answer` right after it, and by order alone "drafting" would hide it at once.
  - Not covered: a failover attempt on a model that cannot see strips the pictures after the line was said (it is gone with the first word anyway); thumbnails from the `photos` tool have their own row ("Looked at 6 photos").
- **Failover.** Every attempt on a model that cannot see gets no image parts, the first one included: the primary may be ticked and the fallback it fails over to not (or a cloud model nobody ticked). The plain loop and the streaming failover in `normal-chat-model/index.ts` build each attempt's messages with the one guard (`messagesForAttempt`), and `stripImageParts` (`turn-images.ts`) puts `STRIPPED_IMAGE_NOTE`, an English text part, in the place of each image part and changes nothing else. A fallback that can see keeps the pictures. Thumbnails from the `photos` tool are decided again for every attempt in the same way (`buildVisionPrepareStep`, below), and an entry that only the person's own box may see is never sent to a cloud attempt, ticked or not.
- **A picture needs no text for a model that can see.** What counts as a picture is `isSeeableImage` (`shared/file-types/seeable-image.ts`, shared because the composer asks it too): an explicit list of registry ids `prepareImageForModel` decodes (jpg, png, gif, webp, tif, heic, heif, svg), never "every image". A BMP (no decoder), an AVIF (refused at upload) and an `image/*` type the registry does not know are not on it, and `prepare-image.test.ts` pins the list against real bytes. For a turn whose model can see, such a picture never blocks the send, whatever became of the reading of its text (no text found, thin text, a failed read, one not finished): preflight asks `modelIdCanSeeImages` once, when something is attached, and passes `exemptImages` to `assertPromptReadyAttachments`, and the context build's own refusal (`buildConstructedContext`, when `collectImages`) asks the same `blockingAttachmentItems` (`knowledge/store/attachments.ts`), the one definition, so a send that passed the first cannot fail the second. Nothing waits for such a picture, and Atlas keeps its text-only gate. Everything else, and every attachment under a model that cannot see, is judged exactly as before. The composer mirrors the rule from the selected model's `supportsImages` (`isPictureForModel`, `composer-chip-presentation.ts`; not while an Atlas report is selected): a photo the reader found no text in reads "No text in this image" and Send stays open, and the Library row reads "No text" (`documents-table.ts`, `isImageWithNoText`).
- **Afterwards, a description.** Whatever a seeing model was shown in a turn is described once, by that model, in the background; later turns carry the words, never the pixels.
  - `describe.ts`: `scheduleImageDescriptions` is called by `prepareOutboundContext` with the turn's `currentImages` (so only pictures actually sent, and nothing for a model that cannot see). It returns at once and never fails or waits on the turn: one call at a time per person, a picture that already has a row or is already queued is skipped, a failure is logged (`[ATTACHMENTS] Image not described`, the artifact and the reason, never the picture) and stores nothing. A restart in the middle of a call leaves that picture with its file name for good; nothing backfills.
  - `describeImage` is one user message (`IMAGE_DESCRIPTION_PROMPT` and the prepared picture), 160 tokens, 60 s. The prompt asks for English and for visible text quoted as written, so a Hungarian sign is described in English around its own words. It takes the family's sampling through `resolveModelCallSampling` (Flash-Next's own default is temperature 1.0) and turns thinking off through `buildNormalChatModelRunProviderOptions(provider, "off")`, as the control model does: a thinking model can spend the cap on reasoning and say nothing. The answer goes through `normalizeAssistantOutput` (a think block goes, as in a title), is folded onto one line, and an empty one throws. Do not import `chat-turn/short-local-text.ts` here: it loads `shared-normal-chat-model-run-helpers.ts`, which imports `describe.ts`, and that is a fifth circular dependency.
  - `descriptions-store.ts` keeps it in `image_descriptions`, keyed by the artifact and written once (uploads are deduplicated per person, so the same photo in a later chat reuses it, and the description is of the image alone, never of a chat). It leaves with its artifact and its person (`account-lifecycle/user-scoped-tables.ts`, no reset scope).
  - History: `context-selection.ts` looks up the descriptions of the history's `isSeeableImage` attachments, and `conversation-history.ts` writes `[image: <name>: <description>]`, or `[attachment: <name>]` for a picture with none yet and for every other file. This is native history only. With the admin override `NATIVE_HISTORY_ENABLED=false` ("Send history as messages", the rollback) history is one flattened text block, and its serializer (`serializePromptMessageContent` in `context-selection.ts`) writes the message text and no attachment at all: no description and no `[attachment: <name>]` line reaches the model. That serializer is left as it is.
- **Immich thumbnails, when a question needs them.** The `photos` tool takes `look: true` (its schema text is the only place the model is told; the tool catalogue has no room for more). The SDK turns a tool result into text, so the pixels cannot ride in it; the result says that N thumbnails follow, and the pictures take another way:
  - `photo-look.ts`: `decidePhotoLook` is the privacy decision, from the person's setting (`connectionLocalDistill`), whether the chat model is a cloud model (`locality.ts`) and whether it can see. A cloud model for a person who keeps summarising local never gets a thumbnail, whatever it can see: `describe_locally` when the summarising model (`getConfig().memoryConsolidationModel`) is not a cloud model and can see, else `withhold`. Anyone else gets `pixels` when the model answering can see, else `withhold`. A setting or model that cannot be read withholds. `queuePhotoThumbnails` first reads whether the person keeps summarising local (an unreadable setting throws before anything is taken), then reserves its share of the turn's 8 (`queue.reserve`: no more than its results or `MAX_LOOK_THUMBNAILS`, whatever is left; none left means nothing is downloaded and `granted` is 0), prepares those thumbnails (`prepareImageForModel`, 512 px, two at a time; one that will not download or prepare is skipped and its share goes back with `queue.release`, and so does all of it for a call that was given up) and pushes one entry. `describePhotoThumbnails` has the local model describe them and returns text, and spends none of the 8. Both go through `eachThumbnail`, so the cap, the order, the concurrency and the deadline are in one place.
  - A look has a deadline, so a slow Immich or a slow local model costs the look and never the search: `PIXELS_LOOK_DEADLINE_MS` (8 s) and `DESCRIBE_LOOK_DEADLINE_MS` (12 s), both under the tool's 20 s timeout (`TOOL_TIMEOUTS_MS.photos`). When it passes, what finished is used and the rest is dropped (the describing call is told to stop through the signal), a thumbnail that arrives late is never queued, and the log line (`[PHOTOS] Look stopped at its deadline`) carries counts only.
  - `photos.ts` (`finishPhotosRead`) does the look before the Option A gate, so what a local model saw (`lookDescription`) is raw text for the connector summary and is stripped from what a cloud model is sent, like the file name and the place. `viewedCount` (tool-call metadata) counts the thumbnails queued, never the results asked for: it is what the activity row reads (`Looked at 6 photos`). A look that breaks is the same as one that could not be made. A look that finds the turn's 8 spent says so in the result (`BUDGET_SPENT`) and the search still comes back; one that was given only some says how many were left.
  - `step-images.ts`: `createToolPack` makes the turn's `StepImageQueue` (it also holds the turn's thumbnail budget: `reserve`, `release`, `room`; a drained entry does not give its share back) and returns it with the tools; both model runs pass it to `normal-chat-model/index.ts`, which builds `buildVisionPrepareStep` for each attempt from that attempt's provider (`providerCanSee`, and `providerIsLocal` from `providerRunsLocally` in `provider-vision.ts`, the same private-address rule as `isCloudModel`) and composes it with the first-step tool choice. The next step gets one user message per queued entry after everything else it sends: the label (`Thumbnails from the photos tool, in result order: 1 = <file name or id>, 3 = ...`, numbered by the photo's place in the results, so a thumbnail that was skipped leaves a gap) and the pictures, or, for an attempt on a model that cannot see, the label and `STRIPPED_IMAGE_NOTE`. An entry rides in that one step; the model's own words carry what it saw into the ones after.
  - An entry cleared for the person's own box only (`localOnly`, set when Option A is on) is decided per attempt, not per turn: an attempt whose provider does not run on a private address (a cloud model, or an address that cannot be read) gets the nameless label (`labelWithoutNames`, positions only) and `STRIPPED_IMAGE_NOTE`, never the pictures or the file names, whether or not that model is ticked "Can see images". The failover from a local primary to a cloud model is the case this closes; an entry without `localOnly` (Option A off) keeps the plain rule above.
  - Result looks (`images/result-look.ts`): `make_image` queues the picture it just made on this same queue, so a photos look and a picture look in one turn share the eight. The entry is labelled `Result of make_image (takeId <id>), changed from picture <n>:` (or without the change clause for a new picture); when the base was not among the message's pictures it goes first under `Before:` (two of the eight). Its `artifactId` is `image-file:<fileId>`; it never rides `currentImages` and no `image_descriptions` row is made. With no room left, or for a picture that lands after the call's wait, there is no look.
  - A thumbnail is not an artifact: it never rides `currentImages`, `scheduleImageDescriptions` never sees it, nothing is stored (no `image_descriptions` row), and the queue dies with the turn. What stays per turn is the tool RESULT's text (file name, place, description), gated for the model the turn started on like every connector's, because `createToolPack` fixes `modelId`: a failover attempt's own `photos` call is not gated again for the model it fails over to.
- **Profile memory** receives descriptions, never pixels.
