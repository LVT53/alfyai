# Read Aloud In The Browser

The browser side of read aloud (spec `docs/superpowers/specs/2026-11-16-read-aloud-design.md`, §4.1–§4.5, §4.8, §4.9): the speech script built from the rendered reply, the marks drawn over it, the reading machine and the controller that carries out its commands, and the language detector. The server side, which checks every request and is the speech service's only reader, is `src/lib/server/services/read-aloud/`.

- **The script is built from the rendered DOM only, never from Markdown** (spec §4.4: no syntax reaches the voice). `speech-script.ts` walks the reply's `.markdown-container` text nodes (or a Document's page), so what is read is what is on screen, and every word keeps a `Range` over its own characters for the marks. Only what is drawn is read: an element that is `hidden` or `display: none` on itself is left out (a Document's tab hides its other sections so), and so is whatever a target's `skip` selector names.
- **What is read is a target: a reply, a Document or a standard report** (spec §4.12, §4.13). The controller reads a `ReadingTarget`; the machine and the view name it by its key (`readingKey`: a reply's message id, a Document's `document:<artifact id>`). A Document's body (`DocumentBody.svelte`) hands the panel a `DocumentReadingSource`, and the controller touches a Document only through it: `root` (where its text is drawn, null while it is not), `skip` (what the page draws that is not text: chips, Alfy's pill and tag), `version` (the version shown, which the session route checks the words against), `revision` (moves only when the shown text or tab does), `settle` (saves what the reader typed, before every session, so the version holds every word read) and `focus` (scrolls the panel's text column; a Document's ⌖ and drag never scroll the thread). A Document's reading stops when its revision moves or its root is gone: an editor changes its text nodes in place, so the anchors that tell a redrawn reply would miss an edit. Held by `controller.test.ts` ("reading a Document").
- **A standard report is read through a bridge, never by reaching into its frame** (spec §4.13, the orchestrator's rules for its security review). The panel frames the report by its own preview address (`DocumentPreviewRenderer.svelte`), so it runs under the policy its response carries, never the page's; the frame stays opaque: scripts and popups, never `allow-same-origin` (`html-sandbox.test.ts`), no policy changed, and a load the panel did not ask for takes it down (`frameLoadTripwire`). Its frame and the page talk by `postMessage` and only of places, a block and a character offset in one walk both sides run from the same source (`$lib/shared/read-aloud/report-units.ts`: markup only, never computed style; the report's chrome is never a unit), so:
  - what is read is the page's own inert copy of what the report's address answered (`makeReportCopy`, `DOMParser`: nothing runs or loads), never a word from the frame; the controller reads it through a `ReportReadingSource` (`ReportReadAloud.svelte` hands it to the panel);
  - the frame's half (`$lib/shared/read-aloud/report-bridge.ts`) is one inline script of the app's own, which the server adds to a standard report's preview response (`generated-file-serving.ts`, `withReportBridge`: never a download, never another file), so a report made before read aloud gets it too. It takes only its parent's messages, of four exact shapes, at most 400 spans, every span inside the report, and posts only to the app's origin, written into it from the request; it draws the marks as CSS highlights in the Document marks' tints written out for light and dark, and scrolls the report's own scroller;
  - the page's half (`report-bridge-host.ts`) takes a message only when `event.source` is the report's frame window and its origin is the opaque `"null"`, of three exact shapes, at most nine keys, every number finite and every position inside its copy; it posts with `"*"`, so nothing but places is ever sent;
  - nothing the frame says starts, resumes or moves a reading: a selection only shows the page's own Read from here, and a mouse press on it counts only once the pointer has come to it.
  `reportBridge`, `reportBlocks`, `positionInBlocks` and `pointInBlocks` are self-contained (their source is written into the report with `Function.prototype.toString`, on the server): they use only their arguments and the frame's globals, never an import or a module's constant. Held by `report-units.test.ts`, `report-bridge.test.ts`, `report-bridge-host.test.ts`, `controller.test.ts` ("reading a report"), `ReportReadAloud.test.ts`, `generated-file-serving.test.ts` and `tests/e2e/read-aloud-report.spec.ts` (the production build, under the enforced CSP too).
- **An editor's DOM is never changed.** A Document's marks are drawn in a frame around its editor, never in it, and code inside an editor (`[contenteditable]`) is painted by a highlight, never given an attribute (`code-marks.ts`): ProseMirror reads any change to its own DOM as an edit.
- **A long Document notches its headings** (spec §4.12). Past `HEADING_NOTCHES_PAST` (40) sentences a Document's scrubber draws a notch only at each sentence that begins a heading (`headingNotches`, the view's `headingNotches`): at 40 sentences a phone's 240 px scrubber has its 2 px notches 6 px apart, about the least that still reads as separate marks. Every sentence is still a place to land. A sentence says whether it begins a heading (`heading`), and a short sentence never joins forward into a heading (`mergeShort`), so a heading always begins its section's first unit and Read from here on one starts that section. A reply keeps a notch per sentence.
- **The player's two rows follow its own width** (`ReadAloudPlayerPill.svelte`): a floating pill under 560 px takes the phone's two rows on any screen, since beside a docked panel the chat's column is 340 to 620 px wide. The smaller buttons stay a phone's under 360 px (a phone's pill is narrower than its screen, and every column of a wide screen holds the 44 px row). The layout is the pill's `data-narrow` and `data-tight`, so the CSS and the Tab order follow one decision.
- **Dashes and brackets are pauses.** Zonos pauses only at the marks it is given, so the script drops no clause mark and gives the voice the ones the page only draws: a dash between words (an em or en dash, `--`, a spaced hyphen between words) becomes a comma after the word before it, an em dash inside a run of words (`eggs—one`) splits it with a comma, and a parenthetical's brackets are not said (the word before the opening bracket takes a comma, and so does the word that closes it, unless a mark ends it already or nothing follows). Only punctuation is touched, never a letter, so the containment check (which compares letters) is unaffected. Held by `speech-script.test.ts` and `spoken-forms.test.ts`.
- **Short sentences join a neighbour** (`short-sentences.ts`, the owner's call of 2026-11-17). Zonos stalls on a short text and goes on speaking past it (the numbers are in `deploy/speech-service/speech_service/steady.py`: three to sixteen characters are bad in 85 to 90% of the clips in the Hungarian voices, 40 to 49 in about one in fourteen, 50 and over in about one in a hundred), and the service's retries mend a sentence but rarely a fragment. So a unit under 50 written characters (its tokens, joined by spaces) is read as one unit with a neighbour, again while the unit is short, in three cases: a sentence takes the next sentence of its paragraph; a list item takes the next item of its list (a long one too: items of one list share a key the script makes from the `<ul>` or `<ol>`, so a nested list or the next list is another list); a paragraph of one sentence ("Sure!", "Thanks!", "You will need:") takes the first sentence of the next paragraph, whatever it is but a heading or a code line, and goes on while it is short. One still short with nothing after it to take (the last, or the next too long or not its to join) joins the one before, by the same rules. A paragraph of one sentence is the only one that crosses a paragraph; an item, or a short sentence of a longer paragraph, does not. Never across a heading, a code line or a language, and never into a unit over `LONG_SENTENCE_CHARS` (240), which `splitLong` would only cut again. The tint covers the joined unit and word marks stay per word. The join makes the pause between the parts: where the first ends in no pause mark (a list item rarely does) it gets a full stop, which Zonos pauses at and the service lengthens, unless a stop would take its token past 80 characters; the stop is on a copy, never on a draft it is given. What it costs is the longer gap before a paragraph or an item (`SPEECH_PARAGRAPH_GAP_SECONDS`): inside a unit the pause is the stop's. It is called from one line in `buildSpeechScript` (`joinShortSentences(mergeShort(drafts), LONG_SENTENCE_CHARS)`), after `mergeShort`, which still joins a sentence of fewer than three tokens across paragraphs; drafts carry `list` and `code` for it. Held by `short-sentences.test.ts` and `speech-script.test.ts`.
- **Every unit ends in a stop** (`closeSentences` in `speech-script.ts`, the walk's Final 1 of 2026-11-17). Zonos can end a clip before the last words of a text that ends in no mark: the last item of a joined list ("Egy csipet só") was never said, and the same text ending in a full stop is read in full (at the service's own seed, 1 of 20 Hungarian list tails dropped its last item with no stop, none of 20 with one; the stall guard cannot see it, the clip is not too long). So the last step of `buildSpeechScript`, after the joins and the split, gives a unit that ends in no mark a full stop, and replaces a comma, semicolon or colon that ends one (the first part of a split sentence, a line that introduces what follows) with one; `.`, `!`, `?` and `…`, with any closing quote or bracket after them, are left. It changes punctuation only: the token count (so every token's range) and every letter stay, and the session route's check (`wordsFitReply`, letters only) is held to that by `speech-script.reply.test.ts`. A stop that would take a token past 80 characters is left off. The stop counts towards the 240 characters: `splitLong` measures a unit as it is sent, and the join keeps one character of room. Held by `speech-script.test.ts` ("the closing stop").
- **Marks never change the reply's DOM or its layout.** They are an overlay behind the text (`ReadAloudMarks.svelte`, `z-index: -1`), and the prose is isolated (`isolation: isolate`) only while it is marked, so the marks can never paint over the composer layer (spec §4.2). Nothing wraps, splits or styles the reply's own text nodes.
- **The reply controller owns its `<audio>` element and the session routes; the voice preview (`voice-preview.ts`) owns the one element every ▶ in Settings and the editor plays through, and the preview route. Components never touch either element, and never fetch.** `controller.ts` owns the reply's element, the `EventSource`, the timers and the calls in `src/lib/client/api/read-aloud.ts`; components read `readAloudView` and call the controller. `voice-preview.ts` owns the preview's element, its renders (the last 12, as object addresses, revoked when evicted or disposed) and `renderVoicePreview`; components read `voicePreviewView` (`src/lib/stores/read-aloud.ts`) and call the preview. The voice and preference routes are called through `src/lib/client/api/read-aloud-voices.ts`, from the Settings card and the editor.
- **The events stream stays open after the service's `done`** (early review R7). `done` is synthesis finished, not playback, and the server tells a reading another tab or device replaced through that stream (`replaced`, which ends this reading quietly and skips the DELETE: the server closed it). The controller closes the stream with the session (✕, a jump, the end's "Finished"), which is also what lets the server close a reading whose audio was all read; the stream's end after `done` is never a break. Held by `controller.test.ts` ("done keeps the events open…", "a reading another tab replaces after done…", "an events stream that ends after done is not a break…") and `tests/e2e/read-aloud.spec.ts`.
- **A session carries at most 2,000 sentences** (`MAX_SENTENCES_PER_SESSION`, `$lib/shared/read-aloud/session-limits`: the speech service's limit, which the session route's schema holds too). A longer reply or Document is read in sessions of that size: when one ends with all its audio read and the reply goes on, the controller closes it (nothing to cancel) and the machine takes a `seek` to the next sentence, so the person sees one reading with a short wait at the join. Held by `controller.test.ts` ("a reply of more than 2,000 sentences…") and `request.test.ts`.
- **The iOS unlock happens synchronously in the press handler.** On the page's first press, before anything is awaited, the controller plays a silent clip on its audio element; iOS then allows that element's later plays. A press handler that awaits before calling `start` loses the unlock. The voice preview's `unlock()` is called the same way: synchronously in the click that opens the editor and in every ▶ handler, before the render is awaited.
- **The detector is the one exception to "no second reader"** (owner, 2026-11-16; written in `src/lib/server/services/chat-turn/AGENTS.md`, after I4). `language.ts` (tinyld, loaded lazily) names each paragraph's language only to pick a voice and the speech service's text rules, and to name a language that has no voice. No model request, title, chip, record or route reads it, and nothing in `chat-turn/` imports it. tinyld never enters the chat's first paint (`check:artifact-chunks --chat-forbid tinyld`).
- **Spoken forms come only from `src/lib/shared/read-aloud/spoken-forms.ts`**, the code the session route checks every token with (`wordsFitReply`). Nothing else makes up a spoken word: a token the dictionary does not make fails the containment check, and the reading never starts.
