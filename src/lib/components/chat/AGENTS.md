# Chat Components

## Mermaid

- `src/lib/components/chat/Mermaid.svelte` is the one place Mermaid is called, and a Mermaid source is untrusted (FX-E). A chat reply, a board's diagram block and the reader's own edit of one all draw through it, and what a model wrote in a reply may have come from a page it read. Measured against Mermaid 11.17, a source made the browser call an address before any gate ran (an `@{ img: … }` shape, which Mermaid decodes itself; an init directive or a front-matter `config:` that turns HTML labels on or carries `themeCSS`; a CSS `url()` in a class or state diagram's `classDef` or `style`, also spelt `\75rl(`; a sequence diagram's `properties A: {"icon": …}`) and showed a link in the picture (`click`, `link`, `links`). So the source goes through `shared/artifacts/mermaid-source.ts`'s `sanitizeMermaidSource` first, which removes those and keeps the rest of the diagram (it is one lazy chunk with Mermaid, not part of the chat route); Mermaid runs with `securityLevel: "strict"`, labels as SVG text and a `secure` list that keeps a directive from changing `htmlLabels`, `themeCSS` and the other keys that bring HTML, CSS or an address in; and the SVG goes through `sanitizeHtml({ svg: true })` (no `<a>`, an `href` only to `#id` or a `data:image/…`, CSS addresses scrubbed from every attribute and `<style>` with escapes undone). Do not call Mermaid from another component, do not keep a second list of what a diagram may not ask for (the board's door, `mermaidSourceProblem`, reads this one), and when a Mermaid upgrade or a new diagram feature takes an address, measure it first with a real request count (`tests/e2e/mermaid-hardening.spec.ts`) and extend the sanitizer and its tests together.

## What A Turn Made

- **What a turn made is drawn after what it said** (F16). A `create_artifact` / `edit_artifact` call reaches the browser only once the model has written the whole item, so its tool row and card always arrive late; in the rail above the text they pushed the words being read down by their own height (measured: 307 px on a Document with a checklist preview). `MessageBubble.svelte` takes those calls out of `thinkingSegmentsForDisplay` (`isArtifactToolCall`, `utils/tool-calls.ts`) and draws them in `message-deliverables` below the prose with the same `ToolActivityList` / `ToolActivityRow` / `ArtifactCard`; the rail keeps the steps. Do not put them back in the rail, and do not insert anything above the prose of a message that is streaming. `tests/e2e/artifact-card-arrival.spec.ts` holds it (the sentences' top edge does not move, frame by frame).

## Permission Cards

- A write to a connected account waits for the person, and the card is where they answer. `connections/write-card.ts` reads the stored row (the same operation and payload the executor runs on confirm, so the card cannot show one thing and do another) into `write.card`: what kind of action, the name of the thing, small lines for where and when, an email's text, and named risks. `write-card-view.ts` turns that into words in the reader's language. `write.preview`'s English sentences reach a person only for a write this version cannot read. The model is handed the preview and never the card, which is how text a tool redacted for a cloud model stays off it.
- These cards are for the person, not an admin or a model (owner, 2026-11-01). The name leads, large, with a location in a much smaller line under it: never a whole path, an internal action id, a server's host name, a reference number, or a word about what was checked. The question sits above the name and the button says what the action does ("Send", not "Save it"). Nothing shows that the person does not need in order to answer: only an email carries its text, because it is what leaves their account. There is one warning at most, the gravest, as one plain line with no box. Red is the confirm button and that line, and only for what the reader loses by it, not for what the write guard calls destructive: an edit Google can undo stays neutral.
- Asking and record are two shapes. `WriteConfirmCard.svelte` wears ArtifactCard's shell while it asks and folds into a `ToolActivityRow` once it is decided, so a settled write reads as what happened, with its details one press away (a failed or expired one opens by itself).
- `WriteConfirmSheet.svelte` is one sheet for the conversation, not one per card: a phone walks the pending writes oldest first. Do not raise a sheet from a card; three of them used to stack. It waits for the turn to end, backing out decides nothing, and each new question keeps its buttons off for a moment, so a double tap cannot answer the question behind it.
- A pending write gets its message id before the turn's terminal frame (`chat-turn/AGENTS.md`), and the page keeps only its latest read of them. A row with no message id is drawn on no message once the reply has stopped streaming.

## Chat Scroller

How a person moves around a long chat: `ConversationJumpRail.svelte` (ADR-0043, amended 2026-11-01). It has props `messages`, `scrollToMessage`, `activeTurnId`, `compact`, `showLatest`, `onLatest`; it reads no viewport store, and `jump-rail.ts` turns the messages into `{ id, label }` rows.

- Nothing below 6 assistant turns. A row's label is the turn's `railSummary`, else the question that was asked (trimmed, no quotes, about 60 characters), else the start of the reply.
- **Wide chat: the ruler.** At most 13 ticks, one per turn up to 13, with one orange mark placed by `round(active / (turns - 1) * (ticks - 1))`. The nav fills the free space above the composer (`bottom: var(--composer-layer-height)`) and is `pointer-events: none`; only the trigger and the list take the pointer, so the list never slides under the composer.
- **The list** opens after the pointer rests on the ruler for 120 ms and closes 180 ms after it leaves (crossing it on the way to the sidebar does nothing). A press or Enter on the trigger toggles it and pins it, which is how touch and the keyboard open it; a finger's or pen's hover never opens it. It opens with the current row centred (`aria-current="true"`). From the keyboard focus moves to the current row, Up, Down, Home and End move between rows, Esc closes it and gives focus back to the trigger, and a press outside closes it. The rows are `tabindex="-1"`: the whole scroller is one Tab stop however many turns there are. Rows are one `--text-sm` line in `--text-muted`, as `ToolActivityRow`'s rows are.
- **Narrow chat: the capsule.** `MessageArea` measures its own surface (`bind:clientWidth`) and passes `compact` below 800 px (the ruler and its margin no longer fit); width 0 means "not measured" and draws neither. The capsule ("11 / 30" and a chevron) shows only once `showLatest` is true, the number opens the list in a `DialogShell` (a sheet on a phone, a centred panel otherwise, above the composer) and the chevron calls `onLatest`. The round jump-to-latest button is not rendered where the capsule is. Do not measure with a CSS container query: layout containment moves `position: fixed` children.
- Reduced motion: no transition on the mark or the list (the duration tokens collapse; the capsule's fade goes through `reducedMotionAware`).
- A chat loads only its last 100 messages, so the list stops at 50 turns. That is a known limit with its own card.

## The Draft

- **A landed turn clears the conversation's saved draft only when the draft is the text that turn sent.** `persistAssistantTurnState` (`chat-turn/finalize-steps.ts`) compares the saved draft with the turn's message, both trimmed; a draft it cannot read or clear never fails the turn. The browser deletes the draft itself when the composer sends, at once and again when the saves on their way have been answered (`deleteDraft` in `createDraftPersistence`), so a late save of an earlier version cannot land behind the delete and stay. The first delete never waits: the landing page navigates straight after it, and the chat page's read must find the draft gone. A save the chat sends meanwhile holds words typed since, and stands. The server's clear is the backstop for a save that lands later all the same, from a second tab say, which a reload would bring back as the message already sent. Any other saved text stays, on screen and after a reload, as the words typed while the reply was coming (a second tab's late save of an earlier version looks the same, and stays too). No flag and no turn origin decides this, so a regenerate, a Retry and the resend of an edit keep a draft because it is not what they sent.
- **On the page, only a send of what the composer holds clears the draft.** `clearDraft` is off unless asked, in `handleSend` and in the runtime's `send`: the composer's own send (`handleComposerSend`) and the landing page's first message pass `true`, and a regenerate, a Retry, a follow-up chip, an Atlas action and the resend of an edit do not. A new way to start a turn clears nothing unless it sends the composer's text. `tests/e2e/chat-edit.spec.ts` holds both halves in a real browser: words typed during a reply, a sent message, a save of it landing late, and a first message sent from the landing page with a save on its way.
- **A restore joins the words the composer holds; it never replaces them.** A turn that stopped, failed or came back from the queue (Stop, the banner's Edit, an error, a Continue Atlas that failed) puts its words back through `restorePayloadToDraft`, and the person may have typed since. `joinRestoredPayload` (the route's `_helpers.ts`) makes the draft: the held words, a blank line, then the restored ones (`joinDraftText`, the join an edit that leaves the chat makes). What is held is `heldDraft`: what the composer last said (`handleDraftChange`) or was last told to show (the chat's saved draft on arrival, the draft a restore joined), let go when a send or a queue empties it. It is not `conversationDraft`: a load of the chat sets that to null, and a read can set a copy older than typing that is not saved yet. Two other places mean the same and read it too: the left-the-chat path of an edit (`draftSetAside` in `handleEdit`, joined to the edit and saved for the chat that was left), and a read that applies a draft (`hydrateConversationDetail`), which sets `heldDraft` as well while it holds no words of its own, since the composer takes a draft only then, so that a later restore joins a draft another device saved instead of replacing it. An empty composer gets the restored words alone, and two texts that are the same once trimmed are not joined. Files, linked sources and card pictures from both stay, each once, and the restored pictures are numbered after the held ones. Held marks stay; the restored turn's come in only when none are held, and then its boxes are lost and the picture its send added for them comes back as a plain picture. While the held draft has words, its skill and Atlas mode stay; with none, the restored turn's come back. A payload whose `conversationId` is another chat's is dropped, as the runtime drops every write of an abandoned turn (`isTurnConversationActive`). The composer takes the joined draft though it is not empty through `draftTakeoverVersion`, which names that one `draftVersion` (the restore's `updatedAt` is always newer than the draft it joins): the next update, the composer's own included, is ordinary again and never overwrites typing. It waits for an open edit like every draft update, leaves an upload in flight alone, and cancels a send queued behind a file, which would send words the person has not seen.
- **A composer's words stay with the chat they were typed in.** The chat page and its composer are reused when the person moves to another chat. On that switch (`prevConversationId` was set) the page `flush`es the draft persistence, so a save still waiting out its 400 ms goes out for the chat it names before `resetState` drops whatever else waits, and then raises `resetRequest`. The composer empties on it (words, files, linked sources, skill, Atlas mode; a file still uploading and a send waiting at its gate lose their answers, `chatEpoch`) and takes the new chat's saved draft as a new composer does, a draft with a file and no words included. The page asks and the composer does not key on its `conversationId`: the landing page's gets one when its prepared conversation is made, while the person is typing, and that must clear nothing (`HomeSurface` never passes `resetRequest`). A host that passes `resetRequest` also owns emptying the composer when the store that names the open chat changes, because that store can name the chat after the draft is in (a reload, Back) and used to wipe a draft with a file and no words; the landing page, which does not pass it, keeps the old reaction. A message queued behind a running reply goes with the chat too: just before the flush the page takes it from the runtime (`takeQueuedTurn`), joins it into the draft held for that chat and saves that (`saveQueuedTurnInDraftOf`; `restorePayloadToDraft` cannot, it reads the chat now shown), and does the same when the page is destroyed for Home or Settings. Nothing is sent, and its card pictures and marks are not kept, as the composer's own pictures are not. Words typed during a running turn are saved as that chat's draft like any others, and an open edit saves the draft set aside, never the edit (Editing A Message). Forking flushes too. Nothing that leaves a chat may call `draftPersistence.clear()` before it flushes: `clear()` drops the waiting save.
- **Words that exist nowhere else are saved until the save lands.** The save of words taken from a waiting message or from the queue (`saveQueuedTurnInDraftOf`) and of words a turn gives back (`restorePayloadToDraft`) goes through `draftPersistence.persistUntilSaved`: during a restart the proxy answers a save with its own page, and a failure that was swallowed left the words nowhere. A save that fails and may land when sent again (the request did not reach the app, or a 5xx, 408 or 429; an answer that refuses it, any other 4xx, never will) is sent again every 3 seconds, by the persistence and not by the page, so it goes on after the person went Home. One keeper per chat (`DraftKeeper` in `conversation-session.ts`, module-level because the page is rebuilt when the person returns while the save its earlier page left is still trying) holds the newest save that has not landed. It ends when the words land, when an answer refuses them, when that chat's draft is deleted (a delete wins, and an emptied draft is a delete), or 8 minutes after the chat's words were first held (the longest an update takes; counted from the first save, not from each, so a person who keeps typing through a long outage does not keep the server asked, or the Refresh notice back, for ever). Every later save of that chat (typed since, flushed on leaving, put back by another turn, from any persistence of the tab) takes the keeper over and is held the same way: the older words are never sent again, and a newer save is sent only once the try that is out has been answered, so older words never land on top of newer ones. A page that opens a chat with words still held shows those (`pendingDraftSave`, `arrivalDraftOf` in `_helpers.ts`: the saved draft is older, or none), and its own saves take them over. The shell holds its Refresh notice while any chat's words are held (`stores/server-update.ts` `pendingDraftSaves`), and signing out ends every hold (`clearConversationSessionState`). `conversation-session.test.ts` ("a save that must not be lost to a failed request") and `page-runtime.test.ts` ("when the save of those words fails because the server is restarting") hold it.
- **A read of the chat says nothing about the draft if the draft changed while it was out.** `hydrateConversationDetail` (the 2.5 s poll while a file, picture or Atlas job runs) carries the draft as the server had it when the read was asked, so a read that was out across a Send would put the sent words back in the emptied box. Every write the page makes to `conversationDraft` goes through `setConversationDraft`, which counts it (`draftEpoch`: a send's clear, a keystroke, a restore, a chat switch), and a read applies `payload.draft` only if the count has not moved since the read began. `tests/e2e/chat-edit.spec.ts` holds these three rules in a real browser too.

## Retry

- **When the list ends in a user message, Retry sends that message again and touches nothing above it.** The server keeps nothing of a turn that fails (it saves the message with the reply, at the end), so after a failure the list ends in a message the server does not have. `retry()` in `client/normal-chat-client-turn-runtime.ts` used to take the last assistant message of the list as its target, remove it and ask the server to regenerate it: in any chat with an earlier reply that was another turn's, which left the screen, and the server answered 409; with none, the message went as plain text without its attachment ids, `pictureRefs` or `imageMarks`. The runtime now remembers the last send (`lastSend`: its payload and its options) and replays it with a new placeholder: the files, the pictures and their marks, the model, depth and personality go again, an edit's resend stays one (`isEditResend`), and a failed regenerate stays a request for the reply it was regenerating, with `retryOrigin: "error_retry"`, since Retry is a verdict on the failure and not on the answer. No second bubble is added: the one on screen is `clientUserMessageId`, so it takes the server's id when the turn lands (the pencil and later edits need it). A turn that failed after a reload (`showFailedReconnectedTurn`) holds no payload and sends its text only; on the page that sent it, after a dropped connection, the remembered send is that very message and is kept, and it is forgotten only when its message differs from the text put back. Only a list that really ends in an assistant message still has that message regenerated.
- A Retry clears no draft and none of the files waiting in the composer: they belong to whatever the person has started since (The Draft, above). `reset()` (every chat switch) forgets the remembered send, and a send of another chat is never replayed into this one. `normal-chat-client-turn-runtime.test.ts` ("Retry when the list ends in the message that failed"), `page-runtime.test.ts` ("Retry after a message that failed") and `tests/e2e/chat-edit.spec.ts` hold it.
- **Retry asks the server before it sends a message again.** A dropped connection does not end a turn: the server keeps running it, saves the message with its reply when it ends, and the page shows an error and a Retry meanwhile, so a plain resend saved the turn twice. `retry()` asks two things, the stream first. Whether the server is still running the turn (`findRunningStream`, which is `checkForOrphanedStream`, the code a reload and a tab back from the background use): the message is not saved until the turn ends, so the chat cannot say, and a resend would be turned away for the person's one reply at a time, tried again by the capacity backoff, and run the turn twice if it ended meanwhile. A running stream is joined (`joinRunningStream`, under the bubble on screen), the chat is not read and nothing is sent. Only the stream of this message is joined: the stream says whose message it runs (`bufferInfo.userMessage`, compared trimmed), and another device's message in the same chat is refused for the person's one reply at a time while its stream runs, so joining it would clear the error with this message unsent and a reload would lose it. A stream for another message is no stream here, and Retry goes on to the chat and the resend, whose capacity backoff handles the rest; a stream that says nothing of its message is taken for this one. And, when no stream is running, whether the chat holds the turn: one helper (`askWhatTheServerHolds`, judged by `judgeServerMessages`) reads the chat through the `readChatMessages` adapter (the page wraps `fetchConversationDetail` in `withinOrNull`, 5 seconds) and compares it with the page's own list by id; the give-up of the network-drop recovery and `showFailedReconnectedTurn` ask it too. The turn *landed* when the server's list ends in an assistant message the page does not hold, right after a user message with this text (trimmed): the page loads the chat and sends nothing, shows no error and offers no Retry. The reply a regenerate was replacing (`lastSend.options.retryAssistantMessageId`) is never that reply: the page took it off its list, so a regenerate that never reached the server would read as landed and bring the old reply back; Retry replays the regenerate instead. A list that ends in a user message with this text and no reply is a message the server holds without one: it goes through `/api/chat/retry` as a retry whose reply is gone, `retryUserMessageId` its id and `retryAssistantMessageId` the new placeholder's, never as a second copy; a remembered regenerate keeps its own ids. The order is what makes the two questions enough: the server saves a turn's message before it unregisters its stream, so a turn that ends between them is found by the second, where asked the other way round it got two noes and was sent again. A question that fails or runs out says nothing, and Retry goes on as it always did: the chat read is bounded by the page (5 seconds), the stream questions by the runtime on its own clock (`answerWithin` on `adapters.schedule`, `STREAM_QUESTION_MAX_MS`, 5 seconds), where no answer is no stream. The press comes down either way, since a flag left up would make every later press do nothing until the browser gave up on a stalled connection.
- **`retry()` is async and holds its place.** A second press while it asks is the same press, and the state is looked at again after the questions: nothing is sent, joined or loaded if a turn has started, the chat has changed or an edit has been opened meanwhile (`isEditOpen`; the failed bubble takes the server's id when its turn lands, so an edit of it would find no message and close with what was typed). Reading the chat back for a landed turn goes through `loadChatHoldingTheTurn`: `loadPersistedData` replaces the page's list and its last step (`completePollingRecovery`) ends the turn state, so a message sent meanwhile would lose its bubble and its `isSending`. The turn state is held through the read (`beginTurn`, the way polling recovery holds it), the composer queues what is sent, and the queue is drained after. The load answers for the chat it was asked about: `loadPersistedData` in the page takes the chat's id before the read and writes nothing if the page has moved to another chat meanwhile, which would show one chat's messages in the next. It still ends the recovery state, unless a turn of the chat the person is in now has started and owns it.
- **A retry whose reply is already gone runs on the user message that ends the chat** (`findRetryTarget` in `chat-turn/retry.ts`). A retry deletes the reply it replaces before the model runs, and the server keeps nothing of a turn that fails, so after a model failure Retry asks again for a reply that is not there; it used to be answered 404 "Assistant message not found" for ever. When `assistantMessageId` is not in the conversation, `userMessageId` is the conversation's last message (a user message) and its text is `userMessage`, the retry just runs on it: nothing is deleted or cleaned up, there is no fork to ask about and no recorded intent to read (the user chose nothing), and the turn stays `skipPersistUserMessage`, so the one copy of the user message remains. A missing reply with anything after the user message, or with another message last, is still 404, and another text 409. The reply that is gone took its record with it, so the browser says what the person chose (`options.retryUserIntent`: a skill, `/web`) in the retry body as `userIntent`; the server reads it, through `parseMessageUserIntent` and `resolveRetryPendingSkill`, only when the reply is gone, and the intent recorded on a reply that is there always wins. `tests/e2e/chat-edit.spec.ts` ("Retry after a regenerate that failed") holds it.

## Editing A Message

A sent message is edited in the real composer, never in a box inside the bubble (owner, 2026-11-01; the box grew wide, left the bubble's edge and was cut off on a phone).

- **The page owns the state, the pieces only emit.** `+page.svelte` holds `editingMessage: { id, text } | null`. The pencil in `MessageBubble` calls `onStartEdit({ messageId })` (the bubble keeps no edit state) and `MessageInput` emits `onEditSubmit(text)` / `onEditCancel()`. The page starts an edit only on a user message, and not on a sealed chat or while a turn is running or an earlier edit is going out; it clears the state when the conversation changes.
- **`handleEdit` is the submit path, and it holds on to the edit until the server has deleted the messages.** A refused gate (the privacy check, the fork confirmation, the turn's own gate below), a failed delete or a declined server-side fork question all leave the edit open with what was typed, on messages that never left the screen: they go from the list only once the delete has succeeded, and only then does `editingMessage` clear. The composer stays live during `prepareTurn` and during the check below, which can take seconds, so `handleEdit` looks again after each, comparing the `editingMessage` object: after a Cancel or Esc in that wait nothing goes, even if the same pencil was pressed again, and a second press of send is dropped. From the moment the delete is out, Cancel is off (`disabled && isGenerating`: a sealed chat must not trap an edit). If the person leaves the chat during the delete, no turn starts (it would land in the chat they moved to) and the text joins the set-aside draft (what the composer held, `heldDraft`) as that chat's draft. After the delete the rows leave and the new turn arrives in two updates (`await tick()`): seen as one the list has not grown, and `MessageArea` would not take the reader to the new turn. `isEditResendPending` stays up through that gap: with the edit gone and no turn running, a send queued behind a file would otherwise go out in the resend's place.
- **An edit meets the turn's gate before its delete.** The resend meets that gate (`prepareChatTurn` in `chat-turn/preflight.ts`: the pictures the request names, then the attachments for the turn's model) only after its message is gone, and a refusal there, a photo the chosen model cannot see (`not_text_readable`) or a file deleted since (`not_available`), left a reload with the message and every reply after it deleted. So right after the fork confirmation and before the delete `handleEdit` asks `POST /api/chat/turn-check` (`checkChatTurn` in `client/api/chat-turn.ts`; `checkChatTurn` in `chat-turn/preflight.ts` behind the thin route) about the resend as it will go out: the turn's own model, the message's attachment ids, the open item and the pictures from `editResendPictures`, with `isEditResend`. The server runs the turn's own read-only checks (`checkTurnInputs`, the code the turn runs too, so there is one path) and nothing else: linked sources, the pending skill and the depth are left out, because they write or spend a model call and an edit's resend carries none. A refusal sets `sendError` through `toFriendlySendError`, the sentence a refused send shows (the route answers in the stream route's shape, which the client reads as an `ApiError`); a check that fails or has not answered in 10 seconds (`EDIT_CHECK_MAX_MS`, `withinOrNull`) says `chat.editCheckFailed`. Either way nothing was deleted, nothing left the screen and the edit stays open with what was typed. After the verdict `handleEdit` reads `$messages` again and takes the ids to delete from that list, from the edited message on: the check can wait up to 10 seconds with the page live, and a recovered stream or a turn that finished in the background (read back when the tab returns) can land under the open edit; a message that has left the list closes the edit, as before. The resend's own gate and `withEditResendPictures` stay: they cover what changes between the check and the resend. The stream route's capacity question (this person's reply running in another chat, one at a time by default, or the server draining) is asked the same way, through one piece, `refuseTurnWhenOverCapacity` in `chat-turn/stream.ts`, which the stream route and the check both answer with: the same 503 `CAPACITY_EXCEEDED`. The client reads it as `busy`, and the page says `chat.editReplyRunning` ("Another reply is still running. Wait for it, then send this edit again."), since `toFriendlySendError` has no sentence for that code and would blame the model provider. A turn can also start under the open edit while the check is out (the page finds the turn the server was still running after a dropped connection and reconnects), so `handleEdit` looks at `isSending` after the verdict and leaves the edit open with the same sentence; and after the delete, which is an await too, if `handleSend` would refuse (a turn running, the chat sealed) the words go through `restorePayloadToDraft`, joined behind what the composer holds, instead of going with the message. A new way to refuse a turn belongs in `checkTurnInputs` (read-only) or after it in `prepareChatTurn`, never in the page.
- **Nothing a person presses starts a turn while an edit is open.** The edit would delete what that turn makes. `MessageArea` draws the messages `readOnly` meanwhile (no pencil, regenerate, fork, follow-up chips or Atlas actions; a second pencil would also drop what was typed), the page hides Retry, and `handleSend`, `handleRegenerate`, `handleRetry` and `handleAtlasLifecycleAction` refuse. The runtime's `retry()` looks again after the questions it asks the server, which can take seconds (Retry). A recovered stream can still land under an open edit, which is why the count is live.
- `laterReplies` is `countLaterReplies` in the page's `_helpers.ts`, taken from the list as it stands (`composerEditing`), so the red line stays true if the list changes under an open edit: the assistant messages after the edited one, minus its own reply, the row right after it. A message whose turn failed has none, so every reply after it counts. An edit deletes everything from that message on, so they really go.
- **The draft set aside survives the edit.** The resend passes `clearDraft = false` and sends the edited words, which are not the draft's, so nothing clears it (The Draft, above).
- **The resend keeps the message's attachments and its pictures.** Its card pictures go again, and its marks while their picture goes along, read from the message's record the way a regenerate reads it (`editResendPictures` in the page's `_helpers.ts`, on `recordedPictureRequest` and `marksRideWith` in `shared/artifacts/image-body.ts`, the same two `chat-turn/retry.ts` and `images/turn-pictures.ts` use). A message sent in this tab holds only the composer's copy of that record, with no boxes, and the landing page's first message and a reconnected one hold no copy at all, so every `handleEdit` reads the server's record beside the gate; the page's copy goes when that read fails or takes more than two seconds. The picture open in the panel is whatever is open when the resend goes, as in every send. A card picture deleted since is dropped quietly, as a regenerate drops it (`withEditResendPictures` in `chat-turn/preflight.ts`, which the check above runs too and the resend runs again): a picture is not what an edit is refused for, and the message is gone before the server sees the resend. The rest keep their numbers, except that the server lets no number pass their count (`images/turn-pictures.ts`): with 2 of 1, 2, 3 deleted, picture 3 reaches the model as 2 while the bubble says 3 until a reload.
- **`MessageInput` with `editing` set.** The draft is put aside and the message's text shows (focus, caret at the end); when `editing` goes away, however it ends, the draft comes back and is emitted again. A composer with nothing in it emits nothing, since an empty emission is how a draft is deleted, and that draft may be one it never showed. The other exception is a chat that changed under the edit: what was set aside stays with the chat it came from, as its saved copy, and nothing is emitted; anything that reached the composer only during the edit, a file that finished uploading say, goes with it. `emitDraftChange` stays quiet in between, so an edit is never saved as the chat's draft. The effect is keyed on the text, not on the `editing` object, which is new whenever the count changes. A draft update waits for the edit to end, and so does a send queued behind a file, since `message` is the edit until then. A send still at its gate when the pencil is pressed is held back: it stays in the set-aside draft and needs another press. There is no command tray. Send and Cmd/Ctrl+Enter (Enter alone is a new line, as always) call `onEditSubmit` with the trimmed text; an empty text turns send off, an unchanged one is the same as cancelling, Esc cancels. The chip row hides (the over-length counter excepted) and the attach, connections and tools faces are off, as are pasting and dropping files: the resend keeps the message's own attachments and pictures, and anything added here would be lost. Pending composer attachments, pictures and marks stay as they were and come back with the draft.
- **The strip** is the first line inside the composer box: no box, no dashed line, a muted `Pencil`, the label (`messageBubble.editMessage`, bold) and a quiet Cancel. With later replies the label becomes one plain `--danger` line (`chat.editLaterReplies`, Hungarian included) and the send button takes the destructive tint. It must stay one line at 360 px in both languages (`tests/e2e/chat-edit.spec.ts` measures it).
- The edited bubble fades to 0.45 and loses its action row while the composer holds it. The fade is on the message body, not the row around it: the row's fade-in animation holds `opacity: 1` once it has run.

## An Update During A Turn

A deploy drains the server (a new message is refused with `reason: "draining"`, still under the code `CAPACITY_EXCEEDED`), waits up to `DRAIN_TIMEOUT_SECONDS` (3 minutes) for the replies that run, then restarts it (the proxy answers its own 503 page). It used to look like a failure of the model provider. ADR-0054 (amendment 2026-11-03) holds the contract.

- **A request refused for an update waits and is sent again, never counted down.** The transport marks the error (`services/streaming.ts`: `status`, `reason`, and `serverUnavailable` for a 502, 503 or 504 whose body is not the app's JSON); `isServerUpdateRefusal` is the one predicate. A fresh request refused so (a send, Retry, a regenerate, an edit's resend: all of `startStream`) keeps its placeholder in the runtime phase `awaiting_update` (`MessageBubble`: one quiet line, `chat.awaitingUpdate`) and asks `/api/health` every 3 seconds (`client/api/health.ts`, four states: `up`, `draining`, `proxy_down` for the proxy's own 502, 503 or 504 page, `unreachable` for a request that failed or any other answer); when the server says `up` the same request goes again, and the other three keep it waiting (a wait cannot tell a server that cannot be reached from the restart). A refusal at admission ran nothing, so that is safe. At 8 minutes health is asked once more before the wait is given up (a phone tab that slept through it wakes to find every timer overdue at once, and the poll that would have seen the server back never ran): the request goes if the server is `up`, and only a server still not back ends it, the placeholder going and the question staying with Retry and `chat.updateStillRunning`. A request refused as an update three times over while health says the server is well fails like any other, and a real `global_limit` or `user_limit` keeps the old three-step backoff.
- **Stop ends the wait; leaving the chat keeps the words.** A message the server never got goes with its bubble and returns to the composer through `restorePayloadToDraft` (joined to what it holds, The Draft). A request the server knows (a regenerate, a Retry of a message it holds without a reply) never ran, but the page took the reply it replaces off the screen when it began, so on Stop the chat is read back (`settleStoppedRequestTheServerKnows`: bounded to 5 seconds, the turn state held through the read so a message sent meanwhile is queued) and the reply the server holds returns; a chat that cannot be read (the restart is still on) leaves the question with `chat.updateStillRunning` and Retry, which renders only beside a sentence, and gives a message queued during the read back to the composer (nothing drains the queue after that). `saveQueuedTurnInDraftOf` (a chat switch, the page's destroy) takes `takeWaitingRequest()` before `takeQueuedTurn()` and saves both in that chat's draft; `reset()` drops the wait; every tick checks that the wait is still current and its chat on screen. Nothing is sent from a chat the person has left. A page that was destroyed keeps its chat id, so the runtime's own `detached` flag (set by `detach()`) is what stops the work a turn had out when the page went (a refusal, a cut reply, a question, a backoff or recovery timer, a Retry's reads) from starting a stream, a wait, a resend or a sign for the shell. Only an entry point the page calls clears it, at its start, before it awaits anything: `send` (a regenerate and an edit's resend are sends), `retry` and `checkForOrphanedStreamOnMount`. Everything else checks it and never clears it: the recoveries, the capacity backoffs, the queue's own sends, `reconnectToOrphanedStream` and the resend a Retry makes; Retry looks again after each read. `streaming.ts` does not report a refusal once its stream was detached.
- **A reply the update cut is asked about, never sent again by itself.** When a stream dies on the connection (`isStreamTransportFailure`: a `TypeError`, or a response closing with no terminal event; no status, no code of the server's own) the runtime reads `updated.current` at once, before it awaits anything (`isNewVersionLive`), and asks the page what the server is doing (`askServerUpdate`, which is `judgeServerUpdate` in `client/server-update-watch.ts`). Four answers. `none`: nothing says an update. The health read is `unreachable` (a phone that lost its signal looks like this; a browser that reports itself offline is not asked at all), or the server is `up` and no new version went live during this turn: a tab that missed a deploy has `updated.check()` true for ever, so only a version that was not live when the failure was handled and is when `updated.check()` (bounded to 5 seconds) is asked counts. The failure is then what it always was. `draining`: the old process is alive and the drain waits for the replies it runs, so the reply is probably still running there. Nothing is waited for: its stream is looked for again and joined (`joinRunningStreamOfCutReply`, at most three times over for a reconnect), and if there is none the server is asked what it holds (`askWhatTheServerHolds`): a turn that landed loads with no error, otherwise the error the failure always was, never the update sentence. A join needs the turn state free and takes nothing off the screen before it knows it can happen: the composer is free after a drop, so a message sent since is a turn that holds the state, and the cut reply is then settled around it like any reply that cannot be joined (the server is asked, the partial reply leaves the screen with no error, the turn is left alone). `restarting` (`proxy_down`): the restart cut it. The turn is held in `awaiting_update` through the same wait and cap, then asks the server what it holds, and says `chat.updateCutReply` with Retry if it did not land. `new_version` (the server answers and a version went live during this turn): no wait either, and the stream is looked for and joined first, as when the server drains (whatever answers may still run the reply); only a reply with no stream left is settled, and only then does the cause choose the wording, here `chat.updateCutReply`. This covers the network-drop recovery's give-up, a reply that died before any text, and a reconnect. Tools may have run: sending again is the person's choice, through Retry, which asks the server first. The stream that failed is let go before the page is asked, and the turn counts as active while it is (`CutReplyQuestion`, so Stop stays within reach): a Stop pressed meanwhile is recorded, asks the server to stop the run it may still have, and the hold honours it, with no wait and the turn ending after the server was asked what it holds.
- **The shell watches.** The runtime reports to `stores/server-update.ts` (state only): a sign, and whether a message waits. A sign makes the layout watch (`createServerUpdateWatch`): every 3 seconds health and `updated.check()` (each read bounded to 5 seconds, so a stalled version fetch cannot stop the watch for good), the draining banner while the server drains or the proxy answers instead of it (`proxy_down`; a server that cannot be reached is neither that nor a calm server), so the Refresh notice comes up within seconds and not at SvelteKit's once-a-minute poll. It ends when the new version is live, after 8 minutes, or after a minute of a server that answers, is not draining and runs this version. `ServerUpdateNotice` is held (`held`) while a message waits and while words a chat left behind have not reached the server (`pendingDraftSaves`, The Draft): a reload would lose them.
- **An edit says it too:** `checkChatTurn` reports `updating` beside `busy` for `reason: "draining"` (`ApiError.reason`) and for the proxy's own page during the restart (`ApiError.serverUnavailable`, set in `client/api/http.ts` for a 502, 503 or 504 whose body is not the app's JSON), and `handleEdit` says `chat.editUpdating`; without the second it said `chat.editCheckFailed`.
- **An Atlas kickoff waits too.** `/api/chat/send` with `atlasMode` skips the capacity check, so a drain does not refuse it (its job is recovered after the restart); the restart itself answers the proxy's page (`ApiError.serverUnavailable`). `startAtlasTurn` takes that for an update refusal: it waits like a refused message (`holdAtlasTurnForUpdate`, the same `beginUpdateWait`, so the shell hears of it) and is submitted again under the same `clientAtlasTurnId` once health says `up`. The server de-duplicates the kickoff by that id (`submitAtlasJobIntake` reuses the job of the key), so the job is made once whether or not the first request got through. At the cap and on Stop it ends like a kickoff that did not start (`failAtlasTurn`): both bubbles go and the words return to the composer in the Atlas mode they were sent in, a message queued behind the kickoff after them, with `chat.updateStillRunning` for the cap and no sentence for Stop. There is no Retry for it: Retry would send the words as a plain turn.
- `tests/e2e/server-update.spec.ts` drives the worker's real server through `POST /api/admin/drain` and puts the drain back in `afterEach`: a worker keeps its server from one spec file to the next.
