# Canvas

A Canvas is a board of blocks, arrows, freehand marks and a camera on the same `artifacts` row (`metadata_json.artifactType: "canvas"`), stored as the canonical JSON of `CanvasBody`. What the browser and the server must agree on is a shared module; what only a reader who opens the board needs is a lazy entry. Rulings are in `docs/plans/claude-at-home-2/decisions.md`. Short paths: `shared/…` is `src/lib/shared/…`, `services/…` is `src/lib/server/services/…`, `canvas/…` and `app/…` are under `src/lib/components/artifacts/`.

- **The body and its vocabulary are shared, browser-safe modules** (`shared/artifacts/`): `canvas.ts` (types), `canvas-blocks.ts` (one zod schema per block kind, declared once, with no Svelte and no server code because the server judges diffs with them — ruling 64), `canvas-body.ts` (`normalizeCanvasBody` never throws: it drops what cannot be drawn and says so; `boardJson` is the canonical string a hash is taken of), `ops.ts` (the generic ops mechanism, ruling 14), `board-ops.ts` (Canvas's vocabulary; every refusal reason has an English and a Hungarian label), `board-diff.ts` and `canvas-review.ts` (what a change touched). Whatever a client sends or a model writes reaches `updateArtifactBody` only through `prepareCanvasBoard` (`services/artifacts/serialize/canvas.ts`: caps, canonical JSON, the one hash, ruling 12); a board saves through the shared body route (`saveArtifactBody`), never a Canvas-only save call.
- **One envelope for an id-addressed change** (ruling 14). `applyArtifactOps` (`services/artifacts/ops.ts`) is the only place a diff is applied: ownership scope, the base version must be the newest, dispatch on kind through `OPS_BRANCHES`, judge every op, then ONE `updateArtifactBody`; a kind with no branch is a 400 and a diff that changes nothing writes nothing. The panel's `POST /api/artifacts/[id]/ops` (thin: author `user`, no review marker), `edit_artifact` and an `@Alfy` reply on a board (author `alfy`) all call it. A new kind adds a vocabulary file beside `board-ops.ts` and one `OPS_BRANCHES` entry; the Document keeps its patch engine (`services/artifacts/document-ops.ts`).
- **What the tool advertises is what the validator parses** (ruling 62). `buildEditArtifactModelInputSchema` (`services/normal-chat-tools/artifact-tools/edit.ts`) advertises `boardOpsArraySchema`, the very schema `applyArtifactOps` reads a diff with, never a twin; the description's one worked example (`EDIT_ARTIFACT_CANVAS_EXAMPLE` in `kind-prose.ts`) is fed by a test through that schema and `validateBoardDiff`, and every refusal names what would have worked. The create handler judges a made board op by op (`parseCanvasCreateBody` in `canvas-model.ts`). The tool text is in the cached prompt prefix: changing it moves `CATALOGUE_TOKEN_CEILING` (`services/normal-chat-tools/index.test.ts`) and the frozen snapshots in the same commit (ruling 23).
- **What Alfy may put on a board, and change** (rulings 64, 67, 74). `add_node` and `add_frame` make six kinds (`MODEL_CREATABLE_KINDS`): the five note-shaped ones and a diagram (`mermaid`), whose Mermaid source Alfy writes exactly as in a chat reply and which `canvas/nodes/MermaidNode.svelte` draws with the chat's own `Mermaid.svelte` (`securityLevel: "strict"`, labels as SVG text, the SVG through `sanitizeHtml`); a map, file, App, photo or web block carries a reference the model cannot mint, so those five land only from the reader's Insert. On them `update_node` may change descriptive fields only (`modelUpdatableFields`: a map's `label`, `route` and `meta`, an App's `title`, nothing on a file, photo or web block), and no op writes a `poster`; otherwise a prompt-injected turn could plant links dressed as the app's own search result. A diagram's fields, its source included, are the model's own, except that a source Alfy writes (an add or an `update_node`) is refused `invalid_data` when it carries what loads or links an address (`mermaidSourceProblem` in `shared/artifacts/mermaid-source.ts`, which reads the one sanitizer's list as a refusal and adds any click line and any web address); what the reader inserts from the chat or types into the block's form is not judged there, it is drawn through that sanitizer (below). What a board may load or link is one rule, `shared/artifacts/block-urls.ts` (a photo is exactly one of the app's thumbnail proxies, a source an http(s) address), shared by the schemas, the chat listing and the blocks. What Alfy adds is stored at its kind's own width (`defaultNodeWidth`: `NODE_WIDTH` for a note or text, a checklist's 340, a chart's 360, a diagram's 480, which is also what the reader's Insert gives; a frame keeps its size); `estimatedNodeSize` is the one estimate of what the panel draws (a chart is as tall as its plot, which `ChartNode` lays out at the ratio `chartAspectRatio` reads), used by `canvas/_lib/board.ts`, the model's read, the placer and the eval, and the tool text is built from the same constants. A diagram is as tall as Mermaid lays its source out; reading that from the source is `shared/artifacts/mermaid-size.ts` (a block's card included, held to 41 sources measured on the board in Chromium and never short), reached through `plannedNodeSize` (`node-size.ts`) by whoever plans a board without a browser (the model's read, the placer, the judge, the eval). The editor measures its blocks and uses `estimatedNodeSize`, which reserves `DIAGRAM_RESERVED_HEIGHT` for a diagram it has not measured, because everything `canvas-blocks.ts` imports is in the editor's first paint (below): what only the model or a planner needs lives beside it (`canvas-model-blocks.ts`: the six kinds the model may add, what it may change, a chart's config as an object; `node-size.ts`; `board-refusals.ts`: the refusal reasons the review controller says), never in it.
- **Where what Alfy adds goes** (ruling 74, the owner's "where AlfyAI places new blocks"). `shared/artifacts/board-placement.ts` (`placeBlock`) is the one placer, pure and deterministic, and `board-ops.ts` is the one caller: the judge settles an `add_node` or `add_frame` once against the board as the accepted ops before it left it, and the op that lands (`accepted` in the run) names a place and a frame and no longer a `near`; `applyOp` stays a plain application, apart from one geometric rule (a block added inside a frame that it sticks out of makes the frame grow, a margin past it). `position` is optional on both ops, and `near` (a block's id) is new; create bodies take both (`parseCanvasCreateBody`), and `@Alfy` replies get it through the same schema. A place the model gives is kept when it is free (no more than a pixel shared with a neighbour, inside its frame) and moved to the nearest free ground, a gap (`PLACEMENT_GAP`) clear of what is there, when it is not; a place left out is found beside the block named in `near` (right, else under, else the nearest free ground), in the next free slot of the frame it names (across, then the next row, from `FRAME_INSET`), or on free ground nearest what the reader is looking at (the camera the board was saved with, else the middle of its content); a frame with no room grows down or to the right when the ground it grows into is free, and otherwise the block goes beside the frame; a block whose middle lies over a frame it was not made a child of becomes the child, as the board does when a reader drops one there. `move` is not settled: an arrangement moves the blocks around one another, and a board is judged by the boards it leaves. Do not place a block in a route, a tool handler or a component; extend the placer.
- **Alfy never overwrites what the reader changed after it read the board** (ruling 67). The judge is the BODY the model was shown, never only a version id: the reader's autosaves within ten minutes are written INTO their own newest version (ruling 47), so the version the model read can hold newer words under the same id (RV-F I-1; `canvas-stale-read.test.ts` runs a coalescing save through the real tools). `read_artifact` records the version it showed on the tool call's record and hands the stored body it showed to the turn's `KnownBoards` (`canvas-model.ts`: in memory, one per tool set so it goes with the turn, at most eight boards, never on a record and never to the model). The edit handler passes that body as `OpsEnvelopeInput.readBody` and the turn's last read version (`lastKnownBoardVersion`) as `readVersionId`, the fallback for a board the store no longer holds, and `applyArtifactOps` gives the vocabulary the board as read (`OpsJudgeContext.readDoc`), which refuses `update_node`, `move` and `remove_node` on a block that differs since as `stale` while the rest of the batch applies. An edit moves the store forward only when the version it landed on had exactly the words the model knew (and not after a call the turn's stop cut off): otherwise what the reader wrote in between is still unseen, and the block the model's own edit changed reads as changed since until it reads the board again. With no read in the turn the edit applies to the board as it is. An `@Alfy` reply on a board (`canvas-comments.ts`) holds the same line with the body it showed the model, and a stale op is named in the reply (`skipped`, localized by the card). The Document's `@Alfy` needs neither: its read snapshots each block's hash and the patch carries it (`block_changed`).
- **An Alfy change to a board is one pending change** (ruling 63). Ruling 61's marker (`metadata_json.review.throughVersion`, bootstrapped by the envelope on the first Alfy write) names the last Alfy version the reader has decided on. `services/artifacts/review.ts` dispatches on kind; for a board the shared `computeCanvasReview` says what waits, on the same `diffBoards` the browser's landing draws from, so the count (`pendingReviewCount` from `read-model.ts`, never a client copy) and the landing agree. There is no per-block Keep or Undo: Keep moves the marker; Undo saves the parent version's body as a **user** version and is refused, with the shared refusal card pointing to Versions, once the reader has changed the board. The landing, rings, pill, review bar and notices are one lazy entry, `canvas/review-parts.ts`.
- **Comments on a board are the Document's feature on the same rows** (ruling 1: `artifact_comments`, never part of a body). A board takes `node` and `point` anchors only (`canvasAnchorResolver` in `shared/artifacts/comments.ts`), and a thread whose block is gone is an orphan by the resolver's answer, never by a local existence check. The pins, the Comment tool and their shared state (`canvas/_lib/comments-controller.svelte.ts`) are one lazy entry, `canvas/comment-parts.ts`. `@Alfy` on a board is `services/artifacts/canvas-comments.ts` (`runCanvasAlfyReply`, dispatched by kind from `runAlfyCommentReply`): the model answers `{ note, ops? }` in `boardOpsArraySchema` itself with the edit tool's own texts (ruling 62), gets one correction, and its ops land through `applyArtifactOps` as one version by `alfy`.
- **The board hands over whole steps.** `canvas/CanvasBoard.svelte` owns the live state and the reader's own history (`canvas/_lib/board-history.ts`, ruling 16), never persistence: a moment after blocks, arrows or marks stop changing it compares its canonical JSON, camera left out, with the last state it reported and calls `onchange` with ONE step; a bare pan is never a step. What the server changed under the reader is drawn with `land` (and `place`, `hold`), never as a step of the reader's own, because an Alfy change is a version. `insertBlock` is the only place a block is created; a kind is a `BLOCK_META` row plus a registry entry (`canvas/_lib/block-meta.ts`, `canvas/_lib/block-registry.ts`).
- **The editor is one chunk plus lazy entries, and a size gate holds the line** (ruling 68). `canvas/CanvasEditor.svelte` is glue; what a reader may never need is ONE entry it loads with `import()` and never imports statically: `canvas/comment-parts.ts`, `canvas/review-parts.ts`, `canvas/export-parts.ts`, `canvas/drawing-parts.ts`, `canvas/state-parts.ts`, `canvas/group-parts.ts`, and what is under `canvas/nodes/` and `canvas/chat-blocks/`. A lazy part imports no `@xyflow/*` (it would pull the library into a second chunk) and as little of the editor as it can. **`canvas/history-parts.ts` (a board's preview in History) is the one that needs the board itself, so it is reached only through `CanvasEditor.svelte`'s module script (`loadHistoryPreview`), which hands it `CanvasBoard` and the flow library (`provideBoardParts`) and which History's registry asks for: the bundler (Rolldown) puts a module two lazy entries both import into a chunk of its own, so a preview that imported the board splits it and the library out of the editor's chunk (measured: +0.7 to +1.6 kB gzip on the editor's closure, over the ceiling), and so does every other module of the editor's first paint it imports directly (`board-model.ts`'s `sameCamera` is handed over too).** A change to what the preview imports from `canvas/` is measured with `npm run check:artifact-chunks` before it is believed. `npm run check:artifact-chunks` (`scripts/check-artifact-chunks.mjs`) holds the editor's first-paint closure to the gzip ceiling ruling 68 records and keeps Chart.js, MapLibre and Mermaid out of it; raise a ceiling only with a recorded reason (ruling 74's work first took the editor's own closure to 74,063 B against 71,680 and was brought back to 71,515, base 71,587, by moving what only planners need out of it, not by raising the ceiling). **The chat route is held by a rule, not a size**: none of Chart.js, MapLibre, Mermaid, the flow library (`@xyflow`), Tiptap/ProseMirror or the Canvas editor's own entry may be reachable through static imports from `/(app)/chat/[conversationId]` (`--chat-forbid`, found by the fingerprints in `PACKAGE_FINGERPRINTS`, so a new heavy library gets a fingerprint measured on a real build before it is listed); an `import()` chunk is allowed, which is how the chat loads Chart.js and Mermaid. The route's first-paint size is printed as information and compared with nothing: the fixed-byte baseline it replaced moved nine times in one wave and read about 660 B heavier on the server's build, so it measured the machine and the chat's own growth, not the mistake it was there to catch. A static `import "chart.js/auto"` in a chat component, built and checked, fails it by name. It is a development gate, run as its own step on a finished `npm run build` (the wave gates and `scripts/gates.sh` do; so should anyone who changes what the editor or the chat shell imports), and it is deliberately NOT part of `npm run build`: the editor's ceiling is still a byte count, and the server's build environment measures bytes differently from a developer machine, so a deploy of gated code must not fail on it.
- **Blocks from the chat.** `GET /api/artifacts/[id]/chat-blocks` (thin over `services/artifacts/chat-blocks.ts`, facade `listCanvasChatBlocks`) lists what the board's own chat made through the same scoped read as every artifact route, only via services that already own the data, each item checked against its block's schema so nothing is offered that a save would drop. Everything the chat draws that is a chart is on the list and is drawn by the chat's own component, so what the chat draws the board draws: a Chart.js chart through `Chart.svelte` (a config is read the way the chat reads it, `parseJsonLenient`, and a chart is placed in the room its plot takes, `insertSize`: a pie is square), a Mermaid diagram (a closed ```mermaid fence of a reply: `diagrams` in the listing, named by its own title else its kind) through `Mermaid.svelte`, which draws in the reader's theme. A `csv` fence (the chat's third diagram fence, a table) has no block yet. Every block but the frame, the note and the text is drawn by `canvas/nodes/LazyNode.svelte`, which owns the shell and loads only the content (`canvas/_lib/lazy-nodes.ts`, a content module plus a `<kind>Shell`); a content module may not import `NodeShell`, the flow library or the block registry (`canvas/nodes/lazy-node.test.ts` reads the sources), or the shell splits out of the editor's chunk. A File block opens through `onOpenItem` (the host's `onOpenDocument`); an App block reuses the panel's `AppFrame` (ruling 58). A live-web block's Refresh and Search (`services/artifacts/canvas-web.ts`) write nothing: the editor puts the snapshot on the board as one step of the reader's own (`CanvasBoard.setBlockData`), so a refresh never races the autosave.
- **A board leaves the panel as a picture, and a block a picture cannot reproduce has a poster.** The browser draws the picture; `POST /api/artifacts/[id]/exports/png` (thin over `services/artifacts/canvas-export.ts`, facade `storeCanvasImage`) judges whose board it is and that the bytes are one whole PNG within what a browser could draw, then keeps them through `storeGeneratedFile` (`services/chat-files.ts`) as a produced file (ruling 18: a chat file, its `generated_output` artifact, a `used_in_output` link to the board). A block a picture cannot reproduce (`needsPoster` in its `BLOCK_META` row: an App, the map, photos, live web) carries a poster instead, sent through the same route: a chat file that hangs from no reply and has no artifact, named by `shared/artifacts/poster-file.ts`, served by `services/generated-file-serving.ts` because of that name, made from a detached copy of the block's content (`canvas/_lib/poster.ts` `stillify`) and set without being a step of the reader's own (`CanvasBoard.setBlockPoster`). Everything a picture is made of is one lazy entry, `canvas/export-parts.ts`; `canvas/_lib/export-png.ts` puts the camera and posters back in a `finally`.
- **The reader's unsaved step and Alfy's change never refuse each other.** A step still inside the board's settle delay is saved before a fresh chat turn starts (the open body registers a flush with the panel, `DocumentWorkspace.svelte` hands it to the chat page, which awaits it, bounded, wherever a turn begins except a queued follow-up the runtime drains by itself, which skips the flush and leaves the step to the merge below). A landing change, or a save the server refused because it had moved on, that meets an unsaved step is merged block by block against the last board the server acknowledged (the reader's version stands on a tie; a dismissible notice counts the blocks) and saved as the reader's own version; only a refusal with nothing newer on the server keeps the banner, after one retry. An App block's tripwire (`app/AppFrame.svelte`) counts loads per frame *window*, never per element: the flow library re-parents an App's wrapper when a frame is re-listed (`parentsFirst`), and the browser then fires a new `load` on the same element in a new window.
- **Several picked blocks are one group** (OW-2). Shift, Cmd and Ctrl add or remove a block (`multiSelectionKey` on the flow; a Shift-click on a frame's ground goes through `handlePaneClick`, which keeps what was picked because the library puts it all down after `onpaneclick`), and a marquee takes what it FULLY encloses (`selectionMode`; the library's real default is partial, which picks a frame the marquee only crosses, so a drag inside a frame picked the frame). Two or more picked blocks give up their own corners, anchors and toolbar (`grouped` on the board context, read by `NodeShell`) to ONE box with eight handles and one toolbar (the count, Delete for all), drawn in screen space by `canvas/GroupBox.svelte`; the arithmetic that scales the blocks with it is `canvas/_lib/group-scale.ts` (pure: one box about the opposite corner, places and sizes scaled together, ONE shared floor where the block that runs out first reaches its kind's `minSize`, a picked frame takes its notes along, whole numbers, each block in the space it is stored in), and a finger's way in (a long press adds a block and starts the picking mode, then taps add and remove; `canvas/_lib/touch-select.ts`) is the same lazy entry, `canvas/group-parts.ts`, loaded when a selection first has two blocks or at once on a coarse pointer (which also holds the keyboard reveal, below). The editor's first paint carries only the hooks (the keys, `grouped`, the loader, the merge of a handle's patches). A handle's drag is ONE step: the board holds its settle timer while `resizing` (`onresizestart`/`onresizeend`, also called if the box goes mid-drag), so it is one history entry and one save; Escape in the drag restores every block. The box imports no flow library and no module the editor shares (it is handed `isTextEntry`: importing it split that module out of the editor's chunk, +230 B gzip). A resize does not re-adopt blocks into frames (a single block's does not either); a move does, by `reparentOnDrop`, for every dragged block.
- **The layers that float over the board stay in the pane and off each other** (RC-3 N3). The change pill, the selection's pill and the zoom control are kept on the screen, never off its edge: `keepPillInPane` and `selectionPillPlacement` slide them along it (`canvas/_lib/floating.ts` holds the shared `ScreenRect`, the edge gap and `measuredBy`, which reads a layer's real size), the selection's pill keeps off the change pill's rectangle (the layer reports it through `BoardLayerApi.changePillBox`; lazy entries never query each other's DOM), and the zoom control steps aside (`visibility`) while a selected block is under it. A new layer that floats reports its box the same way. The zoom control stands over the palette, not beside it, below `STACK_ZOOM_BELOW` (830 px: the palette is centred and 517 px wide in Hungarian, its widest, and the zoom needs 152 px at the edge, so they meet below 821; a docked panel at 1100 px is 713 px), and the overview steps up with it; `artifact-canvas-floats-narrow.spec.ts` sweeps the window in both languages, so a button added to the palette fails it, not a reader. **The picked block's own small toolbar is one of these layers** (CV-B2): the library hangs it centred above its block, and a block within about 50 px of the pane's top had its Edit and Delete cut off (a note near an edge, on a phone, lost a button sideways too). `placeToolbar` (`floating.ts`) says where it hangs: above the block, a gap clear of it (`TOOLBAR_OFFSET`), below it when the pane has no room above, slid in from the pane's sides, held at the top of the pane over a block taller than the pane, and clear of the board's own toolbar and of the change pill. `CanvasBoard.svelte` derives that for the one picked block (`toolbarPlaced`: the blocks, the camera, the pane and the toolbar's measured size, which `NodeShell` reports through the context's `measureToolbar` when the toolbar is drawn and when its buttons change), tells the shell how far to move the library's toolbar from where it hangs it (`toolbarShift`, applied as the toolbar's CSS `translate`: the library keeps placing it, the board only nudges it) and tells the layers where it ended up (`BoardLayerApi.toolbarBox`). The geometry is a lazy part: the board asks for `floating.ts` (`import()`) when it mounts, and until it is here the library's own place stands; the shell hangs the toolbar at the library's 12 px gap itself, which `floating.test.ts` holds to `TOOLBAR_OFFSET`, so nothing static in the editor imports `floating.ts` (the editor's first paint has tens to hundreds of bytes of room: measure with `npm run check:artifact-chunks`). That is how the selection's pill, which hangs under the block, stands under a toolbar that is below the block instead of on it (`selectionPillPlacement`'s `toolbar` option and the `lift` it answers with, which above a block raises the pill over a toolbar taller than a pointer's 60 px clearance: a finger's is 52 tall). Do not place the toolbar from the DOM or a second time in the shell.
- **The board follows its pane only until the reader touches it** (TR-D1, TR-D3). A tour card arriving or going, a window resize or a bar appearing changes the pane's size, and a populated board that had already fitted itself used to be left with rows under the fold. `CanvasBoard` keeps `fitted`, the camera its last fit produced (the library's own first fit, which `onmoveend` reports with no pointer or key behind it, or `fitBoard`: the Fit button is one), and fits again, instantly, whenever what the fit takes in changes (FX-F, RC-F IMP-1): the pane's size (a frame at a time over a transition) or the room the blocks take (`flow.getNodesBounds(nodes)`, compared with what the last fit was told in `fitKey`: Alfy writes a flowchart with a width and no height, the board is fitted around it measured empty, Mermaid draws it a moment later and the block grows downwards out of the pane; `fitted` is state so a fit that finished after the block had grown is looked at, and so is the end of a landing's or a picture's hold), while `followsPane(flow.getViewport(), fitted, touched)` (`_lib/board-model.ts`) holds: the camera is still the fit's and `touched` is false. `touched` is the camera becoming the reader's: a pointer or touch down anywhere in the board, or the focus entering it (two capture listeners on its root: a tap, a click, a Tab, a script moving the focus into a note), sets it, and only the Fit button clears it (it fits, and is the reference again until the next touch). That is what keeps the on-screen keyboard from moving the board: the viewport meta says `interactive-widget=resizes-content`, so on Android Chrome the keyboard that opens when a reader taps a note to type shortens the page, and a board that zooms and moves as it opens (and again as it closes) moves under the note they are writing in; a bar, a sheet or a window resize after their first touch is the same. The camera guard stays beside the flag, for what moves the camera without a press in the board (a centring from the comments column): any pan, zoom, centring or auto-pan changes the camera, so it stops being the fit's. A board saved with a camera of its own has no fit to keep (`fitted` stays null), and nothing is fitted while a picture of the board is drawn or Alfy's landing holds the board. What that leaves, a block lower than the keyboard's top edge hidden while the reader types in it, is the next bullet's. Do not add a second record of where the camera was for the fit, or a second re-fit listener beside it.
- **The block being typed in stays in view over the keyboard** (TR-D4). With the camera staying put after the first touch, a block lower than the keyboard's top edge would be hidden while the reader types in it, and the browser cannot scroll it into view (the flow library undoes its wrapper's scroll, `Wrapper.svelte`'s `wrapperOnScroll`). So the camera pans: when a text field in a block has the focus and what the reader can see of the pane SHRINKS over it (the pane gets shorter, which is what an Android keyboard does under `interactive-widget=resizes-content`, or `window.visualViewport` does, which is what an iOS keyboard does; `visibleRoom` is the pane where the visual viewport is), `revealPan` (`canvas/_lib/keyboard-reveal.ts`, pure) moves the camera by the least distance along each axis that puts the block whole inside it, clear of the board's toolbar (`.canvas-toolbar`'s measured box, where it stands under the block) with `REVEAL_MARGIN` to spare; a block too big for the room it has left (or wider than it) brings the field being typed in instead, and a field too big itself starts at the margin. It never zooms, glides for `REVEAL_PAN_MS` and is instant under reduced motion. `watchKeyboardReveal` applies it: once per opening of the keyboard (a new focus starts again; a pan uses the opening up, and the visible room growing again, the keyboard going, gives the same field the next one, which is how a field that keeps its focus after Android's Back key gets its second keyboard), and only for a CHANGE (a field that takes the focus with nothing changing around it, the keyboard up already, is left where it is), looked at once the pane and the viewport have held still for `REVEAL_SETTLE_MS`, so a keyboard that opens in steps gets one pan, to where it ends. After a pan the camera is the reader's, and what a taller keyboard or their own zoom does next is never fought; when the keyboard closes the camera stays (and is saved with the next step like any pan; Fit gives the fit back). It is part of the lazy `canvas/group-parts.ts`, so it exists on a coarse pointer only (a desktop never loads it: nothing moves for a resized window), and the board hands it the flow library's `getViewport`/`setViewport` and `isTextEntry` rather than it importing either. The first paint carries one effect in `CanvasBoard`. **The same arithmetic brings a block's edit form into view when it opens** (FX-F, RC-F IMP-3): a form in the block is drawn at the board's zoom and makes the block taller, and low on the board its Save was below the pane with the palette over the rest. `BlockEditForm` (not on a phone: its sheet needs no help) loads `revealForm` (`keyboard-reveal.ts`) a frame after it mounts, on any pointer, and asks the board through the context's `panBy` for ONE pan: the block whole in the room the pane leaves, or the form's buttons when it is taller than that, clear of the palette and the overview (`revealPan` takes several obstacles; the zoom control steps aside from a selected block by itself and is not one), and nothing when the form is where it can be used. The camera stays where the pan left it. Playwright cannot raise a real keyboard: `artifact-canvas-keyboard.spec.ts` shortens the page by 336 px (Android's layout) and the visual viewport path is covered by unit tests with a fake `visualViewport` only, not seen on an iPhone.
- **A laptop's touchpad drives the board like Figma's, and the wheel is the board's, not the library's** (CV-C). A two-finger scroll and a mouse wheel pan (both axes, by what the fingers did, at any zoom); Shift turns a scroll across (and does not turn one the system already turned: the event says `deltaX`); a pinch (the browser's Ctrl + wheel), Ctrl or Cmd with the wheel zoom about the pointer, in proportion to the gesture, so a touchpad's small events zoom smoothly while one event is at most a step of about a tenth (a mouse's notch is exactly one step, never a jump to the limit). Over the board the page never scrolls and the browser's history swipe is not offered: every wheel event the board takes is cancelled, a pinch over its own chrome (the toolbar, the zoom, the overview: off the pane) is cancelled too, and the board carries `overscroll-behavior: none` so what scrolls inside it stops there (the part sets it as an inline style, not the board's CSS: a declaration there sits in the editor's first paint). Space+drag, the Hand tool, the middle button and a finger are the library's own and are not touched. `canvas/_lib/wheel.ts` is the policy and the only wheel handling: one lazy entry the board loads when it mounts (`takeWheel` in `CanvasBoard.svelte`, which hands it the camera's two members and `MIN_ZOOM`/`MAX_ZOOM`, the same two numbers the flow's `minZoom`/`maxZoom` take), a capture listener on the library's zoom element that moves the camera with `setViewport` and keeps the event from the library. The library's `panOnScroll` stays on for two reasons: it is the nearest thing before the part has loaded, and it is what debounces the library's move-end to the end of a gesture, so `restingZoom` (the handles' size) is set once per gesture and not on every frame of a pinch (`artifact-canvas-touchpad.spec.ts` holds it). A block keeps its wheel when it carries the library's `nowheel` (a map, an App, an edit form: the events reach it untouched and only a page zoom is cancelled; a note's text field is as tall as its words and never scrolls, so it carries none and the board pans from over it) or scrolls the way the wheel goes (the browser scrolls it; `overscroll-behavior` stops the rest of the gesture at the board). So a new block that scrolls needs nothing, and one that handles the wheel itself needs `nowheel`. Do not turn `zoomOnScroll` back on, add a second wheel listener, put wheel handling in a node, or import `wheel.ts` statically (the editor's first paint carries only the loader, and the ceiling has tens of bytes of room: measure a change here with `npm run check:artifact-chunks`). Safari sends a trackpad pinch as `gesturestart`/`gesturechange`/`gestureend` (a `scale`), not as a Control + wheel, so the same part takes those too (CV-B2): one event zooms about the pointer by the change in `scale` since the last, one to one with the fingers, through the same `zoomAbout` as a wheel pinch, and the page's own zoom is cancelled over the whole board, its chrome too; over a `nowheel` block or off the pane only the page's zoom is cancelled. A touch that is down means a finger's pinch (iOS Safari reports gestures for those as well), which is the library's own and is left alone. It is unit-tested with synthetic gesture events, because Playwright cannot drive Safari's; the one e2e sends the event the page's own way and only checks the wiring.

- **What a reader inserted can be changed afterwards** (CV-B). Every block that has something of its own to change has an Edit button in its selection toolbar (`NodeShell`'s `edit` prop, one button before Delete; Enter and F2 as before), so nothing hangs on knowing that a double-click edits. A note, a text block and a frame edit in place, and the whole block (however tall the reader made it) hears the double-click. A chart, a diagram, a checklist, a map, an App and a photo block open `canvas/nodes/BlockEditForm.svelte`: a title and, for a chart and a diagram, the block's own source (a chart's plain JSON laid out over lines, kept on one again). A form with a source takes the content's place; a title-only form lies over it (a running App or a map is not asked to lay out again) except on a checklist, which is as tall as what it holds and grows. `_lib/block-edit.ts` is the one place that says what is checked (the block's own schema, `canvas-blocks.ts`, judges a source; a chart's must be a config the chat's chart can draw; a diagram's syntax is Mermaid's to judge, as in the chat) and what is written (only what changed, nothing when nothing did). Nothing is written until Save, and Save is ONE `updateNodeData`, so ONE step of the board's own undo (ruling 16); Cancel and Escape write nothing. `LazyShell.editable` is how a lazy block says it has a form (`LazyNode` owns whether it is open and hands the content `editing` and `onclose`); the form is the content module's, never the shell's, and imports no module the editor shares with it (a shared module is a chunk of its own in the editor's first paint: `focus.ts` was one). A File block and a live-web block have no form: a file is a pointer to what the chat holds (a title on the board would misname it) and a web block is about its query (a new query is a new block; Refresh stays). **On a phone** (`isPhoneViewport`, under 640 px) the same form is the app's bottom sheet (`DialogShell`, `z-[150]` like the panel's other phone sheets, as the Insert menu and the comments are) and not a form in the block: in the block it was drawn at the board's zoom, a few pixels tall on a zoomed-out board, and a block low in the pane left Save and Cancel below the fold behind the board's own toolbar (CV-B2). It is the same `<form>` and the same draft (crossing the breakpoint keeps what was typed); Cancel and Save are the sheet's footer, pinned (Save is a submit button of the form by its `form` attribute); the title does not take the focus on open there (the keyboard it opens would cover the sheet; Enter in it saves); its fields are 16 px (a phone zooms the page to a smaller one); and what the block draws stays drawn behind it, which a content module that replaces its content with the form (a chart, a diagram) gives as the form's `children`. A photo block's caption is its optional `label`. A frame's toolbar is lifted to the layer the others have (`canvas-toolbar--frame`): the library puts it one above its block, which for a frame at -1 was under the pane.
- **A File block is picked by a click like every block, and opened on purpose** (CV-B2). A click on it used to open the file, so it could not be selected to be moved, resized or deleted, and nothing said what a click did. Now what opens what a block points at is `NodeShell`'s `open` prop (a lazy block's `LazyShell.open`, which `LazyNode` hands over): a double-click anywhere on the block, not only on its row; Enter or F2 while it has focus, which also works on a board that cannot change (looking changes nothing); and an Open button before Delete in its toolbar, the way in for a finger on a zoomed-out phone board (the row inside the block is a few pixels there). The row says so in its tooltip (`artifacts.canvas.file.hint`). A block with no panel to open in (a board outside a chat) has none of the three.
- **A touchpad's click is a click** (CV-B). A laptop's cursor wanders a pixel or two between the press and the release. The flow took anything past 1 px for a drag and dropped the click that followed (a File block did not open, a frame was not picked by its ground) and nudged the block, as a step of its own. The board passes `nodeClickDistance`, `nodeDragThreshold` and `paneClickDistance` as `WOBBLE_PX` (4); the camera's own gestures (the wheel and the pinch) are not part of this. The wobble spec (`tests/e2e/artifact-canvas-wobble.spec.ts`) drives the pointer the way a touchpad does; every flow that depends on a click on a block or on the board should be tried that way, not only with a still mouse.
